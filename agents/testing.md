# Testing

合意済みの設計に基づいて、期待される結果を検証するテストを作成する。

- テスト要件は、実装ではなく合意済みの設計に基づいて定める。
- テスト対象の結果や副作用を検証し、テスト自身の設定を確認するだけのテストを書かない。
- テストケースは正常系→異常系の順に記述する。
- テストコードも、`agents/implementation.md`の「コードの複雑さ」のうち認知的複雑度の上限に従う。
- 関数の長さの上限は、テストのコードには掛からない(理由は`agents/implementation.md`)。
- テストコードも、`agents/implementation.md`の「識別子の命名」に従う。

## 要求との対応

- 要求とテストは1対1にしない。
- 1要求を複数テストで検証してよく、1つのE2Eで複数要求を通してよい。
- 要求とテストの対応表や識別子による参照は作らない。
- テスト名は、検証する振る舞いが分かる文にする。
- 同じ規則の詳細な組合せは、その規則を担うテスト層で検証し、他の層では接続の確認に必要なケースを選ぶ。
- 画面の配置とデザイン(寸法、余白、列数、並ぶ向き、配色、パネルの位置、動きの見た目(アニメーションの見え方)、横にあふれないこと)はE2Eで確かめず、E2Eでは要素の位置や寸法、スタイルを期待値にしない(押す場所を決める寸法は使ってよい)。操作や状態の変化の結果として対象が隠れるか見えるかが変わること(動作が伴う見た目。例: スクロールしても合計が隠れずに見えること、矢を指した後、点数を入力した後に、指す矢が隠れずに見えること)は振る舞いとしてE2Eで確かめ、対象の上の最前面の要素(`elementFromPoint`)で確かめて、要素の位置や寸法の比較で確かめない。単体・コンポーネントテストでは、入力や状態に依らず固定の見た目の値(既定のクラス、固定のスタイル)を期待値にせず、propsや状態で出力が変わる対応と、見た目を決める計算や状態(色の変換、段の数、動かすかの判定、畳む・展開する状態)は、部品や関数の機能として確かめる。

## テスト層の選択

- テスト種別はツール名でなく、実物で通す境界によって決める。
- 判断や状態遷移を1つの公開契約から検証できる場合は単体テストにする。
- 所有する複数モジュール、DB、ブラウザAPIなど1つの境界との接続を検証する場合は結合テストにする。
- 利用者の主要な目的を実ブラウザ・認証・DBまで通して検証する場合はE2Eにする。
- 保証したい結果を確認できる最小の層を選び、同じ組合せを上位の層で繰り返さない。

## テストデータ

- 検証データは、実際に起こりうる形にする。実際にない形でしか成り立たないテストや、実際のデータで起きる制約を見逃すテストを作らないためである。
- 実際にない形は、次のどちらかの場合に限って使い、その理由をテスト名かコメントから読めるようにする。
    - 値そのものが検証の対象である(入力の境界と検証、一部の値だけを変える編集、判定の境界)。
    - 実際の形では、検証したい状態が成り立たない。
- 速さやデータ量を理由に、実際にない形にしない。準備がAPIの上限(`record_shots`の1回100件など)を超えるときは、準備を分けて満たす。
- 例: ラウンドの距離は、種別が屋外なら各距離を12エンド×3射か6エンド×6射、インドアなら10エンド×3射か5エンド×6射にし、同じラウンドの全距離で同じ形にする。「全てのエンドが矢数に達した」「1本足りない」などの状態も、この形で作る。種別がフィールドのラウンドは、この形の対象外とする。種別を持たない検証データは屋外の形にする。

## フロントエンド単体・コンポーネントテスト

Vitestを使用する。

- Given-When-Then形式で記述し、各フェーズをコメントで明示する。
- WhenとThenには文を1つ以上置き、どちらかが欠ける、または見出しだけのテストは書かない。判定はコメントの有無でなく中身で行う。
- Givenには、検証する操作の前に成立している状態と準備を置く。モックへの設定、タイマーや環境の設定、初期データ、描画済みの状態、前段の操作の結果である。
- Whenには、検証する振る舞いを起こす操作と、その操作に与える入力を置く。対象の呼び出し、描画の結果を確かめるテストの描画、クリックや入力などの操作と、引数、props、children、イベントの組み立てである。入力は呼び出しの引数に直接書くか、Whenの先頭で組み立てる。
- 描画は、描画の結果(表示された内容、属性、子要素の配置)を確かめるテストではWhenに置き、クリックや入力などの操作を検証するテストでは、準備としてGivenに置く。準備の描画に渡すpropsやchildrenも、Givenに置く。
- 純粋な関数のテストでは、入力の用意と呼び出しをWhen、戻り値の検証をThenとする。reducerのように現在の状態と操作を受け取る関数では、現在の状態をGivenに、操作(action)の組み立てと呼び出しをWhenに置く。
- 前提がテスト本体にあるときは、そのコードをGivenの見出しの下に置く。前提が本体の外(`beforeEach`、`beforeAll`、`it.each`の引数、ファイル先頭の`vi.mock`)にあるとき、または既定の状態のときは、Givenを見出しだけにする。既定の状態とは、状態、設定(`vi.stubGlobal`、`vi.useFakeTimers`など)、モックへの設定がどこにも無い状態で、入力の有無は問わない(例: 引数なしで`manifest()`を呼ぶテスト)。
- Givenの見出しに、前提を言い換える説明(`// Given: サイトキーが設定されている`など)を書かない。
- 前提(状態、設定、モックへの設定)を本体に書いたのに、Givenが見出しだけのテストは書かない(例: Whenの中でモックの戻り値を設定したテスト)。
- フェーズの中のコメントは、コードから読み取れない理由(テストが成り立つ理由、jsdomや外部SDKの制約、外部の仕様)に限る。前提、操作、結果を言い直すコメントは書かない。
- 1テストは1つの振る舞いを検証する。1つの振る舞いは、1つの前提のもとで1つの操作を行ったときの結果で、その結果を複数のexpectで確かめてよい。前提か操作が違う検証(失敗の表示と、その後の再送信の成功など)はテストを分け、前段の操作はGivenに置き、Thenには操作を置かない。境界値とその前後、同じ入力の両側の値は、1つの振る舞いとして1つのテストにまとめる。
- モックは、置き換えるだけ(`vi.fn()`の差し込み、外部の部品の固定の代役)なら前提に数えず、前提になる状態や結果を設定した場合(サインイン済みのユーザーを返す、失敗を返すなど)は、設定する場所を問わず前提に数える。
- フェーズの見出しは、`// Given / When`のように結合せず、1フェーズに1つ置く。
- フェーズの規則はE2Eに掛けない。リンクの遷移先は、この層で確かめず、「結合テスト」のリンクの規則に従う。
- アプリケーションロジックでは、分岐・判定・計算・状態遷移・データ変換・入力境界・エラー分岐などの振る舞いを検証する。
- UIコンポーネントでは、アプリケーションロジックとユーザー操作・副作用との接続を検証する。
- 内部依存は原則として実物を使用し、依存先固有の振る舞いはそれ自身のテストで検証する。
- 依存先固有の振る舞いかは、Thenの結果で判定する。自身のテストを持つ子の部品について、結果が親の入力・状態・配線(子へ渡す値、子の置き方、子の結果を受けた親の処理)によらず子の部品だけで決まるなら、親のテストで確かめず、子のテストに任せる。親の組み立てで決まる結果は親の責務として確かめ、自身のテストを持たない子の部品の結果は、従来どおり親のテストが確かめる。
- 例: 入力欄でEnterを押すとフォーカスが外れることは、共通の`Input`の責務で、親のテストでは確かめない。Enterを押しても保存もダイアログの閉鎖も起きないことは、入力欄をformに入れるかなど親の組み立てで決まるため、親のテストで確かめる。
- 例: 親が渡した値による子の表示の違い(取得の状態に応じた`FetchState`の文言、並べた距離に応じた`PresetInfo`の文言など)は、子の文言で観測してよい。子の表記の規則の組合せ(文言の細かな場合分け)は、子のテストで確かめる。
- モックはI/O・非決定性・実行環境の制約など、テスト境界の外側を隔離するために用いる。
- テストは「対象要素→行動→条件」を基準に、適切な粒度で入れ子にしてまとめる。
- 境界条件は境界値とその前後を同一テスト内でまとめて検証する。境界値テストの正常側と正常テストは重複ではない。
- カバレッジを満たすことだけを目的としたテストを書かない。

## 結合テスト

- 所有する複数モジュールの接続はVitest、実ブラウザのAPIとの接続はPlaywright、DBとの接続はpgTAPを使う。
- IndexedDB、Service Worker、認証SDK、RPCなど、データを保存・送受信する境界の契約を検証する。
- 1つの外部境界を主対象にし、他の外部境界は必要に応じて制御する。
- Playwrightを使っていても、1つのブラウザ境界だけを検証するテストはE2Eとして扱わない。
- リンクは、href属性の値だけで確かめず、Playwrightで押して、遷移先のURLと画面が表示されることを確かめる。jsdomは画面遷移と、押下を妨げる要素を再現しないためである。
- 認証状態などの判定の結果は、リンクのhref属性の値で確かめてよく、押して移ることは上の規則のとおりPlaywrightで確かめる。
- リンクのテストは1リンク1件とし、リンクを持つ画面や部品の機能のE2Eのファイルに置き、そのファイルのE2Eと同じ書き方にする。

### 成果物

- 対象の境界に応じたVitest、Playwright、またはpgTAPテストコード

## データベーステスト

pgTAPを使用する。

- 新規または変更するテーブルについてテストを作成する。
- スキーマ、権限、RLS、RPC、冪等性、トランザクションなど、データベースに要求される振る舞いを検証する。
- 権限、RLS、RPCは、期待値表を実測結果と全件比較する行列テストで固定し、表にない対象の追加を網羅性ガードで検出する。
- 行列テストに含まれる検証を、個別のテストで重複させない。
- pgTAPで再現できないサインアップ経路は、E2Eテストで検証する。

### 成果物

- pgTAPテストコード

## E2Eテスト

Playwrightを使用する。

- ユーザー操作を通して、主要な利用経路が成立することを検証する。
- 実ブラウザ・認証・DBを通さないと確認できない高リスクな接続を検証する。
- 単体・コンポーネントテストで判断や入力境界を、DBテストで権限やRLSなどを検証し、E2Eでは主要利用経路や接続に必要なケースを選ぶ。
- テスト名は、前提、操作、利用者から見た結果が分かる文にする。
- フェーズコメントで区切らず、利用者の操作順に記述し、各段階で次へ進めたことを確認してから、最後に利用者目的の結果を確認する。
- 複数の段階を通すテストは、各段階の先頭に、その段階で利用者が行うことと進む先を書くコメントを1つ置く(例: `// メールを送って認証コードの入力画面へ進む。`)。2つ目以降の段階コメントの前には空行を置く。
- 段階は、次の画面または状態へ進んだことの確認で終わる操作のまとまりで、最後の段階は利用者目的の結果の確認で終わる。段階の数は操作の数でなく画面や状態の切り替わりの数で決まり、同じ画面を確かめるexpectが続く箇所は1つの段階の末尾として扱う。画面を開く操作(`page.goto`)と、利用者の操作によらない準備の待ち(`waitForHydration`、自動のセキュリティチェックの完了を待つ`data-captcha-ready`)は、段階の終わりに数えない。
- 段階ヘルパーは、同じspecのファイル内関数で、`page`を受け取り、次の画面または状態へ進んだことの確認で終わる関数である。段階ヘルパーの呼び出しは1つの段階に数え、段階コメントを重ねない。ヘルパー名が段階を示すためである。確認で終わらないヘルパー(画面を開くだけ、入力するだけ、データを用意するだけ)は段階に数えない。
- 段階が1つのテストには段階コメントを置かない。
- 1テストだけが呼ぶヘルパーは、呼び出し元の本文へ展開してよい。展開した段階には段階コメントを置く。
- 1操作ごとのコメントと、段階の中の操作を言い換えるコメントは書かない。段階コメントはフェーズコメントではなく、Given、When、Thenの語を使わない。
- コードから読み取れない理由(待ち、時計、回避策、認証状態の用意)は、段階コメントとは別に、該当する文の直前のコメントで書いてよい。
- 1テストでは1つの利用経路または高リスクな接続を検証する。
