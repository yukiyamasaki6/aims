# Testing

合意済みの設計に基づいて、期待される結果を検証するテストを作成する。

- テスト要件は、実装ではなく合意済みの設計に基づいて定める。
- テスト対象の結果や副作用を検証し、テスト自身の設定を確認するだけのテストを書かない。
- テストはGiven-When-Then形式で記述し、各フェーズをコメントで明示する。
- テストケースは正常系→異常系の順に記述する。
- テストコードも、`agents/implementation.md`の「コードの複雑さ」に従う。

## フロントエンド単体テスト

Vitestを使用する。

- アプリケーションロジックでは、分岐・判定・状態遷移・データ変換などの振る舞いを検証する。
- UIコンポーネントでは、アプリケーションロジックとユーザー操作・副作用との接続を検証する。
- 内部依存は原則として実物を使用し、依存先固有の振る舞いはそれ自身のテストで検証する。
- モックはI/O・非決定性・実行環境の制約など、テスト境界の外側を隔離するために用いる。
- テストは「対象要素→行動→条件」を基準に、適切な粒度で入れ子にしてまとめる。
- 境界条件は境界値とその前後を同一テスト内でまとめて検証する。境界値テストの正常側と正常テストは重複ではない。
- カバレッジを満たすことだけを目的としたテストを書かない。

- Vitestテストコード

## データベース単体テスト

pgTAPを使用する。

- 新規または変更するテーブルについてテストを作成する。
- スキーマ、権限、RLSなど、データベースに要求される振る舞いを検証する。
- 権限、RLS、RPCは、期待値表を実測結果と全件比較する行列テストで固定し、表にない対象の追加を網羅性ガードで検出する。
- 行列テストに含まれる検証を、個別のテストで重複させない。
- pgTAPで再現できないサインアップ経路は、E2Eテストで検証する。

- pgTAPテストコード

## E2Eテスト

Playwrightを使用する。

- ユーザー操作を通して、主要なユーザーフローが成立することを検証する。
- 単体テストで検証できるロジックがあることだけを理由に、E2Eの行を外さない。単体テストとE2Eは組み合わせて使い、E2Eは画面・Server Action・実バックエンドの接続と、ユーザーが期待する操作の実現を確かめる。
- `docs/features/<対象>/<機能>/requirements.md` の1行を1テストとし、テスト名を `<ID>: <Given>のとき、<When>すると、<Then>` とする。「Given」「When」「Then」の語は書かず、結果はユーザーが期待する操作の実現として書き、行動や条件を混ぜない。行動から自明なGivenは省いてよい。
- 順序は `requirements.md` の行の順に従う。
- 1テストのWhenは1つとする。
- 入力検証と送信失敗のエラー表示は、機能ごとに代表1件をE2Eに置く。代表であることが分かるよう「エラーメッセージが表示される」をThenとし、テスト本文に代表例であるコメントを置く。個別の検証規則は単体テストで網羅する。
- 共通部品（確認ダイアログ、メニューなど）の挙動は、各機能の画面が正しく使っていることをその機能で検証する。共通部品であることを理由に省かない。
- 同じ分岐を検出する重複する行は、代表1行にまとめる。
- E2Eから外す行は、外す理由と、代表の行ID・単体テストの場所を、同じPRの説明に記録する。
- 入力値の網羅、計算、表示の組み合わせは単体テストで検証する。権限とRLSはpgTAPで検証する。
- E2Eで検証するのは、画面をまたぐフローと、ブラウザ固有の挙動（PWA、レスポンシブ、サインアップ経路、ナビゲーション）とする。
