# 紹介画面のテスト設計

## 基準と範囲

基準は、[introductionの要件](requirements.md)と[設計](design.md)である。
ロゴを押して紹介画面へ移ることは[app/navigation](../navigation/test-design.md)の責務で、本書では扱わない。
オフラインで`/`を開いたときのオフラインのページは`app/offline-pwa`の責務で、本書では扱わない。
認証済みの転送の規則(`proxy.ts`)は`app/navigation`の責務で、本書では紹介画面の3つのリンクから着くことだけを確かめる。
本書は実装結果から期待値を導かない。
配置候補は既存ファイルを使うための案で、部品の内部構造やprivateな関数を契約にしない。

紹介の項目、文言、図の絵柄、配色、カードの列数、ヘッダーの寸法は、配置とデザインである。文言と図(カード01〜05)は、ユーザーが確定した。
これらはテストの期待値にせず、手動で確認する。
文言は、将来の差し替えがありうるため、テストは文言を`translatorFor("introduction")`で得て、文字列を直書きしない。
文言の差し替えと項目の増減でテストを直さずに済むことを、この設計の条件とする。

壊れた場合の影響が大きい順に、次を防ぐ。

1. 「記録を始める」、サインイン、サインアップを押しても目的の画面へ移れない(入口の喪失)。
2. 最初の表示範囲、または末尾まで読んだ後に、サインアップへ進む操作が隠れて押せない。
3. 認証済みの利用者が、3つのリンクのいずれかで移動先の画面から出られない。
4. 今使えない機能や、利用の条件(料金・登録・ゲスト)を紹介に載せてしまう。
5. 見出し構造と装飾の図の扱いが崩れ、支援技術で読めない。

リンクの押下と遷移先は、規則どおりPlaywrightで確かめる。
単体のhrefの確認は、行き先の接続の確認にとどめる。
位置・寸法・クラス・配色・列数は、E2Eでも単体でも期待値にしない。
単体・コンポーネントは、入力や状態に依らない固定の見た目(固定のクラス、固定のスタイル値)を期待値にしない。

「結合」と「E2E」の分け方は、実物で通す境界で決める。
リンクの1件ずつは、未認証または認証済みの状態を制御して実ブラウザで押す結合とする。
主要な経路の1件だけ、読み進めてから押すE2Eとする。

一覧は、要件の対象外と、要件定義の引継事項にある未実装の機能から取る。
機能が実装された時点で、その語を一覧から外す(紹介に載せるかはレビューで判断する)。
文言と機能の一致そのものは、テストで検出しない(設計判断)。
禁止語は、機能の実装に応じて増減しうる。
一覧は文言にではなく、要件の語にだけ依存させる。
ヘッダーのリンク名「サインイン」「サインアップ」は`main`の外にあるため、2番目の件の対象外で、「アカウント登録」の語と衝突しない。

見出しの数は、設計の「紹介する項目」の数と一致させる。
項目が増減したときは、このテストの数と本書を一緒に直す。

## 結合のケース(Playwright)

配置候補は、新設する`apps/web/tests/e2e/app/introduction.spec.ts`である。
紹介画面の機能のE2Eとして、`navigation.spec.ts`の「紹介画面とロゴ」の紹介画面のテストと、認証済みの紹介画面のテストをここへ移す。
ロゴのテストは`navigation.spec.ts`に残す。
文言は`translatorFor("introduction")`で得る。

### 同名のリンクと探し方

「記録を始める」は2つあるため、`getByRole("link", { name })`だけでは1つに絞れず、strict modeの違反になる。
次のとおり探す。

- ヘッダーのリンクは、`page.getByRole("banner")`の中で、名前で探す。
- 先頭の「記録を始める」は、`page.getByRole("main")`の中の同名のリンクの`first()`、末尾の「記録を始める」は`last()`とする。
- 2つあることは、`main`の中の件数を1件のテストで確かめる。

`first()`と`last()`は文書の順に依る。
順は設計の定義(先頭がキャッチの下、末尾が本文の末尾)であり、実装の詳細ではない。

### 操作できること(隠れていないこと)の確かめ方

Playwrightの`click()`は、対象を自動でスクロールして押す。
そのため、最初の表示範囲や末尾で隠れていないことを、`click()`だけでは確かめられない。
操作できることは、押す前に、対象の中心の点の最前面の要素(`elementFromPoint`)が対象のリンクの中の要素であることと、その点がビューポートの中にあることで確かめる。
要素の位置や寸法の比較では確かめない。
この確認は、同じspecのファイル内の補助関数にまとめる。

## E2Eの主要経路

保存された認証状態を空にした利用者が、`/`を開き、読み進めて、サインアップ画面へ進む経路を1件持つ。
結合のケースの「末尾まで読み進めた後も…」と同じ流れになるため、この経路は上の末尾のテストをE2Eの主要経路として兼ねる。
E2Eを別に増やさない。
サインアップを完了してホームへ着く経路は`auth/signup.spec.ts`の責務で、ここでは繰り返さない。

## 更新の要否を確かめる観点との関係

紹介の文言と機能の一致は、テストで検出しない。
`agents/review.md`の次の2つの観点で、人が確かめる。

- 利用者から見える機能の振る舞いを変える・削除する変更では、紹介画面が今の振る舞いと食い違わないかを確かめる。
- 機能を加える変更では、紹介画面に載せるかを判断し、判断と理由をPRの説明に書く。

テストが担うのは、その補助の守りだけである。
未実装の機能と利用の条件の語を載せないこと(単体の禁止語の2件)は、機械で検出できる最小の範囲として置く。
画面の配置や見た目が変わっても図が誤りにならないことは、図が画面に依存しない概念図であるという設計の性質で保たれ、テストで確かめない。
新しい機能の追加時に、禁止語の一覧から語を外すかをレビューで判断する。

## データと実行上の条件

単体・コンポーネントのテストは、フェーズコメント(Given・When・Then)を`agents/testing.md`の規則に従って置き、正常系から異常系の順に書く。
禁止語のケースは、一覧を同じファイル内に持ち、失敗時に見つかった語が分かるメッセージにする。
紹介画面は状態・データ・通信を持たないため、時刻・通信・視口の偽物は使わない。
E2Eは有効なローカル認証・DB接続設定を使い、本番の秘密情報・共有DB・DBリセットは使わない。
設定が不足する場合は、実行できた検証と未確認のケースを分けて報告する。
紹介画面のリンクは水和の前でも動くため、`waitForHydration`で待たない。
ただし、サインアップ・サインイン画面の水和を要する操作は、既存のspecに従う。

## 検証の完了判定

後続担当は、上の単体・結合・E2Eのケースと、既存の関連するテストを実行する。
既存の関連するテストは、`navigation.spec.ts`のロゴのテスト、`offline-pwa.spec.ts`(`/`の見出し(キャッチ)と、オフラインのページ、ロゴのテスト)、`settings.spec.ts`(紹介画面でパネルが開かない)、`app-logo.test.tsx`、`screen-frame.test.tsx`、`proxy.test.ts`である。
併せて`pnpm lint`と`pnpm typecheck`を実施する。
手動確認は、実施した条件と、未確認の項目を分けて報告する。
未実行、環境の制約による未確認、既存の失敗を、成功に含めない。
行カバレッジの数値を合否にしない。
