# レフトパネルの移動項目、ラウンドの開始ボタン、点数一覧見出しのテスト設計

## 基準と範囲

基準は、[navigationの要件](requirements.md)・[設計](design.md)と、[rounds/historyの要件](../../rounds/history/requirements.md)・[設計](../../rounds/history/design.md)に、開始の入口の基準として[rounds/startの要件](../../rounds/start/requirements.md)・[設計](../../rounds/start/design.md)と[app/settingsの要件](../settings/requirements.md)・[設計](../settings/design.md)を加えたものである。
今回の変更である「点数一覧」への項目名・見出しの統一、ホーム・点数一覧・設定の装飾アイコン、設定上部の区切り線削除に加え、ラウンドの開始画面への2つの入口(レフトパネルの最上部のラウンドの開始ボタンと、ホームの右下のラウンドの開始ボタン)、開始画面の現在地の文言「ラウンドを開始」と、それらが触れる既存の操作を検証する。
さらに、レフトパネルの4ボタンの高さ44pxと外側の余白の変更(設計書のボタンの高さと余白の値)は、見た目の寸法のため手動確認だけで確かめ、既存の単体・E2Eが変わらず通ることで操作の維持を確かめる。
本書は本体コードやテストコードの実装結果から期待値を導かない。
テストの配置候補は既存ファイルを利用するための案であり、部品の内部構造やprivateな関数を契約にしない。

最初に移動先の誤り、現在地の誤表示、キーボード操作不能、開始画面で押したときの選択の消失、設定パネル中の誤った遷移を防ぎ、次にホームの右下のボタンによる最後のカードの遮蔽(手動確認)を防ぐ。
アイコンの図柄と区切り線も必須の受入対象とし、表示確認を省略しない。
認証、DB/RPC、並べ替え・絞り込みの計算や保存形式は変更対象外であり、新しい網羅テストやDBテストは設けない。

## E2Eの主要経路

認証済みのローカル利用者に、サーバー反映済みの完了ラウンドと端末の入力中ラウンドを用意する。
ホームで入力中ラウンドが表示されたことを確認し、メニューの「点数一覧」を選び、見出しと完了ラウンドの名前・実施日・合計点が表示されたことを確認して、そのカードから該当ラウンドの詳細を開けることを確認する。
点数一覧には入力中ラウンドが混ざらないことを確認する。
この経路は既存の同等ケースを再利用し、画面幅と一覧状態の全組合せをE2Eへ追加しない。

## 手動での表示確認

`pnpm preview`をport 3000で起動し、ビルド済みの表示で確認する。
比較対象は設計で定めた外観と、利用できる場合は変更前の同じ画面幅の画像とする。
変更前画像がない場合は、その制約を報告し、比較したと記録しない。
ヘッダーのアイコンは、実装前に、各画面(ホーム、点数一覧、ラウンドの詳細、設定パネル内の戻る)の幅375pxと1024pxで、押せる範囲の幅・高さとヘッダー高さを開発者ツールで計測して記録し、変更後に同じ計測で一致を確かめる。
戻るは幅が文字幅に依るため、変更前後で同じ文言の幅を比べる。
フィルターは、絞り込み中の点がある状態とない状態の両方を目視する。
ヘッダーのアイコンの変更で既存の単体・E2Eは変わらず通る想定とし、新しい自動テストは追加しない。
高さと余白の変更は、実装前に変更前の値で幅375pxと幅1024pxの画像を撮り、変更後と並べて比べる。
寸法は、ブラウザの開発者ツールで要素の計算後の値を読んで確かめ、設計書の値と一致するかを見る。
開始・ホーム間は、両アイコン(svg)の上下端の座標差で測り、44pxであることを確かめる。

| 条件 | 確認内容 |
| --- | --- |
| 幅375pxのドロワーと幅1024pxのレフトパネル | ホームは家（House）、点数一覧は番号付きリスト（ListOrdered）、設定は歯車（Settings）で、全項目に文字が残る。 |
| 同上 | アイコンが文字の左で上下中央に並び、20px四方・間隔8pxを基準として縮まず、文字色を継承する。 |
| 同上 | 設定上部の区切り線がなく、設定は下端の位置を保ち、区画の余白が8pxになる。項目順、ロゴ、閉じるボタンの配置(最上段の行の高さ45px)が維持される。 |
| 各項目の現在地表示 | 背景と文字の強調が維持され、アイコンも文字と整合する。設定パネルを開いても、ホームか点数一覧の強調が残り、設定の項目は強調されない。 |
| 幅1024pxの設定パネルと幅375pxの設定パネル | 選んでいる分類「アカウント」が、レフトパネルの現在のビューの項目と同じ見え方で強調され、マウスを重ねても塗りが変わらない。 |
| 狭い画面で縦向き・横向き、開閉途中 | アイコンと文字が収まり、開閉の動きやクリック可能範囲を損なわない。 |
| 幅375pxのドロワーと幅1024pxのレフトパネル | 開始ボタンが最上部で全幅に伸び、塗りと枠線を持たず、Plusのアイコンと太めの文字と下の空白で、移動項目と見た目で区別でき、現在地の強調の対象にならない。 |
| 幅375pxと幅1024pxのホーム | 右下のボタンがアイコンと文字「ラウンドを開始」を並べた横長の丸角で、本文を末尾までスクロールした最後のカードとメニューがボタンの上に余白を保って止まる。 |
| 幅375pxと幅1024px | 4ボタンの高さが44px、パネルの左右の端とボタンの間が8px、開始ボタンのアイコンとホームのアイコンの縁どうしが44px(ボタンの間の空き20px)、項目間が0px、設定の区画の下端が8px。いずれも変更前(36px、16px、アイコンの縁どうし36px、4px、16px)より、高さと開始・ホームのアイコン間は大きく、左右・項目間・設定の下端は小さい。 |

## データと実行上の条件

文言を描く単体・コンポーネントテストはIntlTestProviderを使い、未登録キーは失敗させる。
内部依存は実物とし、取得の成功・保留・失敗は所有するI/O境界の外側で制御する。
時刻・通信状態・画面幅の制御には共有のClock・Connectivity・Viewportの偽物を使い、実ブラウザでは実際のviewportを変更する。
待機は画面状態や制御したPromiseの解決を使い、任意秒数のsleepや実ネットワークのタイムアウトに依存しない。
完了ラウンドのデータは実際の屋外構成（各距離12エンド×3射または6エンド×6射）を満たし、点数も固定する。
データ量を理由に成立しない短縮ラウンドを作らない。
E2Eは有効なローカル認証・DB接続設定を使い、本番の秘密情報・共有DB・DBリセットは利用しない。
設定が不足する場合は実行できた検証と未確認のケースを分けて報告する。

単体はGiven・When・Thenを分けて正常系から異常系の順に実装し、各テストは1つの前提と操作による結果を確かめる。
ブラウザは利用者の操作順に書き、複数段階では遷移先・状態を確認してから次へ進む。
失敗時は対象項目・パス・画面幅・一覧状態と実際の値が分かるようにする。

## 検証の完了判定

後続担当は対象の単体テスト、既存の関連する遷移・現在地・開閉・フォーカスのテスト、主要E2E、手動確認を実施する。
併せて`pnpm lint`と`pnpm typecheck`を実施する。
未実行、環境制約による未確認、既存の失敗を成功に含めず報告する。
行カバレッジの数値を合否にせず、現在地の一致・不一致、開始ボタンの既定動作の停止、ドロワーと列の開閉の判定が未検証でないかを確認する。
本書の作成ではテスト実装・実行、ビルド、ブラウザ操作は行わない。


## メールOTP一本化に伴う経路の回帰

認証とDBの検証は[認証共通テスト設計](../../auth/test-design.md)に従う。
本書の従来の外観変更の範囲とは分け、既存auth-routes・proxyの単体とnavigation.spec.tsの経路試験を更新する。

- 未認証の/rounds配下からパス・クエリ・設定ハッシュを保ってサインインし、OTP確認後に目的の画面と設定項目へ戻る。
- 認証済みの/signinは安全な遷移元へ、なければホームへ移る。外部URLはホームへ進む。新規・既存で区別しない。
- /signupは廃止しており、未認証と認証済みそれぞれで、クエリ・ハッシュ付きを含め任意の未定義URLと同じ扱いであることを確認する。専用転送先やガードを期待しない。
- /reset-password専用のページ・経路定数・認証ガード・matcher・Service Worker・試験補助の定義を削除し、互換分岐を残さないことを差分レビューする。
- /reset-passwordを開いた結果は、未認証と認証済みそれぞれで任意の未定義URLと同じ扱いであることを確認する。専用転送先を期待せず、廃止したpassword-reset.spec.tsを維持する理由にしない。
- サインアウトと削除成功後は遷移元なしの/signinへ進み、期限切れ等の通常の認証喪失時は既存の遷移元を保つ。

準備は固有利用者の実OTPへ置換し、共有認証状態を失効させない。
未サインイン向けヘッダーは持たない。サインイン画面のロゴ(紹介「/」へのリンク)を押す試験は`auth/signin.spec.ts`の1件に置く。

## 認証Cookieの引き継ぎとキャッシュ禁止

### 基準と検証する境界

本節は[設計](design.md)の`updateSession`と`respond`の契約を基準に、転送時のCookie欠落、書き換えた応答のキャッシュ許可、後続へ渡す古いCookieを防ぐ。
前節までの外観・操作の検証とは別の変更として扱い、既存の認証経路とサインインの判定を維持する。
優先するのは経路と認証の維持、転送への全Cookieの反映、書き換えた応答のキャッシュ禁止、書き換えのない要求の維持、後続への書き換え後のCookieの引き渡しの順とする。

| 層 | 検証する契約 | 配置・観測点 |
| --- | --- | --- |
| 単体(Vitest) | セッションの判定、書き換えの蓄積、転送・非転送の応答、後続へ渡す要求 | `apps/web/src/lib/supabase/infrastructure/session.test.ts`で`updateSession`と返された`respond`を呼び、実物のNextRequest・NextResponseを読む。 |
| モジュールの統合(Vitest) | 経路の判断と、セッションの書き換えを応答へ載せる処理の接続 | `apps/web/src/proxy.test.ts`で実物の`proxy`・`updateSession`・`redirectFor`を通し、応答の転送先・307・Cookie・ヘッダーを読む。 |
| ビルド済みアプリの統合(再現手順) | 実物のSDK・認証サービス・Next.jsを通した更新と削除、静的ページの指定に優先するキャッシュ禁止 | 隔離した認証サービスとビルド済みアプリへHTTP要求を送り、転送を追う前の応答を読む。 |
| E2E(Playwright) | 更新を伴う最初の307だけで最新のCookieが保存され、その後に保護画面を利用できること | `apps/web/tests/e2e/app/navigation.spec.ts`に主要経路を置く。既存のCIと同じローカルSupabaseを使い、転送を追わずにcontextのCookieと認証サービスの現在値を照合してから画面を開く。 |

`proxy`の応答だけでは、後続のNext.jsが重ねる静的ページのキャッシュ指定は保証できない。
最終応答のヘッダーはビルド済みアプリで確認し、単体の成功を代用にしない。
後続へ渡す要求の保証は、承認された判定に従い、`respond(null)`が返す`x-middleware-request-*`の時点で確認する。
後続のNext.jsが要求の`Cache-Control`・`Expires`・`Pragma`を応答の値に置き換えたり追加したりすることは、違反としない。
Cookieを書き換えるときの組み直しで、復号できないCookieが落ち、同名が1つになることも、承認済みの制約として扱う。
転送の判定と307は維持するが、書き換えて転送しない条件付き要求が304から本文ありの200になることは、違反としない。

### 単体で確かめる振る舞い

既存の`response`を使うケースは`respond(null)`へ移し、「応答だけに反映する」という期待を要求と応答の両方への反映へ変更する。
サインイン判定・環境変数・`getAll`の既存ケースは残し、`getClaims`が返すclaimsの有無と失敗時の未認証を確認する。
以下の順で正常系から異常系へ記述し、前提や操作の異なるケースは分ける。

| ケース名の案 | 前提・操作 | 期待結果 |
| --- | --- | --- |
| セッションを更新すると非転送の応答と後続の要求へ全ての分割Cookieを渡す | 複数の分割Cookieと無関係のCookie・要求ヘッダーを用意し、`getClaims`内の`setAll`で分割を更新して`respond(null)`を呼ぶ。 | 応答の全分割が新しい値・指定属性を持つ。後続のCookieも全分割が新しい値で、無関係のCookieとヘッダーは保たれる。転送先はない。 |
| セッションを更新すると転送にも非転送と同じCookieとキャッシュ禁止を載せる | 同じ書き換えを与えた独立の要求から、非転送とURL指定の応答を作る。 | 転送先と307が正しく、Cookieの名前・値・属性・有効期間と、ライブラリから渡された3ヘッダーの値が両応答で一致する。 |
| 複数回の書き換えでも先のCookieとヘッダーを失わず同名は最後の値になる | 実際に複数回になるPKCEの検証用Cookieの削除とセッションの削除等を基に、2回目が1回目の全Cookieを含まない`setAll`を再現する。重複する名前も含め、転送と非転送を別ケースで作る。 | 先にだけ渡したCookieと後から渡したCookieが残り、同名の値と属性は最後の指定になる。3ヘッダーも残り、非転送の要求は最後のCookieの状態になる。 |
| 書き換えがないとCookieとキャッシュ指定を追加せず要求を保つ | `setAll`を呼ばず、Cookieとヘッダーを含む要求から転送・非転送を別ケースで作る。 | `Set-Cookie`・`Cache-Control`・`Expires`・`Pragma`を追加しない。要求の内容は変わらず、非転送で後続へ渡すCookieとヘッダーも元の値である。 |
| 不要な分割を削除すると後続に古い値を渡さずブラウザへ削除を伝える | セッションの分割数が減る更新を再現し、不要な分割はSDKと同じ空の値・`maxAge: 0`で渡す。 | 非転送の要求では不要な分割が空の値になり、残る分割は新しい値になる。転送・非転送の応答には不要な分割の削除属性と3ヘッダーが付く。 |
| セッションを削除すると後続に古い値を渡さずブラウザへ削除を伝える | 全分割を空の値・削除属性へ書き換え、転送・非転送を別ケースで作る。 | 応答は全分割の削除と3ヘッダーを持つ。非転送の要求の全分割は空の値で、無関係のCookieは残る。要求のCookie自体の消滅は期待しない。 |
| 書き換え後に認証判定が失敗しても書き換えを応答に残す | `setAll`の後に`getClaims`がエラーを返す場合と例外を投げる場合を分ける。 | 未認証となり、転送・非転送の応答にはそれまでのCookieと3ヘッダーが残る。例外を投げ直さない。 |
| 書き換え指示のない通信失敗でCookieを独自に削除しない | `setAll`なしで通信失敗を再現する。 | 未認証として返し、要求は変わらず、削除用の`Set-Cookie`やキャッシュ禁止を追加しない。 |

Cookieは名前で照合し、`Set-Cookie`の並び順やヘッダー全体の文字列を固定しない。
有効期間は時計を固定して`maxAge`と`expires`を確かめ、テスト後に時計を復元する。
`Expires`応答ヘッダーと、Cookieの`Expires`属性を区別する。
後続のCookieは`x-middleware-override-headers`に`cookie`が含まれることも確認し、`x-middleware-request-cookie`を復号した名前と値で比較する。
無関係のヘッダーには`x-request-id`などを使い、要求のキャッシュヘッダーもproxyが渡す時点の値で確かめる。
`cookies()`は変更前から更新後を返すため、後続へのCookieの引き渡しの合否には使わない。

### proxyの接続と経路の回帰

既存のmatcher・経路の一致・遷移元の検証は残し、転送ケースでは307も確認する。
経路の細かな組合せは既存の`auth-routes.test.ts`へ任せ、同じ表を上位で繰り返さない。
`proxy.test.ts`では`@supabase/ssr`だけを置き換え、実際の`getClaims`中と同じタイミングで`setAll(cookiesToSet, headers)`を呼ぶ。
`updateSession`や`respond`は置き換えず、転送で書き換えが落ちる変更前の不具合を検出できるようにする。

| 前提・要求 | 応答で確かめる結果 |
| --- | --- |
| 更新後に認証済みとなる`/signin`。遷移元あり・なしを別ケースにする。 | 従来の行き先への307に更新した全Cookieと3ヘッダーがある。 |
| 削除後に未認証となるクエリ付きの`/rounds`配下。 | パスとクエリを遷移元に付けた`/signin`への307に全Cookieの削除と3ヘッダーがある。 |
| 更新後の認証済み`/rounds`配下、削除後の未認証`/signin`。 | 非転送で書き換えと3ヘッダーが残り、後続へ渡すCookieは書き換え後になる。 |
| 書き換えのない認証済み・未認証の要求。 | 従来の転送有無と行き先を維持し、Cookieとキャッシュ指定を追加しない。 |

### ビルド済みアプリでの確認手順

実装を始める前に、基点`79e560a`のビルドで、書き換えのない200と307の`Set-Cookie`・`Cache-Control`・`Expires`・`Pragma`、HTMLとRSCのETagの有無と値、静的な事前生成の一覧、認証サービスへの要求を記録する。
未認証の`/signin`と有効期限に余裕のある認証済み`/rounds`を200の代表とし、認証済み`/signin`と未認証`/rounds`を307の代表にする。
200と307の各代表を、HTML、RSC、通常の先読み、セグメントの先読みの4形式で記録する。
変更後も同じ条件で照合し、静的ページの`Cache-Control: s-maxage=31536000`と、余分なCookie・キャッシュ禁止のない状態を維持する。
静的な事前生成はビルドの出力で確認し、認証要求は同じ鍵方式・期限・経路ごとに比較する。
非対称鍵のJWKSの初回取得と、更新の通信を区別し、環境依存の固定回数を期待しない。

共有Supabaseを変更せずに再現できるよう、使い捨ての専用認証サービス・DB・ネットワークを用意し、アプリの複製をその接続先でビルドする。
この専用環境は本項の再現手順に限り、既存のCIで実行するE2Eの前提にはしない。
手動の画面確認はport 3000の`pnpm preview`を使う。
本番・プレビューの接続先や秘密情報は使わず、共有Supabaseの起動・停止・reset・設定変更はこの手順に含めない。
専用の環境で作った固有利用者を使い、Cookieの形式・符号化・分割は実物のSDKに任せる。
長いセッションは現実に成立する利用者メタデータ等で作り、実際に複数分割になったことを確認する。
期限切れは署名済みアクセストークンの期限も過ぎた状態で作り、Cookie内の`expires_at`だけを変えて削除できたと扱わない。

| セッションの状態と経路 | 確認する結果 |
| --- | --- |
| 更新対象で有効な`/signin`(遷移元あり・なし)、`/rounds`配下。 | 前者は従来の転送先への307、後者は非転送。全分割の更新と、不要な分割がある場合の削除がある。 |
| 更新を拒否される失効済みかつアクセストークン期限切れの`/rounds`配下、`/signin`。 | 前者は遷移元付きの307、後者は非転送。全セッションCookieの削除がある。 |
| 書き換えのない未認証・有効期限に余裕のある認証済みの要求。 | 200と307のいずれも、基点と同じCookieとキャッシュ指定である。 |

各行をHTML、RSC(`RSC: 1`)、通常の先読み、セグメントの先読み(`Next-Router-Segment-Prefetch`)で確認する。
RSCと先読みは、現在のビルドの実ブラウザが発行したURLとrouter関連ヘッダーを採取して使い、実際に該当形式の応答になったことも記録する。
各更新・削除の要求には独立のセッションを用意し、先の更新で状態が変わったCookieを使い回して分岐を取り違えない。
転送を自動追従しないHTTP要求で最初の応答を確認し、転送先で付いたCookieやヘッダーを転送元の結果に含めない。
書き換えた全ての応答で、実物のSDKが渡す`Cache-Control`・`Expires`・`Pragma`と値が一致し、共有キャッシュを許す`s-maxage`等が残らないことを確認する。
SDK指定の採取は使い捨ての複製でCookieアダプターの入力を観測し、トークンの実値は記録しない。
ヘッダー名を本体コードへ固定しないことは差分レビューで確認する。

304の確認はHTMLに限り、同じビルドのETagに一致する`If-None-Match`を送り、書き換えのない非転送は304のまま、書き換えた非転送は本文ありの200とキャッシュ禁止になることを確認する。
RSCは基点でもETagがなく、`If-None-Match`を送っても200になるため、書き換えのない非転送は基点と同じ200、書き換えた非転送は本文ありの200とキャッシュ禁止を期待する。
条件付き要求は、`Cache-Control: no-cache`を自動追加しない`node:http`等で送り、送信側のヘッダー追加によって304の判定が変わらないようにする。
分割が減る更新、失効による削除、通信失敗による再試行を区別し、実物のSDKで通信失敗がCookie削除を新たに指示しないことも確認する。
失効は専用利用者だけに適用する。
調査時のHS256だけで非対称鍵の挙動も確認済みとせず、鍵方式・認証サービスと依存の版・実行できた形式を結果に残す。
再現手順を環境不足で実行できない場合は、未確認の条件と理由を報告する。

### ブラウザの主要経路と既存の安全網

E2Eは既定のPlaywright設定と、CIと同じローカルSupabase・Mailpit・DBを使い、port 3100のpreviewで実行する。
専用の認証サービスや設定を追加せず、固有利用者を既存のOTP準備で作る。
更新対象のセッションを新しいBrowserContextへ用意し、画面はまだ開かず、更新前のトークンを保持する。
そのcontextとCookieを共有する`context.request.get("/signin", { maxRedirects: 0 })`で最初の307だけを受け取り、従来の転送先と更新の`Set-Cookie`があることを確認する。
画面の読み込みやほかのアプリ・認証要求を送る前に、contextに保存された全分割を復元し、更新前と異なるトークンであることと、認証サービスの現在のトークンと一致することを必ず照合する。
照合の補助は`helpers/auth-db.ts`へ置き、既存のローカル接続の検査を使い、当該利用者IDとセッションIDに絞った行だけを読み取る。
トークン方式に応じた現在値との一致を検証し、接続失敗、行がない場合、照合できない方式、不一致はテストを失敗させる。
照合を省略して成功させたり、専用環境がないことを理由にskipや条件付きのアサーションにしたりしない。
トークンの実値はログや失敗メッセージへ出さず、補助から返した一致の真偽を検証する。
この照合が成功してから初めて、307の転送先をブラウザで開き、従来の保護画面へ進んで利用できることを確認する。
基点`79e560a`では最初の307に`Set-Cookie`がなく、後続の要求前の照合で失敗することを確認し、修正後の成功と対にして記録する。
保護画面を開いた後の照合だけでは、転送先で古いトークンの再利用により回復して成功しうるため、最初の307直後の照合を代用しない。
最初の要求は画面を開く前のAPIRequestContextで行うため、ブラウザの自動更新やService Workerによる回復を挟まない。
待機は対象応答・Cookie適用・画面状態で行う。
分割数・属性・ヘッダー・形式の全組合せは上記の単体とHTTPの確認に任せ、E2Eへ重複して追加しない。

既存のnavigation・signin・signout・offline-pwaのE2Eを回帰として実行する。
特に、更新通信が失敗しても一覧に留まるケース、別の書き手の更新と重なっても留まるケースを残し、proxyの通信失敗時の未認証判定と混同しない。
既存の`helpers/stored-session.ts`は単一Cookie専用のため、分割Cookieの確認にそのまま使わない。
必要な補助は既存のE2E補助へ配置し、新しい専用設定・モックサーバー・CIジョブは作らない。
DBの仕様は変更しないため、新しいpgTAPは追加せず、共有DBのresetを伴う`pnpm test:db`も本変更の確認手順に含めない。

### 完了判定と記録

後続担当は変更前の基準を確保し、対象のVitestで不具合の再現と修正後の成功を確認した後、ビルド済みアプリの統合、主要E2Eと既存回帰、`pnpm validate`・`pnpm build`を実施する。
主要E2Eは既存のCI環境で照合を必須とし、基点では最初の307のCookie欠落で失敗し、修正後は後続の要求前の照合と保護画面の利用が成功することを完了条件に含める。
ケースごとに実行した層・状態・形式・結果を記録し、未実行、環境不足、既存の失敗を成功へ含めない。
テスト設計の作成時点では、テスト実装・実行、変更前の基準の採取、ビルド・ブラウザ操作は行わない。
カバレッジ率を目標にせず、転送と非転送、更新と削除と書き換えなし、複数回の蓄積、失敗前の書き換えの保持に未確認の経路がないかを見る。
`session.ts`のコメント・本設計・テストの期待が`respond`と要求のCookie更新に一致することも差分レビューで確認する。
専用環境・一時複製・観測用の変更は確認後に片付け、恒久的に必要な検証結果と未確認範囲はPRへ残す。
本番・Vercel・CDNでの応答の確認は対象外であり、ローカルの結果をその保証に広げない。
