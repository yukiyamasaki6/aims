# rounds/start 設計

## 概要

`/rounds/new`は、個人プリセットと公式プリセットの一覧から選ぶか、選ばずに、ラウンドを作成して`/rounds/[id]`へ遷移する入口である。
ラウンド名・実施日・種別・弓種・距離構成の入力は持たず、作成後に`/rounds/[id]`で編集する。
プリセットなしで始めると、距離を持たない空のラウンドを作る。
作成はクライアントから`create_round` RPCを直接呼ぶ。

## 画面と状態

| 状態 | 表示 | 判定 | 要求 |
| :--- | :--- | :--- | :--- |
| 一覧 | 個人プリセットと公式プリセットを分けて並べる。公式にはメニューボタンを出さない | 常時 | start-01 |
| 個人プリセットなし | 個人プリセット欄にプレースホルダー | 個人が0件 | - |
| 未選択 | 開始ボタンに「プリセット無しで開始」 | `selectedId`が`null` | start-08 |
| 選択中 | 選択カードに距離構成を展開し、開始ボタンにプリセット名を出す | `selectedId`が一覧のIDに一致 | start-05, 09 |
| 未選択へ戻る | 選択中のカードか展開領域をクリックすると未選択に戻る | 同上 | - |
| 作成中 | 開始ボタンにスピナーを出し`aria-disabled`にする。成功後も遷移完了まで解除しない | `submitting`が`true` | start-10, 11 |
| 作成失敗 | 開始ボタンの上にエラーを出し、再び押せる | `error`が設定されている | start-13, 14 |

- 「一覧へ戻る」は通常のリンクである（start-04）。
- 未認証のアクセスは`proxy.ts`が`/signin`へ送る。

## 構成とデータの流れ

- `page.tsx`（Server Component）: 個人（`owner_id`が自分）と公式（`owner_id`が`null`）のプリセットを取得して並べる。
- `round-preset-select-client.tsx`: 選択・作成中・エラーの状態を持ち、開始後に`router.push`で遷移する。
- `start-round.ts`: セッション確認、選択中プリセットの取得、距離の並べ替えと新ID付与、`create_round`の呼び出しを行う。

- 並びは、種別、弓種、距離の本数（多い方が先）、先頭の距離（大きい方が先）、作成日時（新しい方が先）の順である。
- 開始時にプリセットを取得し直すため、一覧表示後に削除されていれば失敗する。
- ラウンドと距離のIDはクライアントで生成して渡す。
- `create_round`は、`round_users`・`rounds`・`distances`を1トランザクションで作る。`rounds`の直接INSERTはRLSで拒否する。
- 画面がアンマウントされた後の結果は破棄する。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| 入口を選択だけにし、入力は`/rounds/[id]`の編集に一本化する | 入力の重複を持たないため | 作成時に入力が必要な要求が出たとき |
| 作成は`create_round`に一本化する | `INSERT ... RETURNING`は、同一文内のトリガー副作用をSELECTポリシーが参照できず失敗するため。詳細: #99 | RLSの評価方式が変わったとき |
| Server Actionを使わずクライアントから直接呼ぶ | 認可の実体はRLSで変わらず、`redirect()`がアンマウント後に遷移を横取りする競合を避け、オフライン対応の土台にもなるため。Server Actionのため競合が起きたのでやめた | オフライン作成の方式が決まったとき |
| 成功後も開始ボタンを無効のままにする | `router.push`は遷移先取得中も本コンポーネントを保持し、解除すると遷移前に再び押せるため | 遷移方式を変えたとき |
| 二重送信を同期的なref（`submittingRef`）で判定する | stateは再描画まで更新されず、連打で2回目が通るため | stateの更新が同期的になる方式に変えたとき |
| 並びを名前でなく構成で決める | 名前は自由入力で内容を反映せず、自然順ソートは漢字の読みで曖昧になるため | プリセットの種類が増えたとき |
| クライアントの認証確認は`getSession()`で行う | `getUser()`はサーバー再検証を伴い、認可の実体はRPCにあるため | クライアント確認を認可に使うとき |
