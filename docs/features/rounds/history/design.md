# rounds/history 設計

## 概要

ラウンドの画面を、ホーム(`/rounds`)と履歴(`/rounds/history`)に分ける。見出しは置かない。
ホームは、端末の記録の入力中のラウンドだけを表示する。履歴の取得も同期の完了も待たず、取得を起こさない。
入力中のラウンドは、端末が知る状態(取得したベースに未送信の操作を重ねた状態)から、詳細と同じ導出と表示の規則(`isRoundInProgress`)で決める。保持の規則(`rounds/sync`)は使わない。
履歴は、履歴の項目から開いたとき(戻る操作で戻ったときを除く)にサーバーで完了と記録されたラウンドだけを、画面の高さに応じた件数(10〜50件)のページごとに取得して表示する(ページ送り)。続きは、一覧の末尾が画面に近づくと自動で取得する(無限スクロール)。取得結果から、端末の入力中のIDと削除済みを除く。端末の完了は履歴に出さず、取得が成功していないときはラウンドを出さない。
各カードに名前・実施日・合計点を出し、カードから`/rounds/[id]`へ、ホームの右下の新規作成ボタンから`/rounds/new`へ遷移する。
ホームと履歴は読み取り中心の画面で、書き込みはカードのメニューからの削除だけである。削除は`rounds/delete`が扱う。
取得はクライアントで行い、枠は静的である。
履歴の上端に、一覧の単位(ラウンド単位・距離単位)の切替と、並べ替えと絞り込み(種別・弓種・期間・得点の範囲・距離の構成・距離単位の距離の行)を置く。距離単位は、完了したラウンドの無効でない距離を1件ずつ、その小計で出す。単位も条件の1つで、ラウンド単位は`rounds_list`、距離単位は`distances_list`が取得し、対象のラウンドは2つが共通の関数(`history_rounds`)から読む。条件の適用とページの切り出しは、サーバーの履歴の関数が履歴全体に対して行い、条件を変えると先頭のページから取得し直す。不正な指定は、画面が反映の前に検出して欄にエラーを出し、条件に反映せず、取得しないため、一覧は直前の表示のままである。条件と絞り込みの開閉はタブごとに保ち、別の利用者には引き継がない。
履歴を離れるとき、表示済みの内容とスクロールの位置をタブのメモリに記憶する。履歴の表示は自分のURLに戻りの印を付け、印のあるURLで開いたとき(詳細の戻る、ブラウザの戻る・進む)は記憶を使い、印の無い`/rounds/history`へ進んだとき(履歴の項目など)は最新を取得する。

## 画面と状態

ホーム:

| 状態 | 表示 |
| :--- | :--- |
| 端末の入力中を読み込む前 | 何も出さない(空の表示も出さない) |
| 入力中が0件 | 「入力中のラウンドはありません」だけ |
| 入力中が1件以上 | 実施日の新しい順のカード(折りたたみ、見出し、線、件数バッジなし) |

- 新規作成ボタンは、ホームの全状態で表示する。ホームだけにあり、履歴・詳細・作成にはない。
- 同期の取得の状態(取得中・失敗・オフライン)で表示を変えない。同期の反映が端末の記録を変えると、購読で表示が更新される。
- 入力中のカードも、既存のメニューと確認で削除でき、その場で消える。

履歴(取得の状態は履歴の中にだけ出す):

| 状態 | 表示 |
| :--- | :--- |
| 取得中(先頭のページ。端末の入力中と保存した条件の読み込み前を含む) | スケルトン |
| 取得の成功・続きあり | 取得したページを連結し除外したラウンドのカード(0件もありうる)。末尾は続きの取得を待つ |
| 取得の成功・続きなし | 表示1件以上: カードと、末尾に「該当するラウンドは以上です」(`historyEnd`)。表示0件: 「該当するラウンドがありません」(`historyEmpty`)だけで、`historyEnd`は出さない |
| 続きの取得中 | 表示済みのカードの下に、取得中の表示(`LoadingState`とスケルトン) |
| 続きのオフライン・エラー | 表示済みのカードの下に、先頭のページと同じ文言(`fetchOffline`、`fetchFailure`)と再試行ボタン |
| オフライン(`navigator.onLine`が`false`) | 「ネットワークに接続されていません」と再試行ボタン(`app/offline-pwa`) |
| エラー | エラーメッセージと再試行ボタン。通信失敗は「読み込めませんでした。」。未認証は「サインインが必要です。」 |

- 履歴の上端に、開閉の取っ手(「並べ替え・絞り込み」)と、その欄を置く。取っ手は取得の状態にかかわらず出し、保存した条件を読み終えるまでは出さず、取得中として扱う(端末の入力中の読み込みと同じ)。
- 欄には、先頭に単位の切替(「ラウンド」「距離」の単一選択。並べ替えの基準と同じ形のボタン)、次に並べ替え(基準「日付」「得点」と向き「昇順」「降順」)、絞り込み、「条件をリセット」を置く。リセットは押すと単位と並べ替えと絞り込み(期間・得点の範囲・距離の構成・距離の行の入力を含む)を既定に戻す(開閉は変えない)。
- 単位を切り替えると、他の条件の変更と同じく表示済みを捨てて先頭から取得し直す。並べ替え・期間・種別・弓種・得点の範囲・距離の構成の値は、単位を切り替えても保つ。距離単位では、基準「得点」と得点の範囲が距離の小計を対象にする(「条件の定義」)。
- 距離単位のカードは、ラウンドのカードと同じ枠と高さで、1行目にラウンドの名前、2行目に実施日と距離の表示、右に小計(`distanceSubtotal`の「小計{total}」)を出す。距離の表示は、ラウンドの中の射つ順の番号と距離で、距離が判明していれば`{distance}m`、無印(`is_marked`が偽)は「Unmarked」を前に置き、距離が無ければ「Unmarked」だけにする(番号の文言は実装で決める)。カードを押すと、ラウンドのカードと同じく`?from=history`付きでそのラウンドの詳細へ移る。メニュー(削除)は置かない。スケルトン(`RoundCardsSkeleton`)は単位によらず同じものを使う。
- 戻ったときの表示、端末での除外、末尾と0件の文言(`historyEnd`、`historyEmpty`)、続きの取得の扱いは、距離単位でもラウンド単位と同じである。除外はラウンドのIDで行い、除くラウンドの距離は全て出さない。
- 閉じている間は欄を描かず、選んだ並べ替えと絞り込みの値もリセットも示さない。条件は適用され続け、表示するラウンドは変わらない。
- 絞り込みは、種別と弓種のそれぞれが「すべて」と各値の単一選択で、「すべて」が絞り込みなしである。選択肢の表示名は画面の既存の表記(`formatOption`、`bowTypeOption`)を使う。
- 絞り込みの期間は開始日と終了日の2つの日付の入力(`type="date"`)、得点の範囲は下限と上限の2つの数字の入力で、どれも空が指定なしである。得点の入力は`type="number"`にしない。`-`や`e`などの途中の入力はブラウザが空として返し、指定なしと区別できず、不正であることを示せないため、文字列として受けて検証する(数字キーボードは`inputMode="numeric"`で出す)。
- 期間と得点の4つの入力は、入力途中の文字(下書き)を、欄の部品が4つまとめて持つ。欄を離れたとき(blur)かEnterを押したときに、4つの下書きをまとめて検証し、正しければ条件へ反映して取得し直す。入力途中は検証も反映もしない。反映する値が条件の現在の値と同じなら、何もしない(スケルトンにしない)。他の入力の下書きも同時に検証するため、開始日を先に直して終了日を後で直す、のような順の入力でも、組が正しくなった時点で反映される。欄を閉じる操作とリセットの操作では、入力が先に欄を離れる(blur)ため、正しい下書きは先に反映される。その後に残る下書きとエラー(不正だったもの)は捨てる(リセットは条件も既定に戻す)。入力の要素は取得の状態によらず同じ要素で描き続け、取得中もフォーカスと入力途中の文字を失わない。
- 検証に通らないときは、条件に反映せず、取得もしない。一覧は、直前に反映した条件の結果をそのまま表示し続け、スケルトンにもしない。欄にエラー(原因ごとの文言)を、該当の入力の近くに出し、入力した文字は直るまで残す。原因は、日付の不正、開始日が終了日より後、点数の不正、下限が上限より大きいの4つである。正しい値に直して欄を離れる(またはEnter)と、エラーが消え、反映して取得し直す。エラーは欄が開いている間だけ存在し、欄を閉じるとエラーと不正な入力は消え、欄を開き直すと反映済みの条件の値が出る。欄の開閉は一覧の表示を変えない。
- 絞り込みの距離の構成は、得点の範囲の下に置く行の並びである。各行は、距離、1エンドの矢数、矢の総数の3つの入力(得点と同じく文字列で受け、`inputMode="numeric"`)と、的、行の削除の操作を持つ。距離は必須で、1エンドの矢数と矢の総数は空が指定なし(外した状態)である。行の下に「距離を追加」があり、押すと末尾に空の行を足す。行の並べ替えの操作はない。
- 的は、未指定の行では「的を加える」の取っ手を出し、押すと的の選択の一覧(`TargetFacePicker`と同じ一覧と種別・弓種のタブ)を開く。選ぶと、その行の的になる。指定済みの行は選んだ的(`TargetFaceInfo`。押すと選び直せる)と「的を外す」を出す。タブの既定は、条件の種別・弓種(指定なしなら「すべて」)である。
- 的の一覧は、端末に保存した的の一覧(`savedTargetFaces`。同期の一括の取得が保存する)を、欄の部品が表示の開始後に読んで使う。履歴のために的を取得しない。保存した一覧が無いときは空の一覧として扱い、的を選べない。指定済みの的が一覧に無いとき(的の削除後、一覧が無いとき)は、既存の的が見つからない表示(`TargetFaceInfo`の`missing`)を出し、条件はそのまま適用し続ける。「的を外す」で外せる。
- 距離の構成の入力は、行ごとの入力途中の文字と的(下書き)を、距離の構成の欄の部品がまとめて持つ。数値の入力を離れたとき(blur)かEnterを押したとき、行を削除したとき、的を選んだとき・外したときに、全ての行の下書きをまとめて検証し、正しければ条件へ反映して取得し直す。行を足したときは反映しない(空の行は不正なため)。反映する値が条件の現在の値と同じなら何もしない。検証に通らないとき、閉じたとき、リセットのときの扱いは、期間と得点の範囲と同じである。エラーは行ごとに、その行の下に出す。原因は、距離の不正(空、整数でない、1〜100の外)、1エンドの矢数の不正(整数でない、1〜12の外)、矢の総数の不正(1以上の安全な整数でない)の3つである。
- 距離単位の距離の行は、単位が距離のときだけ、絞り込みの中で距離の構成の上に、見出し「絞り込む距離」で出す(距離の構成の見出しと分ける)。部品は距離の構成の欄の部品を、行の数の上限を1にして使う。行が無いときだけ「距離を追加」を出し、行を削除すると指定なしになる。入力・的・下書き・検証(`historyDistancesOf`)・反映の契機・エラーの扱いは、距離の構成と同じである。単位がラウンドの間は、指定した行を条件に残すが、出さず、取得にも渡さない。
- 初めて開いたときの絞り込みは開いている。
- 先頭のページの取得は、表示の開始時(保存した条件を読んだ後。戻ったときの表示の記憶を使うときは行わない)と条件の変更・リセットのたびに行い、表示済みのページを捨ててスケルトンにする。再試行ボタンを押すとスケルトンになる。
- 続きの取得は、続きがあり、続きの取得が中でも失敗(オフライン・エラー)でもないときに、一覧の末尾(続きの取得の状態を出す場所)がスクロールの入れ物の下端から1画面分(入れ物の高さ)の距離に入ると、自動で1ページ行う(`IntersectionObserver`。`root`はスクロールの入れ物、`rootMargin`は下へ入れ物の高さ分)。`root`を既定(ビューポート)にすると、先祖の`overflow`の切り取りで末尾が入れ物の中に見えるまで交差せず、先読みが効かないため、入れ物を`root`にする。同時に2つ以上の取得はしない。
- 続きの取得が成功した後も一覧の末尾がその距離にあれば、次のページを続けて取得する。除外で表示0件のページが続いても、利用者の操作なしに続きへ進む。連なる取得は、末尾が画面から離れるか、続きがなくなると止まる。
- 続きの取得が失敗すると自動の取得を止め、スクロールや末尾の出入りでは取り直さない。取り直すのは再試行ボタン(同じ起点。表示済みを残す)だけで、通信が戻っても自動では取り直さない。成功すると自動の取得に戻る。
- 条件の変更、再試行、離れたことで古くなった取得の結果は捨てる(捨てないと、前の条件のページが新しい条件の表示に連結されるため)。
- 続きがないときは取得しない。表示が1件以上なら末尾に`historyEnd`を出す。
- 取得が成功していても、端末の入力中を読み終えるまでは取得中として扱う。
- 取得結果から除くのは、端末の入力中のID、各ページの取得時に端末の記録から求めた削除済みIDの和、この画面で削除したラウンドのIDである。除外は取得した全ページに表示のたびに行い、条件によらない。除外で1ページの表示件数が減ってもよい。他の端末で完了して端末に未取り込みのラウンドは、端末の入力中に残るため、同期が反映するまで履歴に出ない(ホームと二重にしないため)。
- 履歴のカードのメニューと削除の確認は、ホームと同じである。
- 未認証のアクセスは`proxy.ts`が`/signin`へ送る。この挙動は一覧の要求に含めない。

## 構成とデータの流れ

パスは、断りがなければ`apps/web/src/`からの相対である。

### 条件の定義

何で並べ、何で絞るか。取得の形(どこで絞るか)から独立した、純粋な規則である。

- 条件(`HistoryCondition`)は、並べ替え(基準`date`か`score`、向き`asc`か`desc`)、種別(`FormatOption`か指定なし)、弓種(`BowTypeOption`か指定なし)、期間(開始日`dateFrom`、終了日`dateTo`)、得点の範囲(下限`scoreMin`、上限`scoreMax`)、距離の構成(`distances`)、単位(`unit`: `round`か`distance`)、距離の行(`distanceRow`: `HistoryDistanceRow`か`null`)の組である。基準は1つだけで、種別・弓種はそれぞれ1つだけ選べる。複数選択と複合ソートは持たない。
- 期間と得点の範囲は、反映済みの値だけを持つ(常に正しい)。期間の開始日`dateFrom`と終了日`dateTo`は`YYYY-MM-DD`か`null`、得点の下限`scoreMin`と上限`scoreMax`は`0`以上の安全な整数(`Number.isSafeInteger`)か`null`で、`null`が指定なしである。不正な入力は条件に入らない。
- 欄の下書き(`HistoryRangeDraft`: 4つの入力途中の文字列)の検証`historyRangeOf(draft)`が、正しければ4つの値(上の型)、不正なら原因の一覧を返す。原因は、日付の不正(`YYYY-MM-DD`の実在する日付でない)、開始日が終了日より後、点数の不正(前後の空白を除いてASCIIの`0`〜`9`だけでない、または安全な整数を超える。全角数字、符号(`+`、`-`)、小数点、指数は不正で、先頭の`0`は許し`007`は7である)、下限が上限より大きい、の4つである。空(空白だけを含む)は指定なしで、両端の大小は、両方が指定されていて、その値が正しいときだけ比べる。同じ値(開始日と終了日が同じ日、下限と上限が同じ点)は正しい。
- 距離の構成(`distances`)は、射つ順の行(`HistoryDistanceRow`)の配列で、空の配列が指定なしである。行は、距離`distance`(1〜100の整数)、1エンドの矢数`arrowsPerEnd`(1〜12の整数か`null`)、矢の総数`totalArrows`(1以上の安全な整数か`null`)、的`targetFaceId`(的のIDか`null`)を持ち、`null`が指定なしである。値の上限は`DISTANCE_LIMITS`の値を使う。行の数に上限はない。反映済みの値だけを持ち、不正な入力は条件に入らない。
- 距離の構成の下書き(`HistoryDistanceDraft`: 行ごとの3つの入力途中の文字列と的のIDか`null`の配列)の検証`historyDistancesOf(draft)`が、正しければ行の配列、不正なら行の位置と原因の組の一覧を返す。数値の読み方(前後の空白を除き、ASCIIの`0`〜`9`だけ、安全な整数)は得点と同じで、その上で範囲を比べる。距離の空は不正、1エンドの矢数と矢の総数の空は指定なしである。
- 距離の行(`distanceRow`)は、距離の構成の行と同じ型・値の範囲・下書きの検証(行が0か1つの`historyDistancesOf`)を使い、`null`が指定なしである。単位が`distance`のときだけ適用する。
- 既定は、ラウンド単位・日付の降順・種別と弓種と期間と得点の範囲と距離の構成と距離の行の指定なしである。表示の状態(`HistoryViewState`)は、条件と絞り込みの開閉の組で、開閉の既定は開である。
- 絞り込みは、指定がある属性だけを比べ、全ての指定に一致するラウンドを残す。期間は実施日が開始日以上・終了日以下、得点の範囲は合計点が下限以上・上限以下である(境界を含む)。距離の構成は、ラウンドの無効でない距離の行を(`position_key`, `id`)の順に並べたものが、指定の行と同じ個数で、先頭から順に各行が一致することである。行の一致は、距離が判明していて(`is_marked`)距離が等しく、指定のある項目(1エンドの矢数、矢の総数(`total_ends`×`arrows_per_end`)、的)も等しいことである。
- 並べ替えの基準は、`date`が実施日、`score`が履歴のカードに出す合計点である。基準が同じラウンドは、実施日の新しい順、それも同じなら作成時刻の新しい順、それも同じならIDの昇順に並べる。同値の並びは基準の向きによらず、再読み込みしても変わらない。
- 距離単位の件は、完了したラウンドの無効でない距離である。無効な距離、無効な矢は出さず数えない。距離なしの距離と矢の無い距離も出し、小計は0である。小計は、詳細の距離結果の小計と同じく、その距離の無効でない矢の`score_int`の和である。
- 距離単位では、`score`と得点の範囲は距離の小計を、`date`・期間・種別・弓種・距離の構成は距離が属するラウンドを対象にする。距離の行は、その距離が「行の一致」を満たすことで、距離なしの距離は一致しない。基準が同じ距離は、属するラウンドについてラウンド単位と同じ順(実施日の新しい順、作成時刻の新しい順、IDの昇順)に並べ、同じラウンドの中は射つ順(`position_key`, `id`)に並べる。
- 絞り込みと並びの規則の持ち主は、サーバーの履歴の関数(`rounds_list`、`distances_list`)と、2つが読むラウンドの条件の関数(`history_rounds`)だけである。端末は条件を渡し、並べ直さない。
- 保存した値の検証(`historyViewStateOf`)は、未知の値や形の崩れを既定に直す。日付は実在する`YYYY-MM-DD`でなければ`null`に、得点は`0`以上の安全な整数でなければ`null`にする。開始日が終了日より後、下限が上限より大きいときは、その組の両方を`null`にする。直す単位は項目で、範囲だけが壊れても、並べ替え・種別・弓種・開閉は残す(既存の、未知の値をその項目だけ既定に直す扱いと同じ)。保存した値に期間と得点の範囲の項目が無いときは、`null`(指定なし)にする。距離の構成は1つの項目として直し、配列でない、どれかの行が上の型に合わない(的のIDがUUIDの形でないことを含む)、または項目が無いときは、空の配列(指定なし)にする。単位は`round`と`distance`以外か無いときは`round`に、距離の行は距離の構成の行と同じ検査に合わないか無いときは`null`にする。このため、不正な条件が条件・記憶・取得の組に入ることはない。

### 取得の形

どこで絞り、どこで並べ、どこで切り出すか。

- 履歴の取得は、条件と続きの起点と件数を渡して、1ページずつ行う。先頭のページは起点なしで取得する。
- 1ページの件数は、取得のたびに、画面の高さで2画面分を埋める件数(画面の高さ ÷ 1件分の高さ × 2 の切り上げ)を、10〜50件(`HISTORY_PAGE_SIZE_MIN`、`HISTORY_PAGE_SIZE_MAX`)に収めて決める(`historyPageSizeOf`)。2画面分は、続きの取得を始める距離(1画面分)を1回の取得で越えるためである。1件分の高さが測れない(0以下)ときは下限にする。
- 1件分の高さは、コードに値を持たず、その取得のために描いた取得中の表示のスケルトン(`RoundCardsSkeleton`)の1件の高さと列の間隔を、取得の直前に画面から測る(`rounds-history.tsx`が測る関数を渡す)。先頭のページも続きも取得中はスケルトンを描くため、カードが描かれる前でも測れる。スケルトンは読み込み後のカードと同じ形にする(既存の規則)。名前の折り返しでカードが高くなると件数は多めになるが、画面は埋まる。
- 件数がページごとに違っても、起点はIDで決まるため、境界で重複・抜けは出ない。
- 返すのは、各ラウンドの名前・実施日・合計点・IDと、続きの有無だけである。種別・弓種・作成時刻、距離・矢、総件数は返さない。
- 距離単位で返すのは、各距離のID、属するラウンドのID・名前・実施日、射つ順の番号、距離、無印か(`is_marked`)、小計と、続きの有無だけである。1エンドの矢数・エンド数・的、矢、総件数は返さない。
- 続きの起点は、直前のページでサーバーが返した最後のラウンドのID(除外の前の行)である。距離単位では最後の距離のIDで、サーバーはその距離の行と属するラウンドから並びの値を引く。サーバーはそのIDの行から実施日・作成時刻・合計点を引き、それより後のラウンドを返す(キーセット)。論理削除しても行は残るため、起点のラウンドが他の端末で削除・完了の取り消しをされても引ける。
- 結果: 他の端末での完了・削除で境界の前後の行が増減しても、重複・抜けは出ない。読み進める間に、他の端末で続きの起点のラウンドの実施日か合計点が変わったときだけ、次のページで行が抜けるか重なる。重なりは連結で除くため表示されず、抜けは要件の例外として許容する(履歴を開き直すと正しく並ぶ)。
- 端末は、受けたページをIDで重複を除いて連結する(`appendRoundsList`)。他の端末での変更で境界がずれても、同じラウンドを2回出さない。距離単位の項目のIDは距離のIDで、項目は属するラウンドのIDも持つ。重複の除去と起点は項目のID、端末の除外は属するラウンドのIDで行う。単位を変えると表示済みを捨てるため、1つの一覧に2つの単位の項目は混ざらない。
- 端末だけが持つ除外は、サーバーへ渡さず、連結した全ページに表示のたびに行う(「画面と状態」)。
- 条件の変更は履歴の取得を起こすが、同期(一括の取得)は起こさず、ホームに影響しない。
- 履歴の表示の決定(`historyView`)は、連結したページから除外したラウンドと、続きの有無を返す。ラウンドの削除は除外の集合へ足すため、表示からも消える。

#### 履歴の関数(`rounds_list`)

- `SECURITY INVOKER`の読み取り専用(`STABLE`)の関数で、呼び出し元の権限で`rounds`等を読む。取得できるラウンドは、RLSの`select_if_member`により、ユーザーが`round_users`で属するものに限る。実行権限は`authenticated`だけに与える。
- 対象のラウンドは、呼び出し元の所属(`round_users`の`user_id = auth.uid()`の行)から`rounds`を引いて求める(「索引とRLSと条件の評価の順」)。所属から引く形とラウンドの条件は、ラウンドの条件の関数(`history_rounds`)が持ち、`rounds_list`はその結果を読む。これは読む範囲を利用者のラウンドに狭めるためで、認可ではない。認可はRLSのままで、結んだ`round_users`と`rounds`もRLSを通して読む。RLSで見えるラウンドは所属のあるラウンドと同じ集合のため、結果は変わらない。続きの起点の行は、所属から引かず、IDから引く(変えない)。
- 引数は、並べ替えの基準と向き、種別、弓種(どちらも`null`は指定なし)、続きの起点のID(先頭は`null`)、件数、期間の開始日`p_date_from`と終了日`p_date_to`(`date`)、得点の範囲の下限`p_score_min`と上限`p_score_max`(`bigint`)、距離の構成`p_distances`(`jsonb`)である。期間・得点の範囲・距離の構成は末尾に置き、既定値を`null`(指定なし)にする。追加の絞り込みは、引数を足して表す。
- `p_distances`は、射つ順の行の配列`[{ distance, arrows_per_end, total_arrows, target_face_id }]`で、指定のない項目は`null`(鍵が無くても`null`として扱う)である。
- 期間は`rounds.round_date`が開始日以上・終了日以下、得点の範囲は合計点が下限以上・上限以下のラウンドに絞る(境界を含む)。合計点は並べ替え・返す値と同じ1つの値を使う。続きの起点の行は、条件に関わらずIDから引く。
- 距離の構成は、対象の各ラウンドについて、無効でない(`disabled_at is null`)距離に(`position_key`, `id`)の順で番号を振り、`p_distances`の要素の番号(`with ordinality`)と結んだ副問い合わせで判定する。距離の行の数が`p_distances`の要素の数と等しく、全ての行が「条件の定義」の行の一致を満たすラウンドだけを残す。距離が0件のラウンド、行の比較が`null`になる場合(距離なしの行など)は一致しない。この判定は、種別・弓種・期間・完了の判定と所属から引く形とともに、ラウンドの条件の関数(下記)が持つ。列・ビューは持たない。
- 結果(性能): 判定はラウンドごとに、そのラウンドの距離の行を読み、`p_distances`を展開して番号で結ぶ。`p_distances`の展開はラウンドごとに行うため、処理量は理屈の上では対象のラウンドの数×指定の行の数に比例して増える。行の数に上限はない。
  - 計測(事実。ローカルのPostgreSQL 16、RLSなし、合成データ: 完了したラウンド2000件、各4行の距離、各36本の矢、`distances(round_id)`の索引なし): 判定だけの問い合わせは、指定の行が4・100・1000・10000行のどれでも約1.3秒で、行の数による差は測れなかった。判定の費用の大半は、ラウンドごとの`distances`の全件の走査(索引が無いため)だった。この走査は`distances(round_id)`の索引で除いた(「索引とRLSと条件の評価の順」)。
  - 本番の件数・RLSを含めた時間は確かめていない。指定の行の数で重くなる傾向は、上の範囲では見られない。`p_distances`を1度だけ展開する形は、遅さが問題になったときに検討する(今は持たない)。
  - `rpc`の引数は要求の本文(POST)に載るため、行の数はURLの長さの制限を受けない。
- 対象は`disabled_at is null`かつ`status = 'completed'`のラウンドで、条件で絞り、「条件の定義」の並びにする。件数+1件を読み、件数を超えれば続きありとして件数分だけ返す。
- 合計点の規則: ラウンドの無効でない(`disabled_at is null`)距離の、無効でない矢の`score_int`の総和で、矢が無ければ0である。ホームの入力中のラウンドの合計点(端末で求める)と同じ規則である。並べ替え・起点の比較・返す値は、この1つの値を使う。
- 合計点は、`rounds_list`の中で、対象の各ラウンドについて`distances`と`shots`を結んだ副問い合わせ(`coalesce(sum(...), 0)`)で求める。列・ビュー・別の関数は持たない。呼び出し元の権限で動くため、`distances`と`shots`もRLS(`select_if_member`)を通して読む。所属するラウンドの距離・矢は全て読めるため、合計点は欠けない。
- 結果(性能): 並べ替えの基準によらず、条件に一致する全ラウンドの合計点を、ページの取得のたびに求める。DBの処理量は、その利用者の完了したラウンドの矢の総数に比例し、他の利用者のデータの量には比例しない(「索引とRLSと条件の評価の順」)。矢はRLSを通して読むため、矢の1行ごとに`shots`の`select_if_member`(見える距離があるか。距離は見えるラウンドがあるかで、`is_round_member`を1回呼ぶ)の費用がかかり、これが取得の時間の大半を占める。変更前の取得は、開くたびに全ラウンドの全ての矢の行をDBから読み、端末へ転送していた。変更後は、DBで読む行は同じ程度で、転送は1ページ分になる。このため、変更前より悪くならないとして許容する。続きのページでも同じ量を読む点は、読む範囲が利用者1人が属するラウンドに限られるため許容する。日付順でだけ返す行に絞ってから求める工夫や、集計列は持たない(遅さが問題になったときに足す)。

  - PostgRESTの集約関数と`db_aggregates_enabled`の有効化: 使わない(並べ替えに使えず、集計は`rounds_list`の中のSQLで行うため)。`supabase/config.toml`も変えない。

- 引数を検証しない。結果: 未知の基準・向きは既定(日付の降順)の並びになり、件数は呼び出し元が決めた値のまま返す。開始日が終了日より後、下限が上限より大きい指定は、該当なしの0件を返す。`p_distances`の空の配列は0件を返し、UUIDでない的のIDや整数でない値はDBが型のエラーにするが、画面は1行以上の検証済みの行しか渡さない。返るのは呼び出し元が属するラウンドだけで、画面は検証済みの条件と10〜50件しか渡さないため、許容する。点数の型が違う値(整数でない数)はDBが型のエラーにするが、画面は検証を通した整数しか渡さない。起点のIDの行が見えないときは、続きなしの0件を返す(所属を外す経路は現状ない)。

#### ラウンドの条件の関数(`history_rounds`)

- 呼び出し元の所属(`round_users`の`user_id = auth.uid()`の行)から引いた`rounds`のうち、ラウンドの条件(無効でない、`status = 'completed'`、種別、弓種、期間、距離の構成)に一致する行を返す関数で、5つの条件の引数(`p_format`、`p_bow_type`、`p_date_from`、`p_date_to`、`p_distances`)を受ける。`rounds_list`と`distances_list`が対象のラウンドとして読み、ラウンドの条件の規則と、所属から引く形の持ち主はこの関数だけである。得点の範囲は単位で対象が違うため、ここに含めない。
- `SECURITY INVOKER`、`STABLE`の`sql`の関数で、`setof rounds`を返す。読む表はRLSを通る。呼び出し元の権限で動く関数から読むため、`authenticated`に実行権限が要る(無いと`permission denied for function`になる)。結果: PostgRESTから直接呼べる関数が1つ増えるが、返すのは呼び出し元がRLSで読める`rounds`の行だけで、`rounds`を直接読むのと範囲は同じである。`PUBLIC`・`anon`からは取り消し、`rls_matrix.sql`の実行権限の期待値表、`rpc_matrix.sql`の例外、`docs/security.md`に載せる(`distances_list`も同じ)。
  - 変更範囲: `rls_matrix.sql`の期待値表(`rls_fn_expected`)に、`history_rounds`と`distances_list`の行を`authenticated`は`true`、`anon`は`false`で足し、期待値の方針の注記に「履歴の取得(`rounds_list`、`distances_list`)と、それが読むラウンドの条件の関数(`history_rounds`)」を加える。表に無い関数と`PUBLIC`のEXECUTEは、既存の網羅性の検証が落とす。
  - テストの観点: `history_rounds`を`authenticated`で直接呼ぶと、属するラウンドのうち条件に一致する行だけが返り、属さないラウンドは返らない(閲覧者として属するラウンドは返る)。返る行のIDの集合が、同じ条件で`rounds`を直接読んだ結果と一致する。`anon`は実行できない。
- `SET search_path`を付けない。付けると呼び出し元へ展開(インライン化)されず、関数の結果を別に作ってから読むため遅くなる(下の計測)。付けないと展開され、実行計画は`rounds_list`の中に条件を直接書いた形と同じになる。代わりに、本文の表と関数の名前を`public.`・`auth.`で修飾する。リポジトリの他の関数は全て`SET search_path`を付けており、この関数だけが例外である(「設計判断」)。
  - 例外の理由: 展開させ、取得の計画と時間を、条件を`rounds_list`に直接書いた形(#782)と同じに保つため。展開には`SET`句が無いことが要る。
  - 例外の範囲: `history_rounds`の1つだけである。`SECURITY INVOKER`の読み取り専用(`STABLE`)の関数で、呼び出し元の権限で動くため、`search_path`を変えられても権限は上がらない。本文の表・関数は全て`public.`・`auth.`で修飾し、修飾しない名前を持たない。`rounds_list`・`distances_list`を含む他の関数は`SET search_path`を付ける。
  - 変更範囲: 新しい`SECURITY DEFINER`の関数や書き込みの関数には、この例外を広げない。`SET search_path`を付けない関数を足すときは、展開が要ることを計画で確かめ、この節に加える。
  - テストの観点: `rounds_list`の結果が、関数に切り出す前と同じであること(既存の`rounds_list.sql`が変更なしで通ること、使い捨てのDBでの全ページの照合)。`history_rounds`の`proconfig`が空で、本文に修飾しない表名が無いことは、レビューで確かめる。
- 続きの起点の行は、どちらの取得の関数も条件と所属に関わらずIDから引くため、この関数を通さない。

#### 距離単位の履歴の関数(`distances_list`)

- `rounds_list`と同じく、`SECURITY INVOKER`の`STABLE`の関数で、実行権限は`authenticated`だけに与える。引数は`rounds_list`の11個と同じ並びに、距離の行`p_distance`(`jsonb`。`p_distances`の要素と同じ形の1つのオブジェクト。既定値`null`)を末尾に足したものである。
- ラウンドの条件の関数が返すラウンドの無効でない距離を件とし、`p_distance`の行の一致と、得点の範囲(小計が対象)で絞り、「条件の定義」の並びにする。射つ順の番号は、距離の構成と同じく無効でない距離に(`position_key`, `id`)の順で振る。小計は、各距離について`shots`を読む副問い合わせで求める(合計点と同じく、列・ビューを持たない)。起点は距離のIDで、距離の行と属するラウンドから、条件に関わらず引く。件数+1件の読み方、引数を検証しないことは`rounds_list`と同じである。
- 同値の並びのうち、ラウンドの鍵(実施日の新しい順、作成時刻の新しい順、IDの昇順)と並べる値の式(基準と向き)は、`rounds_list`と同じ式を持つ。距離単位は最後に(`position_key`, `id`)を足す。起点との比較は鍵の数が違うため、関数ごとに持つ。
- 戻り値は`{ distances: [{ id, round_id, name, round_date, number, distance, is_marked, total }], has_more }`である(`id`は距離のID、`total`は小計)。型は行の列を生成型(`distances`、`rounds`)から導き、番号と小計だけを足す。画面の名前への写しは1か所に置く。
- 画面は、単位が距離のときだけこの関数を呼び、`p_distance`は行があるときだけ送る。他の引数の送り方は`rounds_list`と同じである。
- 結果(性能): 距離単位も、ページの取得のたびに条件に一致するラウンドの全ての距離の小計を求めるため、DBの処理量は合計点と同じく、その利用者の完了したラウンドの矢の総数に比例し、他の利用者のデータの量には比例しない。矢1行ごとのRLSの判定が時間の大半を占める点も同じである(「索引とRLSと条件の評価の順」)。
- 互換: `rounds_list`は署名を変えず、ラウンドの条件の関数を読む形に`CREATE OR REPLACE`で置き換える。旧い版の端末の呼び出しはそのまま動く。

#### 索引とRLSと条件の評価の順

取得の時間を、他の利用者のデータの量に比例させず、矢のRLSの費用を減らすための形。結果と読める範囲は変えない。

- 索引は、`distances(round_id)`と`round_users(user_id)`のbtreeを持つ。
  - `distances(round_id)`: 合計点、小計、距離の構成の判定、距離単位の距離の列挙は、ラウンドIDで`distances`を引く。索引が無いと、ラウンドごとにDB全体の`distances`を走査し、費用が「利用者の件数×DB全体の距離の数」に比例する。PostgRESTの埋め込み(`rounds`から`distances`)も同じ索引を使える。
  - `round_users(user_id)`: 対象のラウンドを、呼び出し元の所属の行から引く(「履歴の関数」)。索引が無いと、所属を求めるために全利用者の`round_users`を読む。
  - 矢は既存の`shots_live_end_idx`(`distance_id`, `end_number`)で距離ごとに引く。
- 並べ替え(実施日、合計点、小計)のための索引は持たない。並びの値と同値の鍵は関数の中で求め、条件に一致する全ての件に番号を振ってから切り出すため、索引の順では読めない。合計点・小計は矢の集計で、列に無いため索引にできない。
- SELECTのポリシー(`select_if_member`)は、子の表を親が見えるかで書く。ラウンドが見えれば、その距離も矢も見える。
  - `rounds`: `is_round_member(id)`(変えない)。
  - `distances`: 見えるラウンドがあること。`exists (select 1 from rounds r where r.id = distances.round_id)`。
  - `shots`: 見える距離があること。`exists (select 1 from distances d where d.id = shots.distance_id)`。
  - 副問い合わせは呼び出し元の権限で動くため、親の表のRLSがそのまま掛かる。`is_round_member`を直接呼ぶのは`rounds`だけになる。参照は`shots`→`distances`→`rounds`の一方向で、`rounds`は`SECURITY DEFINER`の`is_round_member`だけを呼ぶため循環しない。
  - 読める範囲は変わらない。`distances.round_id`→`rounds`、`shots.distance_id`→`distances`の外部キーにより親の行は必ずあり、「親が見える」は「親のラウンドで`is_round_member`が真」と同じである。削除済み(`disabled_at`)の行の扱いもポリシーに無いため変わらない。
  - 変更前の`shots`のポリシー(`is_round_member((select d.round_id from distances d where d.id = shots.distance_id))`)は、副問い合わせに`distances`のRLSも掛かり、矢1行ごとに`is_round_member`を2回呼んでいた。この形では1回になる。
  - `shot_events`・`distance_events`・`round_events`・`round_users`のポリシーは変えない(アプリはこれらを読まず、履歴の取得も読まないため)。このため、表によってポリシーの書き方が2通りある。
  - 書き込みは`SECURITY DEFINER`のRPCが表の所有者として行い、RLSを通らないため影響しない。`authenticated`の表の権限はSELECTだけで変えない。
- 互換: `rounds_list`の署名は変えず、`CREATE OR REPLACE`で本文だけを置き換える(所有者と実行権限は保たれる)。生成型、`rpc_matrix.sql`・`rls_matrix.sql`の署名、画面は変えない。
- migration: 索引2つ、ポリシー2つ、`rounds_list`の本文を、1つの追加のmigration(`begin`〜`commit`、既存と同じ`lock_timeout 1s`・`statement_timeout 5s`)で行う。定義済みのmigrationは編集しない。
  - ポリシーは`ALTER POLICY "select_if_member" ON ... USING (...)`で式だけを置き換える。名前・対象のロール・操作は保たれ、1つの文で変わる。`DROP POLICY`と`CREATE POLICY`にする場合も、同じトランザクションの中なら他の接続から途中の状態(ポリシーが無く何も見えない状態)は見えない。
  - 錠: 索引の作成はその表への書き込みを、ポリシーの変更はその表の読み書きを、コミットまで止める。`lock_timeout`で他の取得・書き込みと重なるとmigrationが失敗しうるが、全体が巻き戻るため再実行で済む。
  - 戻すときは、逆の内容(ポリシーの式を変更前に戻し、索引を消し、本文を戻す)の追加のmigrationで行う。
  - 索引の2文には、それぞれ直前の行に`-- squawk-ignore require-concurrent-index-creation`を書き、その上に理由のコメントを書く(前例: `20261111000000_distance_practical_limits.sql`)。理由: `create index concurrently`はトランザクションの中で使えず、索引・ポリシー・関数を1つのトランザクションで原子的に適用するため。書き込みの停止は`lock_timeout`で上限を付け、作成時間は合成データ(距離約9万行)で数十ミリ秒だった。`pnpm lint:sql`(squawk)は、この2文を無視の指定なしでは`require-concurrent-index-creation`で失敗し、指定すると通る(同じ形の下書きで確かめた。`ALTER POLICY`と`CREATE OR REPLACE FUNCTION`は検出されない)。
- 条件の評価の順(事実。PostgreSQL 16の実行計画):
  - 1つの表を読むときの`where`の条件は、書いた順でなく、プランナーが見積もった1行あたりの費用の安い順に並べ替えて評価される。絞り込む量(選択率)は順の決定に使われない。費用が同じ条件は書いた順のまま並んだ。RLSの条件は、leakproofでない条件より先に評価される(比較の演算子のようなleakproofの条件は前に出られる)。PostgreSQLの文書は、式の評価の順を保証しない。
  - 結ぶ表や集計に依る条件は、計画の形で順が決まる。距離の構成の判定はラウンドを読むときの副問い合わせで、得点の範囲は合計点の集計の後にしか評価できない。
  - この形での順: 所属(`round_users`を`user_id`の索引で引く)→ 無効 → 種別 → 弓種 → 期間 → 完了 → RLSの`is_round_member` → 距離の構成 → 合計点の集計 → 得点の範囲。
  - 所属は、行ごとの判定(`is_round_member`)を先に評価させても速くならなかった(判定の費用を下げて先に評価させた計測で、変わらないか遅い)。速くなるのは、所属から引く形(読む行そのものを利用者のラウンドに限る)だった。種別と弓種と期間の比較は1行あたりの費用が小さく、順による差は時間に現れない(推論。順を入れ替えた計測はしていない)。
  - ラウンドの条件の関数(`history_rounds`)は展開されるため、`rounds_list`の計画はこの関数を使う前と同じだった(所属は`round_users_user_id_idx`の`Index Scan`、ラウンドは`rounds_pkey`の`Index Scan`で、`Filter`の条件と順も同じ)。`distances_list`の対象のラウンドも同じ順で絞る。
  - `SET search_path`を付けた関数は展開されず、計画は`Function Scan`になった。`rounds`の行を引数に取る述語の関数(`where`で呼ぶ形)も展開されず、`Filter: (is_round_member(id) AND 述語の関数(r.*, ...))`のように、RLSの判定の後に1つの条件として行ごとに呼ばれた(関数がleakproofでないため、安い比較もRLSの前に出られない)。
  - 段を分けて書く形(事実。同じ環境の実行計画と計測): 入れ子の副問い合わせと通常のビュー(`security_invoker`)は、プランナーが1つの問い合わせに展開し、条件は1つの表の`where`に戻った(順は書いた形でなく費用で決まる)。`security_barrier`のビューは、leakproofの比較を中へ入れ、距離の構成だけが外に残った。`MATERIALIZED`のCTEと`OFFSET 0`の副問い合わせは段ごとに別に評価され、段の順は書いた順になった(`MATERIALIZED`は文書が別に計算すると定める。`OFFSET 0`は文書に定めが無い)。段の中の条件の順は費用で決まる。どの形も結果は同じで、時間は差が出なかった(利用者1人・10人とも、絞り込みなし約2.1〜2.5秒、絞り込みあり約0.12〜0.15秒)。順で時間が変わるのは、合計点の集計を他の条件より先に行う場合で、絞り込みありが約0.12秒から約2.2〜2.4秒になった。今の形は、計画の形で合計点の集計を最後に行う。

### 戻ったときの表示

「戻った」か「開いた」かを、画面の構成や遷移の経路でなく、開いたURLの戻りの印で決める。

- 戻りの印は、履歴の経路の検索部の`return=1`である(`ROUNDS_HISTORY_RETURN_PATH`、経路表)。印の無い`/rounds/history`は「開く」、印のあるURLは「戻る」を表す。
- 規則は1つで、履歴の画面はURLの検索部を購読し(`useSearchParams`)、印が無いときはいつでも「開いた」として、表示済みを捨てて先頭のページから取得し、自分のURLを印のある形に置き換える(`window.history.replaceState`)。印が無いのは、印の無いURLで表示を始めたときと、表示中に履歴の項目を押したときである。Next.jsは同じ経路で検索部だけが違う遷移では画面を作り直さない(画面のkeyが検索部を除いて作られる)ため、表示の開始時だけ見ると、履歴の表示中に項目を押しても取得しない。そのため、表示の開始時に限らず検索部の変化を見る。Next.jsは`replaceState`をルーターに取り込み、`useSearchParams`が新しい値を返すため、置き換えの後は印がある状態になり、取得を繰り返さない。置き換えは`window.history.replaceState(null, '', url)`の形で呼ぶ(第1引数に現在の`window.history.state`を渡すと、Next.jsは内部の印`__NA`を見て取り込まず、`useSearchParams`が印の無いままになるため。`app-router.js`の差し替えた`replaceState`)。
- この結果、履歴の項目(どの画面からでも、履歴の表示中でも)は最新を取得し、ブラウザの戻る・進むでこの項目に戻ると、印のあるURLで開く。
- `useSearchParams`を使う部分は、静的な枠の生成のためにSuspenseで包む(待つ間はスケルトン)。
- 詳細の戻り先(`originPathOf("history")`)は印のあるURLにする。詳細の戻るリンク(`back-link.tsx`)と、詳細での削除の後の移動(`round-leaving.ts`)が使う。履歴の項目(レフトパネル/ドロワー)は印の無い`ROUNDS_HISTORY_PATH`のままである。
- 履歴を離れるとき(画面を外すとき)、先頭のページの取得が成功していれば、連結したページ(項目、除外するIDの和、続きの有無、続きの起点)とスクロールの位置を、タブのメモリの記憶(`historyPagesMemory`)に書く。成功していなければ記憶を消す。続きの取得中・失敗の状態は書かない。記憶は最後に離れた履歴の1つだけである。
- 除外するIDの和は、各ページの取得時の削除済みのIDと、この画面で削除したID(`removed`)の和である。`removed`を含めないと、履歴で削除した後に一括の取得が端末の記録から削除の操作を外すと、戻ったときにそのラウンドが再び出るため含める。スクロールの位置は、スクロールの入れ物の位置で、画面を外す直前(DOMを替える前)に読む。
- スクロールの入れ物は、`(main)/layout.tsx`の`overflow-y-auto`の要素である。履歴の画面は、一覧の要素から先祖をたどり、`overflow-y`が`auto`か`scroll`の最も近い要素として得る(`app`の要素を参照しない)。続きの自動の取得の`root`、スクロールの位置の読み書きに使う。
- 表示の開始時にURLに印があり記憶があれば、取得せずに記憶のページを表示し、描いた後にスクロールの位置を戻す。そのとき、端末の記録から削除済みのIDを読み直して(`readDeleted`)、記憶の除外するIDの和に足す。端末の入力中は購読のまま除く。続きは、通常どおり一覧の末尾が画面に近づくと取得する。印があり記憶が無ければ、先頭のページから取得する。
- 条件の変更は通常どおり先頭から取得し直し、離れるときに新しい内容で記憶を書き直す。
- 記憶に利用者と条件を添えない。結果: 利用者が替わる移動(サインイン、サインアウト、セッションの喪失、別の利用者のサインイン)は全て`window.location.replace`によるページの読み込みを伴い、JavaScriptのメモリの記憶が無くなるため、別の利用者に使われない。条件は履歴の画面でしか変わらず、変えたときの内容が離れるときに書かれるため、記憶と保存した条件は食い違わない。
- 記憶はJavaScriptのメモリにだけあり、再読み込み、別のタブ、アプリの起動では無い。

| ラウンドを完了してホームへ移った後に、「履歴」の項目で開く | 最新を取得する(完了したラウンドが出る) |
| ラウンドを完了してホームへ移った後に、ブラウザの戻るを重ねて前の履歴の項目に戻る | 最後に離れた履歴の表示(完了したラウンドは出ない) |
| 再読み込み、直接のアクセス、別のタブ、アプリの起動(印のあるURLを含む) | 最新を取得する(記憶が無いため)。条件と開閉は`sessionStorage`から戻る(再読み込み) |
| 別の利用者で開く | 最新を取得する(利用者が替わる移動はページの読み込みを伴い、記憶が無くなるため) |
| オフラインで戻る | 離れる前の表示(取得しないため、オフラインの表示にならない) |

- 要件との整合: 「戻る操作(詳細の戻る、ブラウザの戻る・進む)で戻ったときは離れる前の表示」は、詳細の戻り先とブラウザの戻る・進むで開くURLが戻りの印を持つことで満たす。「履歴の項目から開くと最新」は、項目のURLが印を持たないことで満たす。要件が設計に委ねた開き方(再読み込み、直接のアクセス、別のタブ、アプリの起動、別の利用者)は、記憶が無いため全て最新を取得し、「履歴の項目から開くと最新」と食い違わない。

### 条件の保持

- 条件と開閉は、タブごとの保存先(`sessionStorage`)に、利用者のIDを添えて記憶する。画面は表示の開始後に記憶を読み、変更のたびに書く。読む前は条件を持たない。
- 記憶の約束(`HistoryViewMemory`: 読む、書く)はapplicationに置き、実装はinfrastructureが持つ。実装は、保存値の利用者が端末の識別情報(`IdentityReader`)の利用者と違うとき、無いとき、検証できないときは既定を返す。保存先を使えないときは、画面の間だけ記憶なしで動く。端末の識別情報の利用者が無いときは、書き込みは何も書かず、読み込みは既定を返す。
- 別の利用者には、保存値の利用者の照合だけで引き継がない。サインアウトでは破棄しない。同じ利用者が再サインインすると、同じタブでは条件と開閉が残る。
- 別のタブとは共有しない。新しいタブは、初めて開いたときの状態(既定の条件、開)から始まる。
- 画面は、記憶を手続きの入れ物から受ける(`rounds-context.tsx`)。

- `app/(main)/rounds/page.tsx`（入口）: `<main>`の中に`RoundsHome`だけを描く。`app/(main)/rounds/history/page.tsx`（入口）は`RoundsHistory`だけを描く。どちらも静的で、何も生成せず、取得もせず、`cookies()`も読まない。見出しはsr-onlyも置かない。
- `features/rounds/ui/rounds-home.tsx`（UI層、Client Component）: `useLocalRoundsList`と手続きの入れ物の`deletion`だけを使う。`homeView`が決めた入力中のカード、0件の表示、削除の確認、新規作成ボタンを描く。履歴の取得の hook と`whenOnline`は使わない。
- `features/rounds/ui/rounds-history.tsx`（UI層、Client Component）: 取得したページ(`use-history-pages.ts`)と端末の入力中から`historyView`が決めた内容に応じて、上端の操作(`history-controls.tsx`)の下に、条件の単位に応じたカード(ラウンドか距離)と一覧の末尾(続きの取得の状態か`historyEnd`)、または取得中・オフライン・エラーの表示を描画する。0件の文言は1つである。
- `features/rounds/application/history-pages-memory.ts`（application）: 戻ったときの表示の記憶(`createHistoryPagesMemory()`: 書く、読む、消す)。タブのメモリに1つだけ持つ。外部に触れず実装は1つのため、約束と実装に分けない。手続きの入れ物から履歴が受ける。
- `features/rounds/ui/use-history-pages.ts`（UI層）: URLの検索部を購読し、戻りの印(`isHistoryReturn`)が無いときは表示済みを捨てて先頭から取得し、自分のURLを印のある形に置き換える。表示の開始時に印があれば、戻ったときの表示の記憶があればそれを表示し、なければ先頭から取得する。離れるときに記憶を書く(画面の`removed`を受け、除外するIDの和に含める)。条件を受けて、先頭のページと続きのページの取得、連結、再試行、先頭のページのオフラインでの通信の復帰による取り直しを扱う。一覧の末尾が画面に近づいたことを受け、自動の取得の可否(続きあり、取得中でない、失敗でない)を決める。取得中の表示を描いた後に、画面の高さ(`window.innerHeight`)と測った1件分の高さから件数を決め、`loadList(condition, after, size)`で取得する。条件が変わると表示済みを捨てて先頭から取得し、古い取得の結果は捨てる。条件を読む前(null)は取得しない。
- `features/rounds/ui/use-history-view.ts`、`history-controls.tsx`（UI層）: 記憶から条件と開閉を読み(読む前はnull)、単位の切替・並べ替え・絞り込み(期間・得点の範囲・距離の構成・距離の行の入力を含む)・開閉・既定に戻す操作を受けて状態を更新し記憶へ書く。操作の部品は、単位の切替、並べ替え、絞り込み(開いているときだけ)、開閉、リセットを描く。期間と得点の範囲の下書き、検証のエラー、反映の操作(blurとEnter)は欄の部品(`history-range-fields.tsx`)が持ち、検証は`historyRangeOf`を使う。下書きとエラーは記憶へ書かない。
- `features/rounds/ui/history-distance-fields.tsx`（UI層）: 距離の構成の欄の部品。行の下書き、検証のエラー、行の追加・削除、的の選択と外す操作、反映の操作を持ち、検証は`historyDistancesOf`を使う。的の一覧は手続きの入れ物の`fetching.savedTargetFaces()`を表示の開始後に読み、的の選択の一覧(`target-face-picker.tsx`)と的の表示(`target-face-info.tsx`)を使う。リセットで作り直す仕組み(期間と得点の欄と同じ`key`)を共有する。下書きとエラーは記憶へ書かない。行の数の上限を受け、距離単位の距離の行にも使う。
- `features/rounds/ui/round-cards.tsx`（UI層）: カード、メニュー、スケルトン。距離単位のカード(メニューなし)も持つ。履歴のカードだけが遷移元`history`を渡し、詳細へのリンクに`?from=history`が付く(`rounds/detail`)。
- `features/rounds/ui/round-delete.tsx`（UI層）: ホームと履歴が共有する、削除済みの集合(`removed`)、確認の対象、確認ダイアログ。削除は手続きの入れ物の`deletion.deleteRound`で行い、`removed`へ足して除き、取得の状態が変わっても失わない。
- `features/rounds/ui/use-local-rounds-list.ts`（UI層）: 窓口(`RoundWindow`)の`watchLocalList`/`localList`を`useSyncExternalStore`で購読する。一括の取得の反映も届く。読み終えるまで(サーバー描画、水和を含む)は`null`を返す。
- `features/rounds/ui/fetch-state.tsx`（UI層）: 取得の状態の表示。履歴は先頭のページの状態に使う(`use-fetch-result.ts`は履歴では使わない)。
- `features/rounds/domain/rounds-list-view.ts`（domain）: 表示の内容を決める純粋関数。`homeView(local, removed)`は端末の入力中から`removed`を除き、実施日の新しい順に返す(読み込み前はnull)。`historyView`は、先頭のページの取得が成功し端末の入力中を読み終えているときだけ、連結したページから端末の入力中のID、削除済み(`deleted`と`removed`)を除いた項目と、続きの有無を返す。除外は項目が属するラウンドのIDで比べる。それ以外はラウンドを持たず、取得の状態だけを返す。
- `features/rounds/domain/round-list.ts`（domain）: 一覧の材料の型(`LoadedRoundsList`、`LocalRoundsList`、`ServerRoundSummary`、距離単位の項目と1件の型)と、削除済みと入力中の導出、ページの連結(`appendRoundsList`)、1ページの件数の決定(`historyPageSizeOf`、`HISTORY_PAGE_SIZE_MIN`、`HISTORY_PAGE_SIZE_MAX`)を持つ。`LoadedRoundsList`は、連結した項目、削除済みのIDの和(`deleted`)、続きの有無、続きの起点を持つ。端末の記録だけから求める入力中のラウンド(`LocalRoundsList`)は削除済みを入れない。
- `features/rounds/domain/round-routes.ts`（domain）: ラウンドの画面の経路の判定・変換(経路に対応する枠を返す`roundFramePathOf`。履歴の枠を詳細の枠より先に判定する)。遷移元の型と変換(`RoundOrigin`、`roundOriginOf`、`originPathOf`)は`rounds/detail`が扱う。履歴の遷移元の戻り先(`originPathOf("history")`)は戻りの印のあるURL(`ROUNDS_HISTORY_RETURN_PATH`)で、URLの検索部に印があるかの判定(`isHistoryReturn`)もここに置く。経路の定数(`ROUNDS_PATH`、`ROUNDS_HOME_PATH`、`ROUNDS_HISTORY_PATH`、`NEW_ROUND_PATH`、`roundPath`)は経路表(`src/routes.ts`)が持つ。
- `features/rounds/domain/history-view-state.ts`（domain）: 条件(単位と距離の行を含む)と表示の状態の型、既定、保存値の検証、期間と得点の範囲の下書きの検証(`historyRangeOf`)、距離の構成の下書きの検証(`historyDistancesOf`)(「条件の定義」)。
- `features/rounds/application/history-view-memory.ts`（application）: 記憶の約束(「条件の保持」)。
- `features/rounds/infrastructure/browser-history-view-memory.ts`（インフラ層）: タブごとの保存先と利用者の照合による記憶の実装。
- `features/rounds/application/rounds-list-store.ts`（手続き）: 履歴の画面に渡す状態。`loadList(condition, after, size)`は、端末の記録(`readList`)を読んで削除済みのラウンドのIDを求め、条件と続きの起点と件数で1ページの取得(`RoundFetching.fetchRoundsList`)を行い、失敗したときはその結果を返し、成功したらページと削除済みのIDを返す。`readDeleted()`は、取得せずに端末の記録の削除済みのIDだけを返す(戻ったときの表示に使う)。1ページごとに`withinFetchTimeout`で10秒に打ち切る(`app/offline-pwa`)。削除が確定済みでも端末の記録へは反映しない(反映は一括の取得の`refreshAll`が行う)。取得の拒否はそのまま伝え、画面の取得の hook が`error`にする。端末内の入力中の一覧は窓口(`features/rounds/application/round-window.ts`の`watchLocalList`/`localList`)が持つ。窓口は購読者が0→1で端末の記録を購読し、変化を同じティックで1回にまとめ、全ての列から導き直し、構造が同値なら参照を変えず通知しない。1→0で値を捨てる(再購読は`null`から始める)。導き直しは、端末の各組を`features/rounds/domain/round-view.ts`の`deriveRoundState`で状態にし、`features/rounds/domain/round-retention.ts`の`isRoundInProgress`が真のものを名前・実施日・合計点にする(`round-list.ts`)。保存済みの的は読まない。入力中と端末が保持するラウンドの一括の取得は、履歴の取得とは別に同期が行う(`features/round-sync/application/round-sync.ts`、`features/rounds/application/round-base-refreshing.ts`)。ユーザーの突き合わせは行わない。ベースと操作の列は端末でユーザーごとに隔離され、取得の利用者と記録の利用者が`same`でない反映は端末へ保存されない。通信の復帰の合図(`whenOnline`)は手続きの入れ物から受ける。画面は時刻、乱数、通信の可否に触らない。
- `features/rounds/application/round-fetching.ts`（手続き）: 取得の順序。`fetchRoundsList(condition, after, size)`が、`fetchContent`（`features/rounds/application/content-fetcher.ts`）経由で認証を確かめて`RoundQueries.roundsList`を呼び、`roundListItemOf`で項目にして続きの有無を添える。
- `features/rounds/infrastructure/round-queries.ts`（インフラ層）: 履歴の問い合わせを`DatabaseGateway<RoundsDbSchema>`の`rpc`で履歴の関数(`rounds_list`)へ行い(`roundsList({ condition, after, size })`)、応答を`ServerRoundSummary`の列と続きの有無のまま`QueryOutcome`で返す。自動の再試行はしない。`rounds_list`の引数のうち、期間と得点の範囲の4つは、`null`でないものだけを送り、距離の構成は行が1つ以上のときだけ`p_distances`として送る(指定のない引数は送らない。`rangeArgsOf`と同じ形)。距離単位のときは`distances_list`を呼び(行があれば`p_distance`を送る)、応答の`distances`を距離単位の項目のページにする。生成型では新しい引数がoptionalのため、`rounds-db-schema.ts`にnull許容の上書きは足さない。`rounds-db-schema.ts`は`rounds_list`と`distances_list`を含み、`distances_list`にも`rounds_list`と同じnull許容の上書きを持つ。名前(`roundsList`、`fetchRoundsList`、`loadList`、`RoundsListStore`)は据え置き、履歴の取得を指す。
- `supabase/migrations/*_rounds_list*.sql`、`*_distances_list*.sql`（DB）: 履歴の関数、ラウンドの条件の関数、距離単位の履歴の関数(「取得の形」)と、その取得が使う索引、`distances`・`shots`のSELECTのポリシー(「索引とRLSと条件の評価の順」)。引数を足すときは、追加のmigrationで旧署名を作り直す。署名を直書きするDBのテスト(`supabase/tests/rpc_matrix.sql`、`rls_matrix.sql`)と生成型(`apps/web/src/types/supabase.ts`)も、同じ変更で新しい署名に合わせる。
- 端末から導く入力中のラウンドの合計点は、状態の距離・矢から、履歴の関数と同じ規則で端末が求める。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| ホームを履歴の取得から切り離す | 入力するために＋を押す利用者が、履歴の取得を経由しないため。ホームが取得を経由しないことを、取得する部品を持たない構造で保証する | ホームに履歴由来の表示を足すとき |
| 履歴の取得をサーバーの`status = completed`で絞り、端末の完了を合わせない | 「サーバーで完了と記録されたものだけ」の要件と一致し、入力中や端末だけの完了を取得しないため。全件取得して画面で除く案は、規則を画面の条件に頼るため採らない | 端末の完了を履歴に出す要件になったとき |
| 履歴から、端末の入力中のIDと削除済みの2つを、取得の後に端末で除き、1ページの表示件数が減るのを許す | 他の端末で完了したラウンドが同期の反映までホームと履歴の両方に出ること、削除のサーバー受理までの間に出ることを防ぐため。除くIDをサーバーへ渡してページを満たす案は、取得の後の削除を端末で除く仕組みが残り、引数が入力中の件数に比例するため採らない | 同期との時間差がなくなるとき |
| `ROUNDS_HOME_PATH`と`ROUNDS_PATH`を同じ値で持ち分ける | ホームを指す呼び出しと、画面全体の範囲(保護の範囲、枠)を指す呼び出しを区別し、`HOME_PATH`(`/`)との取り違えを避けるため | 範囲とホームの値が分かれるとき |
| 見出しを置かない(sr-onlyも置かない) | 要件のため。切替の項目と現在のビューの表示が画面を示す | 見出しが要件に戻るとき |
| ホームの入力中は端末の列を表示の開始時に読み、記録が変わるたびに読み直す | 端末の記録の変化(一括の取得の反映)を取得を待たずに反映するため | 読み直しの費用が問題になるとき |
| 論理削除された行を、ラウンド・距離・矢の3段階で履歴と合計点から除く | 削除を`disabled_at`で射影しており、無効化後の後続イベントも通常表示へ戻さないため | 削除の方式を変えるとき |
| 合計点を`rounds_list`の中の副問い合わせで求め、集計列・ビューを持たない | 合計点を使うのは`rounds_list`だけで、最も単純なため。変更前(全ての矢の行を転送)より転送が減り、DBで読む量は同程度である。集計列は、矢・距離を変える全ての書き込みのRPCで値を保つ必要があり、今の規模では要らないため採らない。PostgRESTの集約関数は並べ替えに使えないため採らない | 履歴の取得の遅さが問題になるとき |
| 履歴の取得は、呼び出し元の権限で動く関数(`SECURITY INVOKER`の`rounds_list`)で行い、認可はSELECTのRLSに任せる | 合計点での並べ替えと、作成時刻を返さないキーセットの起点(作成時刻をIDから引く)は、直接SELECTでは書けないため。認可をRLSに残し、SELECTポリシーを維持する方針と合わせる | 読み取りも認可RPCへ統一するとき |

## 制約と未対応

- 履歴のURLは、表示の開始後は常に戻りの印の付いた形(`/rounds/history?return=1`)になり、アドレス欄や共有するURLにも出る。印の付いたURLを再読み込みや別のタブで開いても、記憶が無いため最新を取得する。既存のE2Eは履歴のURLを`/\/rounds\/history$/`で照合しており(`tests/e2e/rounds/history.spec.ts`の5か所、`tests/e2e/app/offline-pwa.spec.ts`の1か所)、この照合は印の付いたURLに一致しなくなる。
- 戻ったときの表示は取得しないため、離れている間の変更は、履歴の項目で開くか再読み込みするまで出ない。他の端末での変更に加え、この端末で詳細から変えた完了のラウンドの名前・実施日も、戻ったときは離れる前の値のまま出る(完了のラウンドは詳細で名前・実施日を変えても完了のまま。`rounds/completion`)。点数の記録や距離の追加で入力中に戻ったラウンドは、端末の入力中として除かれ、出ない。
- 履歴の関数は、ページの取得のたびに条件に一致する全ラウンドの合計点(距離単位では全ての距離の小計)を求めて並べるため、DBの処理量はその利用者の完了したラウンドの矢の総数に比例する(転送量は1ページ分)。矢はRLSを通して読み、矢1行ごとの判定が時間の大半を占める(合成データで、完了したラウンド2000件・矢約28万本の利用者の絞り込みなしの取得が約1.8〜2.2秒。本番では確かめていない)。遅さが問題になったら、書き込みのRPCが保つ集計列、日付順で切り出してから合計点を求める形を検討する。
- `distances`・`shots`のSELECTのポリシーは親が見えるかで書き、`shot_events`・`distance_events`は`is_round_member`を直接呼ぶ形のまま残す。2通りの書き方があり、読める範囲は同じである。
- ラウンドの条件の関数(`history_rounds`)だけが`SET search_path`を付けない関数である(展開させるため。名前は修飾する)。
- 読み進める間に、他の端末で続きの起点のラウンドの実施日か合計点が変わると、次のページで行が抜けることがある(要件の例外。開き直すと正しく並ぶ)。
- 画面がDBのmigrationより先に配備されると、その間は、期間・得点の範囲・距離の構成のどれかを指定した取得と距離単位の取得だけが、DBに新しい署名の関数が無くエラーになる(許容した)。指定のない取得は動く。画面の配備とDBのmigration(CD)の順序は保証しない。旧い版の画面から新しいDBへの呼び出しは動く。
- 履歴の先頭のページがオフライン表示のときは、通信の復帰（手続きの入れ物の`whenOnline`）で自動再取得する。続きのオフラインは、再試行ボタンで取り直す。通信失敗（`navigator.onLine`が`true`のまま）を含むエラーは、自動で取り直さず、再試行ボタンで取得し直す。
- 完了で未送信の変更が残るラウンドは、サーバーに完了が反映され、履歴を開いて取得するまで、ホームにも履歴にも出ない。
- 一括の取得は、ホームと履歴を開いても起こさず、起動、通信の復帰、画面が見える状態で行う。
- 条件は、ラウンド単位と距離単位の切替、日付・得点の並べ替えと、種別・弓種の絞り込み(それぞれ単一選択)、期間と得点の範囲と距離の構成と距離単位の距離の行(1つ)の絞り込みだけである。閉じている間は、並べ替えと絞り込みのどちらの値も、適用中を示す表示もない。
- 距離単位の件からはラウンドを削除できない(詳細かラウンド単位で削除する)。
- 期間・得点・距離の構成・距離の行の数値の入力は、欄を離れるかEnterを押すまで反映されない。不正な入力のエラーは、欄を閉じるか画面を離れると消え、入力した文字も捨てる(記憶しない)。
- 距離の構成の的の一覧は、端末に保存した一覧(同期の一括の取得が保存する)だけを使う。新しい端末で同期の初回の取得が終わる前に欄を開くと、一覧が空で的を選べない。欄を開き直すと読み直す。
- 別のタブとは条件を共有しない。サインアウトで条件を破棄しないため、同じ利用者が同じタブで再サインインすると条件と開閉が残る。
