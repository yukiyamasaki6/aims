# rounds/history 設計

## 概要

ラウンドの画面を、ホーム(`/rounds`)と点数一覧(`/rounds/history`)に分ける。共用のヘッダー(`app/navigation`)の現在地を「ホーム」「点数一覧」とし、本文の見出しは、ホームの入力中の欄の「入力中のラウンド」だけである。
ホームは、端末の記録の入力中のラウンドだけを表示する。履歴の取得も同期の完了も待たず、取得を起こさない。
入力中のラウンドは、端末が知る状態(取得したベースに未送信の操作を重ねた状態)から、詳細と同じ導出と表示の規則(`isRoundInProgress`)で決める。保持の規則(`rounds/sync`)は使わない。
点数一覧は、点数一覧の項目から開いたとき(戻る操作で戻ったときを除く)にサーバーで完了と記録されたラウンドだけを、画面の高さに応じた件数(10〜50件)のページごとに取得して表示する(ページ送り)。続きは、一覧の末尾が画面に近づくと自動で取得する(無限スクロール)。取得結果から、端末の入力中のIDと削除済みを除く。端末の完了は点数一覧に出さず、取得が成功していないときはラウンドを出さない。
各カード(行)に日付・ラウンド名・種別・弓種を出し、ラウンド単位は距離ごとの距離と小計の一覧と合計点、距離単位は距離と小計を出す。カードから`/rounds/[id]`へ、ホームの右下のラウンドの開始ボタンから`/rounds/new`(ラウンドの開始画面)へ遷移する。
ホームと点数一覧は読み取り中心の画面で、書き込みはカードのメニューからの削除だけである。削除は`rounds/delete`が扱う。
取得はクライアントで行い、枠は静的である。
点数一覧の見出しは`rounds-messages.ts`の`historyTitle`で「点数一覧」と定義し、`HistoryFrame`から`ScreenFrame`へ渡す。Suspenseの代替表示と通常表示で同じ枠を使い、取得状態によらず見出しを維持する。
点数一覧のヘッダーの右端に、フィルターのアイコンのボタンを置く。押すと、点数一覧の本文の中に、一覧と領域を分けた非モーダルのフィルターパネル(名前「フィルター」は支援技術にだけ伝える)が開く。ヘッダーは開いている間も見えて操作でき、閉じる操作は、このボタンの再押下、パネル内のEscと、縦長での「検索」である(横長の「検索」は閉じない)。ボタンは開いている間、背景をやや灰色にして開いていることを見た目でも示す。パネルの中に、先頭の行(表示単位の切り替え「ラウンド」「距離」と、右端のリセット(消しゴムのアイコンのボタン))、中央の入力欄(期間・得点の行に含めた並べ替えの向き、得点の範囲、種別・弓種、ラウンド単位ではラウンド構成、距離単位では距離の指定)、下部に固定した検索を置く(閉じる専用のボタンは置かない)。距離単位は、完了したラウンドの無効でない距離を1件ずつ、その小計で出す。単位も条件の1つで、ラウンド単位は`rounds_list`、距離単位は`distances_list`が取得し、対象のラウンドは2つが共通の関数(`history_rounds`)から読む。条件の適用とページの切り出しは、サーバーの履歴の関数が履歴全体に対して行い、条件を変えると先頭のページから取得し直す。持つ状態は入力値(`HistoryInput`。得点の範囲は単位ごとに持つ)だけで、「検索」で確定し、検索の時点でタブごとに記憶する。パネル内の値は編集中の値(`HistoryFilterDraft`)で、適用までは入力値に影響せず、閉じると捨てる。取得に渡す条件(`HistoryCondition`)と適用中の印は、入力値から一意に導く(`historyConditionOf`。導出されるフィルター)。別の状態として持たず、導出されるフィルターが変わらなければ取得し直さない。不正な指定は、検索の時点で検出して欄にエラーを出し、入力値を変えず、取得しないため、一覧は直前の表示のままである。別の利用者には引き継がない。パネルの開閉と編集中の値は画面を離れた後には保たない。
点数一覧を離れるとき、表示済みの内容とスクロールの位置をタブのメモリに記憶する。点数一覧の表示は自分のURLに戻りの印を付け、印のあるURLで開いたとき(詳細の戻る、ブラウザの戻る・進む)は記憶を使い、印の無い`/rounds/history`へ進んだとき(点数一覧の項目など)は最新を取得する。

## 画面と状態

ホーム:

| 状態 | 表示 |
| :--- | :--- |
| 端末の入力中を読み込む前 | 見出し「入力中のラウンド」だけ(空の表示は出さない) |
| 入力中が0件 | 見出しと、その下に行1つ分の領域の中央に置いた「入力中のラウンドはありません」 |
| 入力中が1件以上 | 見出しと、実施日の新しい順のカード(折りたたみ、件数バッジなし) |

- ラウンドの開始ボタンは、ホームの全状態で表示する。ホームだけにあり、点数一覧・詳細・ラウンドの開始画面にはない(ホーム以外の画面の入口は、レフトパネルのラウンドの開始ボタン。`app/navigation`)。
- ラウンドの開始ボタンは、`Plus`のアイコン(20px四方、`aria-hidden="true"`)と文字「ラウンドを開始」を横に並べた、両端が丸い横長のリンク(`fixed right-6 bottom-6 flex h-14 items-center gap-2 rounded-full bg-primary px-5 text-primary-foreground shadow-lg transition-colors hover:bg-primary/80`)である。高さは56px(`h-14`)で、押せる範囲の目安(44px)を満たす。左右の余白は20px(`px-5`)、アイコンと文字の間は8px(`gap-2`)である。文字の大きさは指定せず、ページの既定(16px)に従う。形は、元のアイコンだけの丸いボタンと同じ`rounded-full`(高さの半分の丸み)にする。名前は表示の文字から得て、`aria-label`は付けない。
- ホームの本文(`main`)は、下の余白を96px(`pb-24`)にする。ボタンは画面の下端から24pxの位置に高さ56pxで重なる(上端は下端から80px)ため、末尾までスクロールしたとき、最後のカードとそのメニューはボタンの上端より16px上で止まり、隠れずに押せる。幅によらず同じ余白で、幅390pxでも成り立つ。
- 見出し「入力中のラウンド」(`rounds-messages.ts`の`homeInProgressHeading`)は、`rounds-home.tsx`が、ホームの全状態で入力中の欄の先頭に`h2`として描く(現在地「ホーム」はヘッダーの`h1`)。欄は`section`で、見出しで名前を付ける。大きさは本文と同じか大きく、太さで見出しと分かるようにし、色や装飾は足さない。本文(`main`)の左端にそろえる。行の一覧は左右に広がるが行の内容は本文の端にそろうため、見出しと行の内容の左端が一致する。見出しは左寄せのままで、0件の文言は行1つ分の領域(「文言の領域」)の中央に置くため、0件から1件に変わっても見出しの位置は動かない。書式と見出しの下の間隔は、`rounds-home.tsx`の見出しの1つのクラスの値だけに持ち、そこだけで調整できる。
- 同期の取得の状態(取得中・失敗・オフライン)で表示を変えない。同期の反映が端末の記録を変えると、購読で表示が更新される。
- 入力中のカードも、既存のメニューと確認で削除でき、その場で消える。

点数一覧(取得の状態は点数一覧の中にだけ出す):

| 状態 | 表示 |
| :--- | :--- |
| 取得中(先頭のページ。端末の入力中と保存した条件の読み込み前を含む) | スケルトン |
| 取得の成功・続きあり | 取得したページを連結し除外したラウンドのカード(0件もありうる)。末尾は続きの取得を待つ |
| 取得の成功・続きなし | 表示1件以上: カードと、末尾に「該当するラウンドは以上です」(`historyEnd`。距離単位は「該当する距離は以上です」(`historyEndDistance`))。表示0件: 「該当するラウンドがありません」(`historyEmpty`。距離単位も同じ文言)だけで、`historyEnd`は出さない。末尾と0件の文言は、行1つと同じ幅・高さの領域の上下左右の中央に置く(境界線なし。「文言の領域」) |
| 続きの取得中 | 表示済みのカードの下に、取得中の表示(`LoadingState`とスケルトン) |
| 続きのオフライン・エラー | 表示済みのカードの下に、先頭のページと同じ文言(`fetchOffline`、`fetchFailure`)と再試行ボタン |
| オフライン(`navigator.onLine`が`false`) | 「ネットワークに接続されていません」と再試行ボタン(`app/offline-pwa`) |
| エラー | エラーメッセージと再試行ボタン。通信失敗は「読み込めませんでした。」。未認証は「サインインが必要です。」 |

- 点数一覧のヘッダーの右端に、フィルターのアイコンのボタン(`aria-label`「フィルター」。`aria-expanded`と`aria-controls`で開閉と領域を伝える通常のボタン)を置く。図柄は開閉によらず漏斗のままで、名前も変えない。開閉は背景で見た目にも示す(「展開中の見た目」)。押すたびに、閉じていれば開き、開いていれば閉じる。ボタンは枠のない`buttonVariants({ variant: "ghost" })`で、focus-visibleの輪は残す。大きさは、ヘッダーのアイコンだけのボタン(メニューボタン、ラウンドのメニュー)にそろえ、押せる範囲の枠を含めて32px四方(`size-8 px-0`)、アイコン24px(`size-6`)にする(`app/navigation`)。ボタンは固定の32px四方(`size-8`)で、中央に置くため、押せる範囲は変わらない。アイコンの色は変えない。アイコンは共用のヘッダーの中にあり、一覧のスクロールの外なので、スクロールしても同じ位置に残り、一覧の項目と重ならない(「アイコンの配置」)。ボタンは取得の状態にかかわらず出し、保存した条件を読み終えるまでは出さず、取得中として扱う。導出されるフィルターが既定でないとき(`isDefaultHistoryCondition`が偽。使わない単位の絞り込む距離・ラウンド構成・得点の範囲は導出に含まれないため数えない)、アイコンの右上に寄せた印(点。`bg-primary`、10px(`size-2.5`)、32pxのボタンの右上に寄せて漏斗の右上に重ねる(`top-0.5 right-0.5`。アイコンを20pxから24pxに広げた分、点を右上へ2px寄せ、漏斗の右上の角との位置関係を従来と同じに保つ。点とその縁取りは32pxの枠の内側に収まる)。周りにヘッダーの背景色の縁取りを付ける。漏斗の線と輪郭が融合して見えにくいため、印の周りにヘッダーの背景色(`bg-card`と同じ色)の縁取りを付け、漏斗から切り離して見せる。画面の読み上げ用に「適用中」の文言を持つ)を出す。印は導出されるフィルターだけで決め、パネル内の編集中の値では変わらない。
- 展開中の見た目: パネルが開いている間(`aria-expanded`が真の間)、漏斗のボタンの背景をやや灰色(`bg-muted`。`ghost`のホバーと同じ色)にし、閉じると(どの閉じる操作でも、閉じる操作の時点で)元の背景(なし)に戻す。縦長・横長で同じである。横長で検索して開いたままのときは灰色が続く。背景は`aria-expanded`と同じ開閉の状態から付け、別の状態を持たない。図柄・アイコンの色・大きさ・名前は変えない。閉じているときのホバーは`ghost`のまま(`hover:bg-muted`)で、展開中の背景はこれと同じ濃さにする。閉じた漏斗にホバーして押すと、ホバーの濃さがそのまま固定されて展開を表し、押した前後で背景は変わらない(ユーザーの判断)。展開中にホバーしたときは、展開中の背景と異なる濃さにする(ユーザーの判断。濃さは「展開中のホバー」)。
  - 展開中のホバー: 展開中の背景より濃くする(`hover:bg-foreground/10`。`ghost`の`hover:bg-muted`を上書きする)。格納中のホバー、押して固定、展開中のホバーの順に一段ずつ濃くなる(ユーザーの判断)。
  - 閉じた後のホバー: マウスで漏斗に乗せたまま閉じると、離すまで格納中のホバー(展開中の背景と同じ濃さ)が見える。これは受け入れ、抑止する仕組みは持たない(ユーザーの判断)。Tailwind CSS v4の`hover:`は`(hover: hover)`の端末でだけ効くため、タッチだけの端末では起きない。
  - 適用中の印との両立: 印(`bg-primary`の点と`ring-card`の縁取り)は変えない。展開中の灰色の上でも、濃い点と白い縁取りが背景から切り離して見えるため、背景の灰色(開いている)と点(適用中)を同時に判別できる。
- アイコンの配置: 点数一覧の枠(`rounds-history.tsx`の`HistoryFrame`。取得中の表示(Suspenseの代替)も同じ枠に入る)は、共用のヘッダー枠(`ScreenFrame`)に現在地「点数一覧」と、`trailing`としてヘッダー操作(`HistoryControls`)を入れ、本文領域に、フィルターパネルと点数一覧が持つスクロールの入れ物(`min-h-0 min-w-0 flex-1 overflow-y-auto`)と、その中の一覧の`main`(`mx-auto max-w-xl px-8 py-8`。ホームと同じ上の余白)を置く。保存した条件を読み終えるまでボタンは出さない(ヘッダーの高さは一定なので、読み終えたときに一覧もヘッダーも動かない)。一覧の上にアイコンの層と、アイコン分の先頭の空白は持たない。スクロールの入れ物は点数一覧の枠の一覧専用の`overflow-y-auto`の要素(`ScreenFrame`の本文領域の枠はスクロールしない)で、一覧の先祖の最も近い`overflow-y`のauto要素として探されるため(`scrollContainerOf`)、続きの取得の監視、戻ったときのスクロールの位置の記憶と復元は、この入れ物に対して働く。入れ物は画面ごとに作られ、ほかの画面のスクロールの位置を持ち越さない。ホームのラウンドの開始ボタンは右下の固定ボタンで、ヘッダーのアイコンとは置き場が別である。
- 文言の領域: 一覧の末尾の「以上です」(`historyEnd`・`historyEndDistance`)、点数一覧の0件の文言(`historyEmpty`)、ホームの0件の文言(`homeEmpty`)は、行1つと同じ幅・同じ高さ(`cardLayout`の数値)の領域の水平・垂直の中央に置く。領域は一覧の行と同じく本文の左右の端まで広がり、`RowNotice`(`round-cards.tsx`)が描く。領域は境界線を引かず、余白の包みも持たない(3か所とも同じ形)。`rounds-history.tsx`が末尾と点数一覧の0件に、`rounds-home.tsx`がホームの0件に使い、同じ形の部品を重複して持たない。文言は`p-4`の内側で折り返す。ラウンド単位と距離単位の行は同じ高さである。続きの取得中の表示(スケルトン)は、同じ高さの`RoundCardsSkeleton`である。
| フィルターの状態 | 操作と遷移 |
| --- | --- |
| 閉じている | 開く操作で適用済み条件から新しい編集を開始する |
| 編集中 | 入力・リセットは下書きだけ変更し、外側操作・向き変更では保持する |
| 検証エラーあり | 不正な検索では開いたままエラーを示し、次の検索・リセットまで保持する |
| 子ダイアログ編集中 | 子の確定だけ下書きへ反映し、子のEsc・中止では外側を保持する |
| 格納中 | 閉じた編集を操作不能にし、再表示は新しいセッションで始める |

- フィルターは、点数一覧の本文の中に置く名前付きの`region`(「パネル」。`HistoryFilterPanel`)とし、`Dialog`とバックドロップを持たない。点数キーボードと同じく、画面の本文の中の通常の領域として、一覧と並べて置く。ヘッダーは縦長・横長とも覆われず、開いている間も見えて操作できる。一覧とパネルの入力欄は独立してスクロールし、一覧の上や余白のタップでは閉じない。開閉の状態は点数一覧専用の`HistoryFrame`が持ち、取得の成功・失敗や0件によらず操作できる。保存した条件の読み込み前とSuspenseの代替表示では操作を出さない。
- 共通の画面の枠(`components/screen-frame.tsx`)、レフトパネル、ほかの画面は変更しない。パネルは本文領域の中に収まり、枠に受け口を要しない。点数キーボードの部品(`bottom-frame.tsx`、`keypad-panel.tsx`など)も変更しない。
- 向きは点数キーボードと同じ`(orientation: landscape)`で判断するが、フォームと子ダイアログのReactツリーは向きで分岐・再配置しない。点数一覧の本文の入れ物は縦長で縦並び(`flex-col`)、横長で横並び(`landscape:flex-row`)とし、パネルと一覧のスクロールの入れ物は、その入れ物の同じ位置の子のままで、置き場所はCSSの指定だけで変える。
- 置き場所は次のとおりである。
  - 縦長: パネルは本文の入れ物の先頭、一覧の上に、流れの中の高さを持って置く(ヘッダーの下、本文の内部の上から)。一覧はパネルの高さの分だけ押し下げられ、その分だけ一覧のスクロールの入れ物が縮む。一覧は覆われず、開いている間も操作とスクロールができる。閉じているときの高さは0で、一覧は動かない。パネルの高さは内容に応じ、本文の高さの半分(`max-h-1/2`)までとし、超えるときは入力欄の領域がスクロールする。
  - 横長: パネルは一覧の右の列に置き(幅は本文の40%(`w-2/5`)を基準とし、点数キーボードの横長のパネルと同じ。中身は、開いたときの幅に固定する(開閉の間も折り返しを変えない。下記))、高さは本文の高さいっぱいとする。一覧は左に残り、パネルの幅の分だけ狭くなる。
  - 縦長の見た目: パネルの下端は角丸にしない(ユーザーの判断。点数キーボードの縦長の本体と同じ四角)。点数キーボードの縦長と同じ枠線(`border-b-2 border-foreground/20`)と、影(キーボードの上向きの影の向きを下にした`shadow-[0_4px_6px_-1px_rgb(0_0_0/0.1),0_2px_4px_-2px_rgb(0_0_0/0.1)]`)を付ける。影が一覧の上に見えるよう、パネルは一覧より前に描く(`relative z-10`。ドロワー・スクリム・ダイアログより低い)。枠線・影は、中身を切り取るパネルの外枠自身に付け(自身の影は自身の`overflow-hidden`でクリップされない)、開いている間だけ付ける。
  - 横長の見た目: 一覧との間の左の線(`border-l`)だけで、角丸も影も付けない(点数キーボードの横長と同じ)。
  - 閉じている間(格納の完了後)は、パネルは高さ(縦長)・幅(横長)が0で、入力欄と先頭の行・下部の行は見えず、操作できず、Tab移動の対象にもならない(`inert`と`aria-hidden`を付け、画面の見えない位置に残さない)。閉じる操作の時点から格納の完了までも、同じく操作できない。
  - 領域の確保と動きは連動させ、既存キーボードの200ms程度のtransitionを基準に展開・格納する(縦長は上から高さが伸び、横長は右から幅が伸びる)。動きを減らす設定では即座に格納する。開閉でスクロールの入れ物は作り直さず、一覧のスクロールの位置は保たれる。
  - 開閉の間の中身: 外枠は幅(横長)だけを動かして中身を切り取り、中身(領域`section`)は、開いたときの幅に固定して、外枠の右端に寄せる(`landscape:w-[calc(40cqw-1px)]`。`1px`は外枠の左の線の分)。幅は入れ物の幅(本文の行を`@container`にし、container query unit `cqw`で40%)から決め、外枠の`w-2/5`と同じ値である。外枠の幅が変わっても中身は再配置されず、文字の折り返しと行数が変わらないまま、中身が現れ・隠れる(レフトパネルの固定幅の中身(`w-56`)と、点数キーボードの横長のパネルと同じ作り)。縦長は高さだけが動き幅は変わらないため、この規則を持たない。
- パネルの中身は、1つのフォーム(`HistoryFilterForm`)が縦に3つに分けて持つ。先頭の行(スクロールしない)は、表示単位の切り替えを行の水平方向の中央に置き、右端にリセット(消しゴムのアイコンのボタン)を置く。切り替えの左に同じ幅の空きを取るため、行に余裕があるときは行の中央になり、余裕がないときは空きが縮み、切り替えがリセットに重ならない。中央の入力欄の領域だけがスクロールする。下部の行(スクロールしない。検索)は、条件の量によらず常に見え、縦長・横長の両方で到達できる。「検索」は行の幅いっぱいを占める(`w-full`)。文言は`whitespace-nowrap`のまま切り取らない。「検索」は`type="submit"`、リセットは`type="reset"`である。向き別に行を複製しない。パネル内に閉じる専用のボタンは置かない(閉じる処理は漏斗とEscが呼ぶ)。ヘッダーの`HistoryControls`は、漏斗のボタンと適用中の印だけを持つ。
- リセットのボタン: 図柄は消しゴム(`lucide-react`の`Eraser`)で20px(`size-5`)、ボタンは枠のない`buttonVariants({ variant: "ghost" })`の32px四方(`size-8 px-0`。ヘッダーのアイコンだけのボタンと同じ)で、focus-visibleの輪は残す。名前は「リセット」(`historyControlsReset`。`sr-only`の文言。図柄は`aria-hidden`)で、図柄だけでなく名前でも目的を支援技術に伝え、色にも依存しない。名前「フィルター」の領域の中にあるため、対象は領域の名前で伝わる。閉じている間は領域ごと`inert`・`aria-hidden`のため、見えず、Tab移動の対象にならない。
- 閉じる操作は次のとおりで、「検索」だけが向きで異なる。
  - ヘッダーの漏斗の再押下(`aria-expanded`が真のとき、押すと閉じる。縦長・横長とも)
  - パネル内にフォーカスがあるときのEsc(縦長・横長とも)
  - 縦長での「検索」(正しい入力のとき)。横長の「検索」は閉じない(下記)
  閉じると、未適用の変更とエラーを破棄する。適用済みの条件は変わらない。パネルの外(一覧、余白、ヘッダー。ヘッダーの漏斗を除く)の操作では閉じない。
- 「検索」後の開閉は、検索を押した時点の向き(`(orientation: landscape)`。実行時に1回読み、状態に持たない)で決める。向きを途中で変えると、次の検索から切り替わった向きの挙動になる。
  - 縦長: 検索して閉じる。一覧はパネルの下に押し下げられていて確認しにくいため。
  - 横長: 検索しても閉じず、開いたままにする。一覧が右のパネルの隣に見えており、条件を直しながら試せるため。編集セッションは継続し、フォームの下書きは作り直さず、検索した内容のまま残す(リセットや、再度の検索の起点も同じ下書き)。不正な入力の検索は、縦長・横長とも、開いたままエラーを出し、適用済みの条件を変えない。正しい検索は、そのときの範囲のエラーを消す。フォーカスは動かさず、押した「検索」に残す(漏斗へは戻さない。Tab・Enterで続けて編集・再検索できる)。条件を変えない検索は、取得し直さず、何も起こさない。
  - 横長で検索した後にEsc・漏斗の再押下で閉じても、検索した内容は適用済みの条件として保たれ、検索後に直した未適用の変更とエラーだけが破棄される。
- パネル内のフォームは単一で、リセット・検索はフォームの子のボタンとして同じフォームのsubmit/resetを呼ぶ。フォームのonSubmitで既存の検証を1回実行し、成功時だけ`onApply`で確定し、閉じるかは向きで決める(上記)。onResetは既定の下書きとエラーなしに戻し、適用済み入力は変えない。ブラウザの標準submit/resetによる遷移や入力の巻き戻しは抑止する。フォーム内の子ダイアログの確定操作は外側のsubmitと区別する。テキスト入力中のEnterによる暗黙submitは抑止し、既存どおり検索ボタンの操作で確定する。
- 入力欄は、上から期間(日付順)、得点(得点順)、種別・弓種、そして単位で入れ替わる欄を置く。ラウンド単位ではラウンド構成、距離単位では距離の指定が、同じ位置に出て、もう一方は出さない。得点の欄は、表示している単位の得点の範囲を編集し、距離単位でも項目名は「最低点」「最高点」のままで、「小計」の語を付けない。フォームは編集中の値とエラーだけを持ち、先頭の行と下部の行を入力欄のスクロール領域から分ける。距離や的は既存の子ダイアログで編集する。
- 初期は閉じている(初めて開いた画面も、再読み込み・別タブも同じ)。開いたときは入力欄(表示単位の選択を含む)ではなくパネルの領域(`tabIndex=-1`)へフォーカスを移し(スマホでキーボードを出さないため。方針は`app/open-focus`)、Tabで先頭の行(表示単位、リセット)・入力欄・下部の行へ、さらに一覧へも移動できる。閉じる操作(漏斗の再押下、閉じるボタン、パネル内のEsc、縦長での有効な検索)のあと、フォーカスをヘッダーの漏斗へ戻す(漏斗の押下で閉じたときは、すでにそこにある)。閉じるボタンで閉じたときも、押したボタンは`inert`になって残せないため、開閉の操作である漏斗へ戻す(ほかの閉じる操作と同じ`HistoryFrame`の閉じる処理を使う)。横長で検索して開いたままのときは動かさない。画面遷移では戻さない。先頭の行・下部の行は向き別に複製しないため、向き変更でフォーカスは動かない。
- Escは、パネルの領域のバブリングだけで扱う。preventDefault済みのイベントと、DOM上その領域の外にある子ダイアログ・SelectのPortalからのイベントは扱わない。ヘッダー(漏斗を含む)、一覧、メニューなど、パネルの外を操作しているときのEscでは閉じない。document全体のEsc監視やcaptureでの横取りは行わない。子ダイアログやSelectは自身の既存の閉じる処理を優先し、開いているものの最前面だけが閉じる(的→距離→パネルの順に一段ずつ)。子のトリガーが削除されて復帰不能なときは、距離の追加・選択など残る操作へフォーカスを戻す。
- 向き変更は配置だけの変更であり、下書き・エラー・子ダイアログの入力・開閉状態を初期化しない(パネルは同じ要素のまま配置だけが変わる)。検索後の閉じ方は向きで決まるため、向きを変えると次の検索から挙動が切り替わる(上記)。閉じたセッションは再利用せず、格納途中の再表示でも適用済みの入力から新しい編集セッションを始める。閉じた後の遅延イベントや終了通知が新しいセッションを破棄・検索しないよう、セッションを識別する。
- 期間の行は、入力「開始日」「終了日」(間に`~`)と、項目名「日付順」の`Select`(「新しい順」「古い順」)を持つ。得点の行は、入力「最低点」「最高点」(間に`~`)と、項目名「得点順」の`Select`(「指定なし」「高い順」「低い順」)を持つ。「昇順」「降順」の語は画面に出さず、内部の値`asc`・`desc`との写しは、日付順は新しい順=`desc`・古い順=`asc`、得点順は高い順=`desc`・低い順=`asc`とする(従来の降順・昇順の意味を変えない)。向きの`Select`も下書きの値で、範囲の入力と同じく「検索」で反映する。狭い幅(スマホ幅)では、向きの`Select`が範囲の入力の下へ折り返してよい。並べ替えの基準を選ぶ操作と、独立した並べ替えの区画は持たない。
- 表示単位の切り替えは、「ラウンド」「距離」の2つの選択肢を並べて常に見せる単一選択(`components/ui/segmented-control.tsx`の共通部品。`@base-ui/react/radio-group`の`RadioGroup`・`Radio`。`role="radiogroup"`と`role="radio"`、`aria-checked`で選択中を伝え、容器は両端が半円の細長い形(`rounded-full`、背景は`bg-muted`、内側に数pxの余白)で、「ラウンド」「距離」の2つの選択肢が同じ幅を取り(容器の幅は内容に合わせた2つ同一の幅)、選択中を示す一回り小さい丸めた背景(`bg-background`、浮かせる影)は、選択肢とは別の1つの要素(指標)で、選択中の選択肢と通常の文字色で区別し、選択していない選択肢は背景なしの控えめな文字色にする(色はテーマのトークン)。指標は選択肢の幅と等しく、選択中の選択肢の位置へ`transform`の移動(200ms、`motion-reduce:transition-none`)で移る。位置は選択の値から導き(選択肢の数と選択中の番号をCSSの変数で渡す)、実測と状態を持たない。選択肢の幅が等しいため、位置は番号×幅で決まる。初期表示と、部品を作り直したとき(パネルを開くたび)は、直前の位置を持たないため動かない。選択中の判別は指標でなく`data-checked`と`aria-checked`で行う。業務の言葉を持たない)である。1回の操作で切り替わり、グループの名前は「表示単位」(`historyUnitLabel`。読み上げ用で画面に出さない)、選択肢の表示は「ラウンド」(`historyUnitRound`)・「距離」(`historyUnitDistance`)である。条件の型(`unit`: `round`か`distance`)と保存値は変えず、選択肢との写しは画面の1か所に置く。切り替えは下書きの値で、適用前でも、中央の入力欄の入れ替わる欄と得点の欄の対象が切り替わる。
- 距離の指定の欄(`HistoryDistanceSelect`)の直上に、ラウンド構成の欄と同じ位置関係・書式の見出し「距離構成」(`historyFilterDistanceGroup`)を置く。見出しは距離の指定の有無によらず出る。見出しの要素は両方の欄で同じ作りにして揃える。
- 共通の`Select`は`modal={false}`にする(実装済み)。既定のmodalでは、開いている間に周りが不活性になり、別の`Select`の取っ手や表示単位の選択肢、入力欄の押下が吸収されるため。modalでなくすことで、パネルの中でも、種別を開いているときに弓種を押すと、種別が閉じて弓種が開く。`Select`の一覧は`Dialog`より手前(`z-[60]`)に出る。
- 単位を検索で切り替えると、他の条件の変更と同じく表示済みを捨てて先頭から取得し直す。並べ替えの向き・期間・種別・弓種の値は、単位を切り替えても共通である。得点の範囲は単位ごとの値を持ち(「条件の定義」)、ラウンド構成と距離の指定は、使わない単位の間も入力値として保つ。距離単位では、得点の向きと得点の範囲が距離の小計を対象にする(「条件の定義」)。
- 点数カード(`round-cards.tsx`): ホームの入力中とラウンド単位の点数一覧は`RoundCards`、距離単位は`DistanceCards`が描く。枠・角丸・影・背景のない、行の境界の線(下側の1px)だけで区切る行の一覧で、リストは左右に12px(`-mx-3`)広げ、行の内容は本文の端にそろえる。各行は全体が1つのリンクで、押すと詳細へ移る(点数一覧の行は`?from=history`付き。ホームは付けない。`rounds/detail`)。押せる行は、hover(`bg-muted/60`)とキーボードの焦点(輪を内側に出す)で見た目が変わる。右端のメニュー(削除。`rounds/delete`)はラウンド単位だけで、距離単位は置かない。
  - 寸法: 行の高さは固定で、60px(上下の余白6pxと内側48px)に境界線1pxを足した61pxである。ラウンド名・距離の数・列の出し分けによらず変わらない。左右の余白は12px、要素の間は8px。高さと幅の値は`card-layout.ts`の`cardLayout`の数値の1か所に持つ(行の高さ60px、境界線1px、合わせて61px)。行、スケルトン(`RoundCardsSkeleton`)、末尾と0件の文言の領域(`RowNotice`)は、数値から`style`で高さを与え、クラス文字列を別に持たない。列の出し分けの計算(`card-columns.ts`)とページの件数の計算(`use-history-pages.ts`)も同じ数値を使う。スケルトンは単位によらず同じ形である。
  - スケルトン: 3行で、各行は読み込み後の行と同じ高さ(境界線を含めて61px。`cardLayout`の数値)・同じ左右の余白で、間隔は0である。各行は`data-testid="round-skeleton-row"`を持つ。行の構成を簡略に模し、左に太さの違う棒を2段、右端に棒を1本置く(タグの図形は作らない)。棒の大きさは`round-cards.tsx`の1か所に持つ。
  - ラウンド単位の行(左から): 左の塊、中央の距離一覧、縦線(1px)、合計点、メニュー。距離単位の行(左から): 左の塊、距離、縦線、小計。左の塊は同じで、上の段に「日付 ラウンド名」(`text-sm text-muted-foreground`。日付は`YYYY/MM/DD`。ラウンド名は日付の後ろに同じ文字で並べ、あふれると「…」で切る)、下の段に種別と弓種を別々の小さなタグ(11pxの`font-semibold`、`bg-muted`の角丸)で並べる。上の段(20px)と下の段(16px)は、行の上下に分けて置くため、ラウンド名が空でも日付とタグの位置は変わらない。n/Nは表示しない。
  - 日付: `formatCardDate`(`domain/round-date.ts`)が、ISO形式の`YYYY-MM-DD`の数字を、ロケールやタイムゾーンに頼らず「YYYY/MM/DD」(ゼロ埋めのまま)にする。形式に合わない値はそのまま返す。
  - 種別・弓種: 既存の表示名(`useOptionLabels`の`formatLabel`・`bowTypeLabel`)をタグにする。値はDBのCHECKで選択肢のどれかに限られ、未設定・nullはない。
  - 距離一覧(ラウンド単位。`DistanceStrip`): 距離ごとに1列で、射つ順(`compareDistancePosition`と同じ(`position_key`, `id`)の順)に並べ、列の間に薄い縦線(1px、`bg-border/50`)を引く。1列は幅38px(「100m」、7.5pxの「Unmarked」、4桁の小計が収まる値)で、段は、種別がフィールドのときだけ上段の「Marked」「Unmarked」(12px、7.5px)、距離(20px、`text-sm font-medium`)、小計(16px、`text-xs`、`tabular-nums`)の3段で、フィールド以外は距離と小計の2段である。全体は行の上下中央に置く。列の領域は全カード共通の固定の幅で右に寄せ、同じ列の数なら全カードで位置が縦にそろう。
  - 距離一覧の列の数: 最大4で、4・3・2のうち入る最大の数(「+N」の列も1つと数える)にする。2列でも入らなければ一覧を出さない。距離の総数が列の数以下なら全て出し、多ければ(列の数-1)個の距離と、最後の列に残りの距離の数「+N」(`historyDistancesRest`。段をまたいで上下中央)を出す。列の数は、日付の幅と固定の幅だけで決まり、ラウンド名・種別・弓種の内容に左右されないため、同じ画面の幅なら全てのカードで同じ数になる。距離が0件の行は一覧を出さない。
  - 距離の表示: 距離が判明していれば`{distance}m`(`historyDistanceMarked`)にする。種別がフィールドのときだけ、距離の上にMarked/Unmarked(`distanceMarked`・`distanceUnmarked`。省略しない)を添える。フィールドの無印で距離が無いときは、Marked/Unmarkedだけを出し、距離の段は空にする。フィールド以外はMarked/Unmarkedを出さない(Marked/Unmarkedを切り替えられるのはフィールドだけ。`rounds/setup`)。フィールド以外で距離が無いときも、距離の段は空にする。`useDistanceParts`が1か所で作り、距離一覧と距離単位の距離で同じである。
  - 距離単位の距離: 幅44pxの領域に右寄せで、`text-base`の距離と、フィールドのときだけ上にMarked/Unmarked(9px)を置く。縦線の右に小計を置く。
  - 合計点・小計: `text-lg font-semibold`の数字だけを、幅40pxの領域に右寄せで置く(「点」「小計」の文言を持たない)。ラウンド単位は、右端にメニューのアイコンの場所(20px)を空ける。
  - 列の出し分け(貪欲法): 優先順位の高い要素から順に、残りの幅に入るなら出し、入らなければその要素だけ出さずに次の要素を試す。順位は、ラウンド単位が合計点(メニューの場所とセット)、日付、距離一覧、ラウンド名、種別、弓種(種別が出ているときだけ)、距離単位が小計、日付、距離、ラウンド名、種別、弓種(同)である。ラウンド名は日付が出ているときだけ、最小幅(全角4文字分)に入るときに出し、残りの幅で「…」で切る。ラウンド名が空・距離が0件の行は、その要素を試さない。幅の基準値(固定のしきい値)は持たず、行の実際の幅から左右の余白を引いた幅と、測った文字の幅(日付は最も広い数字の基準「0000/00/00」、ラウンド名の最小は全角4文字、種別・弓種はタグの文字)と、固定の幅(`cardLayout.widthPx`)から、行ごとに計算する。計算は純粋な関数`selectCardColumns`(`card-columns.ts`)が持ち、測定は`useCardFit`(`use-card-fit.ts`)が行う。画面の幅のメディアクエリでなく行の幅で決めるのは、レフトパネルの開閉で同じ画面の幅でも行の幅が変わるためである。
  - 測定: `useCardFit`が、描画の前(`useLayoutEffect`)に行の幅と文字の幅を測り、行の幅の変化(`ResizeObserver`)とフォントの読み込み後に測り直す。測定の前(サーバーの描画、測定できない環境)は、合計点・日付・ラウンド名だけを出す(行の高さは固定なので変わらない)。
- 戻ったときの表示、端末での除外、0件の文言(`historyEmpty`)、続きの取得の扱いは、距離単位でもラウンド単位と同じである。末尾の文言は、距離単位だけ`historyEndDistance`にする。除外はラウンドのIDで行い、除くラウンドの距離は全て出さない。
- パネルが閉じている間は、未適用の編集を利用せず、入力値と導出されるフィルターは有効であり続ける。パネルを開くたびに、入力値(オフのときの絞り込む距離も含む)から編集中の値を作る。表示するラウンドは、開閉で変わらない。
- 種別と弓種は、それぞれ共通の`Select`(`components/ui/select.tsx`)の単一選択で、未選択の表示は「指定なし」(`null`)で、絞り込みなしである。`Select`の値は文字列のため、指定なしを表す定数の値を選択肢の1つとして渡し、`null`との写しは`history-nullable-select.tsx`(UI層。種別・弓種・得点順の3か所が使う`NullableSelect`)の1か所に置く。選択肢の表示名は画面の既存の表記(`formatOption`、`bowTypeOption`)を使う。点数一覧に「すべて」の選択肢は持たない。
- 絞り込みの期間は開始日と終了日の2つの日付の入力(`type="date"`)、得点の範囲は最低点と最高点の2つの数字の入力(項目名は「開始日」「終了日」「最低点」「最高点」)で、どれも空が指定なしである。得点の入力は`type="number"`にしない。`-`や`e`などの途中の入力はブラウザが空として返し、指定なしと区別できず、不正であることを示せないため、文字列として受けて検証する(数字キーボードは`inputMode="numeric"`で出す)。
- パネル内の値は、パネルの部品(`history-filter-form.tsx`)が1つの編集中の値(`HistoryFilterDraft`)としてまとめて持つ。種別・弓種・日付順・得点順・単位は入力値と同じ型の値、期間の2つの入力と、単位ごと(ラウンド・距離)の得点の2つの入力は入力途中の文字(`HistoryRangeDraft`)、ラウンド構成(`distances`)と絞り込む距離(`distanceRow`)は、距離のダイアログで確定した検証済みの行(`HistoryDistanceRow`の配列と、`HistoryDistanceRow`か`null`)である。単位を切り替えても、単位ごとの得点の入力途中の文字は編集中の値に残る。編集中の値は、パネルを開いたときに入力値から作り(`historyFilterDraftOf`)、閉じると破棄する。入力欄の部品(`history-range-fields.tsx`、`history-distance-fields.tsx`)は値を持たず、値を受けて変更を返すだけである(距離のダイアログだけは、確定までの入力の文字とエラーを自身の`useState`で持つ)。入力の欄を離れる(blur)・Enterでは検証も反映もせず、共通の`Input`の既存の規則(変換中でないEnterはフォーカスを外すだけ)のままである。入力の要素は取得の状態によらず同じ要素で描き続ける。
- 「検索」は、編集中の値を入力値に確定する。1つの処理(`historyInputOfDraft(draft, base)`。`base`は現在の入力値)が、既存の検証(`historyRangeOf`)を呼んで期間と、表示している単位の得点の範囲を検証する。もう一方の単位の得点の範囲は検証せず、`base`の値のまま入力値に残す(その単位を表示して検索するまで、編集中の文字は反映しない)。距離(ラウンド構成と絞り込む距離)は、ダイアログの確定のときに検証済みなので、検索では検証せず、そのまま入力値にする。範囲が正しければ、新しい入力値を返し、画面は入力値を更新して記憶へ書き、縦長ではパネルを閉じ、横長では開いたままにする。取得し直すかは、導出されるフィルターが変わるかで決まり(次の項)、使わない単位の得点の範囲・ラウンド構成・距離の指定だけを変えた検索では取得し直さない。範囲が不正なら、入力値を変えず、記憶へ書かず、取得もせず、パネルを開いたままにして、エラーを返す。エラーは該当の入力の近くに原因ごとの文言で出し(日付・得点の組の下)、入力した文字は直るまで残す。原因は、日付の不正、開始日が終了日より後、点数の不正、最低点が最高点より大きいの4つである。範囲のエラーは検索を押したときにだけ出し、入力を直したり別の操作をしても、次に検索を押すまで更新しない(直した欄のエラーも、検索を押すまで残る)。ただし、表示単位を切り替えるときは、得点の範囲のエラーを消す(切り替えた先の得点の欄は、エラーのない状態から始まる。期間は単位によらず共通なので、期間のエラーは残る。下書きの文字は残す)。距離のエラーも同じ規則で、距離のダイアログの確定のボタンを押したときにだけ出し、次にそのボタンを押すまで更新しない。リセットは編集中の値を既定(両単位の得点の範囲を空、ラウンド構成を空、絞り込む距離を指定なし)に戻し、範囲のエラーも消す。入力値は変えない。検索せずに閉じた変更とエラーは破棄される。
- 絞り込みのラウンド構成は、種別・弓種の下に置く、追加済みの距離の長方形(以下「距離のタイル」)と末尾の「距離を追加」の枠(以下「追加のタイル」)を、射つ順に横へ並べた1本の並びである。距離のタイルは、縦長の固定の大きさ(幅・高さとも定数として1か所で持ち、追加のタイルと共有する。幅は約80px、高さは3項目と余白が収まる約112px)の1つのボタンで、上から「距離」(`{distance}m`)、「射数/エンド」(`distanceArrowsPerEnd`。未指定は何も出さない)、「的」を、固定の位置に置く。的は全体像の図(`TargetFaceIcon`。48px)だけで、サイズ表記と中心の拡大図は出さず、未指定は`historyFilterNone`、見つからないとき(`missing`)は`targetFaceMissing`を、図と同じ48pxの高さの領域に収める(`overflow-hidden`、折り返す)。項目の有無でタイルの大きさと項目の位置は変わらない。矢の総数、総エンド数、Marked/Unmarked、右端の`ChevronRight`は持たない。追加のタイルは、同じ大きさの太めの破線の枠(`border-dashed`。太さ・濃さの値は実装で決める)に、枠線と同じ`ring`色の`Plus`のアイコンだけを中央に置き(文字は表示しない)、支援技術向けの名前として既存の`addDistance`(「距離を追加」)を持たせる(`sr-only`の文字か`aria-label`)。押すとタイルは編集のダイアログ、追加のタイルは追加のダイアログを開く。最初は距離のタイルがなく、追加のタイルだけがある。並べ替えの操作はない。並びは、`flex`の1行(折り返さない)で、タイルは縮まない(`shrink-0`)。並びの要素だけが`overflow-x-auto`(`overscroll-x-contain`)で横にスライドし、並びの入れ物は`min-w-0`でパネルの入力欄の幅に収まるため、ページやパネルは横にあふれない。フォーカスの輪が切り取られないよう、並びに輪の分の内側余白を持たせる。タイルの大きさが固定で、パネルの中身も開いたときの幅に固定されている(上記「開閉の間の中身」)ため、開閉の間に並びの折り返しや大きさは変わらない。
- 距離のダイアログ(`history-distance-dialog.tsx`。UI層): 入れ子の`Dialog`(`DialogContent`の`nested`。名前は`DialogTitle`を`sr-only`で持つ)。項目は、「距離(m)」(必須。文字列で受け`inputMode="numeric"`、`type="number"`にしない)と「射数/エンド」(空可。同じく文字列)を同じ行に2列の等幅(`grid grid-cols-2`。各欄は`min-w-0`、行は`items-start`)で横に並べ、その下に「的」(既定「指定なし」。的の選択はさらに入れ子の`Dialog`)を置く。エラーは各欄の下に出るため、片方だけ、または両方に出ても、ラベルと入力欄は行の上端に揃ったまま動かず、エラーの文は欄の幅の中で折り返す。追加(ラウンド構成)の確定のボタンは「追加」、選択(距離単位)は「決定」、編集は「確定」と「削除」(削除に確認はなく、距離単位ではこれが指定を外す操作)。ダイアログは、開くときに(追加・選択は空の値と的「指定なし」、編集は押した距離の値)から入力の文字と的を作り、これを自身の`useState`で持つ。確定のボタンで`historyDistancesOf`(1行)を呼んで検証し、正しければ`onConfirm(row)`を呼んで閉じる(呼び出し側が編集中の値の`distances`に追加・置換する)。不正なときは閉じず、欄の下にエラー(距離の不正、射数/エンドの不正)を出し、次に押すまで更新しない。Esc・外側のタップで閉じると入力を破棄し、呼び出し側の値は変わらない。編集は、位置(配列の添字)で対象を特定し、置換しても射つ順は変わらない。
- 的は、距離のダイアログの欄で、最初から領域を確保し、未指定のときは「指定なし」(既存の`historyFilterNone`)を表示する。領域は的の情報(`TargetFaceInfo`)の実寸(幅127px、高さ48px。周りに余白と枠)の入れ物(`history-target-selection.tsx`の`TargetSlot`。点数一覧専用)で、的の情報、的が見つからない表示(`missing`)、未指定の「指定なし」は全てその入れ物に入れるため、的を選んでも、的が見つからなくても行の大きさが変わらない。`TargetFaceInfo`は他の画面と共有するため変更しない(寸法を持たせない)。トリガーは`buttonVariants`を使わない(使うと中のSVGが16pxに縮む)。指定済みなら選んだ的(`TargetFaceInfo`)を同じ領域に表示する。「的を加える」「的を外す」は廃止する。領域を押すと、的の選択の一覧(`TargetFacePicker`と同じ一覧と種別・弓種の選択欄(`TargetFaceFilters`))を入れ子の`Dialog`(`DialogContent`の`nested`)で開く。一覧の先頭の項目として、的の各項目と同じ大きさ・同じ枠(選択中は同じ見せ方)で「指定なし」(`TargetSlot`に入れた「指定なし」。種別・弓種の`NullableSelect`と同じ語)を置き、選ぶと的が`null`になる。選択欄の既定は、下書きの種別・弓種(指定していなければ「指定なし」)である。`TargetFaceChoice`は`onSelect(id: string | null)`とし、`TargetFaceList`は任意の`none`(先頭の項目の表示・testId・選択時の処理)を足す(渡さなければ従来どおり)。ダイアログ内の的の選択欄は変えない。距離のタイルの的は、この領域とは別で、全体像の図だけを持つ。トリガーの支援技術向けの名前は欄の`label`との関連付けによる「的」で、指定の状態と操作は`sr-only`の要素を`aria-describedby`で参照して伝える。説明の文言と一覧の候補の的の説明は`rounds`の共通設計(`../design.md`の「的の識別と選択」)に従う。
- 的の一覧は、端末に保存した的の一覧(`savedTargetFaces`。同期の一括の取得が保存する)を、欄の部品が表示の開始後に読んで使う。点数一覧のために的を取得しない。保存した一覧が無いときは空の一覧として扱い、的を選べない(「指定なし」は選べる)。指定済みの的が一覧に無いとき(的の削除後、一覧が無いとき)は、既存の的が見つからない表示(`TargetFaceInfo`の`missing`)を出し、条件はそのまま検索し続ける。「指定なし」で外せる。
- ラウンド構成の入力は、検証済みの行(`distances`)を、パネルの編集中の値が持つ。距離のダイアログの確定(追加・置換・削除)は編集中の値だけを変え、入力値へ反映しない。反映は「検索」のときだけである。空の行、空の行の自動追加、検索の時に空の行を捨てる処理、行の削除のゴミ箱は持たない。行の数は0件以上で、上限は設けない。
- 距離単位の絞り込む距離は、単位が距離のときだけ、ラウンド構成と同じ位置に出る。未指定(`distanceRow`が`null`)なら「距離を選択」のボタン(追加のタイルと同じ大きさ・同じ高さ・同じ見せ方(太めの破線、枠線と同じ`ring`色の`Plus`)の枠に`Plus`のアイコンだけを置き、文字は表示せず、支援技術向けの名前として`historyFilterDistanceSelect`(「距離を選択」)を持たせる。押したときの挙動は従来どおり)、指定済みなら距離のタイル1件(ラウンド構成と同じ部品)を出し、押すと同じ距離のダイアログが編集として開く(「確定」で置換、「削除」で`null`に戻して「距離を選択」に戻る)。追加のタイルはない。部品はラウンド構成の部品と同じ(タイル・ダイアログ)で、1件に固定する。単位がラウンドの間は、指定した距離を入力値に残すが、出さず、取得にも渡さない。単位が距離の間のラウンド構成も同じく、入力値に残すが、出さず、取得にも印にも使わない。
- 画面を開いた直後、フィルターは閉じている。開閉は記憶しない。
- 先頭のページの取得は、表示の開始時(保存した条件を読んだ後。戻ったときの表示の記憶を使うときは行わない)と条件の変更(検索)のたびに行い、表示済みのページを捨ててスケルトンにする。再試行ボタンを押すとスケルトンになる。
- 続きの取得は、続きがあり、続きの取得が中でも失敗(オフライン・エラー)でもないときに、一覧の末尾(続きの取得の状態を出す場所)がスクロールの入れ物の下端から1画面分(入れ物の高さ)の距離に入ると、自動で1ページ行う(`IntersectionObserver`。`root`はスクロールの入れ物、`rootMargin`は下へ入れ物の高さ分)。`root`を既定(ビューポート)にすると、先祖の`overflow`の切り取りで末尾が入れ物の中に見えるまで交差せず、先読みが効かないため、入れ物を`root`にする。同時に2つ以上の取得はしない。
- 続きの取得が成功した後も一覧の末尾がその距離にあれば、次のページを続けて取得する。除外で表示0件のページが続いても、利用者の操作なしに続きへ進む。連なる取得は、末尾が画面から離れるか、続きがなくなると止まる。
- 続きの取得が失敗すると自動の取得を止め、スクロールや末尾の出入りでは取り直さない。取り直すのは再試行ボタン(同じ起点。表示済みを残す)だけで、通信が戻っても自動では取り直さない。成功すると自動の取得に戻る。
- 条件の変更、再試行、離れたことで古くなった取得の結果は捨てる(捨てないと、前の条件のページが新しい条件の表示に連結されるため)。
- 続きがないときは取得しない。表示が1件以上なら末尾に`historyEnd`(距離単位は`historyEndDistance`)を出す。
- 取得が成功していても、端末の入力中を読み終えるまでは取得中として扱う。
- 取得結果から除くのは、端末の入力中のID、各ページの取得時に端末の記録から求めた削除済みIDの和、この画面で削除したラウンドのIDである。除外は取得した全ページに表示のたびに行い、条件によらない。除外で1ページの表示件数が減ってもよい。他の端末で完了して端末に未取り込みのラウンドは、端末の入力中に残るため、同期が反映するまで点数一覧に出ない(ホームと二重にしないため)。
- 点数一覧のカードのメニューと削除の確認は、ホームと同じである。
- 未認証のアクセスは`proxy.ts`が`/signin`へ送る。この挙動は一覧の要求に含めない。

## 構成とデータの流れ

パスは、断りがなければ`apps/web/src/`からの相対である。

### 条件の定義

何で並べ、何で絞るか。取得の形(どこで絞るか)から独立した、純粋な規則である。

- 入力値(`HistoryInput`)は、画面が持ち保存する唯一の状態である。形は条件(`HistoryCondition`)の項目に、距離単位(小計)の得点の範囲の2項目(`distanceScoreMin`・`distanceScoreMax`)を足したもので、全て検証済みの値である。入力値の`scoreMin`・`scoreMax`はラウンド単位(合計点)の範囲であり、条件の`scoreMin`・`scoreMax`は表示中の単位の範囲である。条件との違いは、導出で、得点の範囲を単位のものにし、単位が`round`のときは`distanceRow`を`null`に、単位が`distance`のときはラウンド構成を空にする点である。旧案の`distanceRowInput`(文字の配列)は持たない。
- 導出されるフィルターは、入力値から一意に導く条件(`HistoryCondition`)で、関数`historyConditionOf(input)`が作る。取得へ渡す引数(`round-queries.ts`の引数の組み立て)、取得の組の識別(`use-history-pages.ts`の`JSON.stringify(condition)`)、適用中の印(`isDefaultHistoryCondition`)に使う。入力値の項目を写し、`scoreMin`・`scoreMax`は、単位が`distance`のとき`distanceScoreMin`・`distanceScoreMax`から、`round`のとき入力値の`scoreMin`・`scoreMax`から取り、単位が`round`のときだけ`distanceRow`を`null`に、単位が`distance`のときだけラウンド構成(`distances`)を空にする(検証は要らない)。このため、距離単位の取得は`p_distances`を送らず、ラウンド単位の取得は`p_distance`を送らず、使わない単位の値の変更は取得の組の識別を変えない。条件(`HistoryCondition`)は距離単位の範囲の2項目を持たず、取得の組の識別は条件から決まるため、使わない単位の値は識別に入らない。入力値が同じなら導出されるフィルターは常に同じで、別の状態としては持たない(画面の部品は入力値から`useMemo`で導き、値が同じなら同じ内容として扱う)。導出されるフィルターが変わらない検索は、取得の組の識別が変わらないため、取得し直さない。
- 条件(`HistoryCondition`)は、並べ替えの向き(日付の向き`dateDirection`: `asc`か`desc`、得点の向き`scoreDirection`: `asc`か`desc`か指定なし`null`)、種別(`FormatOption`か指定なし)、弓種(`BowTypeOption`か指定なし)、期間(開始日`dateFrom`、終了日`dateTo`)、得点の範囲(下限`scoreMin`、上限`scoreMax`)、ラウンド構成(`distances`)、単位(`unit`: `round`か`distance`)、距離の行(`distanceRow`: `HistoryDistanceRow`か`null`)の組である。日付の向きは必ず指定される。種別・弓種はそれぞれ1つだけ選べる。複数選択と、日付・得点以外の組の複合ソートは持たない。
- 期間と得点の範囲は、反映済みの値だけを持つ(常に正しい)。期間の開始日`dateFrom`と終了日`dateTo`は`YYYY-MM-DD`か`null`で、単位によらず共通である。得点の下限`scoreMin`と上限`scoreMax`は`0`以上の安全な整数(`Number.isSafeInteger`)か`null`で、`null`が指定なしである。得点の範囲は、入力値ではラウンド単位(`scoreMin`・`scoreMax`。合計点が対象)と距離単位(`distanceScoreMin`・`distanceScoreMax`。距離の小計が対象)で別々に持ち、条件は導出で単位の範囲だけを持つ。不正な入力は条件に入らない。
- 欄の下書き(`HistoryRangeDraft`: 4つの入力途中の文字列)の検証`historyRangeOf(draft)`が、正しければ4つの値(上の型)、不正なら原因の一覧を返す。原因は、日付の不正(`YYYY-MM-DD`の実在する日付でない)、開始日が終了日より後、点数の不正(前後の空白を除いてASCIIの`0`〜`9`だけでない、または安全な整数を超える。全角数字、符号(`+`、`-`)、小数点、指数は不正で、先頭の`0`は許し`007`は7である)、下限が上限より大きい、の4つである。空(空白だけを含む)は指定なしで、両端の大小は、両方が指定されていて、その値が正しいときだけ比べる。同じ値(開始日と終了日が同じ日、下限と上限が同じ点)は正しい。
- ラウンド構成(`distances`)は、射つ順の行(`HistoryDistanceRow`)の配列で、空の配列が指定なしである。行は、距離`distance`(1〜100の整数)、射数/エンド`arrowsPerEnd`(1〜12の整数か`null`)、的`targetFaceId`(的のIDか`null`)を持ち、`null`が指定なしである。値の上限は`DISTANCE_LIMITS`の値を使う。行の数に上限はない。反映済みの値だけを持ち、不正な入力は条件に入らない。
- ラウンド構成の行の検証`historyDistancesOf(draft)`(既存。距離のダイアログが1行の配列で呼ぶ)が、正しければ行の配列、不正なら行の位置と原因の組の一覧を返す。入力は、行ごとの2つの文字列(距離・射数/エンド)と的のIDか`null`(`HistoryDistanceDraftRow`。ダイアログの入力だけが使い、編集中の値・入力値は持たない)。数値の読み方(前後の空白を除き、ASCIIの`0`〜`9`だけ、安全な整数)は得点と同じで、その上で範囲を比べる。距離の空は不正、射数/エンドの空は指定なしである。
- 距離の行(`distanceRow`)は、ラウンド構成の行と同じ型(`HistoryDistanceRow`)・値の範囲・検証を使い、`null`が指定なしである。入力値が持ち、導出されるフィルターは単位が`distance`のときだけ値を持つ。
- 既定は、ラウンド単位・日付の向き降順・得点の向き指定なし・種別と弓種と期間と両単位の得点の範囲とラウンド構成と距離の行の指定なしである。表示の状態(`HistoryViewState`)は、入力値だけを持つ(`{ input }`)。導出されるフィルターは状態に含めない。パネルの開閉は保存しない。
- 絞り込みは、指定がある属性だけを比べ、全ての指定に一致するラウンドを残す。期間は実施日が開始日以上・終了日以下、得点の範囲は合計点が下限以上・上限以下である(境界を含む)。ラウンド構成は、ラウンドの無効でない距離の行を(`position_key`, `id`)の順に並べたものが、指定の行と同じ個数で、先頭から順に各行が一致することである。行の一致は、距離が判明していて(`is_marked`)距離が等しく、指定のある項目(射数/エンド、的)も等しいことである。
- 並びの規則: 得点の向きが指定されているときは、点数一覧のカードに出す合計点を第1キー(向きは得点の向き)、実施日を第2キー(向きは日付の向き)とする。得点の向きが指定なしのときは、実施日だけを第1キー(向きは日付の向き)とする。同値は、作成時刻の新しい順、IDの昇順に並べる。同値の並びは向きによらず、再読み込みしても変わらない。
- 距離単位の件は、完了したラウンドの無効でない距離である。無効な距離、無効な矢は出さず数えない。距離なしの距離と矢の無い距離も出し、小計は0である。小計は、詳細の距離結果の小計と同じく、その距離の無効でない矢の`score_int`の和である。
- 距離単位では、得点の向きと得点の範囲は距離の小計を、日付の向き・期間・種別・弓種は距離が属するラウンドを対象にする。ラウンド構成は距離単位では使わない(画面は`p_distances`を送らない)。距離の行は、その距離が「行の一致」を満たすことで、距離なしの距離は一致しない。並べる値が同じ距離は、属するラウンドについてラウンド単位と同じ順(作成時刻の新しい順、IDの昇順)に並べ、同じラウンドの中は射つ順(`position_key`, `id`)に並べる。
- 絞り込みと並びの規則の持ち主は、サーバーの履歴の関数(`rounds_list`、`distances_list`)と、2つが読むラウンドの条件の関数(`history_rounds`)だけである。端末は条件を渡し、並べ直さない。
- 保存した値の検証(`historyViewStateOf`)は、未知の値や形の崩れを既定に直す。並べ替えは、保存した値の`dateDirection`・`scoreDirection`を項目ごとに読み(日付の向きは`asc`・`desc`以外か無いときは`desc`に、得点の向きは`asc`・`desc`以外か無いときは指定なしにする)。日付は実在する`YYYY-MM-DD`でなければ`null`に、得点は`0`以上の安全な整数でなければ`null`にする。開始日が終了日より後、下限が上限より大きいときは、その組の両方を`null`にする。得点の範囲は、保存した値の`scoreMin`・`scoreMax`(ラウンド単位)と`distanceScoreMin`・`distanceScoreMax`(距離単位)を、それぞれ同じ規則で直す。直す単位は項目で、範囲だけが壊れても、並べ替えの向き・種別・弓種は残す(既存の、未知の値をその項目だけ既定に直す扱いと同じ)。保存した値に期間と得点の範囲の項目が無いときは、`null`(指定なし)にする。距離単位の得点の範囲の項目が無いときは、ラウンド単位の範囲を読み、距離単位の範囲を指定なしにする。ラウンド構成は1つの項目として直し、配列でない、どれかの行が上の型に合わない(的のIDがUUIDの形でないことを含む)、または項目が無いときは、空の配列(指定なし)にする。単位は`round`と`distance`以外か無いときは`round`に、距離の行はラウンド構成の行と同じ検査に合わないか無いときは`null`にする。このため、不正な条件が条件・記憶・取得の組に入ることはない。
- 保存した値は入力値の形で読む(`historyViewStateOf`)。ラウンド構成(`distances`)は検証済みの行の配列、絞り込む距離は`distanceRow`(検証済みの行か`null`)として読み書きする。項目が無いときは指定なしとする。型に合わない値(行の項目が型・範囲に合わない、的のIDがUUIDの形でない、配列でない)は捨てて既定(ラウンド構成は空の配列、距離の行は`null`)にし、未知の項目は読まない。

### 取得の形

どこで絞り、どこで並べ、どこで切り出すか。

- 履歴の取得は、条件と続きの起点と件数を渡して、1ページずつ行う。先頭のページは起点なしで取得する。
- 1ページの件数は、取得のたびに、画面の高さで2画面分を埋める件数(画面の高さ ÷ 1件分の高さ × 2 の切り上げ)を、10〜50件(`HISTORY_PAGE_SIZE_MIN`、`HISTORY_PAGE_SIZE_MAX`)に収めて決める(`historyPageSizeOf`)。2画面分は、続きの取得を始める距離(1画面分)を1回の取得で越えるためである。画面の高さが0以下のときは下限にする。
- 1件分の高さは、行の固定の高さ(境界線を含めて61px。`cardLayout`の数値)で、行の間隔は0である。`use-history-pages.ts`が、この数値と画面の高さ(`window.innerHeight`)から件数を決める。
- 件数がページごとに違っても、起点はIDで決まるため、境界で重複・抜けは出ない。
- 返すのは、各ラウンドのID・名前・実施日・種別・弓種・合計点と、距離ごとの距離・無印か・小計(射つ順)、続きの有無だけである。作成時刻、各射の点、総件数は返さない。
- 距離単位で返すのは、各距離のID、属するラウンドのID・名前・実施日・種別・弓種、距離、無印か(`is_marked`)、小計と、続きの有無だけである。射数/エンド・エンド数・的、矢、総件数は返さない。
- 続きの起点は、直前のページでサーバーが返した最後のラウンドのID(除外の前の行)である。距離単位では最後の距離のIDで、サーバーはその距離の行と属するラウンドから並びの値を引く。サーバーはそのIDの行から実施日・作成時刻・合計点を引き、それより後のラウンドを返す(キーセット)。論理削除しても行は残るため、起点のラウンドが他の端末で削除・完了の取り消しをされても引ける。
- 結果: 他の端末での完了・削除で境界の前後の行が増減しても、重複・抜けは出ない。読み進める間に、他の端末で続きの起点のラウンドの実施日か合計点が変わったときだけ、次のページで行が抜けるか重なる。重なりは連結で除くため表示されず、抜けは要件の例外として許容する(点数一覧を開き直すと正しく並ぶ)。
- 端末は、受けたページをIDで重複を除いて連結する(`appendRoundsList`)。他の端末での変更で境界がずれても、同じラウンドを2回出さない。距離単位の項目のIDは距離のIDで、項目は属するラウンドのIDも持つ。重複の除去と起点は項目のID、端末の除外は属するラウンドのIDで行う。単位を変えると表示済みを捨てるため、1つの一覧に2つの単位の項目は混ざらない。
- 端末だけが持つ除外は、サーバーへ渡さず、連結した全ページに表示のたびに行う(「画面と状態」)。
- 条件の変更は履歴の取得を起こすが、同期(一括の取得)は起こさず、ホームに影響しない。
- 点数一覧の表示の決定(`historyView`)は、連結したページから除外したラウンドと、続きの有無を返す。ラウンドの削除は除外の集合へ足すため、表示からも消える。

#### 履歴の関数(`rounds_list`)

- `SECURITY INVOKER`の読み取り専用(`STABLE`)の関数で、呼び出し元の権限で`rounds`等を読む。取得できるラウンドは、RLSの`select_if_member`により、ユーザーが`round_users`で属するものに限る。実行権限は`authenticated`だけに与える。
- 対象のラウンドは、呼び出し元の所属(`round_users`の`user_id = auth.uid()`の行)から`rounds`を引いて求める(「索引とRLSと条件の評価の順」)。所属から引く形とラウンドの条件は、ラウンドの条件の関数(`history_rounds`)が持ち、`rounds_list`はその結果を読む。これは読む範囲を利用者のラウンドに狭めるためで、認可ではない。認可はRLSのままで、結んだ`round_users`と`rounds`もRLSを通して読む。RLSで見えるラウンドは所属のあるラウンドと同じ集合のため、結果は変わらない。続きの起点の行は、所属から引かず、IDから引く(変えない)。
- 引数は、日付の向き`p_date_direction`(`text`。`asc`以外は降順として扱う)、得点の向き`p_score_direction`(`text`。`asc`・`desc`以外(`null`を含む)は指定なし)、種別、弓種(どちらも`null`は指定なし)、続きの起点のID(先頭は`null`)、件数、期間の開始日`p_date_from`と終了日`p_date_to`(`date`)、得点の範囲の下限`p_score_min`と上限`p_score_max`(`bigint`)、ラウンド構成`p_distances`(`jsonb`)である。期間・得点の範囲・ラウンド構成は末尾に置き、既定値を`null`(指定なし)にする。追加の絞り込みは、引数を足して表す。
- `p_distances`は、射つ順の行の配列`[{ distance, arrows_per_end, target_face_id }]`で、指定のない項目は`null`(鍵が無くても`null`として扱う)である。
- 期間は`rounds.round_date`が開始日以上・終了日以下、得点の範囲は合計点が下限以上・上限以下のラウンドに絞る(境界を含む)。合計点は並べ替え・返す値と同じ1つの値を使う。続きの起点の行は、条件に関わらずIDから引く。
- ラウンド構成は、対象の各ラウンドについて、無効でない(`disabled_at is null`)距離に(`position_key`, `id`)の順で番号を振り、`p_distances`の要素の番号(`with ordinality`)と結んだ副問い合わせで判定する。距離の行の数が`p_distances`の要素の数と等しく、全ての行が「条件の定義」の行の一致を満たすラウンドだけを残す。距離が0件のラウンド、行の比較が`null`になる場合(距離なしの行など)は一致しない。この判定は、種別・弓種・期間・完了の判定と所属から引く形とともに、ラウンドの条件の関数(下記)が持つ。列・ビューは持たない。
- 結果(性能): 判定はラウンドごとに、そのラウンドの距離の行を読み、`p_distances`を展開して番号で結ぶ。`p_distances`の展開はラウンドごとに行うため、処理量は理屈の上では対象のラウンドの数×指定の行の数に比例して増える。行の数に上限はない。
  - 計測(事実。ローカルのPostgreSQL 16、RLSなし、合成データ: 完了したラウンド2000件、各4行の距離、各36本の矢、`distances(round_id)`の索引なし): 判定だけの問い合わせは、指定の行が4・100・1000・10000行のどれでも約1.3秒で、行の数による差は測れなかった。判定の費用の大半は、ラウンドごとの`distances`の全件の走査(索引が無いため)だった。この走査は`distances(round_id)`の索引で除いた(「索引とRLSと条件の評価の順」)。
  - 本番の件数・RLSを含めた時間は確かめていない。指定の行の数で重くなる傾向は、上の範囲では見られない。`p_distances`を1度だけ展開する形は、遅さが問題になったときに検討する(今は持たない)。
  - `rpc`の引数は要求の本文(POST)に載るため、行の数はURLの長さの制限を受けない。
- 対象は`disabled_at is null`かつ`status = 'completed'`のラウンドで、条件で絞り、「条件の定義」の並びにする。件数+1件を読み、件数を超えれば続きありとして件数分だけ返す。
- 合計点の規則: ラウンドの無効でない(`disabled_at is null`)距離の、無効でない矢の`score_int`の総和で、矢が無ければ0である。ホームの入力中のラウンドの合計点(端末で求める)と同じ規則である。並べ替え・起点の比較・返す値は、この1つの値を使う。
- 合計点は、`rounds_list`の中で、対象の各ラウンドについて`distances`と`shots`を結んだ副問い合わせ(`coalesce(sum(...), 0)`)で求める。列・ビュー・別の関数は持たない。呼び出し元の権限で動くため、`distances`と`shots`もRLS(`select_if_member`)を通して読む。所属するラウンドの距離・矢は全て読めるため、合計点は欠けない。
- 結果(性能): 並べ替えの基準によらず、条件に一致する全ラウンドの合計点を、ページの取得のたびに求める。DBの処理量は、その利用者の完了したラウンドの矢の総数に比例する。矢はRLSを通して読み、`shots`の`select_if_member`は行の`round_id`を`member_round_ids()`の結果と照合する。この関数はポリシーを適用する箇所ごとに1回実行し、矢の行ごとの距離の参照と関数の呼び出しは無い(計測は「索引とRLSと条件の評価の順」)。変更前の取得は、開くたびに全ラウンドの全ての矢の行をDBから読み、端末へ転送していた。変更後は、DBで読む行は同じ程度で、転送は1ページ分になる。このため、変更前より悪くならないとして許容する。続きのページでも同じ量を読む点は、読む範囲が利用者1人が属するラウンドに限られるため許容する。日付順でだけ返す行に絞ってから求める工夫や、集計列は持たない(遅さが問題になったときに足す)。
- Issue #386 の論点との関係(事実):
  - 一覧が矢の行を転送しないこと: `rounds_list`が合計点だけを返すことで満たす。合計点が要る一覧は点数一覧だけで、ホームは端末の記録から求め、サーバーから取得しない。
  - PostgRESTの集約関数と`db_aggregates_enabled`の有効化: 使わない(並べ替えに使えず、集計は`rounds_list`の中のSQLで行うため)。`supabase/config.toml`も変えない。
  - 詳細画面の都度の集計: 対象外。詳細はスコアカードに矢を1本ずつ表示するため矢の行を取得し、エンドの小計・距離計・合計を端末で求める(`scorecard-scoring.ts`)。矢の行の転送は表示に必要で、集計だけをDBへ移しても転送は減らない。
- 引数を検証しない。結果: 未知の基準・向きは既定(日付の降順)の並びになり、件数は呼び出し元が決めた値のまま返す。開始日が終了日より後、下限が上限より大きい指定は、該当なしの0件を返す。`p_distances`の空の配列は0件を返し、UUIDでない的のIDや整数でない値はDBが型のエラーにするが、画面は1行以上の検証済みの行しか渡さない。返るのは呼び出し元が属するラウンドだけで、画面は検証済みの条件と10〜50件しか渡さないため、許容する。点数の型が違う値(整数でない数)はDBが型のエラーにするが、画面は検証を通した整数しか渡さない。起点のIDの行が見えないときは、続きなしの0件を返す(所属を外す経路は現状ない)。
- 並びは第1キー`v1`、第2キー`v2`、作成時刻の新しい順、ID(距離単位はさらに射つ順)で決め、起点との比較も同じ鍵で行う。`v1`は得点の向きがあれば合計点×向き、なければ実施日×日付の向き、`v2`は得点の向きがあれば実施日×日付の向き、なければ`0`とする。
- 期間と得点の範囲の4引数は、指定がある(`null`でない)ものだけを送る。ラウンド構成は行が1つ以上のときだけ`p_distances`を送り、指定のない引数で通信量を増やさない。
- 戻り値は`jsonb`の`{ rounds: [{ id, name, round_date, format, bow_type, total, distances: [{ distance, is_marked, total }] }], has_more }`である(「カードの項目の取得」)。`ServerRoundSummary`は行の列を生成型(`rounds`、`distances`)から導き、合計点と距離ごとの小計だけを足す。画面の名前への写しは`roundListItemOf`の1か所である。

#### ラウンドの条件の関数(`history_rounds`)

- 呼び出し元の所属(`round_users`の`user_id = auth.uid()`の行)から引いた`rounds`のうち、ラウンドの条件(無効でない、`status = 'completed'`、種別、弓種、期間、ラウンド構成)に一致する行を返す関数で、5つの条件の引数(`p_format`、`p_bow_type`、`p_date_from`、`p_date_to`、`p_distances`)を受ける。`rounds_list`と`distances_list`が対象のラウンドとして読み、ラウンドの条件の規則と、所属から引く形の持ち主はこの関数だけである。得点の範囲は単位で対象が違うため、ここに含めない。
- `SECURITY INVOKER`、`STABLE`の`sql`の関数で、`setof rounds`を返す。読む表はRLSを通る。呼び出し元の権限で動く関数から読むため、`authenticated`に実行権限が要る(無いと`permission denied for function`になる)。結果: PostgRESTから直接呼べる関数が1つ増えるが、返すのは呼び出し元がRLSで読める`rounds`の行だけで、`rounds`を直接読むのと範囲は同じである。`PUBLIC`・`anon`からは取り消し、`rls_matrix.sql`の実行権限の期待値表、`rpc_matrix.sql`の例外、`docs/security.md`に載せる(`distances_list`も同じ)。
  - 変更範囲: `rls_matrix.sql`の期待値表(`rls_fn_expected`)に、`history_rounds`と`distances_list`の行を`authenticated`は`true`、`anon`は`false`で足し、期待値の方針の注記に「履歴の取得(`rounds_list`、`distances_list`)と、それが読むラウンドの条件の関数(`history_rounds`)」を加える。表に無い関数と`PUBLIC`のEXECUTEは、既存の網羅性の検証が落とす。
  - テストの観点: `history_rounds`を`authenticated`で直接呼ぶと、属するラウンドのうち条件に一致する行だけが返り、属さないラウンドは返らない(代理の人として属するラウンドは返る)。返る行のIDの集合が、同じ条件で`rounds`を直接読んだ結果と一致する。`anon`は実行できない。
- `SET search_path`を付けない。付けると呼び出し元へ展開(インライン化)されず、関数の結果を別に作ってから読むため遅くなる(下の計測)。付けないと展開され、実行計画は`rounds_list`の中に条件を直接書いた形と同じになる。代わりに、本文の表と関数の名前を`public.`・`auth.`で修飾する。リポジトリの他の関数は全て`SET search_path`を付けており、この関数だけが例外である(「設計判断」)。
  - 例外の理由: 展開させ、取得の計画と時間を、条件を`rounds_list`に直接書いた形(#782)と同じに保つため。展開には`SET`句が無いことが要る。
  - 例外の範囲: `history_rounds`の1つだけである。`SECURITY INVOKER`の読み取り専用(`STABLE`)の関数で、呼び出し元の権限で動くため、`search_path`を変えられても権限は上がらない。本文の表・関数は全て`public.`・`auth.`で修飾し、修飾しない名前を持たない。`rounds_list`・`distances_list`を含む他の関数は`SET search_path`を付ける。
  - 変更範囲: 新しい`SECURITY DEFINER`の関数や書き込みの関数には、この例外を広げない。`SET search_path`を付けない関数を足すときは、展開が要ることを計画で確かめ、この節に加える。
  - テストの観点: `rounds_list`の結果が、関数に切り出す前と同じであること(既存の`rounds_list.sql`が変更なしで通ること、使い捨てのDBでの全ページの照合)。`history_rounds`の`proconfig`が空で、本文に修飾しない表名が無いことは、レビューで確かめる。
- 続きの起点の行は、どちらの取得の関数も条件と所属に関わらずIDから引くため、この関数を通さない。

#### 距離単位の履歴の関数(`distances_list`)

- `rounds_list`と同じく、`SECURITY INVOKER`の`STABLE`の関数で、実行権限は`authenticated`だけに与える。引数は`rounds_list`の11個と同じ並びに、距離の行`p_distance`(`jsonb`。`p_distances`の要素と同じ形の1つのオブジェクト。既定値`null`)を末尾に足したものである。
- ラウンドの条件の関数が返すラウンドの無効でない距離を件とし、`p_distance`の行の一致と、得点の範囲(小計が対象)で絞り、「条件の定義」の並びにする。同じラウンドの距離は(`position_key`, `id`)の順に並べる。小計は、各距離について`shots`を読む副問い合わせで求める(合計点と同じく、列・ビューを持たない)。起点は距離のIDで、距離の行と属するラウンドから、条件に関わらず引く。件数+1件の読み方、引数を検証しないことは`rounds_list`と同じである。
- 同値の並びのうち、ラウンドの鍵(実施日の新しい順、作成時刻の新しい順、IDの昇順)と並べる値の式(得点の向きによる第1キーと第2キー)は、`rounds_list`と同じ式を持つ。距離単位は最後に(`position_key`, `id`)を足す。起点との比較は鍵の数が違うため、関数ごとに持つ。
- 戻り値は`{ distances: [{ id, round_id, name, round_date, format, bow_type, distance, is_marked, total }], has_more }`である(`id`は距離のID、`total`は小計)。型は行の列を生成型(`distances`、`rounds`)から導き、小計だけを足す。画面の名前への写しは1か所に置く。
- 画面は、単位が距離のときだけこの関数を呼び、`p_distance`は行があるときだけ送る。他の引数の送り方は`rounds_list`と同じである。
- 結果(性能): 距離単位も、ページの取得のたびに条件に一致するラウンドの全ての距離の小計を求めるため、DBの処理量は合計点と同じく、その利用者の完了したラウンドの矢の総数に比例する。矢の閲覧の判定も合計点と同じである(「索引とRLSと条件の評価の順」)。

#### カードの項目の取得(`rounds_list`・`distances_list`の戻り値)

- カードの項目: `rounds_list`の各ラウンドに`format`、`bow_type`、`distances`(無効でない距離を(`position_key`, `id`)の順に並べた`[{ distance, is_marked, total }]`。`total`は無効でない矢の`score_int`の和で、矢が無ければ0)。`distances_list`の各件に`format`、`bow_type`。ラウンドごとに、`distances`の`total`の和は`total`と等しい。距離一覧の列の数を超える距離の切り詰めは画面で行い、サーバーは全ての距離を返す(ホームの端末の導出と同じ規則を画面の1か所に置くため)。
- 距離ごとの小計は、ページに入る行(件数分。続きの有無の確認の1件を除く)についてだけ、対象のラウンドの距離と矢から求める。並べ替え・絞り込みのための合計点・小計の求め方は変えない。RLSは今までどおり`distances`・`shots`の`select_if_member`を通す。
- 結果(性能): 追加の読みはページの件数分の距離と矢だけで、全ラウンドの合計点を求める読みは変わらない。合成データ(矢約30万本)の計測でも、`rounds_list`の時間に差は測れなかった。`distances_list`は、種別・弓種の2列を足すだけで、読む行は増えない。

#### 索引とRLSと条件の評価の順

取得の時間を抑え、矢のRLSの費用を減らすための形。読める範囲は、所属するラウンドと、その距離・矢である。

- 索引は、`distances(round_id)`と`round_users(user_id)`のbtreeを持つ。
  - `distances(round_id)`: 合計点、小計、ラウンド構成の判定、距離単位の距離の列挙は、ラウンドIDで`distances`を引く。索引が無いと、ラウンドごとにDB全体の`distances`を走査し、費用が「利用者の件数×DB全体の距離の数」に比例する。PostgRESTの埋め込み(`rounds`から`distances`)も同じ索引を使える。
  - `round_users(user_id)`: 対象のラウンドを、呼び出し元の所属の行から引く(「履歴の関数」)。索引が無いと、所属を求めるために全利用者の`round_users`を読む。
  - 矢は主キー(`distance_id`, `end_number`, `shot_number`)で距離ごとに引く。
- 並べ替え(実施日、合計点、小計)のための索引は持たない。並びの値と同値の鍵は関数の中で求め、条件に一致する全ての件に番号を振ってから切り出すため、索引の順では読めない。合計点・小計は矢の集計で、列に無いため索引にできない。
- SELECTのポリシー(`select_if_member`)は次の形で書く。所属するラウンドが見えれば、その距離も矢も見える。
  - `rounds`: `is_round_member(id)`。
  - `distances`: 見えるラウンドがあること。`exists (select 1 from rounds r where r.id = distances.round_id)`。
  - `shots`・`shot_events`: `round_id in (select public.member_round_ids())`。`member_round_ids()`は、本人が参加するラウンドのIDを返す`SECURITY DEFINER`の関数である(`rounds/roles`)。
  - `member_round_ids`は`round_users`だけを読み、`distances`は`rounds`を辿り、`rounds`は`SECURITY DEFINER`の`is_round_member`を呼ぶため、ポリシーは循環しない。
  - 矢の`round_id`と距離のラウンドは、`(round_id, distance_id)`の複合外部キーが一致させる。矢の読める範囲は、距離のラウンドに参加していることと同じである。削除済み(`disabled_at`)の行の扱いはポリシーに無い。
  - `round_users`・`round_events`・`distance_events`は`is_round_member`を直接呼ぶ。このため、表によってポリシーの書き方が3通りある。
  - 書き込みは`SECURITY DEFINER`のRPCが表の所有者として行い、RLSを通らないため影響しない。`authenticated`の表の権限はSELECTだけで変えない。
- 索引の2文には、それぞれ直前の行に`-- squawk-ignore require-concurrent-index-creation`を書き、その上に理由のコメントを書く(配置先: `20261127010005_history.sql`)。理由: `create index concurrently`はトランザクションの中で使えず、索引と関数を1つのトランザクションで原子的に適用するため。書き込みの停止は`lock_timeout`で上限を付け、作成時間は合成データ(距離約9万行)で数十ミリ秒だった。`pnpm lint:sql`(squawk)は、この2文を無視の指定なしでは`require-concurrent-index-creation`で失敗し、指定すると通る(同じ形の下書きで確かめた。`CREATE OR REPLACE FUNCTION`は検出されない)。
- 条件の評価の順(事実。PostgreSQL 16の実行計画):
  - 1つの表を読むときの`where`の条件は、書いた順でなく、プランナーが見積もった1行あたりの費用の安い順に並べ替えて評価される。絞り込む量(選択率)は順の決定に使われない。費用が同じ条件は書いた順のまま並んだ。RLSの条件は、leakproofでない条件より先に評価される(比較の演算子のようなleakproofの条件は前に出られる)。PostgreSQLの文書は、式の評価の順を保証しない。
  - 結ぶ表や集計に依る条件は、計画の形で順が決まる。ラウンド構成の判定はラウンドを読むときの副問い合わせで、得点の範囲は合計点の集計の後にしか評価できない。
  - この形での順: 所属(`round_users`を`user_id`の索引で引く)→ 無効 → 種別 → 弓種 → 期間 → 完了 → RLSの`is_round_member` → ラウンド構成 → 合計点の集計 → 得点の範囲。
  - 所属は、行ごとの判定(`is_round_member`)を先に評価させても速くならなかった(判定の費用を下げて先に評価させた計測で、変わらないか遅い)。速くなるのは、所属から引く形(読む行そのものを利用者のラウンドに限る)だった。種別と弓種と期間の比較は1行あたりの費用が小さく、順による差は時間に現れない(推論。順を入れ替えた計測はしていない)。
  - ラウンドの条件の関数(`history_rounds`)は展開されるため、`rounds_list`の計画はこの関数を使う前と同じだった(所属は`round_users_user_id_idx`の`Index Scan`、ラウンドは`rounds_pkey`の`Index Scan`で、`Filter`の条件と順も同じ)。`distances_list`の対象のラウンドも同じ順で絞る。
  - `SET search_path`を付けた関数は展開されず、計画は`Function Scan`になった。`rounds`の行を引数に取る述語の関数(`where`で呼ぶ形)も展開されず、`Filter: (is_round_member(id) AND 述語の関数(r.*, ...))`のように、RLSの判定の後に1つの条件として行ごとに呼ばれた(関数がleakproofでないため、安い比較もRLSの前に出られない)。
  - 段を分けて書く形(事実。同じ環境の実行計画と計測): 入れ子の副問い合わせと通常のビュー(`security_invoker`)は、プランナーが1つの問い合わせに展開し、条件は1つの表の`where`に戻った(順は書いた形でなく費用で決まる)。`security_barrier`のビューは、leakproofの比較を中へ入れ、ラウンド構成だけが外に残った。`MATERIALIZED`のCTEと`OFFSET 0`の副問い合わせは段ごとに別に評価され、段の順は書いた順になった(`MATERIALIZED`は文書が別に計算すると定める。`OFFSET 0`は文書に定めが無い)。段の中の条件の順は費用で決まる。どの形も結果は同じで、時間は差が出なかった。順で時間が変わるのは、合計点の集計を他の条件より先に行う場合で、遅くなった。今の形は、計画の形で合計点の集計を最後に行う。
- 計測(事実。ネットワークなしの使い捨てのPostgreSQL 17、合成データ。矢の`round_id`・射手番号の列と距離の複合外部キーを加えた状態。利用者ごとに完了したラウンド2000件(全2222件)、各4距離・各36本。矢は利用者1人で約32万本、10人で約320万本。`authenticated`でRLSを有効にし、予備1回の後の5回の中央値。単位はms):

「戻った」か「開いた」かを、画面の構成や遷移の経路でなく、開いたURLの戻りの印で決める。

- 戻りの印は、点数一覧の経路の検索部の`return=1`である(`ROUNDS_HISTORY_RETURN_PATH`、経路表)。印の無い`/rounds/history`は「開く」、印のあるURLは「戻る」を表す。
- 規則は1つで、点数一覧の画面はURLの検索部を購読し(`useSearchParams`)、印が無いときはいつでも「開いた」として、表示済みを捨てて先頭のページから取得し、自分のURLを印のある形に置き換える(`window.history.replaceState`)。印が無いのは、印の無いURLで表示を始めたときと、表示中に点数一覧の項目を押したときである。Next.jsは同じ経路で検索部だけが違う遷移では画面を作り直さない(画面のkeyが検索部を除いて作られる)ため、表示の開始時だけ見ると、点数一覧の表示中に項目を押しても取得しない。そのため、表示の開始時に限らず検索部の変化を見る。Next.jsは`replaceState`をルーターに取り込み、`useSearchParams`が新しい値を返すため、置き換えの後は印がある状態になり、取得を繰り返さない。置き換えは`window.history.replaceState(null, '', url)`の形で呼ぶ(第1引数に現在の`window.history.state`を渡すと、Next.jsは内部の印`__NA`を見て取り込まず、`useSearchParams`が印の無いままになるため。`app-router.js`の差し替えた`replaceState`)。置き換えるURLは、今のURLのハッシュ(設定パネルの表示。`app/settings`)を保つ。ハッシュを落とすと、ハッシュ付きで開いた点数一覧で設定パネルが閉じるため。
- この結果、点数一覧の項目(どの画面からでも、点数一覧の表示中でも)は最新を取得し、ブラウザの戻る・進むでこの項目に戻ると、印のあるURLで開く。
- `useSearchParams`を使う部分は、静的な枠の生成のためにSuspenseで包む(待つ間はスケルトン)。
- 詳細の戻り先(`originPathOf("history")`)は印のあるURLにする。詳細の戻るリンク(`back-link.tsx`)と、詳細での削除の後の移動(`round-leaving.ts`)が使う。点数一覧の項目(レフトパネル/ドロワー)は印の無い`ROUNDS_HISTORY_PATH`のままである。
- 点数一覧を離れるとき(画面を外すとき)、先頭のページの取得が成功していれば、連結したページ(項目、除外するIDの和、続きの有無、続きの起点)とスクロールの位置を、タブのメモリの記憶(`historyPagesMemory`)に書く。成功していなければ記憶を消す。続きの取得中・失敗の状態は書かない。記憶は最後に離れた点数一覧の1つだけである。
- 除外するIDの和は、各ページの取得時の削除済みのIDと、この画面で削除したID(`removed`)の和である。`removed`を含めないと、点数一覧で削除した後に一括の取得が端末の記録から削除の操作を外すと、戻ったときにそのラウンドが再び出るため含める。スクロールの位置は、スクロールの入れ物の位置で、画面を外す直前(DOMを替える前)に読む。
- スクロールの入れ物は、点数一覧の枠(`HistoryFrame`)の`overflow-y-auto`の要素である。点数一覧の画面は、一覧の要素から先祖をたどり、`overflow-y`が`auto`か`scroll`の最も近い要素として得る(`app`の要素を参照しない)。続きの自動の取得の`root`、スクロールの位置の読み書きに使う。
- 表示の開始時にURLに印があり記憶があれば、取得せずに記憶のページを表示し、描いた後にスクロールの位置を戻す。そのとき、端末の記録から削除済みのIDを読み直して(`readDeleted`)、記憶の除外するIDの和に足す。端末の入力中は購読のまま除く。続きは、通常どおり一覧の末尾が画面に近づくと取得する。印があり記憶が無ければ、先頭のページから取得する。
- 条件の変更は通常どおり先頭から取得し直し、離れるときに新しい内容で記憶を書き直す。
- 記憶に利用者と条件を添えない。結果: 利用者が替わる移動(サインイン、サインアウト、セッションの喪失、別の利用者のサインイン)は全て`window.location.replace`によるページの読み込みを伴い、JavaScriptのメモリの記憶が無くなるため、別の利用者に使われない。条件は点数一覧の画面でしか変わらず、変えたときの内容が離れるときに書かれるため、記憶と保存した条件は食い違わない。
- 記憶はJavaScriptのメモリにだけあり、再読み込み、別のタブ、アプリの起動では無い。

この仕組みでの、開き方ごとの結果:

| 開き方 | 結果 |
| :--- | :--- |
| 詳細(点数一覧から開いた)の戻るリンク、詳細での削除の後の移動 | 離れる前の表示と位置。取得しない。詳細で削除したラウンドは出ない |
| ブラウザの戻る・進むで点数一覧に戻る(どの画面からでも) | 最後に離れた点数一覧の表示と位置。取得しない |
| レフトパネル/ドロワーの「点数一覧」(どの画面からでも。点数一覧から開いた詳細からも、点数一覧の表示中にも) | 最新を取得する(表示中に押したときは、表示済みを捨ててスケルトンにし、先頭から取得する) |
| ラウンドを完了してホームへ移った後に、「点数一覧」の項目で開く | 最新を取得する(完了したラウンドが出る) |
| ラウンドを完了してホームへ移った後に、ブラウザの戻るを重ねて前の点数一覧の項目に戻る | 最後に離れた点数一覧の表示(完了したラウンドは出ない) |
| 再読み込み、直接のアクセス、別のタブ、アプリの起動(印のあるURLを含む) | 最新を取得する(記憶が無いため)。条件は`sessionStorage`から戻る(パネルは閉じる)(再読み込み) |
| 別の利用者で開く | 最新を取得する(利用者が替わる移動はページの読み込みを伴い、記憶が無くなるため) |
| オフラインで戻る | 離れる前の表示(取得しないため、オフラインの表示にならない) |

- 要件との整合: 「戻る操作(詳細の戻る、ブラウザの戻る・進む)で戻ったときは離れる前の表示」は、詳細の戻り先とブラウザの戻る・進むで開くURLが戻りの印を持つことで満たす。「点数一覧の項目から開くと最新」は、項目のURLが印を持たないことで満たす。要件が設計に委ねた開き方(再読み込み、直接のアクセス、別のタブ、アプリの起動、別の利用者)は、記憶が無いため全て最新を取得し、「点数一覧の項目から開くと最新」と食い違わない。

### 条件の保持

- 入力値は、タブごとの保存先(`sessionStorage`)に、利用者のIDを添えて記憶する。画面は表示の開始後に記憶を読み、入力値が変わる(検索する)たびに書く。読む前は入力値を持たない。導出されるフィルターは保存しない(保存値から毎回導く)。パネルの開閉と編集中の値・エラーは記憶しない。
- 記憶の約束(`HistoryViewMemory`: 読む、書く)はapplicationに置き、実装はinfrastructureが持つ。実装は、保存値の利用者が端末の識別情報(`IdentityReader`)の利用者と違うとき、無いとき、検証できないときは既定を返す。保存先を使えないときは、画面の間だけ記憶なしで動く。端末の識別情報の利用者が無いときは、書き込みは何も書かず、読み込みは既定を返す。アカウント削除のため、保存値の利用者が指定と同じなら消す`eraseHistoryViewMemory(userId)`も公開する。
- 別の利用者には、保存値の利用者の照合だけで引き継がない。サインアウトでは破棄しない。同じ利用者が再サインインすると、同じタブでは条件が残る。
- 別のタブとは共有しない。新しいタブは、初めて開いたときの状態(既定の条件、閉)から始まる。
- 画面は、記憶を手続きの入れ物から受ける(`rounds-context.tsx`)。

- `features/rounds/domain/round-routes.ts`（domain）: ラウンドの画面の経路の判定・変換(経路に対応する枠を返す`roundFramePathOf`。点数一覧の枠を詳細の枠より先に判定する)。遷移元の型と変換(`RoundOrigin`、`roundOriginOf`、`originPathOf`)は`rounds/detail`が扱う。点数一覧の遷移元の戻り先(`originPathOf("history")`)は戻りの印のあるURL(`ROUNDS_HISTORY_RETURN_PATH`)で、URLの検索部に印があるかの判定(`isHistoryReturn`)もここに置く。経路の定数(`ROUNDS_PATH`、`ROUNDS_HOME_PATH`、`ROUNDS_HISTORY_PATH`、`NEW_ROUND_PATH`、`roundPath`)は経路表(`src/routes.ts`)が持つ。
- `features/rounds/domain/history-view-state.ts`（domain）: 入力値(`HistoryInput`)、導出されるフィルター(条件。単位と距離の行を含む)、表示の状態の型、既定、入力値から条件を導く`historyConditionOf`、保存値の検証と正規化、期間と得点の範囲の下書きの検証(`historyRangeOf`)、ラウンド構成の下書きの検証(`historyDistancesOf`)(「条件の定義」)。
- `features/rounds/application/history-view-memory.ts`（application）: 記憶の約束(「条件の保持」)。
- `features/rounds/infrastructure/browser-history-view-memory.ts`（インフラ層）: タブごとの保存先と利用者の照合による記憶の実装。
- `features/rounds/application/rounds-list-store.ts`（手続き）: 点数一覧の画面に渡す状態。`loadList(condition, after, size)`は、端末の記録(`readList`)を読んで削除済みのラウンドのIDを求め、条件と続きの起点と件数で1ページの取得(`RoundFetching.fetchRoundsList`)を行い、失敗したときはその結果を返し、成功したらページと削除済みのIDを返す。`readDeleted()`は、取得せずに端末の記録の削除済みのIDだけを返す(戻ったときの表示に使う)。1ページごとに`withinFetchTimeout`で10秒に打ち切る(`app/offline-pwa`)。削除が確定済みでも端末の記録へは反映しない(反映は一括の取得の`refreshAll`が行う)。取得の拒否はそのまま伝え、画面の取得の hook が`error`にする。端末内の入力中の一覧は窓口(`features/rounds/application/round-window.ts`の`watchLocalList`/`localList`)が持つ。窓口は購読者が0→1で端末の記録を購読し、変化を同じティックで1回にまとめ、全ての列から導き直し、構造が同値なら参照を変えず通知しない。1→0で値を捨てる(再購読は`null`から始める)。導き直しは、端末の各組を`features/rounds/domain/round-view.ts`の`deriveRoundState`で状態にし、`features/rounds/domain/round-retention.ts`の`isRoundInProgress`が真のものを名前・実施日・合計点にする(`round-list.ts`)。保存済みの的は読まない。入力中と端末が保持するラウンドの一括の取得は、履歴の取得とは別に同期が行う(`features/round-sync/application/round-sync.ts`、`features/rounds/application/round-base-refreshing.ts`)。ユーザーの突き合わせは行わない。ベースと操作の列は端末でユーザーごとに隔離され、取得の利用者と記録の利用者が`same`でない反映は端末へ保存されない。通信の復帰の合図(`whenOnline`)は手続きの入れ物から受ける。画面は時刻、乱数、通信の可否に触らない。
- `features/rounds/application/round-fetching.ts`（手続き）: 取得の順序。`fetchRoundsList(condition, after, size)`が、`fetchContent`（`features/rounds/application/content-fetcher.ts`）経由で認証を確かめて`RoundQueries.roundsList`を呼び、`roundListItemOf`で項目にして続きの有無を添える。
- `features/rounds/infrastructure/round-queries.ts`（インフラ層）: 履歴の問い合わせを`DatabaseGateway<RoundsDbSchema>`の`rpc`で履歴の関数(`rounds_list`)へ行い(`roundsList({ condition, after, size })`)、応答を`ServerRoundSummary`の列と続きの有無のまま`QueryOutcome`で返す。現在の成功応答を`ServerHistoryPage`へ写し、`has_more`を`hasMore`にする。通信失敗とDBエラーは`failureOfResponses`で判定する。自動の再試行はしない。`rounds_list`の引数のうち、期間と得点の範囲の4つは、`null`でないものだけを送り、ラウンド構成は行が1つ以上のときだけ`p_distances`として送る(指定のない引数は送らない。`rangeArgsOf`と同じ形)。距離単位のときは`distances_list`を呼び(行があれば`p_distance`を送る)、応答の`distances`を距離単位の項目のページにする。生成型では任意の引数がoptionalのため、`rounds-db-schema.ts`にnull許容の上書きは足さない。`rounds-db-schema.ts`は`rounds_list`と`distances_list`を含み、`distances_list`にも`rounds_list`と同じnull許容の上書きを持つ。名前(`roundsList`、`fetchRoundsList`、`loadList`、`RoundsListStore`)は据え置き、履歴の取得を指す。
- `supabase/migrations/20261127010005_history.sql`（DB）: 履歴の関数、ラウンドの条件の関数、距離単位の履歴の関数(「取得の形」)と、その取得が使う索引。`distances`のSELECTポリシーは`supabase/migrations/20261127010003_rounds.sql`に、`shots`・`shot_events`のSELECTポリシーは`supabase/migrations/20261128010001_shooters_unified.sql`に置く(「索引とRLSと条件の評価の順」)。署名を直書きするDBのテスト(`supabase/tests/rpc_matrix.sql`、`rls_matrix.sql`)と生成型(`apps/web/src/types/supabase.ts`)も、同じ変更で新しい署名に合わせる。
- 端末から導く入力中のラウンドの種別・弓種・距離ごとの小計・合計点は、状態(`deriveRoundState`)の設定、距離・矢から、履歴の関数と同じ規則で端末が求める(`localRoundsList`)。距離は無効でないものを(`position_key`, `id`)の順(`compareDistancePosition`)に並べ、小計は距離ごとの無効でない矢の`score_int`の和、合計点は小計の和(矢が無ければ0)である。ホームでは、途中の値になる。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| ホームを履歴の取得から切り離す | 入力するためにラウンドの開始ボタンを押す利用者が、履歴の取得を経由しないため。ホームが取得を経由しないことを、取得する部品を持たない構造で保証する | ホームに点数一覧由来の表示を足すとき |
| 履歴の取得をサーバーの`status = completed`で絞り、端末の完了を合わせない | 「サーバーで完了と記録されたものだけ」の要件と一致し、入力中や端末だけの完了を取得しないため。全件取得して画面で除く案は、規則を画面の条件に頼るため採らない | 端末の完了を点数一覧に出す要件になったとき |
| 履歴から、端末の入力中のIDと削除済みの2つを、取得の後に端末で除き、1ページの表示件数が減るのを許す | 他の端末で完了したラウンドが同期の反映までホームと点数一覧の両方に出ること、削除のサーバー受理までの間に出ることを防ぐため。除くIDをサーバーへ渡してページを満たす案は、取得の後の削除を端末で除く仕組みが残り、引数が入力中の件数に比例するため採らない | 同期との時間差がなくなるとき |
| `ROUNDS_HOME_PATH`と`ROUNDS_PATH`を同じ値で持ち分ける | ホームを指す呼び出しと、画面全体の範囲(保護の範囲、枠)を指す呼び出しを区別し、`HOME_PATH`(`/`)との取り違えを避けるため | 範囲とホームの値が分かれるとき |
| 本文に現在地と重なる見出し(「ラウンド一覧」など)を置かず、現在地「ホーム」「点数一覧」は共用のヘッダーの`h1`で示す。ホームの入力中の欄だけ、欄の内容を示す見出し「入力中のラウンド」を`h2`で置く | 要件のため。現在地の表示は全画面で同じヘッダーの位置にそろえる(`app/navigation`)。欄の見出しは現在地と別の内容を示し、読み込み前・0件でも欄が何かを示す | 見出しの要件が変わるとき |
| ホームの入力中は端末の列を表示の開始時に読み、記録が変わるたびに読み直す | 端末の記録の変化(一括の取得の反映)を取得を待たずに反映するため | 読み直しの費用が問題になるとき |
| 論理削除された行を、ラウンド・距離・矢の3段階で履歴と合計点から除く | 削除を`disabled_at`で射影しており、無効化後の後続イベントも通常表示へ戻さないため | 削除の方式を変えるとき |
| 合計点を`rounds_list`の中の副問い合わせで求め、集計列・ビューを持たない | 合計点を使うのは`rounds_list`だけで、最も単純なため。変更前(全ての矢の行を転送)より転送が減り、DBで読む量は同程度である。集計列は、矢・距離を変える全ての書き込みのRPCで値を保つ必要があり、今の規模では要らないため採らない。PostgRESTの集約関数は並べ替えに使えないため採らない | 履歴の取得の遅さが問題になるとき |
| 履歴の取得は、呼び出し元の権限で動く関数(`SECURITY INVOKER`の`rounds_list`)で行い、認可はSELECTのRLSに任せる | 合計点での並べ替えと、作成時刻を返さないキーセットの起点(作成時刻をIDから引く)は、直接SELECTでは書けないため。認可をRLSに残し、SELECTポリシーを維持する方針と合わせる | 読み取りも認可RPCへ統一するとき |
| 取得の時間は、`distances(round_id)`と`round_users(user_id)`の索引、`rounds_list`で対象のラウンドを呼び出し元の所属から引く形、`distances`のSELECTのポリシーを親が見えるかで書き`shots`・`shot_events`を`member_round_ids()`の集合で書く形で縮める。認可はRLSのままにする | 費用が「利用者の件数×DB全体の距離の数」と全ラウンドの走査に比例するのを避け、読める範囲を変えないため。矢は行の`round_id`の照合にして、行ごとの距離の参照と関数の呼び出しをなくし、一覧を速くする。親の可視性を集合(`in (select id from ...)`)で書く形は、DB全体の行を読むため他の利用者のデータの量に比例し、1件の詳細の取得も遅くなったため採らない。`member_round_ids()`は`round_users(user_id)`の索引で本人の参加行だけを読むため、この理由に当たらない(本人の参加が多い場合の1件の詳細は同程度)。行ごとに`is_round_member(round_id)`を呼ぶ形は、行ごとの関数の呼び出しが残り一覧の短縮が小さいため採らない。判定関数の中から`is_round_member`を呼ぶ階層の形は、関数の中から関数を呼ぶ費用が大きいため採らない。`authenticated`が呼べる関数は`member_round_ids`の1つで、返すのは本人の参加ラウンドのIDだけである。`rounds_list`を所有者の権限(`SECURITY DEFINER`)で動かし所属で絞る案は、約0.1秒になったが、認可がRLSから関数の条件へ移り、誤りが他の利用者のデータの漏れになるため採らない。条件の書く順や関数の費用の設定で評価の順を変える案は、文書が順を保証せず、計測で速くならなかったため採らない。段を分けて順を決める形(`MATERIALIZED`のCTE、`OFFSET 0`、ビュー)は、結果も時間も変わらず、ビューは`security_invoker`を付け忘れるとRLSを通らず全てのラウンドが見える(試した)ため採らない。並べ替えの索引は、計画で使われないため持たない | 矢の読み取りの費用が問題になるとき。読み取りの認可の方式を変えるとき |
| 枠は静的にし、取得はクライアントから行う（枠をSWが返す前提。詳細は#648） | 静的な枠を即座に返し、取得の失敗を枠内で区別して示すため | 履歴をサーバーで取得する必要が生じたとき |
| ラウンドの開始ボタンをホームの右下に固定し、ホームの全状態で表示する。アイコンだけの丸いボタンでなく、文字を並べた両端が丸い横長(`rounded-full`)にする | 入力の入口を常に示し、履歴の取得の状態に左右されないため。入口の名前「ラウンドを開始」を目で見て分かるようにし、レフトパネルの入口と同じ名前にそろえるため。横長にすると本文の右下を覆う範囲が広がるため、本文の下の余白をボタンの上端より上まで取る | 開始の入口の置き場を変えるとき。ボタンの大きさや位置を変えるとき(下の余白も合わせる)。 |
| ラウンドの開始ボタンに`data-hydrated`を付ける | ハードナビゲーション直後の操作が、ハイドレーション前に空振りするのをE2Eが待てるようにするため | ハイドレーション完了の通知を共通化するとき |
| 履歴の取得と一括の取得を別々に行い、点数一覧は一括の取得を待たず、一括の失敗で隠さない | 点数一覧の表示を一括の取得の成否に依存させないため。ホームは端末の記録から作り、他の端末で完了したラウンドが残る時間は、次の契機(起動、通信の復帰、画面が見える状態)まで延びる | ホームの鮮度が問題になるとき |
| 入力中のラウンドは、詳細と同じ導出(`deriveRoundState`)と表示の規則で決め、保持の規則を使わない。的は使わない | 一覧と詳細の値を一致させ、完了で未送信の変更が残るラウンドを入力中と見せないため。的は画面に出ず、未送信の矢の点数が距離の的に無い異常系だけ合計が詳細と異なり得る(送信と取得の後は一致する) | 一覧に的を使う表示が入るとき |
| 履歴の取得と端末の入力中の読み込みを`RoundsListStore`に持たせ、削除と通信の復帰の合図は手続きの入れ物から受ける。画面は時刻、乱数、通信の可否に触らない | 画面に渡す形を1つにし、画面を変えずに手続きを検証するため。窓口は判断か写しを持つメンバーだけにする | 画面に別の手続きを渡す必要が出たとき |
| ラウンドの開始画面と詳細の経路を経路表(`src/routes.ts`)が持つ | 経路の文字列の持ち主を1つにするため | 画面の経路の階層を変えるとき |

| 条件をタブごとの保存先(`sessionStorage`)に、利用者を添えて記憶する | 再読み込みと詳細からの戻りで保て、アプリの起動で前回のビューを復元しない現行の要求と、他のタブとの食い違いの書き込みを避けるため。端末全体の保存先は、新しい起動でも復元するため採らない。利用者の照合は、別の利用者への引き継ぎを防ぐ | 起動をまたぐ復元の要求が出たとき |
| 点数一覧はユーザーを突き合わせず、現在のハブのユーザーの組を読むだけにする | ベースと操作の列はストアとハブでユーザーごとに隔離され、詳細も同じ前提で読むため。毎回突き合わせる仕組みは、隔離と重複するため採らない | ハブのユーザーの切り替えの手順を変えるとき |

## 制約と未対応

- 点数一覧のURLは、表示の開始後は常に戻りの印の付いた形(`/rounds/history?return=1`)になり、アドレス欄や共有するURLにも出る。印の付いたURLを再読み込みや別のタブで開いても、記憶が無いため最新を取得する。既存のE2Eは点数一覧のURLを`/\/rounds\/history$/`で照合しており(`tests/e2e/rounds/history.spec.ts`の5か所、`tests/e2e/app/offline-pwa.spec.ts`の1か所)、この照合は印の付いたURLに一致しなくなる。
- 戻ったときの表示は取得しないため、離れている間の変更は、点数一覧の項目で開くか再読み込みするまで出ない。他の端末での変更に加え、この端末で詳細から変えた完了のラウンドの名前・実施日も、戻ったときは離れる前の値のまま出る(完了のラウンドは詳細で名前・実施日を変えても完了のまま。`rounds/completion`)。点数の記録や距離の追加で入力中に戻ったラウンドは、端末の入力中として除かれ、出ない。
- 履歴の関数は、ページの取得のたびに条件に一致する全ラウンドの合計点(距離単位では全ての距離の小計)を求めて並べるため、DBの処理量はその利用者の完了したラウンドの矢の総数に比例する(転送量は1ページ分)。矢はRLSを通して読む(合成データで、完了したラウンド2000件・矢約29万本の利用者の絞り込みなしの`rounds_list`が約0.2〜0.4秒。本番では確かめていない)。遅さが問題になったら、書き込みのRPCが保つ集計列、日付順で切り出してから合計点を求める形を検討する。
- `distances`のSELECTのポリシーは親が見えるかで、`shots`・`shot_events`は`member_round_ids()`で、`rounds`・`round_users`・`round_events`・`distance_events`は`is_round_member`で書く。読める範囲の条件は同じで、参加の条件は2つの関数が持つ。
- ラウンドの条件の関数(`history_rounds`)だけが`SET search_path`を付けない関数である(展開させるため。名前は修飾する)。
- 読み進める間に、他の端末で続きの起点のラウンドの実施日か合計点が変わると、次のページで行が抜けることがある(要件の例外。開き直すと正しく並ぶ)。
- 日付の幅は最も広い数字の基準で、固定の幅(合計点40px、距離一覧の1列38px、距離単位の距離44px)は4桁までの数字と、「100m」「Unmarked」が収まる値である。これより広い内容(5桁以上の点数)は、領域からはみ出しうる。
- 点数一覧の先頭のページがオフライン表示のときは、通信の復帰（手続きの入れ物の`whenOnline`）で自動再取得する。続きのオフラインは、再試行ボタンで取り直す。通信失敗（`navigator.onLine`が`true`のまま）を含むエラーは、自動で取り直さず、再試行ボタンで取得し直す。
- 完了で未送信の変更が残るラウンドは、サーバーに完了が反映され、点数一覧を開いて取得するまで、ホームにも点数一覧にも出ない。
- 一括の取得は、ホームと点数一覧を開いても起こさず、起動、通信の復帰、画面が見える状態で行う。
- 条件は、ラウンド単位と距離単位の切替(表示単位の切り替え)、日付順・得点順(日付順は必ず指定、得点順は指定なしがある)と、種別・弓種の絞り込み(それぞれ単一選択)、期間と、単位ごとの得点の範囲と、ラウンド構成(ラウンド単位)と距離単位の距離の行(1つ)の絞り込みだけである。パネルを閉じている間は、中の値を表示しないが、導出されるフィルターが既定でないことはアイコンの印で示す。ラウンド単位の間の絞り込む距離と、距離単位の間のラウンド構成と、使わない単位の得点の範囲は、入力値として保たれるが、取得にも印にも使われない。
- 距離単位の件からはラウンドを削除できない(詳細かラウンド単位で削除する)。
- 期間・得点の入力は、「検索」を押すまで反映されず、エラーも検索を押すまで出ない。距離(ラウンド構成・距離単位)は、距離のダイアログの確定のボタンで検証して編集中の値に入れ、検索を押すまで入力値には反映されない(エラーは確定のボタンを押したときだけ出す)。検索せずに閉じる、または画面を離れると、入力した文字とエラーは捨てる(記憶しない)。
- ラウンド構成の的の一覧は、端末に保存した一覧(同期の一括の取得が保存する)だけを使う。新しい端末で同期の初回の取得が終わる前に欄を開くと、一覧が空で的を選べない(「指定なし」は選べる)。欄を開き直すと読み直す。
- 別のタブとは条件を共有しない。サインアウトで条件を破棄しないため、同じ利用者が同じタブで再サインインすると条件が残る。
- 未適用の変更とエラーは、閉じる操作のほか、詳細・ほかの画面への移動、戻る、再読み込み、タブを閉じるのいずれでも破棄する(記憶しない)。適用済みの条件は保たれる。
- パネルを開いている間、一覧のスクロールの入れ物は、縦長ではパネルの高さの分(最大で本文の高さの半分)だけ、横長では本文の幅の40%の分だけ狭くなる。
- フィルターの「適用」ボタンの名称を「検索」にする。変えるのは、ボタンの文言(`historyControlsApply`の値)とテスト用の識別子(`history-controls-apply`)だけである。状態・概念を表す語(適用済みの条件、適用中の印、未適用の変更、適用前・適用後)は「適用」のままとする。コード上の識別子(`onApply`、`applyInput`、`historyControlsApply`など)は改称しない。
