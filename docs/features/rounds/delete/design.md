# rounds/delete 設計

## 概要

ラウンドの削除は、ラウンド一覧の各カードのメニューと、ラウンド詳細画面のヘッダーのメニューから行う。
どちらも確認ダイアログを経て、確認と同時に操作の列（`rounds/sync`）へ`round.disabled`を積み、画面から除く。
送信は常駐の送信器が行い、オフラインでも削除できる。復帰後に`disable_round` RPCが送られる。

## 画面と状態

| 状態 | 表示 | 次の状態 | 要求 |
| :--- | :--- | :--- | :--- |
| メニュー閉 | 一覧はカードごと、詳細はヘッダーにメニューボタン | メニューボタンで展開 | delete-01, 04 |
| メニュー展開 | 一覧は「削除」、詳細は「ラウンドを削除」 | 削除ボタンで確認中、外側クリックで閉じる | delete-02, 05, 07 |
| 確認中 | 説明文とキャンセル・確認ボタン | キャンセル・背景クリックで閉じる、確認ボタンで閉じて削除済み | delete-08, 09 |
| 削除済み | 一覧はカードが消え、詳細は`/rounds`へ置き換えて遷移する | - | delete-03, 06, 12, 13, 16 |

- 確認文言は、一覧ではラウンド名を含み、詳細では含まない。一覧でも名前の無いラウンドは名前を含めず、詳細と同じ文言にする（メニューボタンの読み上げ名も「ラウンドのメニュー」）。どちらも、記録したスコアがすべて失われることを明示する。
- 確認後の画面更新は画面ごとに異なる。一覧は削除済みの集合へ足してカードを除き、詳細は列への保存の後に`/rounds`へ`replace`で遷移する（戻るボタンで削除したラウンドの詳細へ戻らない）。
- E2Eは、ダイアログ固有の行（delete-08、delete-09）をラウンド一覧で検証する。delete-10、11は欠番である。

## 構成とデータの流れ

- `rounds/rounds-list-client.tsx`: 一覧のカードのメニューと、削除済みの集合によるカードの除去。
- `rounds/[id]/round-menu.tsx`: 詳細のヘッダーのメニュー。保存の後に`/rounds`へ置き換えて遷移する。
- `rounds/_shared/delete-round.ts`: `round.disabled`を新しい`eventId`で列へ追記する。保存の試みの完了で解決し、拒否しない。
- `components/ui/confirm-dialog.tsx`の`ConfirmDialog`: 確認後すぐ閉じる。
- `rounds/overlay-rounds-list.ts`、`rounds/load-rounds-list.ts`: 一覧の取得結果と端末の入力中のラウンドから、列で削除済みのラウンドを除く（`rounds/history`）。
- `rounds/[id]/load-round-detail.ts`: 列に削除があれば、取得せずに削除済みを返す（`rounds/detail`）。

流れは、メニューから確認ダイアログを開き、確認で`deleteRound`を呼ぶ。
一覧は、そのラウンドを削除済みの集合へ足して除く。詳細は、保存の完了後に`/rounds`へ置き換える。
送信は常駐の送信器が行い、画面が閉じても続く。未確定の作成のラウンドは、既存の衝突規則で作成の確定を待って削除が送られる。
認可の拒否と契約の不一致は破棄され、一覧を取得し直すとラウンドが再表示される。

`disable_round`（`SECURITY DEFINER`、`authenticated`にのみEXECUTEを付与）の契約は次のとおり。
- 認可: 対象ラウンドを行ロックし、呼び出し元が`round_users.role = 'editor'`でなければ`PT403`で拒否する。
- 冪等性: `event_id`が既に`round_events`にあれば何もしない。
- 副作用: `DISABLED`イベントを追記し、`rounds.disabled_at`を設定して`revision`を進める。
- 削除の前後に届いた距離・矢の操作は、サーバーで効かず、表示されない。
- 論理削除であり、距離・矢の行は残る。一覧と詳細は`disabled_at is null`で絞るため、削除したラウンドは一覧に出ず、詳細は「見つかりません」になる。
- クライアントからの直接のDELETEは、RLSで拒否する。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| 確認後すぐ閉じる`ConfirmDialog`で、操作の列へ積む | オフラインでも削除でき、確認後に待たせないため。失敗は再表示で足りる。詳細: #393 | 削除の取り消しや失敗の通知を求めるとき |
| プリセット削除とサインアウトは、完了を待つ`BlockingConfirmDialog`のまま | オフライン対応が不要で、失敗をダイアログ内に示して再試行させるため | プリセット削除をオフラインで認めるとき |
| 削除を、`disabled_at`による論理削除にする | 追記専用のイベントログと射影を用いるため。再送しても二重に適用されない | 保持期間や物理削除の運用を決めるとき |
| 認可を、RPC内の`round_users.role = 'editor'`の確認で行う | 書き込みを権限確認するRPCの境界へ統一したため。クライアントのセッション確認は予防にすぎず、`readSession`で未認証と不明（通信失敗）を区別し（ラウンド削除とプリセット削除で同じ判定）、`getUser()`でなく`getSession()`を使う | 認可の方式を変えるとき |
| 詳細のメニューを、`RoundConfigPanel`でなくページのヘッダーに置く | 将来の印刷・共有などラウンド全体の操作の置き場も兼ねるため | ラウンド全体の操作を別の場所へ集めるとき |
| 列への追記を`_shared/delete-round.ts`で共通にし、画面からの除去は各画面が行う | 一覧と詳細で処理が重複していたため | 画面ごとの成功後の処理が揃うとき |

## 制約と未対応

- 編集権限のないメンバー（`viewer`）にも削除メニューを表示する。実行するとカードは消え、サーバーが拒否して破棄するため、一覧を取得し直すと通知なく再表示される。
- 破棄された削除と、別のタブで行った削除は、開いている一覧には即座に反映されず、一覧を取得し直したときに反映される。
- 未認証のときの削除は、列に保留され、同じユーザーのサインインで送られる。
- 削除したラウンドを元に戻す機能はない。論理削除した行の保持期間は決めていない。
