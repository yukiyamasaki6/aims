# rounds/delete 設計

## 概要

ラウンドの削除は、ラウンド一覧の各カードのメニューと、ラウンド詳細画面のヘッダーのメニューから行う。
どちらも確認ダイアログを経て、`disable_round` RPCを呼ぶ。
削除は破壊的で低頻度なため、送信キュー（`rounds/sync`）を使わず、完了を待ってから画面へ反映する。
失敗時はダイアログを開いたままエラーを表示し、再試行できる。

## 画面と状態

| 状態 | 表示 | 次の状態 | 要求 |
| :--- | :--- | :--- | :--- |
| メニュー閉 | 一覧はカードごと、詳細はヘッダーにメニューボタン | メニューボタンで展開 | delete-01, 04 |
| メニュー展開 | 一覧は「削除」、詳細は「ラウンドを削除」 | 削除ボタンで確認中、外側クリックで閉じる | delete-02, 05, 07 |
| 確認中 | 説明文とキャンセル・確認ボタン | キャンセル・背景クリックで閉じる、確認ボタンで削除中 | delete-08, 09 |
| 削除中 | 確認ボタンにスピナー。キャンセル・確認ボタン・背景クリック・Escは無効 | 成功で閉じる、失敗で削除失敗 | delete-03, 06, 10 |
| 削除失敗 | ダイアログ内にエラー。ボタンは操作可能に戻る | 再試行、またはキャンセル | delete-11 |

- 確認文言は、一覧ではラウンド名を含み、詳細では含まない。どちらも、記録したスコアがすべて失われることを明示する。
- 成功後の画面更新は画面ごとに異なる。一覧はカードを除き、詳細は`/rounds`へ遷移する。
- E2Eは、ダイアログ固有の行（delete-08〜delete-11）をラウンド一覧で検証する。

## 構成とデータの流れ

- `rounds/rounds-list-client.tsx`: 一覧のカードのメニューと、成功後のカード除去。
- `rounds/[id]/round-menu.tsx`: 詳細のヘッダーのメニュー。成功後に`/rounds`へ遷移する。
- `rounds/_shared/delete-round.ts`: セッション確認、`disable_round`の呼び出し、エラー文言への変換。結果は成功・失敗・破棄のいずれかを返す。
- `components/ui/confirm-dialog.tsx`の`BlockingConfirmDialog`: 完了待ち、二重送信の防止、送信中の操作無効化、失敗の保持。

流れは、メニューから確認ダイアログを開き、確認で`deleteRound`を呼ぶ。
成功なら呼び出し元の画面が更新し、失敗ならダイアログ内にエラーを出す。
完了を待つ間に画面がアンマウントされた場合は、結果を破棄し、state更新も遷移も起こさない。

`disable_round`（`SECURITY DEFINER`、`authenticated`にのみEXECUTEを付与）の契約は次のとおり。
- 認可: 対象ラウンドを行ロックし、呼び出し元が`round_users.role = 'editor'`でなければ拒否する。
- 冪等性: `event_id`が既に`round_events`にあれば何もしない。
- 副作用: `DISABLED`イベントを追記し、`rounds.disabled_at`を設定して`revision`を進める。
- 論理削除であり、距離・矢の行は残る。一覧と詳細は`disabled_at is null`で絞るため、削除したラウンドは一覧に出ず、詳細は404になる。
- クライアントからの直接のDELETEは、RLSで拒否する。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| 完了を待つ`BlockingConfirmDialog`で削除し、送信キューへ積まない | 破壊的で低頻度であり、失敗をダイアログ内に示して再試行させたいため。キュー化は、確認の完了を待つ契約と合わないため採らない。詳細: #393 | 削除のオフライン対応が要求されたとき |
| 確認後すぐ閉じる`ConfirmDialog`（距離削除用）と、完了を待つ`BlockingConfirmDialog`の2種に分ける | 距離削除は送信キューへ積む操作で、確認後の振る舞いが異なるため | 距離削除も完了待ちにするとき |
| 二重送信の判定を、stateでなく同期的な`ref`で行う | stateはレンダーまで更新されず、連打の2回目が古い値のまま実行されるため | 同時実行を別の仕組みで防げるとき |
| アンマウント後に完了した結果を破棄する。マウント時に破棄フラグを戻す | アンマウント後のstate更新と遷移を避け、Strict Modeの二重実行でも動かすため | 非同期結果の扱いを共通化するとき |
| 削除を、`disabled_at`による論理削除にする | 追記専用のイベントログと射影を用いるため。再送しても二重に適用されない | 保持期間や物理削除の運用を決めるとき |
| 認可を、RPC内の`round_users.role = 'editor'`の確認で行う | 書き込みを権限確認するRPCの境界へ統一したため。クライアントのセッション確認は予防にすぎず、`getUser()`でなく`getSession()`を使う | 認可の方式を変えるとき |
| 詳細のメニューを、`RoundConfigPanel`でなくページのヘッダーに置く | 将来の印刷・共有などラウンド全体の操作の置き場も兼ねるため | ラウンド全体の操作を別の場所へ集めるとき |
| 削除の共通処理を`_shared/delete-round.ts`へ置き、成功後の更新は各画面に残す | 一覧と詳細で処理が重複していたため | 画面ごとの成功後の処理が揃うとき |

## 制約と未対応

- 編集権限のないメンバー（`viewer`）にも削除メニューを表示し、実行すると「このラウンドを削除する権限がありません。」で失敗する。
- 通信断での失敗は、専用の扱いをせず、通信エラーのメッセージを出す。
- 削除したラウンドを元に戻す機能はない。論理削除した行の保持期間は決めていない。
- `SyncOperation`に`round.disabled`が残るが、画面から積む経路はない。
