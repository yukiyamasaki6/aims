# sync 設計

## 概要

ラウンド詳細画面（`/rounds/[id]`）の変更操作は、サーバーの完了を待たずに画面へ反映する（楽観的UI）。
操作はまずIndexedDBの操作の列へ追記し、タブに常駐する送信の集まりが、どの画面を表示していても認可つきの書き込みRPCを呼ぶ。複数タブのときは1つのタブだけが送る。
操作の列は追記専用で、端末の順序は`autoIncrement`の`seq`で持つ。送信は、衝突する組だけを順序づけて行い、失敗時のリトライ、オフライン中の保留、オンライン復帰時の再送を持つ。
1回の保存を1つの操作として送り、サーバーが確定の順で項目ごとに、後勝ちと規則(決定1、削除、不変条件)で判定する。
サーバーが拒否するのは認可と契約の不一致だけで、他は受理したうえで効かせない項目を応答で返す。
画面の状態は、ベース(取得したサーバーの状態)へ操作の列を重ねる`applyOperations`1つだけから導く。
ベースと操作の列は、ラウンドごとに1つの組として、端末(IndexedDB)とタブ(送信器のメモリ)の2か所に持ち、組を変える書き込みは、端末では1つのトランザクション、タブでは1回の通知で行う。
ベースは取得のたびに差し替わり、反映済みの操作は、差し替えと同時に列から外れる。
対象はラウンドの作成・削除と、ラウンド・距離・矢の変更で、プリセット削除、サインアウトは対象外である（完了を待つダイアログで行う）。

## 画面と状態

同期の状態は画面に表示しない。送信器の操作は次の状態をとる。

| 状態 | 意味 |
| :--- | :--- |
| 保留 | 送らずに待っている(オフライン、またはサインインが必要)。オンラインへの復帰か、サインインし直しで送る |
| リトライ待機 | オンラインで送信が失敗し、次の試行を待っている。衝突する後続の操作も止まる |
| 送信中 | 保存中、または送信中の操作がある |
| 送信済み | 未送信の操作がない |

- リトライの待機時間は3秒から2倍ずつ増やして60秒で頭打ちにし、回数に上限を設けない。
- 同期の状態、送信の失敗、破棄は、画面に表示しない。

## 構成とデータの流れ

機能は2つで、依存は同期からラウンドの一方向である(ラウンドは同期を知らない)。パスは`apps/web/src/`からの相対で示す。

- ラウンド(`features/rounds/`): 業務の規則、端末の記録、画面に渡す正しい状態と変更の方法、突き合わせの一歩(操作の送信と確定の記録、ベースの取得と反映)を持つ。
- 同期(`features/round-sync/`): いつ送り、いつ取り直すかを決める唯一の手続きと、契機の受け取りを持つ。他の機能へ公開する名前が無いため、入口を置かない。
- 画面は、文脈から受け取る状態と変更の方法(`RoundsStore`)だけを使う。取得の状態(読み込み中、オフライン、見つからない、エラー)は、画面に渡す見え方の型に持たせる。画面は「開いた」「もう一度読む」を依頼するだけで、取得と反映の時点は同期が決める。
- パッケージ: 画面は`react`、端末の保存は`idb`(`lib/local-op-log/`だけ)、データベースは`@supabase/supabase-js`(機能では認証のインフラ層だけ。他は`lib/supabase/`)を使う。ラウンドと同期は、非画面のパッケージを直接参照しない。

契機の受け取り(`sync-triggers.ts`)は、規則(`sync-trigger.ts`)で同期の手続きの操作に変える。

| 契機 | 反応 |
| :--- | :--- |
| 開始 | `sync.start(端末の識別情報の利用者)` |
| サインインの終了 | `sync.switchUser(null)` |
| サインインした、開いたときの確認、トークンの更新(利用者あり) | 照合が`same`なら`sync.resume()`、`other`と`unowned`(記録の利用者がnull)なら`sync.switchUser(id)` |
| 利用者の無い開いたときの確認 | 何もしない |
| サインインした、開いたときの確認(利用者あり) | 上に加えて`sync.refreshAll("resident")` |
| 通信の復帰、切断、画面が見える状態 | `sync.online()`、`sync.offline()`、`sync.visible()` |

照合の結果ごとの反応は、認証の通知は上の表のとおり、送る前は`same`と`unowned`で送り`other`で未認証として保留、常駐の一括の取得の前段は`same`だけ行い、取得したベースの反映は`same`だけ端末へ保存して他はこのタブだけに反映する。

同期の手続き(`round-sync.ts`)は、常駐の一括の取得と、ラウンドごとの取り直しを、それぞれ同時に1回までにする。一覧の一括の取得とラウンドごとの開く依頼は、新しい依頼の番号ごとにすぐ実行を始め、先の実行を待たずに並行して走る。同じ番号のあいだに記録の知らせが届いても、実行を重ねない。これらは互いを待たない。
一括の取得は、常駐の契機(サインイン、開いたときの確認、通信の復帰、見える状態)と、一覧を開いたときの依頼で行う。常駐の取得と一覧の取得は別々に走り、一覧は常駐の取得の終わりを待たない。常駐の契機では、サインイン済みで記録の利用者と同じときだけ取得と反映を行い、一覧の依頼だけの実行は、一覧の取得が成功したときだけ反映する。成功の回数は、常駐の前段を通って反映した実行だけを数える。
1つのラウンドの取り直しは、開いたときの依頼を常に行い(開いたときの依頼は、取り直しの実行中でもすぐに始める)、端末のベースで開いた後の取り直し、効かなかった結果、重ねられなかった確定済みの操作は、オフラインでは行わない。端末のベースで開いている間は、`retryDelayMs`の間隔で取り直し、通信の復帰と見える状態で試行を0から数え直し、切断で時計を止める。

画面に渡す状態と変更の方法(`RoundsStore`)は、詳細を開く`load`、一覧を開く`loadList`、端末だけの一覧`loadLocalList`、開いた詳細の購読と追記`round`、追記`append`、ラウンドの削除`deleteRound`、プリセットの取得`loadPresets`・個人プリセットの削除`deletePreset`、ラウンドの開始`startRound`、完了`completeRound`・削除して離れる`deleteRoundAndLeave`・一覧へ戻る`leaveRound`、プリセットの保存`savePreset`、IDの払い出し`newId`・`newShotId`、通信の復帰の合図`whenOnline`、待ちの経過の合図`afterFallbackWait`を持つ。`loadList`は一覧の取得を自分で行う。合図は表示の読み直しと切り替えの合図で、同期の経路ではない。詳細は、端末の記録を読み、削除があれば取得せずに削除済みを返し、確定していない作成があれば取得せずに作成の操作を基準にする。サーバーの状態は同期が取得して反映した結果を待ち、通信できないとき(オフライン、取得の失敗、取得が`FALLBACK_WAIT_MS`を超えた)は、端末の記録が保持の規則に当たれば端末のベースで開く。全体を`FETCH_TIMEOUT_MS`で打ち切り、打ち切った時点の通信の可否でofflineかerrorを返す。端末の保存(`aims-sync`)は、現在の形のデータだけを前提にする。

流れは次のとおりである。

1. 操作を操作の列へ追記し、IndexedDBへの保存が完了した操作から画面の状態へ反映して送信する。保存の完了前の離脱で、画面に見えた操作を失わない(保存は約10msで、入力の遅れとして知覚されない)。画面は`selectRoundState(applyOperations(base, 操作の列))`だけから導き、読み込み時と操作時で同じ関数を使う。
2. 保存の完了後に、衝突の規則(`round-op-conflicts.ts`)で、同期の計画(`op-plan.ts`)が送れる要求を組む。衝突する先行がある操作は、先行が確定するまで送らない。作成に続く同じラウンドの操作は、作成の確定まで送らない。衝突しない操作は、止まった先行を待たず送る。矢の記録と取り消しは、距離ごとに別の要求(`record_shots`、`clear_shots`)へまとめて送る(1要求は同じ距離の矢だけ、100件まで。異なる距離の要求は並行して送ってよい)。
3. 書き込みRPCは、認可つきで、イベントIDにより冪等である。再送しても二重に適用されない。
4. 失敗は、`sync-failure.ts`が判定する。
   サーバーが認可の拒否(`PT403`)または契約の不一致(`PT422`)で拒否した操作だけを破棄する。破棄は、その操作を列から外す(`retire`)ことで、後続を止めない。
   未認証は破棄せず保留し、同じユーザーがサインインした時点で再送する。
   それ以外の失敗(通信失敗、5xx、408、429、認証の不明、例外、`PGRST202`を含むPostgRESTのコード、`P0001`など)は、上限なく待機して再試行する。
   2件以上の要求が破棄の対象になったときは、単独の要求に切り分け、拒否された1件だけを破棄する。
   サーバーは、受理した操作の各項目を確定の順で判定し、効かなかった項目を応答で返す。効かなかった操作は列から外し、効いた項目だけを確定として残す。
   効かなかった操作または項目がある応答を受けたとき、サーバーの状態を取り直してベースを差し替える。
   確定済みの操作をベースに重ねられなかったとき(ベースが他端末の変化を知らないとき)も、オンラインなら取り直す。
   それ以外の成功では再取得しない。
5. 効いた操作は、RPCが返した`revision`と効いた項目を付けて列に残す。確定の時点では外さない。列から取り除くのは、取得したベースが組に入るとき、そのベースに反映済みだと確かめた操作だけである。確かめるのは1つの規則(`reflectsBase`。確定の`revision`と取得の`revision`の比較)で、特例を持たない。失敗した操作は、再読み込み後に再送できるよう残す。
6. 試行の直前にオフラインなら送らず保留にする。この見送りはリトライ回数を消費しない。リトライ待機中のオフライン検知でも保留にする。保留からの再開は`online`イベントのみで行う。
7. 画面を開くと、サーバーの状態を取得して組へ反映する(`commit`)。ベースは新しい取得(`startedAt`)の方を使い、確定した`revision`が取得の`revision`以下の操作は列から外れる。残りは`seq`順にベースへ重ねて表示する。未確定の操作は、同じイベントIDで再送する。ベースの差し替えは取得の時点だけで行い、操作ごとには取得しない。
7a. ベースは、オンラインの間に、画面を開く取得のほかに、入力中のラウンドと端末が保持するラウンドの一括の取得(認証イベント・`online`・可視化のほか、一覧を開いたとき)でも更新する。保持の規則は、状態が入力中か、ベースに反映されていない操作(未送信、または確定済みで取得に未反映)が残るラウンドで、削除済みにも例外を設けない。当たらない(完了で送信済み、削除が受理された)ラウンドは、ベースも操作も端末に残さない。未送信の削除が残るラウンドはベースごと保持し、開くと削除済みとして一覧へ戻る。通信できないとき、保持するラウンドは端末のベースと操作の列で開く。
8. レコードは`userId`を持つ。現在の端末のユーザー以外のレコードは、表示と同期の対象から外し、削除しない。
9. 起動時に現在のユーザーの全ての列を読み、どの画面でも送る。
10. Web Locksで得たタブだけが送り、他のタブは追記してBroadcastChannelで知らせる。送るタブは、自分の追記の後も列を読み直してから送る。保留はチャネルで共有し、どのタブも同じ判定で扱う。
11. 送信の直前に、セッションのユーザーと列のユーザーを照合し、違えば保留する。

### DBの契約

- 書き込みは認可つきRPCに限り、RLSで直接の書き込みを禁止する。認可、不変条件、並行更新の検証はDB側で保証する。
- 変更は追記専用のイベントログに記録し、既存テーブルを同一トランザクションの射影とする。
- `create_round`は他の書き込みRPCと同じ形で、作成の`revision` 1を返す。重複の`event_id`は作成者を照合し、違えば`PT403`とする。
- 書き込みRPC(`create_round`、`update_round`、`create_distance`、`update_distance`、`disable_distance`、`record_shots`、`clear_shots`)は、操作ごとに`{revision, applied, applied_fields, rejected_fields, reason}`を返す。`disable_round`は従来どおり`revision`を返す。
- `record_shots`と`clear_shots`は、配列の先頭から順に1トランザクションで処理し、入力の順の結果の配列を返す。
- 設定の保存は、変えた項目だけを持つjsonbの差分(`p_changes`)で送る。`update_round`の差分は、ラウンドの状態(`status`。`rounds/completion`)も項目として持ち、常に効く。キーがあれば変えた項目、無ければ変えていない項目で、値のnullは「未設定にする」を表す(距離(m)だけ)。構成は的・エンド数・矢数の1組で、`config`キーに3項目を揃えて持つ。
- 判定は確定の時点の状態だけで行い、操作に前提の版を持たせない。効く項目は同じ項目の後勝ちで、規則に当たる項目だけを効かせない。
  - 削除: 削除済みのラウンド・距離への操作は効かない(`DISABLED`)。削除が勝つ。
  - 存在しない距離への操作は、認可より前に`MISSING`で効かないと返す(距離IDは推測できず、情報は漏れない)。
  - 矢: 矢は端末が作るUUID(`shot_id`)で指し(新しい矢は時刻順のUUID。作り方と並べ方は`rounds/score-entry`。サーバーはUUIDの版を確かめない)。現在の構成で無効な矢(エンドの範囲外、的に無い点数、射順が1〜矢数の外)は効かない(`UNFIT`)。
  - 矢数の上限: 生きている矢を増やす記録(新しい矢、消した矢の復活)は、距離の行をロックしてエンドの生きている矢を数え、矢数以上なら効かない(`UNFIT`)。制約トリガーが最後に止める(違反は例外で、再試行され続ける)。
  - 矢の項目: `record_shots`は要素に含まれる項目だけを変える。射手(`shooter_id`)と射順(`shot_number`)はキーがあるときだけ変え、新しい矢で射手が無ければ実行者にする。射順が同じエンドの他の生きている矢と重なるなら、射順の項目だけを効かせない。消した矢の復活で行の射順が重なるなら、射順をnullにして復活させる。部分一意索引が最後に止める。
  - 射手の保持: 端末は射手をこの端末の利用者として記録する矢の操作に射手を含めず、射手は変わらない(`rounds/sync`のE2E)。別の利用者を射手にした矢が、射手を含まない操作で書き換えられても射手を保つことは、DBのテスト(pgTAP、`supabase/tests/shot_identity.sql`)で担保する。
  - 存在しない矢のクリアは`MISSING`で、記録しない。取り消し済みの矢へのクリアは効いた操作として記録する。
  - 構成: 表示中の矢に新しい構成で無効なもの(射順の範囲を含む)があるか、生きている矢の数が新しい矢数を超えるエンドがあれば、3項目とも効かない(`UNFIT`)。効くときは表示中の矢を値も位置も変えずに引き継ぐ。画面は得点のある距離の構成を変えさせないため、遅れて届く変更への備えである。
  - 不変条件: Unmarkedはフィールドだけ、Markedは距離(m)必須。破る後の項目は効かせず(`INVARIANT`)、補正しない。同じ操作の中ではMarked/Unmarkedを距離(m)より先に判定するが、Markedの判定には同じ操作で変更する距離(m)(保存後の値)を使い、Markedと距離(m)の入力を同じ保存で両方効かせる。
- 記録は効いた項目だけをイベントに残す(`set_fields`)。効かなかった操作・項目と、破棄した操作は、どの表にも記録せず、射影も`revision`も変えない。
- `revision`は対象(ラウンド、距離、矢)ごとの1本で、効いた操作の確定の順に進む。
- 効いた操作の`event_id`の再送は、状態に依存する検証より先に照合し、記録した結果を返す。射影もイベントも変えず、後に別の操作で置き換わった値は戻らない。効かなかった操作は記録が無いため、遅れて届けば届いた時点の状態で判定する。
- 拒否は2種類で、認可の拒否は`PT403`、契約の不一致(配列でない、101件以上、`p_changes`の形が不正など)は`PT422`である。`PTxyz`は、Postgres自身のコードと重ならないよう、PostgRESTがHTTPステータスxyzで返す独自のSQLSTATEである。
- `event_id` はクライアント生成のUUIDで、冪等性キーである。順序はサーバーが対象ごとに採番する `revision` で決める。
- 削除は論理削除とする。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| 端末の順序を`autoIncrement`の`seq`で持ち、時計を使わない | 時計の戻りと同時刻で順序が崩れるため | 端末をまたいで順序を決めるとき |
| 衝突する組だけを順序づける | 全体を直列にすると、拒否や再試行中の1件が無関係な操作まで止めるため | 衝突の表で表せない依存が出たとき |
| 破棄の対象で2件以上の要求が拒否されたら、単独の要求に切り分ける | 1件の拒否が、同じ要求の正常な操作まで破棄するため | 要求を分ける必要がなくなったとき |
| いつ送り、いつ取り直すかを同期の1か所で決め、画面には状態と変更の方法だけを渡す | 経路の重複の解消(受け入れ条件12)と画面の検証の独立のため | 画面が送信の状態を表示するようになったとき |
| 画面の導出を`applyOperations`1つにする | 読み込み時と操作時で導出が食い違い、表示がちらつくため | 導出が1つで足りなくなったとき |
| 基準と最終状態をサーバーのテーブルの形にし、操作ごとの処理をRPCに1対1で対応させ、画面の形は`selectRoundState`で導く | サーバーの規則の変更が、対応するRPCの1か所へ写せ、画面の形への影響が投影で止まるため | サーバーのテーブルの形が変わるとき |
| 反映の判定は、RPCが返す`revision`と取得の`revision`の比較にする | 時刻や取得のやり直しの推測では、取得が確定の前後どちらに当たるか決められないため。取得は1つのスナップショットでなく、適用の前後を時刻で決められない | 取得が1つのスナップショットになったとき |
| 反映済みの判定に特例を持たない | 特例は、取得より新しく確定した取り消しだけを外し、前の記録が重なり直るため | 反映を確かめられない操作が増えたとき |
| 矢をUUIDで識別し、エンド内の位置を持たない | 位置で識別すると、入力した位置が射順と読まれ、2端末が同じ位置へ書くと先の矢が上書きで消えるため。距離を作るときに矢の枠を先に作る案は、2端末が同じ空の枠へ書いて点数が消えるため採らない | 矢を位置で指す入力を設けるとき |
| 矢数の上限を、確定の時点に距離の行のロックの下で数え、トリガーでも守る | 端末・タブ・オフラインの追加は互いに知らずに届くため、確定の順で先の矢を残す。RPCの判定に漏れがあってもDBで守る | 上限を利用者に知らせる要求が出たとき |
| 矢の書き込みは要素に含まれる項目だけを変える | 点数の変更が、他端末が後で変えた射手・射順を古い値で戻さないため | 項目ごとの差分の操作を別に設けるとき |
| ベースと操作の列を1つの組として、端末では1つのトランザクション、タブでは1回の通知で変える | 別のDBやstoreを別々に書くと原子的に書けず、他のタブの画面で、ベースが古いまま列から操作だけが外れて点数が消えるため。`ops`と`bases`を同じDB(`aims-sync`)に置く | 組を変える書き込みが1つのトランザクションで足りなくなったとき |
| 変更をIndexedDBへ先に永続化し、非同期に送る | 書き込み完了を待つと入力が遅く、再読み込みや通信断で記録を失うため。Realtimeによる他端末の変更の受信は対象外である | 他端末との共同編集が要るとき |
| 同期の状態(送信中、保留、送信済み)を画面に表示しない | 同期は自動で行われ、利用者が関与せず、表示が求める対処も無いため。表示はそのラウンドを開いている間しか見えず、対処が要る場面の手がかりとしても弱い | 利用者が対処すべき同期の問題を知らせる要求が出たとき |
| 同じキーの新しい操作による古い操作のキャンセルをやめた | 距離の作成が編集で上書きされて消える、古い値が復活する、矢の取り消しより先に設定変更が届いて拒否される、の不整合が出るため。 | 圧縮を入れるとき |
| オンライン判定は `navigator.onLine` に頼る | 実通信の可否は保証されないが、誤判定時はバックオフを待って再試行するだけで害が小さいため | 誤判定による再試行の遅れが利用者の問題になったとき |
| リトライに回数の上限を設けない(待機は3秒から2倍で60秒まで) | 破棄は回復しないと分かる拒否(`PT403`、`PT422`)だけにするため、それ以外は回復を待つ方が操作を失わないため。失敗を伝える画面を持たず、再試行を続ける | 再試行が続いていることを利用者へ伝える要求が出たとき |
| 作成を操作の列に載せる | 通信の無い現場でも開始でき、同期の規則を作成と他の変更で揃えるため | - |
| プリセット削除、サインアウトを操作の列に載せない | 破壊的で低頻度であり、オフライン対応が不要なため。完了までダイアログで待ち、失敗時は再試行できる | オフラインでの削除を認めるとき |
| 同時に1回までの扉は常駐の取得と取り直しにだけ置き、一覧と開く依頼は依頼ごとに並行して実行する | 一覧と開く依頼が、同じ種類の先の実行も含めて他の実行を待たずに、自分の取得の時間で返るため(変更前の並行の関係)。並行する結果は、開始の新しい実行の結果を正とし、端末の記録への反映は開始時刻とrevisionで古い取得を退けるため、整合は保たれる | 同じ取得の結果を分け合う必要が出たとき |
| データベースの約束はスキーマの形を型引数で受け、起動地点で生成した型と照合する | 約束に技術の型を含めずに、RPCの名前と引数、表と列の誤りをコンパイルで検出するため | 生成した型の形(`Functions`、`Tables`)が変わったとき |
| 画面は`RoundsStore`だけから列へアクセスし、ユーザーは記録のハブで解決する | 入り口が複数あると、一覧・詳細・作成・削除の読み書きがユーザーや削除済みの規則で食い違うため | 列の種類が増えるとき |
| プリセットの保存を、保留中の書き込みの完了を待たないローカル起点にする | 完了を待つと、操作の列のリトライ中にダイアログが閉じられず固まるため、待つ方式をやめた。DBから読み直すサーバー起点は採らない | 保存直後にサーバーの値との一致が要る要求が出たとき。詳細: #472 |
| 破棄は`PT403`と`PT422`だけにする。区別できない失敗は残して再試行する | `PGRST202`はデプロイ直後のスキーマキャッシュの遅れでも同じ応答になり、`P0001`は業務ルール違反と対象なしを区別できない。判定を1か所(`sync-result.ts`)に集め、区別できない失敗は残す側に倒す | 失敗の種類をコードで区別できるようになったとき。詳細: #650 |
| 同じ項目は、確定の順の後勝ちにする。操作に前提の版を持たせない | 前提を持たせると、他端末の変更を知らずに保存した操作が効かなくなり、利用者の保存が消えるため。収束先は確定の順だけで決まる | 利用者が競合を見て選ぶ要求が出たとき |
| 1回の保存を、1つの操作として送る | 項目ごとの操作に分けると、1回の保存が複数の要求とイベントになり、同じ保存の項目の間の規則(構成と距離(m)など)を判定できないため | 項目ごとに別々に再送する要求が出たとき |
| `revision`を項目ごとに持たない | 項目ごとの後勝ちは確定の順に効いた項目を置き換えるだけで版の比較を要さず、取得の反映の判定は対象ごとの比較で足りるため | 項目ごとの履歴を見せる要求が出たとき |
| 構成の変更は、表示中の矢が全て有効なときだけ効かせる | 先に確定した矢を、後から届いた構成の変更で失わないため。構成は的・エンド数・矢数の1組で、一部だけ効かせない | 矢を新しい構成へ移す要求が出たとき |
| 不変条件を破る後の項目は効かせ、補正しない(Unmarkedはフィールドだけ、Markedは距離(m)必須) | サーバーが利用者の指定していない値を変えないため。クライアントは保存前に知らせる | 他端末との競合を自動で解く要求が出たとき |
| 構成ごとに新しい距離を作る方式を採らない | 距離の同一性、プリセット、履歴、集計に影響が広がるため | 構成の履歴を持つ要求が出たとき |
| 効かなかった項目がある応答のときに、ラウンド全体を取り直す。イベントの増分は取らない | イベントの版は対象ごとで、ラウンドを通した順序が無く、効かなかった操作は記録されないため。1ラウンドの取得は小さい | ラウンドを通した版(イベントの増分の取得)が要る場合やRealtimeを扱うとき |
| 複数タブのうち、Web Locksで得た1つのタブだけが送る | 効かなかった操作は記録されず、遅れて届けば届いた時点で判定されるため、2つのタブが同じ操作を送ると、衝突する操作の確定の順が逆転する。SharedWorkerはAndroid Chromeに無く、Service Workerはセッションを持たず内容を扱わない設計のため採らない | 端末をまたいで順序を決めるとき |
| 送るタブは、自分の追記を保存した後にも、列をIndexedDBから読み直してから送る | 他のタブの先の追記を知らずに後の操作を送ると逆転するため。`seq`の小さい操作は保存が先に完了している | 追記ごとの読み直しが入力の遅れとして知覚されたとき |
| 送信の直前に、セッションのユーザーと列のユーザーを照合する | 常駐の送信はサインインし直しをまたいで動くので、イベントの順序だけでは、別のユーザーの認証で送らないことを保証できないため | 共有端末で秘匿が必要になったとき |
| 未送信の操作を、端末の最後にサインインしたユーザーごとに分ける | オフラインでは `proxy.ts` が実行されず、JWTの有効期限に頼れないため。暗号的な機密性は対象外とする | 共有端末で秘匿が必要になったとき |
| 端末DBの保存の形を変えるときはversionを上げ、更新では全てのstoreを内容を移行せずに作り直す | 版ごとの移行の分岐を持たずに、どの版の端末でも開けるようにするため。未送信の操作も捨てる | 未送信の操作を更新で失えない要求が出たとき |
| 取得の新旧は、開始時刻に加えてrevisionで比べる | 同時に始まった取得では、後から始まった取得が先の状態を返すことがあり、開始時刻では決められないため | revisionを持たないデータを列に足すとき |

## 制約と未対応

- 組が消えた後に、別のタブが古い取得を反映すると復活しうる(送信器のメモリはタブごと)。
- 認可で拒否された削除は破棄され、ラウンド一覧を取得し直したときに、通知なく再表示される。
- 同期は、アプリの画面が1つでも開いている間だけ動き、全て閉じると止まる(閉じた後の送信は扱わない)。
- 同期の状態を表示しないため、未送信の操作を端末に残したままアプリを閉じたとき(通信のある状態で開き直すまで送られない)と、更新前のビルドの旧いタブや背景で凍結されたタブが送る役を持って送信が止まったときに、利用者は画面からそれに気づけない。
- IndexedDBへ保存できない端末では、開始したラウンドの詳細は、作成の確定まで見つからない表示になりうる。
- サインイン切れは共通のガードがサインイン画面へ導き、サインイン後に遷移元へ戻る（`app/navigation`、`auth/signin`）。
- 別のユーザーでサインインしたとき、前のユーザーの未送信は送らず、表示せず、残す。そのユーザーが再びサインインしたときに送る。
- アクセストークンの更新の失敗はauth-jsが60秒キャッシュする。不明は上限なく再試行するため、通信が回復すれば自動で再送される。
- 他端末の操作で置き換わった値を、利用者が見て復元する手段は無い。別の作業で扱う。
- 効かなかった操作は記録されず、復元できない。
- 確定した操作は、取得(画面を開く取得、一括の取得)でベースとともに外れるまで端末に残る。
- 矢数を超えて効かなかった矢の追加・復活と、射順が重なって効かなかった射順の書き込みは、利用者に知らせない。取り直すまでの間、他端末が消した古い矢が見えることがある(件数は矢数を超えない)。
- 送る役のタブを閉じる直前に送った要求が遅れて届き、その操作が引き継いだタブの再送では効かず、遅れて届いた時点では効く場合に限り、衝突する後続より後に効き得る(効かなかった操作は記録されず、届いた時点で判定されるため)。
- 送る役のタブが背景で抑制・凍結されている間は、他のタブの送信が遅れ得る。操作は失われず、凍結が解けるか、そのタブを閉じれば送られる。送る役は、タブを閉じたときだけ移る。
- Web Locksの無いブラウザでは各タブが送り、複数タブの間の順序を保証しない。IndexedDBへの保存に失敗した操作は、持っているタブが送り、タブ間の順序を保証しない。どちらも二重には適用されない。
