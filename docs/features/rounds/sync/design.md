# sync 設計

## 概要

ラウンド詳細画面（`/rounds/[id]`）の変更操作は、サーバーの完了を待たずに画面へ反映する（楽観的UI）。
操作はまずIndexedDBの操作の列へ追記し、送信器がバックグラウンドで認可つきの書き込みRPCを呼ぶ。
操作の列は追記専用で、端末の順序は`autoIncrement`の`seq`で持つ。送信は、衝突する組だけを順序づけて行い、失敗時のリトライ、オフライン中の保留、オンライン復帰時の再送を持つ。
画面の状態は、サーバーの状態へ操作の列を重ねる`applyOperations`1つだけから導く。
対象はラウンド・距離・矢の変更で、ラウンド削除、プリセット削除、サインアウトは対象外である（完了を待つダイアログで行う）。

## 画面と状態

同期状態は5つで、画面上部の固定ヘッダーに4種類の文言で表示する。
複数が同時に成り立つときは、表の上から優先して表示する。

| 状態 | 意味 | 表示 | 要求 |
| :--- | :--- | :--- | :--- |
| 同期保留中 | オフラインのため送らずに待っている | 「同期保留中」 | sync-04, 05, 12 |
| リトライ待機 | オンラインで送信が失敗し、次の試行を待っている。衝突する後続の操作も止まる | 「同期中…」 | sync-06, 07, 11, 13 |
| 送信中 | 保存中、または送信中の操作がある | 「同期中…」 | sync-02 |
| 送信失敗 | リトライを使い切った、再試行しても回復しない拒否、またはサインインが必要。衝突する後続の操作は止まる | 「同期失敗」 | sync-09, 14 |
| 同期済み | 未送信の操作も失敗もない | 「同期済み」 | sync-01, 03 |

- 「同期失敗」をクリックすると、最も古い未解決の失敗1件を、操作名とエラー内容のポップアップで表示する。
- リトライの待機時間は3秒、6秒、12秒、24秒で、4回を使い切ると送信失敗にする。

## 構成とデータの流れ

汎用の部分は`apps/web/src/features/op-log/`、ラウンドの部分は`apps/web/src/app/(main)/rounds/[id]/`に置く。

- `op-log-store.ts`: DB`aims-sync`のstore`ops`(`seq`が`autoIncrement`)。追記、`loadStream`、`ack`、`retire`。
- `op-plan.ts`: 送れる要求の計画。衝突する先行がある操作を含めない。
- `op-sync.ts`: 送信器。リトライ、オフライン中の保留、拒否した要求の切り分け。
- `sync-result.ts`: 送信結果を、再試行する・止めて残す・成功の確定に分ける。認証を確認できない結果を、失敗の結果へ変換する。
- `sync-status.ts`、`sync-types.ts`: 件数から状態を導く。型。
- `round-op-conflicts.ts`: 操作の衝突の表と、並べる単位(lane)。
- `round-op-apply.ts`: 画面の状態の導出`applyOperations`。
- `round-op-transport.ts`: 操作の種類ごとにRPCを呼び、確定した`revision`を返す。送信前に`classifySession`で認証を確認する。
- `use-round-op-stack.ts`: 送信器のフック。`scorecard-client.tsx`が、状態、同期状態、操作の追記に使う。
- `sync-events.ts`: 操作の型。操作はクライアント生成のイベントIDを持つ。
- `load-round-detail.ts`、`fetch-round-detail.ts`: 画面を開くときの取得と、反映済みの判定。
- `apps/web/src/features/auth/session-state.ts`の`classifySession`: `getSession()`の結果を認証済み・未認証・不明に分ける。

流れは次のとおりである。

1. 操作を操作の列へ追記し、IndexedDBへの保存が完了した操作から画面の状態へ反映して送信する。保存の完了前の離脱で、画面に見えた操作を失わない(保存は約10msで、入力の遅れとして知覚されない)。画面は`applyOperations(base, 操作の列)`だけから導き、読み込み時と操作時で同じ関数を使う。
2. 保存の完了後に、衝突の規則(`round-op-conflicts.ts`)で送れる要求を組む。衝突する先行がある操作は、先行が確定するまで送らない。衝突しない操作は、止まった先行を待たず送る。矢の記録と取り消しは、距離ごとに別の要求(`record_shots`、`clear_shots`)へまとめて送る(1要求は同じ距離の矢だけ、100件まで。異なる距離の要求は並行して送ってよい)。
3. 書き込みRPCは、認可つきで、イベントIDにより冪等である。再送しても二重に適用されない。
4. 失敗は、`sync-result.ts`が判定する。
   通信失敗、サーバー障害（5xx）、408、429、認証の不明（アクセストークンの更新が通信失敗）、例外は、待機して再試行する。
   未認証と、サーバーが拒否した（408・429以外の4xx）失敗は、再試行しない。拒否した操作は、同じ対象の後続を止めて列に残し、サーバーの状態へ自動で戻さない。
   2件以上の要求が拒否されたときは、単独の要求に切り分け、拒否された1件だけを止める。
   同期の成功でも再取得せず、楽観値を正とする。サーバーの状態の取得は、画面を開くときだけである。
5. 成功した操作は、RPCが返した`revision`を付けて列に残す。列から取り除くのは、次に画面を開いたとき、取得した対象ごとの`revision`が確定した`revision`以上だと確かめた操作だけである(`retire`)。失敗した操作は、再読み込み後に再送できるよう残す。
6. 試行の直前にオフラインなら送らず保留にする。この見送りはリトライ回数を消費しない。リトライ待機中のオフライン検知でも保留にする。保留からの再開は`online`イベントのみで行う。
7. 画面を開くと、サーバーの状態を取得し、操作の列を読み直す。列は、取得の前後に読んだ結果を`eventId`で合わせて使う。確定した`revision`が取得の`revision`以下の操作は重ねず、それ以外は`seq`順に重ねて表示する。未確定の操作は、同じイベントIDで再送する。
8. レコードは`userId`を持つ。現在の端末のユーザー以外のレコードは、表示と同期の対象から外し、削除しない。

### DBの契約

- 書き込みは認可つきRPCに限り、RLSで直接の書き込みを禁止する。認可、不変条件、並行更新の検証はDB側で保証する。
- 変更は追記専用のイベントログに記録し、既存テーブルを同一トランザクションの射影とする。
- 各RPCは、確定した対象の`revision`を返す。確定済みの`event_id`の再送は、状態に依存する検証より先に判定し、拒否せず既存の`revision`を返す。
- `record_shots`と`clear_shots`は、配列の先頭から順に1トランザクションで処理し、入力の順の`revision`の配列を返す。
- `event_id` はクライアント生成のUUIDで、冪等性キーである。順序はサーバーが対象ごとに採番する `revision` で決める。
- 削除は論理削除とする。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| 端末の順序を`autoIncrement`の`seq`で持ち、時計を使わない | 時計の戻りと同時刻で順序が崩れるため | 端末をまたいで順序を決めるとき |
| 衝突する組だけを順序づける | 全体を直列にすると、拒否や再試行中の1件が無関係な操作まで止めるため | 衝突の表で表せない依存が出たとき |
| 保存先は既存のDBを作り直し、移行しない | 旧形式の未送信の操作を取り込む仕組みを持たないため | 旧形式の操作が残る利用者が無視できないとき |
| 拒否で2件以上の要求が止まったら、単独の要求に切り分ける | 1件の拒否が、同じ要求の正常な操作まで止めるため | 要求を分ける必要がなくなったとき |
| 画面の導出を`applyOperations`1つにする | 読み込み時と操作時で導出が食い違い、表示がちらつくため | 導出が1つで足りなくなったとき |
| 反映の判定は、RPCが返す`revision`と取得の`revision`の比較にする | 時刻や取得のやり直しの推測では、取得が確定の前後どちらに当たるか決められないため。取得は1つのスナップショットでなく、適用の前後を時刻で決められない | 取得が1つのスナップショットになったとき |
| 変更をIndexedDBへ先に永続化し、非同期に送る | 書き込み完了を待つと入力が遅く、再読み込みや通信断で記録を失うため。Realtimeによる他端末の変更の受信は対象外である | 他端末との共同編集が要るとき |
| 同じキーの新しい操作による古い操作のキャンセルをやめた | 距離の作成が編集で上書きされて消える、古い値が復活する、矢の取り消しより先に設定変更が届いて拒否される、の不整合が出るため。 | 圧縮を入れるとき |
| 「同期保留中」はオフラインそのものを表し、リトライ待機は「同期中」と表示する | 利用者が対処できない待機と、通信を待つ保留を区別するため | 利用者がリトライ待機を保留と区別する必要が出たとき |
| オンライン判定は `navigator.onLine` に頼る | 実通信の可否は保証されないが、誤判定時は従来どおりバックオフを消費して「同期失敗」になるだけで害が小さいため | 誤判定による「同期失敗」が利用者の問題になったとき |
| リトライを4回使い切ったら「同期失敗」にする | 無期限に再送すると、失敗を利用者へ伝えられないため | 通信の一時的な不調で4回では足りない失敗が多発したとき |
| ラウンド削除、プリセット削除、サインアウトを操作の列に載せない | 破壊的で低頻度であり、オフライン対応が不要なため。完了までダイアログで待ち、失敗時は再試行できる | オフラインでの削除を認めるとき |
| プリセットの保存を、保留中の書き込みの完了を待たないローカル起点にする | 完了を待つと、操作の列のリトライ中にダイアログが閉じられず固まるため、待つ方式をやめた。DBから読み直すサーバー起点は採らない | 保存直後にサーバーの値との一致が要る要求が出たとき。詳細: #472 |
| 失敗した操作を自動で破棄しない。失敗は、再試行する・止めて残すの2つに分け、判定を1か所に集める | `permanent` が再試行の停止と、削除・通知を兼ねていたため、認証を確認できない失敗が削除された。PostgRESTの`P0001`は、RPCの業務ルール違反と対象なしを区別できない既定のコードで、コードで破棄を決めると回復可能な操作も失う。判定はHTTPステータスの区分で行い、回復しない拒否は残す側に倒す | 残った操作を利用者が取り消せるようにするとき。詳細: #650 |
| 未送信の操作を、端末の最後にサインインしたユーザーごとに分ける | オフラインでは `proxy.ts` が実行されず、JWTの有効期限に頼れないため。暗号的な機密性は対象外とする | 共有端末で秘匿が必要になったとき |

## 制約と未対応

- 同期の処理は画面と同じ寿命で、ページを閉じると止まる。常駐と並列実行は #501 で扱う。
- ラウンド作成は操作の列の対象外である。サインイン切れは共通のガードがサインイン画面へ導き、サインイン後に遷移元へ戻る（`app/navigation`、`auth/signin`）。
- 未認証で確定した操作は、同じ画面でサインインし直しても自動では再送されず、画面を開き直したときに再送される。別のユーザーでサインインしたときの前のユーザーの未送信は残り続ける。
- アクセストークンの更新の失敗はauth-jsが60秒キャッシュする。不明の再試行は合計45秒（3+6+12+24秒）のため、通信の回復を待てないことがある。使い切っても操作の列には残り、再読み込み後に再送できる。
- 止めて残した操作を、利用者が再送・取り消しする手段が無く、画面を開くたびに再送して「同期失敗」になる。段階(2)で自動で解決する。
- サーバーが拒否した操作の楽観値は、利用者が解消するまで画面に残る。操作の列に残る限り、再読み込みでも重ね合わせで再び出る。拒否された操作は同じ対象の後続を止め、再読み込み後も残る。
- 確定した操作は、そのラウンドの画面を次に開いて反映が確かめられるまで端末に残る。開き直されないラウンドの分は残り続けるが、後続の段階と#501で解消する。影響は保存量と開いたときの比較の件数で、表示と送信は変わらない。
- 同じラウンドを複数のタブで同時に編集したときの順序の逆転は扱わない（#501の送信者の調整で扱う）。重複は冪等で無害である。
