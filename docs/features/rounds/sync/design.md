# sync 設計

## 概要

ラウンド詳細画面（`/rounds/[id]`）の変更操作は、サーバーの完了を待たずに画面へ反映する（楽観的UI）。
操作はまずIndexedDBの操作の列へ追記し、タブに常駐する送信の集まりが、どの画面を表示していても認可つきの書き込みRPCを呼ぶ。各タブは自分の追記を送る。ホームも詳細もメモリの記録で作る。
操作の列は追記専用で、端末の順序は`autoIncrement`の`seq`で持つ。送信は、衝突する組だけを順序づけて行い、失敗時のリトライ、オフライン中の保留、オンライン復帰時の再送を持つ。
1回の保存を1つの操作として送り、サーバーが確定の順で項目ごとに、後勝ちと規則(決定1、削除、不変条件)で判定する。
サーバーが拒否するのは認可と契約の不一致だけで、他は受理したうえで効かせない項目を応答で返す。
画面の状態は、ベース(取得したサーバーの状態)へ操作の列を重ねる`applyOperations`1つだけから導く。
ベースと操作の列は、ラウンドごとに1つの組として、端末(IndexedDB)とタブ(送信器のメモリ)の2か所に持ち、組を変える書き込みは、端末では1つのトランザクション、タブでは1回の反映で行う。
ベースは取得のたびに差し替わり、反映済みの操作は、差し替えと同時に列から外れる。
対象はラウンドの作成・削除と、ラウンド・距離・矢の変更で、プリセット削除、サインアウトは対象外である（完了を待つダイアログで行う）。

## 画面と状態

同期の状態は画面に表示しない。送信器の操作は次の状態をとる。

| 状態 | 意味 |
| :--- | :--- |
| 保留 | 送らずに待っている(オフライン、またはサインインが必要)。オンラインへの復帰か、サインインし直しで送る |
| リトライ待機 | オンラインで送信が失敗し、次の試行を待っている。衝突する後続の操作も止まる |
| 送信中 | 保存中、または送信中の操作がある |
| 送信済み | 未送信の操作がない |

- リトライの待機時間は3秒から2倍ずつ増やして60秒で頭打ちにし、回数に上限を設けない。
- 同期の状態、送信の失敗、破棄は、画面に表示しない。

## 構成とデータの流れ

機能は2つで、依存は同期からラウンドの一方向である(ラウンドは同期を知らない)。パスは`apps/web/src/`からの相対で示す。

- ラウンド(`features/rounds/`): 業務の規則、端末の記録、画面に渡す正しい状態と変更の方法、送信の機構(送信器、列ごとの送信の状態、送れる要求の計画、失敗の分類、操作の送信と確定の記録)、ベースの取得と反映を持つ。
- 同期(`features/round-sync/`): 契機を受けて、いつ取り直すかを決める唯一の手続きと、契機の受け取りを持つ。他の機能へ公開する名前が無いため、入口を置かない。ラウンドの入口が公開する記録の制御`RoundRecordControl`(3操作: `start`、`isRecordUser`、`signInChanged`)と、取り直しの制御`RoundRefreshControl`(4操作: `refreshNeeds`、`onRefreshNeeds`、`refreshAll`、`refreshRound`)の、平らな操作だけを使う。送信の内部の概念(送信の待ち、保留、リトライ待機、衝突、lane、失敗の分類)は境界を越えない。サインインの変化への反応(保留の再開)と、通信の回復での再送は、ラウンドが決める。利用者の切り替えはラウンドが行わず、認証の見張りが記録の利用者(`isRecordUser`)との不一致でページ全体を読み込み直す。
- 画面は、画面ごとの文脈から受け取る状態と変更の方法(履歴の取得は`RoundsListStore`、端末内の入力中一覧(ホーム、点数一覧の除外)と詳細は`RoundWindow`。ラウンドの開始画面は窓口を持たず手続きの入れ物から受ける)だけを使う。共通の構造は[`rounds/design.md`](../design.md)に従う。取得の状態(読み込み中、オフライン、見つからない、エラー)は、画面に渡す見え方の型に持たせる。詳細の窓口は、IDを購読すると記録から存在と画面の状態を導き、ラウンドの取得を1回始める(`retry`で取り直す)。効かなかった結果の取り直しは同期が決める。
- パッケージ: 画面は`react`、端末の保存は`idb`(`lib/local-op-log/`だけ)、データベースは`@supabase/supabase-js`(機能では認証のインフラ層だけ。他は`lib/supabase/`)を使う。ラウンドと同期は、非画面のパッケージを直接参照しない。

| `lib/local-op-log/` | `lib/<能力>`(操作の列の端末の保存) | 約束`contract/op-log-store.ts`と、IndexedDBの実装`infrastructure/indexeddb-op-log-store.ts`。DB`aims-sync`のstore`ops`(`seq`が`autoIncrement`)と`bases`(キーは`[userId, streamId]`。取得の開始時刻`startedAt`とベース。サーバーに無い`null`は保存に書かず、以前の版が書いた行を読むときだけ現れる)。追記、`loadAll`(現在のユーザーの組)、取得したベースを反映する`commit`、`ack`、`retire`、アカウント削除のための`erase`(指定した利用者の`ops`と`bases`の行を1トランザクションで消す。他の利用者と利用者なしの行は消さない)。組を変える`commit`・`ack`・追記は`ops`と`bases`にまたがる1つのトランザクションで行い、途中で失敗すれば両方とも変えない。`commit`は、保存済みより`startedAt`が古い取得では何も変えない。保存済みのベース、または記録が最後に取り込んだベースよりrevisionが古い取得も反映しない(`isOlder`)。新しければ、ベースに反映済みの操作を消し、保持の規則に当たればベースを保存し、当たらなければ組(ベースと操作)を丸ごと消す。`null`(サーバーに無い)のときは、確定済みの操作を全て消してベースの行を消し、未送信の操作だけを残す(印は保存しない。未送信の操作は、破棄で組ごと消え、確定では次の取得の反映で消える)(ベースに反映されていない操作が残る組は必ず当たる。古い取得で新しい保存を上書き・削除しない)。`ack`は確定を記録するだけで、操作を消さない。versionの更新が古い版の接続で塞がれているときは、接続を閉じも失敗にもせず、塞ぎが解けるまで開く処理が待つ(画面の読み込みは既存の10秒で「読み込めませんでした。」になる)。versionの更新では、全てのstoreを内容を移行せずに作り直す |
| `lib/clock/`、`lib/connectivity/`、`lib/supabase/` | `lib/<能力>` | 時刻(`Clock`)、通信の可否(`Connectivity`。復帰の通知を持つ)、データベースへの問い合わせ、削除、手続きの呼び出し(スキーマの形を型引数で受ける`DatabaseGateway<S>`と実装。ラウンドは使う部分の型`RoundsDbSchema`を、生成した型の`Pick`で宣言し、入口が型引数に渡して受け取る) |
| `SessionReader`の`readSession`(認証の機能の入口が公開する型。実装は`features/auth/infrastructure/supabase-auth.ts`) | 認証の入口 | 保存先を読み直して、認証済み・未認証（確定）・不明に分ける。同期は`SessionReader`の型で直接、取得と送信の手続きも`SessionReader`の型で、送信と取得のたびに読む。認証の変化は`SignInChanges`の型で同期の契機の受け取りが1本だけ受ける |

契機の受け取り(`sync-triggers.ts`)は、契機を同期の手続きの操作に変える。サインインの変化は、そのまま記録の制御へ渡る。契機の購読は開始で一度行い、解除しない(停止の経路を持たない)。

| 契機 | 反応 |
| :--- | :--- |
| 開始 | `sync.start(端末の識別情報の利用者)`。開始の中で常駐の一括の取得を1回頼む(サインインの通知を待たない) |
| サインインの変化(終了を含む) | `sync.signInChanged(change)`。signed-inは保留した送信を戻し(別の利用者の送信は送信器の照合が保留のままにする)、サインアウトでは何もしない。利用者の無い変化と判断できない変化は何もしない。記録の利用者と違う利用者のサインインは、`(main)`の間は認証の見張りが識別情報を書いて今の場所を読み込み直し、新しい文書がその利用者の記録で起動する。サインインの完了は、それ自体がページ全体の置き換えで、新しい文書が最初からその利用者の記録で起動するので、見張りは読み込み直さない |
| 通信の復帰 | 上の`sync.resume()`。送信器は通信の回復を自分で購読し、リトライ待機の要求をすぐに再送する |
| 通信の復帰、画面が見える状態 | `sync.resume()`(常駐の取得を頼む)。切断は購読しない |

照合の結果ごとの反応は、認証の通知は上の表のとおり、送る前は`same`と`unowned`で送り`other`で未認証として保留、常駐の一括の取得の前段は`same`だけ行い、取得したベースの反映は`same`だけ端末へ保存して他はこのタブだけに反映する。

同期の手続き(`round-sync.ts`)は、常駐の一括の取得と、ラウンドごとの取り直しを、それぞれ同時に1回までにする。詳細の窓口の取得(購読の開始、作成の確定、`retry`)は扉を通さず、窓口が自分で始める。これらは互いを待たない。
一括の取得は、常駐の契機(起動、通信の復帰、画面が見える状態)で行う。サインインの通知と、ホーム・点数一覧を開くことは契機ではない。サインイン済みで記録の利用者と同じときだけ取得と反映を行う。一括の取得の対象は、端末が持つ(ベースか操作がある)ラウンドのうち、作成が確定しているものとし、削除の操作の有無では分けない。返らなかった対象は保存を消し、メモリの記録だけが削除済み(ベース`null`)を持つ(確定していない作成は、サーバーにまだ無いため対象にしない)。取得の問い合わせ(個別と一括)には、ライブラリの再試行(GETの520・503とネットワークの例外を最大3回)を付ける。
1つのラウンドの取り直しは、見つからなかったとき、一括と同じく保存を消してメモリの記録を削除済みにする(未確定の作成だけが起点のラウンドは書かない)。詳細の窓口は、購読の開始ごとに取得を1回始め(サーバーに無いラウンドは、作成が確定した時点で1回。メモリが削除済みのラウンドは取得しない)、効かなかった結果の取り直しは、オフラインでは行わない。端末のベースで開いている間に取得が失敗しても、定期的な取り直しは行わず、次の契機まで保存済みの表示が続く。的は、窓口が個別に取得する(常駐の一括の完了を待たない)。

画面に渡す状態と変更の方法は履歴と詳細の2つの窓口で、詳細と端末内の入力中一覧は窓口(`RoundWindow`)の`watch`/`view`/`retry`/`append`、`watchLocalList`/`localList`が、履歴の取得は`RoundsListStore`の`loadList`が持つ。詳細の画面は、完了(ホームへ)・削除して離れる(遷移元へ)・戻る(遷移元へ)・プリセットの保存・IDの払い出しの手続きを、ホームと点数一覧の画面は、ラウンドの削除の手続きを(点数一覧は`whenOnline`も)、ラウンドの開始画面は、ラウンドの開始・個人プリセットの削除・プリセットの取得・`whenOnline`を、窓口を通さず手続きの入れ物から受ける。通信の復帰の合図`whenOnline`は、手続きの入れ物から受ける(詳細の窓口は同じ契約で、offlineの間の自動の再取得を窓口の内側で行う)。`loadList`は履歴の取得を自分で行う。合図は表示の読み直しと切り替えの合図で、同期の経路ではない。詳細は、メモリの記録で、削除があれば取得せずに存在しないとし、確定していない作成があれば取得せずに作成の操作を基準にする。端末にベースと的があれば、取得の結果を待たず、取得が失敗しても端末のベースで開く。記録の読み込みを10秒で打ち切り、打ち切った時点の通信の可否でofflineかerrorを出す。各取得は`fetchContent`の10秒で打ち切る。端末の保存(`aims-sync`)は、現在の形のデータだけを前提にする。

流れは次のとおりである。

1. 操作を操作の列へ追記し、追記の直後に画面の状態へ反映する。送信は、IndexedDBへの保存が完了した操作だけを対象にする(サーバーへは保存の完了前の操作を送らない)。保存の完了前に画面を離れると、保存が未完の末尾の数件が端末に残らない窓がある(保存は通常数ms〜十数msだが、連打、取得の反映の直後、CPUの遅い機器で伸びる。Safari系は未実測)。保存の完了は画面の状態を変えない。画面は`selectRoundState(applyOperations(base, 操作の列))`だけから導き、読み込み時と操作時で同じ関数を使う。
2. 保存の完了後に、衝突の規則(`round-op-conflicts.ts`)で、送信器の計画(`op-plan.ts`)が送れる要求を組む。衝突する先行がある操作は、先行が確定するまで送らない。作成に続く同じラウンドの操作は、作成の確定まで送らない。衝突しない操作は、止まった先行を待たず送る。矢の記録と取り消しは、距離ごとに別の要求(`record_shots`、`clear_shots`)へまとめて送る(1要求は同じ距離の矢だけ、100件まで。異なる距離の要求は並行して送ってよい)。
3. 書き込みRPCは、認可つきで、イベントIDにより冪等である。再送しても二重に適用されない。
4. 失敗は、`sync-failure.ts`が判定する。
   サーバーが認可の拒否(`PT403`)または契約の不一致(`PT422`)で拒否した操作だけを破棄する。破棄は、その操作を列から外す(`retire`)ことで、後続を止めない。
   未認証は破棄せず保留し、同じユーザーがサインインした時点で再送する。
   それ以外の失敗(通信失敗、5xx、408、429、認証の不明、例外、`PGRST202`を含むPostgRESTのコード、`P0001`など)は、上限なく待機して再試行する。
   2件以上の要求が破棄の対象になったときは、単独の要求に切り分け、拒否された1件だけを破棄する。
   サーバーは、受理した操作の各項目を確定の順で判定し、効かなかった項目を応答で返す。効かなかった操作は列から外し、効いた項目だけを確定として残す。
   効かなかった操作または項目がある応答を受けたとき、サーバーの状態を取り直してベースを差し替える。
   それ以外の成功では再取得しない。
5. 効いた操作は、RPCが返した`revision`と効いた項目を付けて列に残す。確定の時点では外さない。列から取り除くのは、取得したベースが組に入るとき、そのベースに反映済みだと確かめた操作だけである。確かめるのは1つの規則(`reflectsBase`)で、確定の`revision`と取得の`revision`を比べ、射手の追加は取得の射手の一覧の番号で確かめる。失敗した操作は、再読み込み後に再送できるよう残す。
6. 試行の直前にオフラインなら送らず保留にする。この見送りはリトライ回数を消費しない。リトライ待機中のオフライン検知でも保留にする。保留からの再開は`online`イベントのみで行う。
7. 画面を開くと、サーバーの状態を取得して組へ反映する(`commit`)。ベースは新しい取得(`startedAt`)の方を使い、確定した`revision`が取得の`revision`以下の操作は列から外れる。残りは`seq`順にベースへ重ねて表示する。未確定の操作は、同じイベントIDで再送する。ベースの差し替えは取得の時点だけで行い、操作ごとには取得しない。
7a. ベースは、オンラインの間に、画面を開く取得のほかに、入力中のラウンドと端末が保持するラウンドの一括の取得(認証イベント・`online`・可視化。ホーム・点数一覧を開いたときは含めない)でも更新する。保持の規則は、状態が入力中か、ベースに反映されていない操作(未送信、または確定済みで取得に未反映)が残るラウンドで、削除済みにも例外を設けない。当たらない(完了で送信済み、削除が受理された)ラウンドは、ベースも操作も端末に残さない。未送信の削除が残るラウンドはベースごと保持し、開くと削除済みとして遷移元へ戻る。通信できないとき、保持するラウンドは端末のベースと操作の列で開く。
8. レコードは`userId`を持つ。現在の端末のユーザー以外のレコードは、表示と同期の対象から外し、削除しない。
9. 起動時に現在のユーザーの全ての列を読み、どの画面でも送る。
10. 各タブは自分の追記を送る。起動時は、保存から読み込んだ操作を全て読んでから送る。
11. 送信の直前に、セッションのユーザーと列のユーザーを照合し、違えば保留する。

### DBの契約

- 書き込みは認可つきRPCに限り、RLSで直接の書き込みを禁止する。認可、不変条件、並行更新の検証はDB側で保証する。
- 変更は追記専用のイベントログに記録し、既存テーブルを同一トランザクションの射影とする。
- `create_round`は他の書き込みRPCと同じ形で、作成の`revision` 1を返す。重複の`event_id`は作成者を照合し、違えば`PT403`とする。
- 書き込みRPC(`create_round`、`update_round`、`disable_round`、`create_distance`、`update_distance`、`disable_distance`、`record_shots`、`clear_shots`)と`add_round_shooter`は、操作ごとに`{revision, applied, applied_fields, rejected_fields, reason}`の形で返す(`create_round`、`disable_round`、`disable_distance`、`add_round_shooter`は`applied_fields`と`rejected_fields`を持たず、`add_round_shooter`の`revision`はnull)。
- `record_shots`と`clear_shots`は、配列の先頭から順に1トランザクションで処理し、入力の順の結果の配列を返す。
- 設定の保存は、変えた項目だけを持つjsonbの差分(`p_changes`)で送る。`update_round`の差分は、ラウンドの状態(`status`。`rounds/completion`)も項目として持ち、常に効く。キーがあれば変えた項目、無ければ変えていない項目で、値のnullは「未設定にする」を表す(距離(m)だけ)。構成は的・エンド数・射数/エンドの1組で、`config`キーに3項目を揃えて持つ。
- 判定は確定の時点の状態だけで行い、操作に前提の版を持たせない。効く項目は同じ項目の後勝ちで、規則に当たる項目だけを効かせない。
  - 削除: 削除済みのラウンド・距離への操作は効かない(`DISABLED`)。削除が勝つ。削除済みのラウンドを別の`event_id`で削除する要求と、取り消し済みの矢を別の`event_id`で取り消す要求も、書かずに`DISABLED`で返す(履歴に同じ消去を並べない)。同じ`event_id`の再送は、既存の`revision`を返す。
  - 存在しない距離への操作は、認可より前に`MISSING`で効かないと返す(距離IDは推測できず、情報は漏れない)。
  - 矢: 矢はマス(`distance_id`、`end_number`、`shot_number`)で指し、矢のIDを持たない。要素の`end_number`と`shot_number`は1以上の整数で、外れれば契約の不一致(`PT422`)である。現在の構成で無効な記録(エンドがエンド数を超える、マスの番号が射数/エンドを超える、的に無い点数)は効かない(`UNFIT`)。
  - 同じマス: `record_shots`は、マスに行があれば上書きし(消した行は生き返る)、無ければ行を作る。同じマスへの記録・取り消しは、確定の順の後勝ちである。
  - 射数/エンドの上限: マスの範囲の判定(距離の行のロックの下で行う)と、マスごとに1行(主キー)であることで守り、生きている矢を数えない。範囲内のマスの数が射数/エンドに等しいため、生きている矢は射数/エンドを超えない。
  - 矢の項目: `record_shots`は点数と射手番号を必須とし、両方を書く(`rounds/shooters`)。取り消しは射手番号を変えない。
  - 射手の追加: `shooter.added`は`add_round_shooter`を単独の要求で呼ぶ。応答は`{revision: null, applied, reason}`で、成功は確認済みの印(`ackedRevision = 0`)で保存し、取得の射手の一覧に番号が現れるまで列に残す。`applied`が偽の操作は列から外す。
  - ベースの新旧: 残っているラウンドで、既知の射手番号が欠けた取得は古いベースとする(射手は一覧から消えないため)。
  - 行の無いマスのクリアは`MISSING`、取り消し済みのマスのクリアは`DISABLED`で、どちらも記録しない。
  - 構成: 表示中の矢に新しい構成で無効なもの(新しい範囲の外のマスの矢、新しい的に無い点数)があれば、3項目とも効かない(`UNFIT`)。同じ保存の他の項目は効く。効くときは表示中の矢を値もマスも変えずに引き継ぐ。画面は得点のある距離の構成を変えさせないため、遅れて届く変更への備えである。
  - 不変条件: Unmarkedはフィールドだけ、Markedは距離(m)必須。破る後の項目は効かせず(`INVARIANT`)、補正しない。同じ操作の中ではMarked/Unmarkedを距離(m)より先に判定するが、Markedの判定には同じ操作で変更する距離(m)(保存後の値)を使い、Markedと距離(m)の入力を同じ保存で両方効かせる。
- 記録は効いた項目だけをイベントに残す(`set_fields`)。効かなかった操作・項目と、破棄した操作は、どの表にも記録せず、射影も`revision`も変えない。
- `revision`は対象(ラウンド、距離、矢(マス))ごとの1本で、効いた操作の確定の順に進む。
- 効いた操作の`event_id`の再送は、状態に依存する検証より先に照合し、記録した結果を返す。射影もイベントも変えず、後に別の操作で置き換わった値は戻らない。効かなかった操作は記録が無いため、遅れて届けば届いた時点の状態で判定する。
- 拒否は2種類で、認可の拒否は`PT403`、契約の不一致(配列でない、101件以上、`p_changes`の形が不正など)は`PT422`である。`PTxyz`は、Postgres自身のコードと重ならないよう、PostgRESTがHTTPステータスxyzで返す独自のSQLSTATEである。
- `event_id` はクライアント生成のUUIDで、冪等性キーである。順序はサーバーが対象ごとに採番する `revision` で決める。
- 削除は論理削除とする。

### 更新前の矢の移行

矢をマスで指す形への変更は、1つのmigrationが1トランザクションで、既存の行を新しい形へ写す。矢の状態によらず必ず完了し、失敗で止まらない。

- 生きている矢(`disabled_at`がnull)は、エンドごとに、点数の高い順(X、10、9、…、1、M。Xは同じ`score_int`の10より上、Mは最下位)、同点は旧`id`の昇順(更新前の表示の順)で、1から順にマスの番号(射順)を振る。旧`shot_number`の値は使わない。点数・射手・`revision`・時刻は変えない。
- 取り消し済みの矢の行と、その矢の`shot_events`は消す。生きている矢の`shot_events`は、旧`shot_id`の代わりに振ったマスで指し、`shot_number`を振った番号にし、`set_fields`から`shot_number`を除く。`revision`は変えず、マスの`revision`は旧い矢の続きになる。
- 振った番号は射数/エンド以下、エンドはエンド数以下に収まり、範囲の補正は持たない。矢と構成の書き込みはRPCだけで、`record_shots`はエンドの範囲と生きている矢の数を、`update_distance`は構成を狭める変更を、距離の行のロックの下で判定してきたためである。範囲はDBの制約でなくRPCが守るため、移行が範囲によって失敗することもない。
- 的に無い点数の矢はそのまま残す。削除済みの距離・ラウンドの矢も同じ規則で写す。
- 写した後に、`shots`の主キーをマスにし(`id`を消し、`shot_number`をNOT NULLにする)、`shot_events`の`shot_id`を消してマスの3列をNOT NULLにし、一意の制約を`(distance_id, end_number, shot_number, revision)`にする。生きている矢の索引(`shots_live_end_idx`、`shots_live_shot_number_key`)は主キーが代わるため消す。`record_shots`・`clear_shots`・`shot_fits`・`update_distance`は新しい契約で作り直す。RLS(`select_if_member`)と`updated_at`のトリガーは`id`に依存しないため変えない。
- 端末の保存(`aims-sync`)はversionを上げ、既存の規則どおり、未送信の操作とベースを移行せずに捨てる。送信を完了した記録はサーバーにあり、更新後の取得で表示される。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| 端末の順序を`autoIncrement`の`seq`で持ち、時計を使わない | 時計の戻りと同時刻で順序が崩れるため | 端末をまたいで順序を決めるとき |
| 衝突する組だけを順序づける | 全体を直列にすると、拒否や再試行中の1件が無関係な操作まで止めるため | 衝突の表で表せない依存が出たとき |
| 破棄の対象で2件以上の要求が拒否されたら、単独の要求に切り分ける | 1件の拒否が、同じ要求の正常な操作まで破棄するため | 要求を分ける必要がなくなったとき |
| いつ送り、いつ取り直すかを同期の1か所で決め、画面には状態と変更の方法だけを渡す | 経路の重複の解消(受け入れ条件12)と画面の検証の独立のため | 画面が送信の状態を表示するようになったとき |
| 画面の導出を`applyOperations`1つにする | 読み込み時と操作時で導出が食い違い、表示がちらつくため | 導出が1つで足りなくなったとき |
| 基準と最終状態をサーバーのテーブルの形にし、操作ごとの処理をRPCに1対1で対応させ、画面の形は`selectRoundState`で導く | サーバーの規則の変更が、対応するRPCの1か所へ写せ、画面の形への影響が投影で止まるため | サーバーのテーブルの形が変わるとき |
| 反映の判定は、RPCが返す`revision`と取得の`revision`の比較にする | 時刻や取得のやり直しの推測では、取得が確定の前後どちらに当たるか決められないため。取得は1つのスナップショットでなく、適用の前後を時刻で決められない。射手の追加は`revision`を持たないため、取得の射手の一覧の番号で確かめる | 取得が1つのスナップショットになったとき |
| 反映済みの判定に特例を持たない | 特例は、取得より新しく確定した取り消しだけを外し、前の記録が重なり直るため | 反映を確かめられない操作が増えたとき |
| 矢をマス(距離、エンド、マスの番号)で識別し、矢のIDを持たない。マスの番号を射順にする | マスが射順を兼ね、1つのマスの矢が1本に決まるため。矢をIDで識別して射順を別に持つ方式は、同じマスの2本を防ぐ規則(射順の重なりを効かせない、復活で射順を外す)と、並べるための時刻順のIDが要るためやめた | 1つのマスに複数の矢を持つ要求(射手別のマスなど)が出たとき |
| 同じマスへの記録・取り消し・生き返りを、確定の順の後勝ちにする | 同じマスは同じ1本の矢で、ラウンド・距離の項目と同じ規則で収束させるため。先に確定した矢を残して後の記録を効かせない案は、戻る・直しが知らない他端末の書き込みに負けて利用者の操作が消えるため採らない。上書きされた矢は利用者に知らせない(要求の対象外) | 利用者が上書きを知る・選ぶ要求が出たとき |
| 射数/エンドの上限を、マスの範囲の判定と主キーで守り、生きている矢を数えない | 範囲内のマスの数が射数/エンドに等しく、上書きは矢の数を増やさないため、範囲を守れば数は超えない。範囲の判定は距離の行のロックの下で行い、構成の変更と直列にする | 1つのマスに複数の矢を持つとき |
| 矢の記録は点数と射手を1つの操作で書く | 射手の指定を必須にし、同じマスを射手を含めて後に保存した内容にするため(`rounds/shooters`) | 射手を指定せずに点数だけを変える操作を設けるとき |
| ベースと操作の列を1つの組として、端末では1つのトランザクション、タブでは1回の反映で変える | 別のDBやstoreを別々に書くと原子的に書けず、画面で、ベースが古いまま列から操作だけが外れて点数が消えるため。`ops`と`bases`を同じDB(`aims-sync`)に置く | 組を変える書き込みが1つのトランザクションで足りなくなったとき |
| 変更をIndexedDBへ先に永続化し、非同期に送る | 書き込み完了を待つと入力が遅く、再読み込みや通信断で記録を失うため。Realtimeによる他端末の変更の受信は対象外である | 他端末との共同編集が要るとき |
| 同期の状態(送信中、保留、送信済み)を画面に表示しない | 同期は自動で行われ、利用者が関与せず、表示が求める対処も無いため。表示はそのラウンドを開いている間しか見えず、対処が要る場面の手がかりとしても弱い | 利用者が対処すべき同期の問題を知らせる要求が出たとき |
| 同じキーの新しい操作による古い操作のキャンセルをやめた | 距離の作成が編集で上書きされて消える、古い値が復活する、矢の取り消しより先に設定変更が届いて拒否される、の不整合が出るため。 | 圧縮を入れるとき |
| オンライン判定は `navigator.onLine` に頼る | 実通信の可否は保証されないが、誤判定時はバックオフを待って再試行するだけで害が小さいため | 誤判定による再試行の遅れが利用者の問題になったとき |
| リトライに回数の上限を設けない(待機は3秒から2倍で60秒まで) | 破棄は回復しないと分かる拒否(`PT403`、`PT422`)だけにするため、それ以外は回復を待つ方が操作を失わないため。失敗を伝える画面を持たず、再試行を続ける | 再試行が続いていることを利用者へ伝える要求が出たとき |
| 作成を操作の列に載せる | 通信の無い現場でも開始でき、同期の規則を作成と他の変更で揃えるため | - |
| ラウンド・距離・矢の変更は操作列への追記(`RoundRecordHub.append`)を通し、書き込みRPCの呼び出しは送信部(`round-op-transport.ts`)に集める。新しい書き込みの種類は、操作列に載せるか、載せない理由をここに書く | 画面や手続きがRPCを直接呼ぶと、オフラインで入力が消え、二重送信、順序の逆転、イベントの不整合が起きるため。画面と手続きはDB接続の実装をimportできない(biome) | 操作列を使わない書き込みが要るとき |
| プリセットの保存・削除、サインアウトを操作の列に載せない | 破壊的で低頻度であり、オフライン対応が不要なため。完了までダイアログで待ち(上限10秒)、失敗時は再試行できる | オフラインでの削除を認めるとき |
| 同時に1回までの扉は常駐の取得と取り直しにだけ置き、履歴と詳細の窓口の取得は扉を通さず並行して実行する | 履歴と詳細の窓口が、同じ種類の先の実行も含めて他の実行を待たずに、自分の取得の時間で返るため。並行する結果は、開始の新しい実行の結果を正とし、端末の記録への反映は開始時刻とrevisionで古い取得を退けるため、整合は保たれる | 同じ取得の結果を分け合う必要が出たとき |
| データベースの約束はスキーマの形を型引数で受け、入口で生成した型と照合する | 約束に技術の型を含めずに、RPCの名前と引数、表と列の誤りをコンパイルで検出するため | 生成した型の形(`Functions`、`Tables`)が変わったとき |
| 画面は自分の窓口(`RoundsListStore`、`RoundWindow`)と手続きの入れ物の手続きだけから列へアクセスし、ユーザーは記録のハブで解決する | 入り口が複数あると、ホーム・点数一覧・詳細・作成・削除の読み書きがユーザーや削除済みの規則で食い違うため | 列の種類が増えるとき |
| プリセットの保存を、保留中の書き込みの完了を待たないローカル起点にする | 完了を待つと、操作の列のリトライ中にダイアログが閉じられず固まるため、待つ方式をやめた。DBから読み直すサーバー起点は採らない | 保存直後にサーバーの値との一致が要る要求が出たとき。詳細: #472 |
| 破棄は`PT403`と`PT422`だけにする。区別できない失敗は残して再試行する | `PGRST202`はデプロイ直後のスキーマキャッシュの遅れでも同じ応答になり、`P0001`は業務ルール違反と対象なしを区別できない。判定を1か所(`sync-result.ts`)に集め、区別できない失敗は残す側に倒す | 失敗の種類をコードで区別できるようになったとき。詳細: #650 |
| 同じ項目は、確定の順の後勝ちにする。操作に前提の版を持たせない | 前提を持たせると、他端末の変更を知らずに保存した操作が効かなくなり、利用者の保存が消えるため。収束先は確定の順だけで決まる | 利用者が競合を見て選ぶ要求が出たとき |
| 1回の保存を、1つの操作として送る | 項目ごとの操作に分けると、1回の保存が複数の要求とイベントになり、同じ保存の項目の間の規則(構成と距離(m)など)を判定できないため | 項目ごとに別々に再送する要求が出たとき |
| `revision`を項目ごとに持たない | 項目ごとの後勝ちは確定の順に効いた項目を置き換えるだけで版の比較を要さず、取得の反映の判定は対象ごとの比較で足りるため | 項目ごとの履歴を見せる要求が出たとき |
| 構成の変更は、表示中の矢が全て新しい範囲のマスにあり有効なときだけ効かせる | 先に確定した矢を、後から届いた構成の変更で失わないため。構成は的・エンド数・射数/エンドの1組で、一部だけ効かせず、同じ保存の他の項目は効かせる | 矢を新しい構成へ移す要求が出たとき |
| 不変条件を破る後の項目は効かせ、補正しない(Unmarkedはフィールドだけ、Markedは距離(m)必須) | サーバーが利用者の指定していない値を変えないため。クライアントは保存前に知らせる | 他端末との競合を自動で解く要求が出たとき |
| 構成ごとに新しい距離を作る方式を採らない | 距離の同一性、プリセット、履歴、集計に影響が広がるため | 構成の履歴を持つ要求が出たとき |
| 効かなかった項目がある応答のときに、ラウンド全体を取り直す。イベントの増分は取らない | イベントの版は対象ごとで、ラウンドを通した順序が無く、効かなかった操作は記録されないため。1ラウンドの取得は小さい | ラウンドを通した版(イベントの増分の取得)が要る場合やRealtimeを扱うとき |
| 各タブが自分の追記を送り、タブの間の知らせ・送る役の選出・保留の共有を持たない | 他のタブの影響を反映する仕組みを持たず、各タブを独立させて簡略にするため。ホームも詳細もメモリの記録で作るため、別のタブの変更は再読み込みまで見えない | 他のタブの変更の即時反映、または複数タブの送信順序の保証が要るとき |
| ホームの「入力中」と削除済みは、メモリの記録から作る | 1つのタブでは、記録の更新と保存の更新が同じ順で進み、取得の反映で保存の組が消える列も、メモリは保存と同じ規則で扱うため、ホームは保存を読み直さなくても再読み込み後と一致する。保存を読み直す処理と、書き込みに失敗した列を別に扱う処理を持たずに済む | 別のタブの変更をホームに即時に反映する要求が出たとき |
| 送信の直前に、セッションのユーザーと列のユーザーを照合する | 常駐の送信はサインインし直しをまたいで動くので、イベントの順序だけでは、別のユーザーの認証で送らないことを保証できないため | 共有端末で秘匿が必要になったとき |
| 未送信の操作を、端末の最後にサインインしたユーザーごとに分ける | オフラインでは `proxy.ts` が実行されず、JWTの有効期限に頼れないため。暗号的な機密性は対象外とする | 共有端末で秘匿が必要になったとき |
| 更新前の版の端末が送る矢のID(`shot_id`)の形の要素は受けず、契約の不一致(`PT422`)で破棄し、知らせない | 射順を持たない旧い要素をマスへ写す規則と、旧い形を受ける経路を持たずに済むため。破棄は送信器が後続を止めずに行う | - |
| 更新前の生きている矢に、エンドごとに点数の高い順・同点は旧`id`の昇順で射順を振る | 更新前の表示の順をそのまま射順として残し、見た目と合計・小計を変えないため。旧`shot_number`はアプリが送らず値を持たないため使わない | - |
| 移行で、取り消し済みの矢の行とその履歴を消す | 新しい主キーはマスに1行のため、取り消し済みの行を残すと生きている矢とマスを取り合い、範囲外か衝突になるため。取り消し済みの矢は表示・集計に使わない | - |
| 端末DBの保存の形を変えるときはversionを上げ、更新では全てのstoreを内容を移行せずに作り直す | 版ごとの移行の分岐を持たずに、どの版の端末でも開けるようにするため。未送信の操作も捨てる | 未送信の操作を更新で失えない要求が出たとき |
| 取得の新旧は、開始時刻に加えてrevisionで比べる | 同時に始まった取得では、後から始まった取得が先の状態を返すことがあり、開始時刻では決められないため | revisionを持たないデータを列に足すとき |
| 同期は、ラウンドの記録を自分で持たず、ラウンドが公開する制御の平らな操作(`RoundRecordControl`、`RoundRefreshControl`)だけを呼ぶ。同期が持つのは取り直しの扉だけで、記録の正はラウンドである。同じ記録の知らせが重ねて届いても、取り直しは重ねて実行しない | 同じ事実を2か所に持つと食い違い、通知は合図にすぎないため | 同期が記録の解釈に要る結果を返すようになったとき |

## 制約と未対応

- 組が消えた後に、別のタブが古い取得を反映すると復活しうる(送信器のメモリはタブごと)。新しい対策は持たない。
- 別のタブが残した未送信の操作は、開いているタブから送られず、次にアプリを開き直すまで遅れる。受け入れる。
- 両方のタブで同じラウンドを削除すると、後に削除したタブのホーム・点数一覧にそのラウンドが戻って見える。画面が見える状態に復帰して常駐の取得が走ると消える。受け入れる。
- 認可で拒否された削除は破棄され、履歴を取得し直したときに、通知なく再表示される。
- 同期は、アプリの画面が1つでも開いている間だけ動き、全て閉じると止まる(閉じた後の送信は扱わない)。
- 同期の状態を表示しないため、未送信の操作を端末に残したままアプリを閉じたとき(通信のある状態で開き直すまで送られない)に、利用者は画面からそれに気づけない。
- IndexedDBへ保存できない環境(書き込みの失敗を含む)は想定しない。保存できない環境では、操作が保存されず送られず、開始したラウンドの詳細は見つからない表示になりうる。
- サインイン切れは共通のガードがサインイン画面へ導き、サインイン後に遷移元へ戻る（`app/navigation`、`auth/signin`）。
- 別のユーザーでサインインしたとき、前のユーザーの未送信は送らず、表示せず、残す。そのユーザーが再びサインインしたときに送る。
- アクセストークンの更新の失敗はauth-jsが60秒キャッシュする。不明は上限なく再試行するため、通信が回復すれば自動で再送される。
- 他端末の操作で置き換わった値を、利用者が見て復元する手段は無い。別の作業で扱う。
- 効かなかった操作は記録されず、復元できない。
- 確定した操作は、取得(画面を開く取得、一括の取得)でベースとともに外れるまで端末に残る。
- 同じマスへの記録が他端末の後の記録で置き換わったことと、範囲外のマスで効かなかった記録は、利用者に知らせない。取り直すまでの間、他端末が置き換えた・消した古い点数が見えることがある。
- 複数のタブで同じマスを変えたり消したりしたときの送信順序を保証しない。
- 未送信の操作を持つタブを閉じると、その操作は端末に残り、次の起動などの機会まで送られない。
- 端末の保存の版更新が、古い版のタブの接続で塞がれている間は、保存の読み書きが終わらず、ホームと詳細が10秒後に「読み込めませんでした。」になる。塞がれている間、保存の内容は保持される。古いタブを閉じて再読み込みし、版更新が完了すると読み込みが再開する。版更新の完了時は、既存の仕様どおり、未送信を含む既存の保存内容が破棄される。端末の保存の内容の移行は対象外である。
- 矢をマスで指す形へ変えた版の公開時、更新前の版の端末が送る矢のID(`shot_id`)の形の要素は、契約の不一致(`PT422`)で破棄され、知らせない。更新の時点で未送信だった記録は、端末の版更新でも破棄され、保証しない(送信を完了した記録は「更新前の矢の移行」で残る)。
- 更新前の版の端末は、取得の列(`shots.id`)がサーバーに無いため取得が失敗し、新しい版へ更新するまで端末に保持した内容で表示するか「読み込めませんでした。」になる。
- migrationの適用(CD)と新しい版のアプリの公開の間は、更新前の版の端末の矢の記録が破棄される。
