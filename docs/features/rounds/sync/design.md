# sync 設計

## 概要

ラウンド詳細画面（`/rounds/[id]`）の変更操作は、サーバーの完了を待たずに画面へ反映する（楽観的UI）。
操作はまずIndexedDBへ永続化し、送信キューがバックグラウンドで認可つきの書き込みRPCを呼ぶ。
送信は、失敗時のリトライ、オフライン中の保留、オンライン復帰時の再送を持つ。
対象はラウンド・距離・矢の変更で、ラウンド削除、プリセット削除、サインアウトは対象外である（完了を待つダイアログで行う）。

## 画面と状態

同期状態は5つで、画面上部の固定ヘッダーに4種類の文言で表示する。
複数が同時に成り立つときは、表の上から優先して表示する。

| 状態 | 意味 | 表示 | 要求 |
| :--- | :--- | :--- | :--- |
| 同期保留中 | オフラインのため送らずに待っている | 「同期保留中」 | sync-04, 05 |
| リトライ待機 | オンラインで送信が失敗し、次の試行を待っている | 「同期中…」 | sync-06, 07, 11 |
| 送信中 | 保存中、または送信中の操作がある | 「同期中…」 | sync-02 |
| 送信失敗 | リトライを使い切った、再試行しても回復しない拒否、またはサインインが必要 | 「同期失敗」 | sync-09 |
| 同期済み | 未送信の操作も失敗もない | 「同期済み」 | sync-01, 03 |

- 「同期失敗」をクリックすると、最も古い未解決の失敗1件を、操作名とエラー内容のポップアップで表示する。
- リトライの待機時間は3秒、6秒、12秒、24秒で、4回を使い切ると送信失敗にする。

## 構成とデータの流れ

`apps/web/src/app/(main)/rounds/[id]/` の次のファイルで構成する。

- `use-sync-queue.ts`: 送信キューのフック。`scorecard-client.tsx` が状態の表示とポップアップに使う。
- `sync-events.ts`: 操作の型。操作はクライアント生成のイベントIDを持つ。
- `sync-outbox.ts`: IndexedDBへの永続化。
- `sync-shots.ts`、`sync-shot-batch.ts`: 矢の記録・取り消しを距離単位でまとめて送る。
- `sync-result.ts`: 送信結果を、再試行する・止めて残す・成功の確定に分ける。送信側が返す失敗の種類をここで判定する。認証を確認できない結果を、失敗の結果へ変換する。
- `sync-retry.ts`: リトライ待機とオフライン中の保留。
- `sync-restore.ts`: 画面を開いたときの未送信の操作の復元。
- `sync-status.ts`: 件数から状態を導く。
- `apps/web/src/features/auth/session-state.ts` の `classifySession`: `sync-events.ts` と `sync-shots.ts` が送信前の認証確認に使う。`getSession()` の結果を認証済み・未認証・不明に分ける。

流れは次のとおりである。

1. 操作は、IndexedDBへ先に保存してから送信キューへ積む。画面は楽観値をすぐ反映する。
2. ラウンド・距離の操作は、ラウンド単位の1本の直列キューで順に送る。作成中の距離への操作は、作成の完了を待つ。
3. 矢は距離単位でまとめて送る。同じマスの未送信の古い値は、新しい値に置き換える。距離の設定変更は、その距離の未送信の矢の完了を待つ。
4. 書き込みRPCは、認可つきで、イベントIDにより冪等である。再送しても二重に適用されない。
5. 送信側は失敗の種類（認証の状態、HTTPステータス、例外）だけを返し、`sync-result.ts` が判定する。送信前に `getSession()` の結果を `classifySession` で認証済み・未認証・不明に分ける。
   通信失敗、サーバー障害（5xx）、408、429、認証の不明（アクセストークンの更新が通信失敗）、例外は、待機して再試行する。
   未認証と、サーバーが拒否した（408・429以外の4xx）失敗は、再試行しない。拒否した操作も、サーバーの状態へ戻さない。
6. 成功だけをIndexedDBから取り除く。失敗した操作は、再読み込み後に再送できるよう残す。
7. 試行の直前にオフラインなら送らず保留にする。この見送りはリトライ回数を消費しない。リトライ待機中のオフライン検知でも保留にする。保留からの再開は `online` イベントのみで行う。
8. 画面を開くと、IndexedDBに残る未送信の操作を依存順に積み直し、同じイベントIDで再送する。
9. レコードは `userId` を持つ。現在の端末のユーザー以外のレコードは、表示と同期の対象から外し、削除しない。

### DBの契約

- 書き込みは認可つきRPCに限り、RLSで直接の書き込みを禁止する。認可、不変条件、並行更新の検証はDB側で保証する。
- 変更は追記専用のイベントログに記録し、既存テーブルを同一トランザクションの射影とする。
- `event_id` はクライアント生成のUUIDで、冪等性キーである。順序はサーバーが対象ごとに採番する `revision` で決める。
- 削除は論理削除とする。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| :--- | :--- | :--- |
| 変更をIndexedDBへ先に永続化し、非同期に送る | 書き込み完了を待つと入力が遅く、再読み込みや通信断で記録を失うため。Realtimeによる他端末の変更の受信は対象外である | 他端末との共同編集が要るとき |
| 同じキーの新しい操作による古い操作のキャンセルをやめた | 距離の作成が編集で上書きされて消える、古い値が復活する、矢の取り消しより先に設定変更が届いて拒否される、の不整合が出るため。 | 順序を保つ別の仕組みを入れるとき |
| 「同期保留中」はオフラインそのものを表し、リトライ待機は「同期中」と表示する | 利用者が対処できない待機と、通信を待つ保留を区別するため | 利用者がリトライ待機を保留と区別する必要が出たとき |
| オンライン判定は `navigator.onLine` に頼る | 実通信の可否は保証されないが、誤判定時は従来どおりバックオフを消費して「同期失敗」になるだけで害が小さいため | 誤判定による「同期失敗」が利用者の問題になったとき |
| リトライを4回使い切ったら「同期失敗」にする | 無期限に再送すると、失敗を利用者へ伝えられないため | 通信の一時的な不調で4回では足りない失敗が多発したとき |
| ラウンド削除、プリセット削除、サインアウトを送信キューに載せない | 破壊的で低頻度であり、オフライン対応が不要なため。完了までダイアログで待ち、失敗時は再試行できる | オフラインでの削除を認めるとき |
| プリセットの保存を、保留中の書き込みの完了を待たないローカル起点にする | 完了を待つと、キューのリトライ中にダイアログが閉じられず固まるため、待つ方式をやめた。DBから読み直すサーバー起点は採らない | 保存直後にサーバーの値との一致が要る要求が出たとき。詳細: #472 |
| 失敗した操作を自動で破棄しない。失敗は、再試行する・止めて残すの2つに分け、判定を1か所に集める | `permanent` が再試行の停止と、削除・通知を兼ねていたため、認証を確認できない失敗が削除された。PostgRESTの`P0001`は、RPCの業務ルール違反と対象なしを区別できない既定のコードで、コードで破棄を決めると回復可能な操作も失う。判定はHTTPステータスの区分で行い、回復しない拒否は残す側に倒す | 残った操作を利用者が取り消せるようにするとき。詳細: #650 |
| 未送信の操作を、端末の最後にサインインしたユーザーごとに分ける | オフラインでは `proxy.ts` が実行されず、JWTの有効期限に頼れないため。暗号的な機密性は対象外とする | 共有端末で秘匿が必要になったとき |

## 制約と未対応

- 同期の処理は画面と同じ寿命で、ページを閉じると止まる。常駐と並列実行は #501 で扱う。
- ラウンド作成は送信キューの対象外で、サインイン切れの共通のリダイレクトと再認証後の再送もない（#303）。
- 未認証で確定した操作は、同じ画面でサインインし直しても自動では再送されず、画面を開き直したときの復元で再送される。別のユーザーでサインインしたときの前のユーザーの未送信は残り続ける。
- アクセストークンの更新の失敗はauth-jsが60秒キャッシュする。不明の再試行は合計45秒（3+6+12+24秒）のため、通信の回復を待てないことがある。使い切ってもoutboxには残り、再読み込み後に再送できる。
- 止めて残した操作を、利用者が再送・取り消しする手段が無く、画面を開くたびに再送して「同期失敗」になる（#645）。
- サーバーが拒否した操作の楽観値は、再読み込みまで画面に残る。
- 先行の操作が残ったまま後続が成功すると、再読み込みの再送で先行が後続を上書きする（#501）。
