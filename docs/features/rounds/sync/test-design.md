# 矢のマス目形式(同期・DB・移行)のテスト設計

## 基準と範囲

基準は[syncの要件](requirements.md)・[設計](design.md)(「更新前の矢の移行」を含む)と[ERD](../../../erd.md)の「矢の記録」だけである。
実装やマイグレーションの内容から期待値を導かない。
画面と指すマスの規則は[score-entryのテスト設計](../score-entry/test-design.md)で扱う。
既存の同期の規則(ラウンド・距離の項目ごとの後勝ち、失敗の再送、サインイン、削除)は変更対象外であり、既存テストを維持する。

優先順位は、更新で既存の記録を失わない・合計と小計が変わらないこと、同じマスの後勝ちと別のマスが残ること、射数/エンドの上限、旧い形の要素の安全な破棄の順とする。

## テスト層と観測

| 層 | 保証する内容 | 観測方法 |
| --- | --- | --- |
| 単体(Vitest、domain) | 操作の衝突、重ね合わせ`applyOperations`、送信の計画 | 純粋関数の入力と戻り値。 |
| 単体(Vitest、application・infrastructure) | RPCの要求の形、旧形式の拒否の扱い、端末DBの版更新、取り直しに`overlay`が無いこと | 公開の窓口と送信部。外部は偽物で隔離する。 |
| DB(pgTAP) | RPCの契約、主キーと制約、履歴、移行 | 実DBの行と応答。期待値表と実測を全件比較する行列テストを維持する。 |
| E2E(Playwright) | オフラインで同じマスを書き直す、他の端末と同じマス・別のマスへ書く経路 | 実ブラウザ・実DB。他端末は`helpers/other-device.ts`。 |
| 手動確認 | 本番に近いデータでの移行の前後の比較、更新前の版の端末の振る舞い | 下の「移行の確認」。 |

| 同じ操作の列を重ねても結果は変わらない。衝突しない操作の入れ替えで結果は変わらない | 冪等性と交換の既存の検証を、マス目形式で維持する。 | 結果が同じ。 |
| 同じマスの操作は適用順で最後が残る | 同じマスへ別の点数を2回、記録とクリアの順を入れ替えて重ねる。 | 後の操作の結果になる。 |

### 移行(更新前の矢をマスへ写す)

目的は、「更新は必ず完了し、生きている矢の合計・小計が変わらず、取り消し済みが残らない」ことの保証である。
ケースは更新前の形のデータを用意して移行を実行し、結果を確かめる。
実行の方式は、pgTAPのトランザクション内で行う(確定済み)。手順は次のとおりである。
1. `supabase db reset`後の最終形から、`shots`と`shot_events`を更新前の形へDDLで戻す(`id`・`shot_id`の列、旧い主キーと制約、`shot_number`のNULL許可、旧い一意索引)。DDLはトランザクション内なので巻き戻せる。
2. 更新前の形のデータ(下の表の前提)を投入する。
3. 移行SQLの本体を、`\i`などで同じトランザクション内に読み込んで実行する。前提は、移行のSQLが単体で再実行でき、実行の前後でCIの`supabase test db`がファイルを読める置き場とパスにあることである。
4. 結果を検証し、巻き戻す。
成立しない場合(更新前の形へ戻せない、移行SQLを読み込めないなど)は、手動確認(案B)で代替し、CIへ前までを適用してから移行を適用する工程を足す案(案C)の要否を添えて、再度判断を求める。体系の追加は、判断なしに行わない。

| テスト名の案 | 更新前の前提 | 期待結果 |
| --- | --- | --- |
| 各エンドで点数の高い順(X、10、9、…、1、M)に1から射順が振られる | 1エンドに順不同の点数(Mを含む)の生きている矢。 | マスの番号が1から順に、X、10、…、M。Xは10より前、Mは最後。 |
| 同点は旧`id`の昇順で振られる | 同じ点数の矢を、`id`の順と作成時刻が逆になるように複数。 | 旧`id`の昇順に番号が付く。 |
| 旧`shot_number`の値(NULL・範囲外)は使われない | `shot_number`がNULL、射数/エンド超過の矢。 | 点数順に振り直される。 |
| 旧`shot_number`が別の矢の振る番号と衝突するエンドでも、失敗せず点数順に振り直される | 点数の低い矢が旧番号1、高い矢が旧番号2のように入れ替わる、欠番がある。生きている矢の旧番号は重複しない(部分一意索引のため)。 | 失敗せず、点数順に1から振られる。 |
| エンドごとに独立して1から振られ、距離・エンドをまたがない | 複数のエンドと距離。 | 各エンドで1から連番。 |
| 取り消し済みの矢と、その`shot_events`は残らない | 生きている矢と取り消し済みの矢が混在。 | 取り消し済みの行・履歴が無く、生きている矢の番号は取り消し済みを数えない(連番に欠けが出ない)。 |
| 生きている矢の履歴は、マスへ付け替えられ、`revision`・点数・射手・時刻・件数は変わらない | 複数回直した矢。 | 履歴の件数と`revision`が同じで、マスが矢のマスと一致し、`set_fields`に`shot_number`が含まれない。履歴の`shot_number`が振った番号。 |
| 移行後のマスの`revision`は、更新前の続きになる | 移行後に同じマスへ記録する。 | `revision`が更新前の最大の次になる。 |
| 生きている矢の合計・小計が移行の前後で一致する | ラウンド・距離ごとの和を前後で比べる。 | 一致する。 |
| 的に無い点数の矢と、削除済みの距離・ラウンドの矢も同じ規則で写る | 各状態。 | 失敗せず、同じ規則で番号が付く。 |

| 範囲外の行(射数/エンドを超える数など)があっても失敗しない | 範囲外の生きている行を仮に置く。 | 完了する(範囲の補正は行わない)。 |

上記は既存のE2Eの規模を超えない。同じマスの順序や構成の判定の組合せは単体とpgTAPで確かめ、E2Eには足さない。
更新前の版の端末と移行は、E2Eでは再現できないため、手動確認に置く。

## 移行の確認(手動)

移行のpgTAPとは別に、本番に近いデータで次を確かめる。
- 更新前の版でラウンドを作り、順不同の点数・同点・取り消し済みの矢・直した矢を用意し、更新後の版で開いて、各エンドが点数の高い順に表示され、合計・小計・件数が更新の前後で一致する。
- 更新後に、移行した矢を直す・消す・一つ戻る・一つ進むが動く。
- 更新前の版の端末(古いタブ)が矢を記録しても保存されず、表示に変化や知らせが出ないこと。端末の更新後に、送信を完了した記録が表示されること。
- 端末の保存の版更新の後、未送信の記録が無くなり、取得した内容で開くこと。
