# rounds/roles テスト設計

## 基準と範囲

基準は[rolesの要件](requirements.md)・[設計](design.md)、[deleteの要件](../delete/requirements.md)・[設計](../delete/design.md)、[履歴の設計](../history/design.md)の閲覧の範囲である。
実装やマイグレーションの内容から期待値を導かない。
射手の行と矢の射手は[shootersのテスト設計](../shooters/test-design.md)、アカウント削除は[delete-accountのテスト設計](../../auth/delete-account/test-design.md)で扱う。
役割を加える操作と画面の出し分けは無い。

優先順位は、読めてはならない記録の漏れの防止、他の射つ人の記録を消す操作の拒否、射つ人のいないラウンドの防止、代理の人の記録の許可の順とする。

## テスト層と観測

| 層 | 保証する内容 | 観測方法 |
| --- | --- | --- |
| DB(pgTAP) | 認可、閲覧、実行権限、射つ人の不変条件 | 実DBの行と応答。役割と操作の全組合せは行列テストに置く。 |
| 複数接続のDB結合(Playwright) | ロックによる直列化 | ローカルDBへの複数の接続。 |
| 単体(Vitest) | 拒否された削除の破棄(既存の送信のテスト) | 既存のテストを維持する。 |
| E2E(Playwright) | 拒否された削除のラウンドが再び表示されること | `delete.spec.ts`の既存の経路を維持し、役割の組合せは足さない。 |

検証データは[shootersのテスト設計](../shooters/test-design.md)の「検証データ」に従う。

## 行列テスト

### `rpc_matrix.sql`

アクターは、唯一の射つ人、代理の人、非参加者とする。
`anon`の拒否は`rls_matrix.sql`の実行権限の期待値表で固定し、ここでは扱わない。
各ラウンドには代理の人と紐づかない射手を置く。
`viewer`の列は削除する。

| 操作 | 射つ人 | 代理の人 | 非参加者 |
| --- | --- | --- | --- |
| `update_round`(状態の変更を含む) | 許可 | 許可 | 拒否 |
| `create_distance`、`update_distance`、`disable_distance` | 許可 | 許可 | 拒否 |
| `record_shots`(別の射手への付け替えを含む)、`clear_shots` | 許可 | 許可 | 拒否 |
| `add_round_shooter` | 許可 | 許可 | 拒否 |
| `disable_round` | 許可(論理削除される) | `PT403` | 拒否 |

拒否は、認可の拒否のコードに加え、行・履歴・`revision`が変わらないことを確かめる。

### `rls_matrix.sql`

- アクターは、射つ人、代理の人、非参加者、利用者IDの無い`authenticated`、`anon`とする。
- 対象のラウンドには紐づかない射手の行を置き、`rounds`、`round_users`、`distances`、`shots`、`round_events`、`distance_events`、`shot_events`のSELECTの可否を固定する。射つ人と代理の人だけが読め、非参加者と利用者IDなしは0行、`anon`は権限の拒否である。
- 各表の直接のINSERT・UPDATE・DELETE・TRUNCATEは、全アクターで権限の拒否のままである。
- 関数の実行権限の期待値表に次を加える。

| 関数 | `anon`・`PUBLIC` | `authenticated` |
| --- | --- | --- |
| `member_round_ids()`、`add_round_shooter(uuid,jsonb)` | 不可 | 可 |
| `anonymize_round_shooter`、射手の番号と射つ人の検査のトリガー関数、削除の本体の内部関数 | 不可 | 不可 |

加える関数と作り直す関数は、`SECURITY DEFINER`、所有者`postgres`、`search_path`の固定を既存の属性の確認に含める(内部関数の属性は設計の定義に従う)。

## 閲覧の範囲(pgTAP)

既存の`history_read_visibility.sql`に置く。
行ごとの条件が広すぎる誤りを検出できるよう、複数の利用者と複数のラウンドを用意する。

| テスト名の案 | 前提と操作 | 期待結果 |
| --- | --- | --- |
| 射つ人と代理の人は、参加するラウンドの距離・矢・各履歴だけを読める | 参加するラウンドと参加しないラウンドを、削除済みの行を含めて用意する。 | 参加分の行の集合と一致し、ID指定でも他は読めない。 |
| `member_round_ids()`は本人が参加するラウンドだけを返す | 射つ人、代理の人、非参加者、利用者IDなしで呼ぶ。 | 本人の参加分(削除済みのラウンドを含む)だけで、後の2つは空である。 |
| 参加を失った利用者は読めなくなる | 射手の行の利用者を別の利用者へ変える。 | 変更前の利用者は0行、変更後の利用者は読める。 |

ポリシーの式と実行計画は期待値にしない。

## 射つ人の不変条件と削除(pgTAP)

新しい`supabase/tests/round_roles.sql`に置く。
射つ人の検査はコミットの時点で働くため、`SET CONSTRAINTS ALL IMMEDIATE`で検査させ、ロールバックだけで成功と判定しない。

| テスト名の案 | 前提と操作 | 期待結果 |
| --- | --- | --- |
| ラウンドの作成は、作成者を射手1の射つ人にする | `create_round`を呼び、検査させる。 | 参加の行は(作成者、`owner`、1)の1行で、検査が通る。 |
| 作成の再送は射手を増やさない | 同じ操作を再送する。 | 1行のままである。 |
| 同じトランザクションの途中で射つ人が居なくても、確定の時点で居れば通る | 唯一の射つ人の行を匿名化し、別の射つ人を加えてから検査する。 | 成功する。 |
| 射つ人が他に居れば、射つ人の行を消せる | 2人の射つ人の片方を外して検査する。 | 成功する。 |
| ラウンドを物理削除するトランザクションは検査を通る | 履歴とラウンドを削除して検査する。 | 成功する。 |
| 射つ人の居ないラウンドは作れない | 参加の行なし、代理の人と紐づかない射手だけのラウンドを作って検査する。 | 検査の制約違反になる。 |
| 最後の射つ人は失えない | 最後の射つ人の行の削除と匿名化を、それぞれ行って検査する。 | 制約違反になる。 |
| 他に射つ人がいるラウンドは、どの射つ人も削除できない | 2人の射つ人がそれぞれ呼ぶ。 | `PT403`で、行と履歴は変わらない。 |

射つ人が1人のラウンドの削除の許可と、代理の人の拒否は`rpc_matrix.sql`で固定する。
`disable_round`の再送と削除済みの結果は、`rounds.sql`の既存のケースを維持する。

## 複数接続のDB結合

pgTAPは1接続のため、既定のPlaywright構成のspecに置く。
アカウント削除との競合は`tests/e2e/auth/delete-account.spec.ts`、射手の追加と距離の作成の競合は`tests/e2e/rounds/sync.spec.ts`に置く。
接続は、`tests/e2e/helpers/auth-db.ts`の`pg`の接続(ローカルのホストだけを許す)を、両方のspecが共有できる補助にして使う。
認証済みの利用者としてRPCを呼ぶ接続は、役割と`request.jwt.claims`を設定する。
利用者とデータはテストごとに作る。
先の接続のトランザクションを開いたまま後の接続を呼び、後の接続のロック待ちを`pg_stat_activity`で確かめてから先を確定する。
固定の時間の待ちで順序を作らず、上限と`finally`の解放を設ける。
削除は内部関数`purge_account`を直接呼ぶ。

### アカウント削除との競合(`delete-account.spec.ts`)

| テスト名の案 | 前提と操作 | 期待結果 |
| --- | --- | --- |
| 2人の射つ人が同時にアカウントを削除しても、射つ人のいないラウンドは残らない | 2人の射つ人と代理の人のラウンドで、2接続から削除する。 | 両方成功し、ラウンドと距離・矢・履歴が残らない。 |
| 射つ人3人のうち2人が同時にアカウントを削除しても、2人の射手は別々に残る | 3人の射つ人がそれぞれの射手の矢と履歴を持つラウンドで、2接続から2人を削除する。 | 両方成功し、ラウンドが残る。2人の射手の行は行のIDと番号を保って利用者と役割がNULLになり、矢と履歴の射手番号は変わらず、残る射つ人の行は変わらない。2人が操作者の履歴は匿名化先になる。 |
| 他の射つ人の削除と並行するラウンドの削除は、確定後の射つ人の数で判定する | 2人の射つ人の片方の削除中に、他方が`disable_round`を呼ぶ。 | 待った後に成功する。 |
| 唯一の射つ人の削除と並行する記録は、デッドロックせず`MISSING`になる | 削除中に代理の人が記録する。 | 待った後`MISSING`で、記録が残らない。 |
| 記録中の削除は記録の確定を待ち、記録を残さず消す | 代理の人の記録を未確定のまま、唯一の射つ人を削除する。 | 両方成功し、ラウンドの記録が残らない。 |

### 射手の追加と距離の作成の競合(`sync.spec.ts`)

| テスト名の案 | 前提と操作 | 期待結果 |
| --- | --- | --- |
| 同じ番号の同時の追加は、1つの射手になる | 2接続の認証済みの利用者が同じ番号を追加する。 | 両方`applied:true`で、1行。 |
| 未確定の同じ作成と並行する距離の作成は、記録した結果を返し、距離は1つになる | 先の接続が未確定のまま同じ作成の操作を後の接続から呼び、後の接続の待ちを確かめて先を確定する。 | 後の要求は成功し、先の要求と同じ`revision`の適用した結果を返す。距離と履歴は1つである。 |
| 操作の照合の後に同じ作成が確定しても、距離の作成は拒否せず記録した結果を返す | 下の3接続の手順で、同じ作成の操作を2接続から呼ぶ。 | 後の要求は`PT422`にならず成功し、先の要求と同じ`revision`の適用した結果を返す。距離と履歴は1つである。 |

操作の照合の後の確定は、次の順で作る。
関数は変えず、後の要求を距離IDの確認の前で待たせる。

1. 先の接続が作成を呼び、確定せずに保つ。
2. 3つ目の接続が`target_faces`を`ACCESS EXCLUSIVE`でロックし、その待ちを確かめる。
3. 後の接続が同じ作成を呼び、その待ちを確かめる。
4. 先の接続を確定し、3つ目の接続がロックを得た後に確定する。

この手順は、関数が操作の照合と距離IDの確認の間で`target_faces`を読むことに依る。
読む順が変わってもテストは失敗せず、この順序を通らなくなる。
ロックの間は並行する他のテストの的の読み取りも待つため、待ちの上限を短くする。

## 手動確認(性能)

隔離したローカルDBで、[履歴の設計](../history/design.md)の計測と同じ件数・条件を用意し、`rounds_list`、`distances_list`、ラウンドの詳細の取得を測る。
設計の計測の値と比べて報告し、自動テストの期待値にはしない。
共有のローカルDBと本番は使わない。
