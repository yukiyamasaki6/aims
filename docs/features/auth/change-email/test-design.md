# auth/change-email テスト設計

## 基準と範囲

[要件](requirements.md)・[設計](design.md)を基準とし、既存の両メール確認を維持したまま、OTPによるログインと発行Hookへ接続できることを確認する。
認証準備・実行・ダブルの規則は[共通テスト設計](../test-design.md)に従う。
既存のchange-emailの単体・UI・E2Eを再利用し、パスワードによる準備と変更後ログインをOTPへ置換する。

## 保持する検証

| 前提・操作 | 期待結果 |
| --- | --- |
| 現在と新しいメールに届いた別々のコードを両方確認する | 確認順序によらず変更が完了し、利用者IDと記録を保持する。Hookはemail_changeを許可する。 |
| 一方だけを確認する、または確認前に離脱する | メールを変更せず、旧メールのOTPでログインできる。 |
| 新しい両コードで変更を完了し、既存セッションのない状態で新メールのOTPを確認する | 元と同じ利用者IDのアカウントと記録を利用できる。 |
| 変更完了後、未登録となった旧メールへ新しく届いた有効なOTPを、既存セッションのない状態で確認する | 元と異なる利用者IDの別アカウントとして新規登録できる。元の記録は引き継がず、元アカウントと記録にはアクセスできない。新メールでは引き続き元の利用者IDと記録を利用できる。案内と遷移は統合認証の共通規則に従う。 |
| 旧メールで別アカウントを作成した後、同じメールのOTPで再び認証する | 作成済みの別アカウントとその記録を利用でき、重複作成や変更済みの元アカウントへの接続は起きない。 |
| 両コードの順序・片方の誤り・期限・再送・送付先の変更を扱う | 既存の入力と段階の契約を守り、再要求後は以前のコードと片側確認済みを引き継がない。 |
| 確認が完了する | 完了表示へ進んでその画面に留まり、再表示では新しい現在メールを表示する。 |

メール送付・閲覧のみでは新たな認証が成立しないことと、変更前からのセッション維持は別途確認する。
既存セッションによるアクセスを、旧メールの新たな認証で元アカウントへアクセスできたと誤判定しない。

## 再送待機の共通化

| 前提・操作 | 期待結果 |
| --- | --- |
| コード要求または再送が受理される | 60秒の待機が始まり、残り秒数を表示する。待機中の再送は拒否し、待機終了後はチェック完了で再送できる。 |
| 待機の刻みを受ける | 残り秒数が1ずつ減り、0で止まり負にならない。刻みの予約は共通の`tickResendCooldown`・`useResendCooldownTick`を通る。 |
| 完了する、入力へ戻る、画面を離れる | 完了・入力へ戻ると0になり、離脱後は予約が取り消され、その画面への更新が起きない。 |
| 再送が成功する、失敗する | 成功は両方のコード欄を空にし確認済みを消して待機を始める。失敗は成功扱いにせず理由を示し、入力を保って再試行できる。 |

0の下限と予約・取消の規則の組合せは共通側([共通テスト設計](../test-design.md))で確認する。
ここではメール変更の状態遷移(完了・戻る)と画面の接続だけを確かめ、固有の1秒定数や予約処理が残らないことは差分レビューで確認する。
配置は`change-email-flow.test.ts`・`change-email.test.ts`・`change-email-form.test.tsx`である。

## 旧アドレスの再登録(実Auth結合)

既存`change-email.spec.ts`の準備を用い、既存セッションのない新しいブラウザ状態で、新旧の利用者IDと記録をローカルDBで照合する。

| 前提・操作 | 期待結果 |
| --- | --- |
| 変更を片側のみ確認、または確認前に離脱し、旧メールで認証する | 変更は完了せず、元の利用者IDと記録を使える。 |
| 変更を完了し、新メールで認証する | 元の利用者IDと記録を使える。 |
| 同じ状態で、旧メールへ新しく届いたOTPを確認する | 元と異なる利用者IDで開始し、元の記録を持たない。元の利用者ID・記録にアクセスできない。 |
| 旧メールで作ったアカウントへ再び認証する | 同じ別アカウントとその記録を使い、重複作成も元アカウントへの接続も起きない。 |

変更前からのセッションの維持と、旧メールの新たな認証を取り違えない。
認証サービスが変更後の旧アドレスの再登録を拒否した場合は、テストを緩めず、根拠を添えて要件(D5)の判断へ戻す。

コードの順序や入力・処理中・失敗の詳細は既存のdomain/application/UI単体へ任せ、主要な完了経路を既存change-email.spec.tsで通す。
本文のメール変更案内・現在/新メール・15分期限は既存テンプレートの契約を維持し、登録/ログイン用の共通メールへ誤って統合しない。
Hook切替でemail_changeの保存値を消去・失効させず、進行中の変更を壊さないことは隔離環境の切替試験でも確認する。
