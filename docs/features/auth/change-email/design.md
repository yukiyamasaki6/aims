# auth/change-email 設計

## 概要

設定パネルの項目の画面(ハッシュ`#settings/account/email`。`app/settings`)で、サインイン済みの利用者が新しいメールアドレスを入力し、現在と新しいメールアドレスへ届く2つの認証コードを確認して変更する。
認証サービスの二重確認(`[auth.email] double_confirm_changes = true`)を明示して維持する。
要求は`updateUser({ email })`、確認は`verifyOtp({ type: 'email_change' })`、再送は`resend({ type: 'email_change' })`で、どれもこの端末の接続で行う。
Turnstileは再送だけに使う(要求と確認の呼び出しはチェックを検証しない)。
段階は「新しいメールアドレスの入力」と「コードの確認」の2つで、コードの確認では、変更前と変更後の2つの入力欄と確認ボタン1つを出し、1回の操作で2つの欄をまとめて確認する。画面の名称(メールアドレス変更)と分類「アカウント」へ戻る操作は、画面のヘッダー(`ScreenFrame`)にあり、どの段階でも出る。完了では、本文に完了の文言だけを表示する。
完了時に認証サービスが返すセッション(amr=otp)はSDKが採用し、画面は置き換えもセッションの種類の判定もしない(`docs/security.md`の残余リスク(6))。
背景の画面がオフラインで開けるときは、この画面もオフラインで開け(`app/offline-pwa`)、送信は直前にオフラインを判定して拒否する。

## 画面と状態

| 状態 | 表示 | 次の状態 |
| --- | --- | --- |
| 入力 | 現在のメールアドレス(読めたとき)、新しいメールアドレス、送信 | 受け付けでコード確認、失敗は理由を表示して留まる |
| コード確認 | 「変更前(現在のアドレス)」と「変更後(新しいアドレス)」の2つのコード欄、確認ボタン1つ、再送(待機の残り秒数)、本文の戻る(入力へ)、迷惑メールの案内 | 両方の確認で完了、戻るで入力、再送でコード欄を空にして確認済みを消す |
| 処理中 | 要求・確認・再送・本文の戻るは互いに排他で、実行中の間は他の操作を受け付けない。ヘッダーの戻る(分類「アカウント」へ)も押せず、設定パネルの閉じる操作と分類の切り替えも受け付けない | 結果で解除 |
| 完了 | 本文に完了の文言(`role="status"`)だけを表示する(ヘッダーの名称と戻るはほかの段階と同じ)。入力欄、コード欄、確認、再送、チェック、現在のメールアドレスは出さない | ヘッダーの戻るで分類「アカウント」へ。続けて変更するには開きなおす |

- ヘッダーの戻る(分類「アカウント」へ)は、段階によらず同じ1つで、実行中の操作があるとき(`pending`が`null`でない)は押せない。本文には分類「アカウント」へ戻る操作を置かない。
- 実行中の操作があるかを、受け取った処理中の知らせ(`onBusyChange`)で設定パネルへ知らせる。設定パネルは、その間、閉じる操作と分類の切り替えを受け付けない(`app/settings`)。ブラウザの戻る・進むで画面が外れたときは、離脱の原則(`docs/features/auth/design.md`)に従う。

- 現在のメールアドレスは、完了の間を除いて表示する。入力の段階では説明に、コード確認の段階では変更前の欄のラベルに出す。
- 認証コードの欄は、それぞれ`autocomplete="one-time-code"`を持つ。値は制御せず、確認の送信時にDOMから読む。
- 確認ボタンは、2つの欄を確認する。どちらかの欄が未入力なら、未入力の欄ごとに未入力のエラーを出し、どの欄も確認しない。
- 欄のラベルは「変更前(アドレス)」「変更後(アドレス)」で対称にする。文言は`ui/auth-messages.ts`が持つ。
- 確認済みかどうかは、欄ごとに「確認できたコードの値」として集約が持ち、表示も案内も変えない(入力欄のままで、状態を示す領域に何も出さない)。
  確認では、値が確認できたコードのままの欄を呼ばない。値を変えた欄は新しい入力として確認する。
  変えた値が誤りでも、確認できた値は残り、もう一方の確認で完了できる。
  確認済みの状態は、再送、戻る、要求しなおしで消える(認証サービスも、再送と要求しなおしで確認済みを引き継がない)。
- 呼ぶ欄が2つのときは、変更前、変更後の順に`verifyOtp`を1回ずつ呼ぶ。片方が失敗しても、もう一方も呼ぶ(完了や、誤りだった欄を決めるため)。
  完了したら、以降は呼ばない。サーバー側で既にもう一方が確認済みのとき、1つ目(変更前)の呼び出しで完了する。この場面は、前の確認の応答が失われたとき、確認済みの欄の値を変えたときに起きる(例: 変更後が確認済みで、変更前を直して送り、同時に変更後の値も変えたとき、1つ目で完了し、2つ目は呼ばれない)。
  結果は1つの事実にまとめて反映する。完了のときは失敗を示さない。完了では再送の待ちを止め(0にし)、チェックのトークンを消す(完了後は再送が描かれず、待機の刻みを止めるため)。
- 確認の結果が一方だけの確認か完了かは、応答のセッションの有無で分ける(一方だけは`user`も`session`もnull、完了はどちらも持つ)。
- 失敗の示し方は、コードに紐づくか否かで分ける。
  誤りまたは期限切れ(`code_expired`)は、誤りだった欄のエラーとして示し(両方誤りなら両方)、欄と`aria-describedby`で結ぶ。全体のエラーには出さない。
  制限、通信の失敗、その他は、全体のエラーとして示す(複数あれば最初のもの)。
  結果が不明だった確認の後に同じコードで再確認したときの「誤りまたは期限切れ」も、欄に示す。
- 要求と再送が受け付けられたら、コード欄を空にする(欄を作り直す。失敗のときは入力を保つ)。
- 状態を示す領域(`role="status"`)は常に描画し、完了の文言だけを差し込む。完了の表示は、再読み込みや別の画面への移動の後は出ない。
- 画面の作りはchange-passwordに揃える(`main`は`mx-auto flex min-h-full max-w-sm flex-col items-center justify-center gap-4 p-8`)。
  `main`は、共用のヘッダー枠(`ScreenFrame`)の本文領域に画面が置くスクロールの入れ物(`h-full overflow-y-auto`)の中に置く(change-passwordと同じ)。ヘッダーには現在地(メールアドレス変更)と、`leading`に分類「アカウント」へ戻るリンク(`SettingsBackLink`)を入れる。ヘッダー枠は設定パネルの中で描かれ、メニューボタンは出ない(`app/settings`)。`AuthHeader`は使わず、段階の説明(現在のメールアドレス、コード確認の案内)は本文の先頭の文、コード確認の段階の戻る(入力段階へ)は本文の先頭のボタンとして描く。2つのコード欄は、画面が1つのフォームとして`AuthField`と`Input`で描く。再送は`otp-code-step.tsx`の`ResendSection`(exportする)、チェックは`Turnstile`を使う。

## 構成とデータの流れ

チェック未完了の送信は、集約の開始の命令が待ちの状態にし、画面が`useCheckWait`でトークンの到着を受けて同じ操作を再開する(追加チェックの表示中は待ち、失敗と上限は不備として示す)。規則は`docs/features/auth/design.md`の「セキュリティチェックの待ち」に従う。

構造の方針は`docs/architecture.md`に従う。

- `supabase/config.toml`: `[auth.email]`に`double_confirm_changes = true`を足し、`[auth.email.template.email_change]`(件名「【AIMS】メールアドレス変更の認証コード」、`content_path`は`./supabase/templates/change-email.html`)を足す。
  `otp_expiry = 900`は変更のコードにも効く。`[remotes.*]`は上書きしないため、`supabase config push`で本番とプレビューにも反映される。
- `supabase/templates/change-email.html`: 変更前(`{{ .Email }}`)、変更後(`{{ .NewEmail }}`)、認証コード(`{{ .Token }}`)、有効期限15分、再要求で前のコードが無効になること、破棄してよいこと、両方のコードが要ることを示す。
  本文は2つの宛先で同じで、宛先で出し分ける変数は無い。
- `src/app/(main)/settings-panel-entry.tsx`: 入口。設定パネルの表示が`#settings/account/email`のときに描く項目の画面として、認証の実装、`Connectivity`、`Clock`、手続き、サイトキーを生成して画面へ渡し、設定パネルから受けた戻る操作と処理中の知らせも渡す。表示が変わると画面ごと外れ、次に開くと手続きも作り直す。
- `src/features/auth/ui/change-email-form.tsx`: 画面。状態を`useScreenView`で持ち、開いたときに現在のメールアドレスを読む。コード欄は要求と再送の受け付けごとに作り直し、完了では本文に完了の文言だけを描く。ヘッダーの戻るの押せなさと、処理中の知らせ(`onBusyChange`)に渡す値は、集約の`pending`から決める。戻るの押下は受け取った`onBack`を呼ぶ。
- `src/features/auth/ui/settings-back-link.tsx`: 設定パネルの分類「アカウント」へ戻るリンク(文言は「戻る」)。`href`は経路表の`SETTINGS_ACCOUNT_HASH`で、押下は既定の動作を止めて、受け取った`onBack`(設定パネルの移る操作。履歴を1つ積む)を呼ぶ。メールアドレス変更、パスワード変更、アカウント削除のヘッダーが使う。押せないとき(`disabled`)は行き先(`href`)を持たない要素として描き、押下もフォーカスも受けず、見た目を薄くする(`opacity-50`)。
- `src/features/auth/application/change-email.ts`: 手続き(`createChangeEmail({ authenticator, connectivity, clock })`)と約束(`ChangeEmailAuthenticator`)。操作は`load`、`request`、`confirm`、`resend`、`tickCooldown`である。分類「アカウント」へ戻るのは画面のリンク(設定パネルの移る操作)で、手続きは遷移を持たない。
  約束の頼みごとは、現在のメールアドレスの読み取り、要求(結果は受け付けか失敗。受け付けのとき、応答の現在のメールアドレスを持つ)、確認(1つのコードにつき、結果は一方だけの確認か完了か失敗。手続きが欄の数だけ順に頼み、まとめる)、再送である。
- `src/features/auth/domain/change-email-flow.ts`: 集約。段階、現在と新しいメールアドレス、欄ごとの確認できたコードの値、実行中の操作(`request`、`confirm`、`resend`)、再送の待ち、チェックのトークン、欄ごとのエラーと失敗、コード欄を作り直す世代(要求と再送の受け付けで進む)、完了(`completed`。終わりの状態)を持つ。
  開始の命令は`beginRequestEmailChange`、`beginConfirmEmailChange`、`beginResendEmailChangeCode`で、実行中 → 入力 → オフライン(再送は待機 → チェックを入力に含む)の順に判定する。
  事実は、要求の受け付け(段階をコード確認にし、再送の待ちを始め、応答の現在のメールアドレスを採る)、コードの確認の結果(確認できた欄とコード、誤りだった欄、完了したか、コードに紐づかない最初の失敗。完了なら完了にし、そうでなければ確認できたコードを残し、誤りだった欄に誤りを、最初の失敗を全体に示す)、再送の受け付け、失敗、チェックの消費を伴う拒否、戻る、待機の1秒、チェックの完了である。
- `src/features/auth/domain/auth-failure.ts`、`flow.ts`: 失敗の種類に`email_exists`と`same_email`、欄の誤りに`currentCode`と`newCode`(未入力と、誤りまたは期限切れ)を足す。
- `src/features/auth/infrastructure/supabase-auth.ts`: 約束の実装を足す。応答のコードは専用の対応(下表)で写す。
- `src/features/auth/ui/auth-messages.ts`: 上の種類と画面の文言を足す。
- `src/features/auth/ui/otp-code-step.tsx`: `ResendSection`だけをexportする(`OtpCodeStep`の振る舞いは変えない)。`ResendSection`は再送ボタンと再送の失敗だけを描き、セキュリティチェックの失敗の文言は持たない。文言は、画面が`flow.error`と同じ段落(再送の部分の下)に出す(`docs/features/auth/design.md`の「セキュリティチェックの待ち」)。
- `src/features/settings/ui/settings-account.tsx`、`settings-messages.ts`、`src/routes.ts`: 「メールアドレス変更」項目(パスワード変更の上)と、`CHANGE_EMAIL_HASH`(`#settings/account/email`)。
  保護と遷移元は背景の画面(`/rounds`の配下)のものが効き、遷移元はハッシュを含む(`auth/signin`)。

流れは次のとおりである。

1. 要求: 送信の直前にオフラインを1回読み、入力(形式)→ オフラインの順に判定して、`updateUser({ email })`を1回呼ぶ。
   認証サービスは、現在と新しいメールアドレスへ別々のコードを送る(captchaは要さない)。
2. 確認: 値が確認できたコードのままでない欄のコードを、その欄のメールアドレス(変更前の欄は現在、変更後の欄は新しいメールアドレス)を付けて、1回の操作の中で順に`verifyOtp`で確認する。
   一方だけでは認証サービスは完了せず、もう一方で完了して新しいセッションを返す。SDKは採用し、この端末のサインインは維持される。
3. 再送: 現在のメールアドレスを付け、チェックのトークンを添えて`resend`を呼ぶ。両方のアドレスへ新しいコードが届き、前のコードは無効になる。成功も失敗もトークンを消費してやり直す(全画面の規則。`docs/features/auth/design.md`)。
4. 応答の後、画面が表示中のときだけ状態を更新する。離れていても、確認の残りの呼び出しを含め、呼び出しは進める。

### 応答の写し

| 認証サービスの応答 | 失敗の種類 |
| --- | --- |
| 要求が422 `email_exists` | `email_exists` |
| 要求が200で、応答の`email`が要求と同じ(大文字小文字を無視) | `same_email` |
| 確認が403 `otp_expired`(誤りも期限切れも) | `code_expired` |
| 429 `over_email_send_rate_limit`、`over_request_rate_limit` | `rate_limited` |
| 再送が400 `captcha_failed` | `captcha_failed` |
| 通信の断、呼び出しが投げた、`AuthRetryableFetchError`(確認の500を含む) | `unreachable` |
| その他 | `other` |

- 同じメールアドレスの要求は、認証サービスが200を返すが、メールを送らず、`new_email`も付けない。このため応答の現在のメールアドレスと比べ、受け付けとしない。
  保留中の変更があっても、`new_email`は前の値のままで、要求の値とは別になる。
- 新しいメールアドレスは小文字で保存される。確認は入力のままの大文字小文字でも成功する。
- 要求の後に他の利用者が同じアドレスを登録すると、完了の確認が500(`Error confirm email`、コードなし)になり、変更されない。SDKは`AuthRetryableFetchError`にするため、通信エラーと区別できない。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| 2つのコード欄を同じ段階に並べ、1つの確認ボタンで未確認の欄を順に確認する | 認証サービスは1回の呼び出しで1つのコードしか確認できず、順序も問わないため、手続きが順に頼む。本文が同じ2通のメールを欄で見分けられる(受け取ったアドレスの欄に入れる)。コードが1欄だと、どのアドレスのコードか決められず、認証サービスの確認がアドレスを要する。固定順の2段階は、順序を問わない要求を満たさない | 認証サービスが、アドレスなしでコードを確認できるようになったとき |
| 現在のメールアドレスは、要求の応答のものを以後の確認と再送に使い、開いたときの読み取りは表示だけに使う | 別の端末が変更した後でも、サーバーの値で確認できる。読み取りの失敗(オフラインで期限切れなど)が要求を妨げない。読めないときは表示しない | 現在の値の表示を、読み取りの失敗でも必須にするとき |
| 同じアドレスの判定を、画面の比較でなく、応答の現在のメールアドレスとの比較にする | 判定の根拠をサーバーの値の1つにし、端末の古い値で誤らない | 認証サービスが同じアドレスを拒否するようになったとき |
| 確認済みを、確認できたコードの値として集約が持ち、表示せず、認証サービスへ問い合わせない | 問い合わせる手段が無く、再送と要求しなおしで消える規則が認証サービスと一致する。使い終えたコードの再確認は403になるため、値が同じ欄は呼ばない。離れると消えるのは要求どおり | 経過を保つ要求を加えるとき |
| 完了時のセッションの置き換えをしない | 要求で受け入れた残余リスクで、`verifyOtp`の応答をSDKが採用する挙動のままにすると画面の処理が増えない。パスワードでの置き換えはチェックを要し、要求が対象外にしている | 現在のパスワードなしのパスワード変更を許さない要求にするとき |
| 要求と確認でTurnstileを使わない | 認証サービスが検証せず、画面に置いても直接呼び出しを抑止できない。再送だけが検証する | 認証サービスが要求にもチェックを要するようになったとき |
| 二重確認を設定で明示する | 無効にすると、新しいアドレス宛ての1通だけで完了し、盗まれたセッションでアドレスを乗っ取られる(`docs/security.md`)。設定に無いと既定に依るため、`config push`で本番とプレビューへ明示する | 本人確認を別の方法で強制できるとき |
| 別の端末の終了も、現在のパスワードの確認も実装しない | 認証サービスが終了せず、現在のパスワードを要さない(画面で求めても直接呼び出しに効かない)。要求で受け入れた | 認証サービスの挙動が変わったとき |

## 制約と未対応

- 要求と再送は、最後の送付から`max_frequency`(本番・プレビューは60秒)の間、429になる。別のメールアドレスでの要求しなおしも同じで、前の要求のコードは有効なまま残るが、画面は戻る時点で捨てているため使えない。
- 完了の確認が500のときは、通信エラーと表示され、同じコードで再試行しても同じになる。別のメールアドレスで要求しなおす。
- 確認の応答が失われると、完了していることがある。同じコードでの再確認は、その欄の「誤りまたは期限切れ」になる。
- 現在のメールアドレスの表示は、端末のセッションから読む。アクセストークンが切れていて更新できないときと、別の端末が変更した直後は、表示されないか古い。変更の確認は要求の応答の値を使う。
- 登録の有無が分かること、完了時のセッションの免除、他の端末が残ることは`docs/security.md`の残余リスク(6)〜(8)に従う。
