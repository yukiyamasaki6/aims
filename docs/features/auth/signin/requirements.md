# auth/signin

## 目的

利用者がメールアドレスを確認し、パスワードを管理せずに、新規・既存を区別せずAIMSを使い始め、または再開できるようにする。
メールアドレスの確認の代わりに、Googleアカウントでも、新規・既存を区別せず使い始め、または再開できるようにする。

## 要求

### サインインする

- 未登録のメールアドレスへ届いた有効な認証コードを入力すると、パスワードを入力・設定・再認証せずに登録して利用を開始できる。
- 登録済みのメールアドレスへ届いた有効な認証コードを入力すると、パスワードなしで元のアカウントと記録を利用でき、重複アカウントや記録の置換を起こさない。
- 登録とサインインの入口を分けず、新規・既存で画面・文言・流れを分けない。登録有無を、コード送付後の画面や案内で知らせない。
  ただし、Googleアカウントにだけ残るメールアドレスのときは例外とする(「Googleアカウントにだけ残るメールアドレスでコードを要求したとき」)。
- コードの要求・受信・メール閲覧・リンク操作だけでは、新しいサインインは成立しない。
- 未入力・誤り・期限切れ・使用済みコードでは新しいサインインが成立せず、認証が必要な記録を取得できない。
- 許可された遷移元がある場合は新規・既存を区別せず認証後にその画面へ戻り、ない場合や外部URL等の場合はホームへ進む。
- `/signup`は提供せず、ページ・ルート・定数・ガード対象と互換のためのリダイレクト等を設けない。
- パスワードの入力・再設定の操作や導線を表示しない。
- メール入力欄はメールの自動入力、コード欄はメールコードの自動入力に対応する。

### Googleアカウントでサインインする

- サインイン画面には、Googleアカウントで続ける操作がある。登録とサインインで操作を分けない。
- Googleアカウントで続ける操作は、セキュリティチェックの完了を要さない。
- Googleでの認証を済ませた利用者は、そのGoogleアカウントに結び付いたAIMSのアカウントにサインインし、許可された遷移元があればその画面へ、なければホームへ進む。外部URLなど許可されていない遷移元のときは、外部へ送られずホームへ進む。
- AIMSのアカウントを持たない利用者がGoogleでの認証を済ませると、新しいアカウントが作られ、同じく遷移元またはホームへ進む。新規・既存で画面・文言・流れを分けない。
- メールアドレスの認証コードで登録済みの利用者が、同じメールアドレスのGoogleアカウントで認証を済ませると、新しいアカウントは作られず、既存のアカウントと記録にサインインする。以後、そのアカウントには、メールアドレスの認証コードでも、Googleアカウントでもサインインできる。
- Googleアカウントで作ったアカウントにも、そのアカウントのメールアドレスへ届いた認証コードでサインインできる(同じアカウントと記録に入る)。
- Googleでの新規ログインは、直接API経由も含め成立する。パスワードによる新規ログインを拒否することは、変わらない(「パスワード認証を直接要求する」)。

### Googleアカウントでの認証が済まなかったとき

- オフラインでGoogleアカウントで続ける操作をすると、ネットワークの案内が表示され、Googleの画面へは移らない。
- Googleの画面で利用者が認証を取り消した、または拒否したときは、サインインされず、アカウントも作られず、サインイン画面へ戻る。何も知らせず、再度操作できる。
- Googleでの認証の後に、AIMS側で失敗したとき(認証サービスの拒否・制限、通信の失敗)は、サインインされず、「Googleでの認証に失敗しました。」が表示され、再度操作できる。認証サービスの文言は表示しない。
- Googleの画面へ移るまでの間に操作を繰り返しても、処理は重複して行われない。

### Googleアカウントにだけ残るメールアドレスでコードを要求したとき

- 対象: どのアカウントのメールアドレスでもなく、結び付いたGoogleアカウントのメールアドレスとしてだけ残るアドレス。
  例: メールアドレス変更の前のGoogleのアドレス。アカウントと異なるアドレスで追加したGoogleのアドレス。
- このアドレスで認証コードを要求すると、コードは送られない。
  「このメールアドレスはGoogleアカウントで登録されています。」が表示され、コード入力へは進まない。
  コードの送付に成功したようには見せない。
- 案内のために、新しいメールの送信の仕組みは設けない。
- この案内は、「登録有無を、コード送付後の画面や案内で知らせない」の例外である。
  - 例外の範囲: Googleアカウントにだけ残るアドレスに限る。
  - 通常の登録済み・未登録のアドレスは、従来どおり、同じ画面・文言・流れで扱う。
  - 理由: 認証サービスは、このアドレスへの要求を、メールを送らずに拒否する。そのため、認証サービスを直接呼び出せば区別が分かり、画面で隠しても守れない。隠すと、正当な利用者がコードを待ち続ける不利益だけが残る。
  - この例外は、`docs/security.md`に記録する。

### 認証コードの入力中

- 再送は送付から60秒待ち、残り秒数と、メールが届かない場合の確認事項が表示される。
- 待機後はセキュリティチェックを完了して新しいコードを要求でき、発行後に古いコードは使えない。
- メール入力へ戻るとメールを再利用でき、コードを入力し直せる。
- 新規・既存のいずれの利用者へのメールも、コードと15分の期限、心当たりがない場合の案内を持ち、クリックだけで認証を成立させるリンクを含まない。

### 認証済みで開く

- 認証済みで開くと、有効な遷移元があればその画面へ、なければホームへ移る。
- 切替前の有効なセッションは一律に失効させず、従来の更新条件で維持する。終了後の新規ログインはOTPを要求する。

### パスワード認証を直接要求する

- 切替時に保存済みパスワードハッシュを削除・上書きせず、以前のパスワードによる新規ログインを直接API経由も含め拒否する。
- 直接APIでパスワードの新規設定・変更・再設定を試みた後も、パスワードによる新規ログインは成立しない。

### 入力不備・重複・失敗があるとき

- メール未入力・形式不正またはコード未入力では理由を表示して対象処理を行わず、修正して再試行できる。
- 送信・再送のチェック未完了で押すと処理中として待ち、追加操作の間も待ち、完了後に自動で再開する。
- チェック欄は追加操作・失敗で表示され、完了後も取り直すまで表示を保つ。
- チェック失敗または追加操作のない待機の上限では、理由を示して解除し、再操作で改めて待てる。
- 送信・確認・再送の実行中に操作を繰り返しても同じ処理を重複開始しない。
- 誤ったコード・期限切れ・使用済み・制限・通信失敗では理由を表示し、成功と誤表示せず再試行できる。
- 送信・再送で消費したチェックは成否によらず取り直し、認証サービスの送信・確認制限を回避しない。
- オフラインでは入力不備またはネットワークの案内を表示し、処理を送信も保留もしない。

## 対象外

- メールを受信できない場合の別の復旧経路。
- Google以外の外部の認証(Apple、GitHubなど)、Googleのワンタップ・自動サインイン、Googleアカウントの名前やプロフィール画像の取り込み。
- サインイン後に、Googleアカウントの結び付きを追加・解除すること。
  auth/link-googleで扱う。
- メールアドレスの認証コードでのサインインを、アカウントから取り除くこと。
  全てのアカウントは、現在のメールアドレスの認証コードでサインインできる。
- 同じメールアドレスのGoogleアカウントが、既存のアカウントへ自動で結び付くことを止めること。
  認証サービスの仕様で止められない。
  そのGoogleアカウントを使える者は、既存のアカウントに入れる。
  そのメールアドレスを使える者が認証コードで入れることと同じ程度の危険として受け入れ、`docs/security.md`に残余リスクとして記録する。
- Googleアカウントで作ったアカウントへの、メールアドレスの認証コードでのサインインを止めること。
  止めると、登録の有無と手段を、コード送付後の画面や案内で知らせることになるため。
- 本番でGoogleアカウントでのサインインが動くための、運営者の作業。
  Google CloudのOAuthクライアントと同意画面の作成、リダイレクトURIの登録、クライアントシークレットの認証サービスへの登録、同意画面の公開に要る情報(プライバシーポリシーのURLなど)の用意、ホスト版の認証サービスの設定は、運営者が行う。
  アプリの開発では秘密情報を扱わない。
  本番とプレビュー環境で、実際のGoogleアカウントを使った確認も、運営者が行う。
