# auth 共通設計

## 概要

認証の5機能(`signin`、`signup`、`password-reset`、`signout`、`change-password`)が共有する構造と、機能ごとに別の言い方にしない判断を書く。
機能ごとの画面と流れは、各機能の`design.md`に従う。構造の方針は`docs/architecture.md`に従う。
利用者のセッションで認証サービスに触る実装は`infrastructure/supabase-auth.ts`の1つで、画面がブラウザの接続を渡す。各手続きは使う頼みごとだけの約束の型で受け取る。
集約の入口は、開始の命令(`begin<操作>`)が`Start`を返し、実行中を集約が副作用なしで拒否する。

## 構成

- `src/features/auth/domain/flow.ts`: 命令の結果の型(`Start`、`Step`)と欄ごとのエラーの型(`FieldErrors`)。
- `src/features/auth/domain/auth-failure.ts`: 失敗の種類(`AuthFailureKind`)。失敗値の作成(`UNREACHABLE`など)も持つ。文言は持たない。文言は、UI層の文言の一覧(`ui/auth-messages.ts`)が、失敗の種類ごと、欄ごとの入力の誤りの種類ごとに持つ。失敗の種類`offline`は、送信の前に端末のオフラインを判定して集約が作り、認証サービスの応答からは作らない。
- `src/features/auth/domain/auth-routes.ts`: 保護対象の画面、未認証専用の画面、サインインのURL、遷移元の規則と、要求のリダイレクト先(`redirectFor`)。認証の画面の経路の文字列(`SIGN_IN_PATH`、`SIGN_UP_PATH`、`RESET_PASSWORD_PATH`)は経路表(`src/routes.ts`)が持つ。保護の範囲の根の経路は、経路表(`src/routes.ts`)の`ROUNDS_PATH`と`SETTINGS_PATH`を読む。`ROUNDS_PATH`はサインインの後の既定の行き先でもある。`src/proxy.ts`が、セッションの更新の結果の利用者から`redirectFor`を呼ぶ。既定の行き先の規則(`destinationOf`)は、サインインとサインアップの手続きが使う。
- `src/features/auth/domain/password.ts`: パスワードの入力と文字種の規則(空でなく、半角英数記号のみ)。長さと強さは認証サービスが拒否する。最小長と最大長の数値は、規則の文面に要るため、ここだけが持つ。規則の文面は一覧が持ち、入力の検証と弱いパスワードの拒否が同じ文面を使う。
- `src/features/auth/application/call-result.ts`: 認証サービスへの頼みごとの結果(`CallResult`)。
- `src/features/auth/infrastructure/supabase-auth.ts`: 利用者のセッションで認証サービスに触る唯一の実装。画面がブラウザの接続を渡す。応答の変換(エラーのクラス名とコード、イベント名、セッションの形)も、このファイルだけが知る。
- `src/features/auth/ui/use-screen-view.ts`: 画面の状態、表示中の判定、チェックのウィジェットの参照を持ち、手続きへ渡す画面の約束を作る(約束は描画ごとに作り、`begin`は描画済みの状態に適用する)。
- `src/features/auth/ui/auth-field.tsx`、`src/components/ui/busy-button.tsx`: 入力欄とエラー文の結び付け、処理中のボタンの表現。
- `src/features/auth/ui/auth-header.tsx`、`turnstile.tsx`: 認証画面の見出しと、セキュリティチェックの部品(サイトキーは入口が引数で渡す)。

## 命名の規則

認証の概念の語彙を示す。機能をまたぐ構造の部品の命名(手続き、約束、依存の引数名、実装)は`agents/implementation.md`の「構造の部品の命名」に従う。

| 概念 | 規則 | 例 |
| --- | --- | --- |
| 集約の型と初期値 | `<操作>Flow`、`initial<型名>` | `SignInFlow`、`initialSessionEndFlow` |
| 開始の命令 | `begin<操作>(流れ, 入力)`が`Start<流れ, 依頼>`(新しい状態と、開始するときだけ依頼。開始しないときは`null`)を返す | `beginSignIn`、`beginSignOut` |
| 結果つきの命令 | `<動詞><操作>(流れ, 入力)`が`Step<流れ, 結果>`を返す | `endSignOut` |
| 状態を持たない判定 | `<動詞>(流れ, 入力)`が結果だけを返す(`Step`を使わない) | `leave` |
| 画面から送る事実 | 過去形の出来事。reducerは`<操作>Reducer` | `captchaChecked`、`failed` |
| サインインの変化の通知 | `SignInChange`(値)、`SignInChanges`(約束)。型は1つで、他の機能へも入口で公開する | |
| 認証サービスに頼む約束 | `<手続き>Authenticator`。手続きの補助の頼みごとは、役割を表す名前(`OtherSessionsSignOut`) | `SignInAuthenticator`、`SessionAuthenticator` |
| 「セッション」を含む名前 | `Session`(手続き)、`SessionEndFlow`(集約)、`SessionStatus`(分類)、`SessionReading`(読み取り結果)。SDKの`Session`はこのアプリの名前に使わない | |
| 「届かなかった」 | 失敗の種類`unreachable`だけ。頼みごとの結果は`accepted`か`failed`の2つ | |

## セキュリティチェックのトークンの消費と保持

| 操作 | 受け付けられた | 失敗 |
| --- | --- | --- |
| サインイン | 遷移する(送信中のまま) | 消費し、チェックをやり直す |
| コード送信と再送 | 消費し、チェックをやり直す | 消費し、チェックをやり直す |
| コード確認 | 使わない | - |
| パスワード設定(再設定) | 使わない | - |
| パスワード設定(サインアップ) | 設定の後のサインイン(`signInWithPassword`)が消費する。`updateUser`は使わない | サインインの失敗は消費し、チェックをやり直す。`updateUser`の失敗は保つ |
| パスワード変更 | 使わない(更新の呼び出しはチェックを経由しない) | - |

失敗は、拒否も、通信の断(値で返す場合も、呼び出しが投げた場合も)も区別せず、全て同じに扱う。通信の失敗でトークンが使われたかを、利用者側から確かめられないためである。通信の失敗の後は、チェックをやり直して再送信する。

## 離脱の原則

- 処理の応答待ちに画面を離れた後は、離れた画面の処理は遷移しない(サインイン、パスワードの設定)。手続きは、応答の後に、画面が表示中か(`ScreenView`の`isMounted`)を確かめる。離れた画面の状態は破棄されるため、状態の更新とチェックのやり直しは抑止しない。
- サインアウトの完了を待つ間に離れても、終えられたらサインインへ移る。この端末のサインインの終了の依頼は取り消さない。
- 例外は、サインアウトの完了の遷移である(遷移は画面に属さず、離れても行う)。
  再設定で設定の応答待ちに離れたときは、再設定の処理は表示も遷移もしない。
- もう1つの例外は、サインアップのパスワード設定である。
  (1)の成功後は、離れても(2)と(3)を進め、遷移だけ行わない(`docs/features/auth/signup/design.md`)。
- この原則が抑えるのは、離れた画面の処理による表示と遷移だけである。
  離れた先の画面が自分の役割で行う遷移(ラウンドの画面の見張りが、喪失を検知してサインインへ移すなど)は対象外で、従来どおり行われる。

## パスワードの更新と他の端末のサインイン

サインイン済みの端末が`updateUser({ password, current_password })`でパスワードを更新すると、認証サービスは、更新を呼んだセッション以外の全てのセッションを終える(`secure_password_change`の設定によらない)。
呼んだセッションは維持される。
他の端末は、アクセストークンの期限(3600秒)内はデータの読み書きが通りうる(`docs/features/app/navigation/design.md`)。
期限後の更新の拒否で検知される。
`[auth.email] require_current_password = true`のとき、認証サービスは更新に現在のパスワードを要する。
無ければ400 `current_password_required`、誤りなら400 `current_password_invalid`(メッセージは同文でコードだけが違い、サインインの`invalid_credentials`とも別)、現在のパスワードが正しく新しいパスワードと同じなら422 `same_password`で拒否する(パスワード由来のセッション)。
検証の順は、新しいパスワードが72バイト超(400 `validation_failed`)、規則違反(422 `weak_password`)、現在のパスワード(400 `current_password_required`、`current_password_invalid`)、同じパスワード(422 `same_password`)である(amr=passwordでローカルの実測。順序はソース未読で、挙動からの結論)。
72バイト超と規則違反は、現在のパスワードが正しくても、誤りでも、無くても、先に返る。
72バイト超の現在のパスワードだけでは`validation_failed`にならず、新しいパスワードが有効なら400 `current_password_invalid`になる(長さの検証は新しいパスワードにだけ掛かる)。
拒否(現在のパスワードの誤り・必須、規則違反、72バイト超、同じパスワード)の後は、別の端末のサインインが無効にならず(取得もリフレッシュも成功)、ハッシュ、更新時刻、セッション数が変わらない(実測)。
対照として、正しい現在のパスワードで別のパスワードへ変更に成功すると、別の端末は無効になる(取得は403、リフレッシュは400)。
この更新はチェック(Turnstile)を要さない。
認証コード由来(サインアップ、回復)のセッションでも、同じパスワードの再設定は422 `same_password`で拒否される(現在のパスワードの有無によらない。実測)。
未測定: 認証コード由来(amr=otp)のセッションでの上の検証順と拒否の後の不変、MFA(aal2)との併用、`secure_password_change`有効時、先頭72バイトが一致する73バイトの現在のパスワードの純粋な検証。
根拠は、ローカルの認証サービス(v2.197.0、Supabase CLI 3.1.0)での実測(他の接続のセッションが終わり、呼んだ接続は更新後も維持され、旧パスワードではサインインできず、新パスワードでサインインできる。上のエラーの出し分け)、v2.195.0での調査(更新の応答にセッションは含まれない。v2.197.0では再確認していない)、ソース(`User.UpdatePassword`が現在のセッション以外を終える。2023年7月の変更`#1162`)である。
本番での実測はない。
24時間を超えたセッションでの更新も未実測である。

## 認証コード由来のセッションの免除と置き換え

`require_current_password = true`でも、認証サービスは、パスワード未設定の利用者と、認証コード(OTP)・マジックリンク・回復で得たセッション(amr=otp)の更新を、現在のパスワードの検査から免除する(誤った値を付けても通る)。
免除は、パスワード設定の後も、リフレッシュの後も続く。
根拠は、ローカルv2.197.0の実測とソース(`user.go`、`factor.go`)である。
本番は未確認である。
再設定は、設定の後にこの端末のセッションを終えてサインインへ移る(`signOutHere`)ため、通常は認証コード由来のセッションを残さない。
確認の成功後の離脱と、`signOutHere`の失敗では残る。
サインアップは、パスワード設定の完了時に、`signInWithPassword`(amr=password、captcha要)でこの端末のセッションを置き換え、新しいセッションからの`signOut({ scope: 'others' })`で古いセッションをサーバー側でも無効にする(実測: 置き換えただけでは古いセッションは残り、`others`で消え、旧アクセストークンは403、リフレッシュは400)。
新しいセッションでは現在のパスワードなしの更新が400で拒否される。
手順は`docs/features/auth/signup/design.md`に従う。
残余リスクは`docs/security.md`を正本とする。
既存の認証コード由来のセッションの掃除はしない。
`secure_password_change`は有効にしない。
有効にすると、作成から24時間を超えたセッションの更新にメールの認証コード(nonce)を要するが、起点は作成時刻(`session.CreatedAt`)で固定、24時間は設定できず、24時間以内は検証しない(実測)。
現在のパスワードとコードの両方を要する構成は採らず、コードだけの構成は24時間以内が無検査になる。
Google認証など、amrがotpでもpasswordでもないセッションでの`require_current_password`の扱いは未測定で、足すときに確かめる。
管理APIには、利用者ごとのセッションの列挙・削除が無く(v2.197.0)、`service_role`でも他者のセッションは終えられない。

## 確立した前提

1. 接続は、使う時に取得する。事前描画に環境変数を要求せず、頼みごとの時の欠落は通信エラーとして示す。適用範囲: 認証サービスへの頼みごととサインインの状態の読み取り。認証状態の変化の購読は、接続を得られないとき同期に投げる(起動時から欠落した画面は購読で止まり、通信エラーの表示と再試行は無い。変更前と同じ)。
2. 確かめられないときは、`unknown`を返す。サインインの状態の読み取りは投げない。
3. 接続を作る関数は、同じ画面では同じ接続を返す(ブラウザ)。
4. 読み取りが投げた場合を、利用側が個別に受けない。

## 認証の変化の出来事

サインインの変化(`SignInChange`)は、`signed-in`(サインイン、利用者のいる起動時の復元)、`signed-out`の2種で、`signed-in`は利用者(`userId`)を持つ。利用者のいない起動時と、トークンの更新を含むその他の出来事(パスワードの再設定の途中など)は、インフラ層の変換が通知しない。
トークンの更新は通知しないため、端末の識別情報の記録とサインインの喪失の見張りは、トークンの更新で動かない。取得の認証の拒否が起こす強制更新も通知しないため、同期の取得が止まらなくなる循環は起きない。同期はサインインの通知で取得を始めない(常駐の取得は同期の開始で1回頼む)。記録の制御はsigned-inのときだけ保留した送信を戻す。

## 約束の例外の契約

投げない: 認証サービスへの頼みごと(`CallResult`で返す)、サインインの状態の読み取り、画面の約束(`PageNavigation`、`PageReplace`を含む)、通信の可否。
投げることがある: `SignInChanges.subscribe`(接続を得られないとき同期に投げる。手続きは扱わない)。
端末の識別情報の読み書きは、保存先が使えない環境を想定せず、例外を捕まえない。ただし見張りは、書き込みか読み戻しに失敗したとき、読み込み直しの繰り返しを防ぐために置き換えない。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| 認証サービスに触るブラウザ側の実装を1つにし、手続きは使う頼みごとだけの約束で受け取る | 同じ頼みごとの呼び出しを1か所にするため | 認証サービスを差し替えるとき |
| 開始の可否と開始の遷移を、集約の1つの命令にする | 判定を経ない開始や、実行中の開始を、集約自身が副作用なしで拒否するため。画面は現在の段階の操作だけを描くので、段階は検査しない | 開始の条件を持たない操作を足すとき |
| 実行中の判定は集約が持ち、確認ダイアログは外から実行中を受け取る表現だけの部品にする | 判定の持ち主を1つにするため。呼び出し元ごとの状態は呼び出し元が持つ(サインアウトは集約、プリセット削除は削除側のフックの同期の`ref`) | 確認ダイアログ以外からサインアウトを呼ぶとき |
| 利用者向けの文言はUI層の文言の一覧(`ui/auth-messages.ts`)だけが持ち、ドメイン層は失敗と入力の誤りの種類を返す | 文言は表示の関心であるため。種類の型に対する`satisfies`で、全ての種類に本文があることを型で確かめる。インフラ層は種類を返す。表に無い失敗も固定の文言で示し、認証サービスの文言(外部の言語)は出さない | 画面ごとに文言を変えるとき |
| 経路の判定・変換の規則は`auth-routes.ts`が持ち(経路の文字列は経路表が持つ)、共有の技術は関数として受ける | 共有の技術は機能を参照しない(R3) | サーバー側の保護を機能の外へ出すとき |
| パスワードの規則の文面を1つにし、入力の検証と弱いパスワードの拒否で同じ文面を示す | 同じ規則を同じ文言で知らせるため。一覧の同じ本文に、入力の誤り(`invalidRule`)と`weak_password`を写す。パスワードの設定だけは、`validation_failed`(72バイト超など)も`weak_password`に写す。数値は`password.ts`だけが持ち、一覧が参照する | 認証サービスのパスワードの設定を変えるとき |

## 制約と未対応

- 同期とラウンドの取得の手続きは、入口が生成した通信の可否を約束(`Connectivity`)で受け取る。サインイン、サインアップ、パスワード再設定の送信の手続き(コードの送付、確認、パスワード設定を含む)も、入口が生成した`Connectivity`を、送信の直前の読み取り(`isOffline()`を1回。購読しない)に使う。
- `src/proxy.ts`の`config.matcher`は、経路を文字列で再掲する(Next.jsの静的な設定のため)。`proxy.test.ts`が、`ROUNDS_PATH`と`SETTINGS_PATH`とその下で一致することを確かめる。
