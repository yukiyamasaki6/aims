# auth 共通設計

## 概要

認証の4機能(`signin`、`signup`、`password-reset`、`signout`)が共有する構造と、機能ごとに別の言い方にしない判断を書く。
機能ごとの画面と流れは、各機能の`design.md`に従う。構造の方針は`docs/architecture.md`に従う。
利用者のセッションで認証サービスに触る実装は`infrastructure/supabase-auth.ts`の1つで、画面はブラウザの接続を、再設定の要求の入口はサーバーの接続を渡す。各手続きは使う頼みごとだけの約束の型で受け取る。
集約の入口は、開始の命令(`begin<操作>`)が`Start`を返し、実行中と段階外を集約が副作用なしで拒否する。

## 構成

- `src/features/auth/domain/flow.ts`: 命令の結果の型(`Start`、`Step`)と欄ごとのエラーの型(`FieldErrors`)。
- `src/features/auth/domain/auth-failure.ts`: 失敗の種類と利用者向けの文言の表。失敗値の作成(`UNREACHABLE`など)と、確かめられなかったときの文言(`unconfirmedMessage`)も持つ。
- `src/features/auth/domain/routes.ts`: 保護対象の画面、未認証専用の画面、サインインのURL、遷移元の規則と、要求のリダイレクト先(`redirectFor`)。`src/proxy.ts`が`lib/supabase/session.ts`へ関数として渡す。
- `src/features/auth/domain/password.ts`: パスワードの入力と強さの規則。最小長と最大長の数値は、ここだけが持つ。規則の文面(`PASSWORD_RULE_MESSAGE`)も持ち、入力の検証と弱いパスワードの拒否が使う。
- `src/features/auth/application/call-result.ts`: 認証サービスへの頼みごとの結果(`CallResult`)。
- `src/features/auth/infrastructure/supabase-auth.ts`: 利用者のセッションで認証サービスに触る唯一の実装。画面はブラウザの接続を、再設定の要求の入口はサーバーの接続を渡す。応答の変換(エラーのクラス名とコード、イベント名、セッションの形)も、このファイルだけが知る。
- `src/lib/supabase/server.ts`: サーバーでの接続。管理者の接続と、要求の利用者のセッションの接続。
- `src/features/auth/ui/use-screen-view.ts`: 画面の状態、表示中の判定、チェックのウィジェットの参照を持ち、手続きへ渡す画面の約束を作る。
- `src/features/auth/ui/auth-field.tsx`、`src/components/ui/busy-button.tsx`: 入力欄とエラー文の結び付け、処理中のボタンの表現。

## 命名の規則

| 概念 | 規則 | 例 |
| --- | --- | --- |
| 集約の型と初期値 | `<操作>Flow`、`initial<型名>` | `SignInFlow`、`initialSessionEndFlow` |
| 開始の命令 | `begin<操作>(流れ, 入力)`が`Start<流れ, 依頼>`を返す | `beginSignIn`、`beginSignOut` |
| 結果つきの命令 | `<動詞><操作>(流れ, 入力)`が`Step<流れ, 結果>`を返す | `endSignOut`、`leave` |
| 画面から送る事実 | 過去形の出来事。reducerは`<操作>Reducer` | `captchaChecked`、`failed` |
| 認証サービスの状態変化 | `AuthChange`(ドメイン)、`AuthChanges`(約束) | |
| 認証サービスに頼む約束 | `<手続き>Authenticator` | `SignInAuthenticator`、`SessionAuthenticator` |
| 手続きの依存の引数名 | 約束の型名の先頭を小文字にした名前 | `navigation`、`pageLoad`、`pageReplace` |
| 「セッション」を含む名前 | `Session`(手続き)、`SessionEndFlow`(集約)、`SessionStatus`(分類)、`SessionReading`(読み取り結果)。SDKの`Session`はこのアプリの名前に使わない | |
| 「届かなかった」 | `unreachable`だけ。「拒否された」は`refused` | |

## セキュリティチェックのトークンの消費と保持

| 操作 | 受け付けられた | 拒否された | 届かなかった |
| --- | --- | --- | --- |
| サインイン | 遷移する(送信中のまま)。遷移が投げたら、消費し、チェックをやり直す | 消費し、チェックをやり直す | 保持する。チェックをやり直さない(通信の断を値で返す場合も) |
| コード送信と再送 | 消費し、チェックをやり直す | 消費し、チェックをやり直す(通信の断を値で返す場合も) | 保持する。チェックをやり直さない |
| 登録済みの判定(サインアップ) | 使わない | - | 保持する(確かめられなかった場合も) |
| コード確認、パスワード設定 | 使わない | - | - |

拒否は、応答があった失敗である。届かなかったは、応答が無かった(呼び出しが投げた、接続を得られない)こと。サインインは、通信の断を値で返す場合も、照合が届かなかったとして保持する。

## 離脱の原則

- 処理の応答待ちに画面を離れた後は、離れた画面の処理は、画面の状態を更新せず、遷移せず、チェックのやり直しもしない。手続きは、遷移や事実の送信の直前(間に待ちを挟まない位置)で、画面が表示中か(`ViewLifetime`)を確かめる。共通の順序の関数の中の確かめは、呼び出し元の待ちの後を保証しないため、呼び出し元で確かめ直す。
- 安全に関わる副作用(パスワードの変更の後の全端末のサインインの終了)は、離れた後も完了させる。再設定は、変更と終了をサーバーへの1回の要求にして満たす。
- 確認コードのメールの送信は、安全に関わる副作用に当たらない。登録確認の待ちで離れたら送らない。
- サインアウトの完了を待つ間に離れたら、結果を破棄し、遷移しない。この端末のサインインの終了の依頼は取り消さない。
- 例外は無い。再設定で変更の応答待ちに離れたときも、変更と終了の結果によらず、再設定の処理は表示も遷移もしない。
- この原則が抑えるのは、離れた画面の処理による表示と遷移だけである。離れた先の画面が自分の役割で行う遷移(ラウンドの画面の見張りが、喪失を検知してサインインへ移すなど)は対象外で、従来どおり行われる。

## 再送信の間のエラー表示

- 4画面(サインイン、サインアップ、パスワード再設定、認証コードの入力と再送)で同じ規則にする。規則は2つの集約(`sign-in-flow.ts`、`password-setup-flow.ts`)だけが持つ。
- 送信の開始では、以前のエラー(上部の理由、欄ごとのエラー)を消さない。送信中の表示と同時に出てよい。
- 次の結果でだけ変える。成功は消す(段階が進む、再送の成功、遷移で終わる成功)。新たな失敗は、上部の理由をその理由に差し替え、欄のエラーを消す。入力の検証の失敗は、上部の理由を消し、欄のエラーに差し替える。
- 同じ失敗が再び起きたときは、合図も通知も足さない。変化は送信中の表示が出て消えることだけである。エラー表示の読み上げの扱いは変えない。
- 送信を伴わない操作(メール入力へ戻る)は、従来どおりエラーを消す。
- サインアウトとプリセット削除の確認ダイアログには適用しない。

## 確立した前提

1. 接続は、使う時に取得する。事前描画に環境変数を要求せず、頼みごとの時の欠落は通信エラーとして示す。適用範囲: 認証サービスへの頼みごととサインインの状態の読み取り。認証状態の変化の購読は、接続を得られないとき同期に投げる(起動時から欠落した画面は購読で止まり、通信エラーの表示と再試行は無い。変更前と同じ)。
2. 確かめられないときは、`unknown`を返す。サインインの状態の読み取りは投げない。
3. 接続を作る関数は、同じ画面では同じ接続を返す(ブラウザ)。サーバーの要求の入口は、1回の要求で1つの接続を作って渡す。
4. 読み取りが投げた場合を、利用側が個別に受けない。

## 約束の例外の契約

投げない: 認証サービスへの頼みごと(`CallResult`で返す)、サインインの状態の読み取り、端末の識別情報の書き込み、画面の約束、通信の可否。
投げることがある: `Navigation`、`PageLoad`(手続きが通信エラーの失敗として扱う)、`RegistrationLookup`(届かなかった失敗として扱う)、`PasswordChange`(通信エラーの失敗として扱う)、`PageReplace.replace`(見張りもサインアウトも扱わない。以後の遷移も行わない)、`AuthChanges.subscribe`(接続を得られないとき同期に投げる。手続きは扱わない)。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| 認証サービスに触るブラウザ側の実装を1つにし、手続きは使う頼みごとだけの約束で受け取る | 同じ外部の実装を分けない(方針の第8節の3)。同じ頼みごとの呼び出しを1か所にするため | 認証サービスを差し替えるとき |
| 開始の可否と開始の遷移を、集約の1つの命令にする | 判定を経ない開始や、実行中と段階外の開始を、集約自身が副作用なしで拒否するため | 開始の条件を持たない操作を足すとき |
| 実行中の判定は集約が持ち、確認ダイアログは外から実行中を受け取る表現だけの部品にする | 判定の持ち主を1つにするため。呼び出し元ごとの状態は呼び出し元が持つ(サインアウトは集約、プリセット削除は削除側のフックの同期の`ref`) | 確認ダイアログ以外からサインアウトを呼ぶとき |
| 利用者向けの文言は`auth-failure.ts`の表だけが持つ | 種類と文言は一緒に変わる。インフラ層は種類を返す。表に無い失敗も固定の文言で示し、認証サービスの文言(外部の言語)は出さない | 画面ごとに文言を変えるとき |
| 経路の規則は`routes.ts`が持ち、共有の技術は関数として受ける | 共有の技術は機能を参照しない(P01) | サーバー側の保護を機能の外へ出すとき |
| `already_registered`を共有の失敗の種類に残す | 文言の表と種類の定義を1つに保つため。作るのは手続きだけ | 登録済みを他の画面でも扱うとき |
| 約束は使い手の手続きの数で置く | 使い手が1つの約束は手続きのファイル、2つ以上は自分のファイル(方針のR02) | 手続きの使い手が変わるとき |
| 失敗後のトークンの消費と保持を操作ごとの規則にする | 送信が使ったトークンは再利用できず、使っていないトークンは再利用できるため | 認証サービスが、値で返す通信の断とトークンの使用の関係を示したとき |
| パスワードの規則の文面を1つにし、入力の検証と弱いパスワードの拒否で同じ文面を示す | 同じ規則を同じ文言で知らせるため。数値は`password.ts`だけが持つ | 認証サービスのパスワードの設定を変えるとき |
| エラーを変えるのを結果だけにし、開始では消さない | 送信のたびに画面がずれないようにするため。規則を集約に置き、画面の4か所に複製しない | 送信中に別の表示を出すとき |

## 制約と未対応

- 利用側の機能(取得、同期、ラウンド)は、通信の可否の実装を層のパスで参照し、自分で生成している。約束の型で受け取る注入は別作業である。
- `src/proxy.ts`の`config.matcher`は、経路を文字列で再掲する(Next.jsの静的な設定のため)。`proxy.test.ts`が一致を確かめる。
- 遷移が投げたときの扱い(再設定、サインイン、サインアップ)は未決定で、現行のまま(通信エラーを示す)。
