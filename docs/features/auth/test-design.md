# auth 共通テスト設計

## 基準と優先順位

基準は承認済みの[共通設計](design.md)と、各機能のrequirements.md・design.mdである。
最優先は直接APIを含むパスワード新規認証の拒否、削除認可と対象の取り違え防止、削除の原子性である。
次に既存セッション・利用者ID・記録の維持、OTPだけの登録・ログイン、待機・再試行・離脱を保証する。
本書は期待する検証の設計であり、実装済み・検証済みを意味しない。

| 層・既存の体系 | 保証する境界 | 配置候補 |
| --- | --- | --- |
| Vitest単体 | 入力、段階、排他、時間、失敗変換、完了先 | `apps/web/src/features/auth/{domain,application,infrastructure}/*.test.ts` |
| Vitestコンポーネント | 公開操作、状態の表示、チェック・OTP部品との接続 | `apps/web/src/features/auth/ui/*.test.tsx`、設定の既存テスト |
| pgTAP | Hook・RPCの権限と認可、削除・匿名化、rollback | `supabase/tests/auth.sql`、`delete_account.sql`、`rls_matrix.sql`、`rpc_matrix.sql`、`migrations_final_state.sql` |
| 実Auth・PostgREST結合 | 発行方式、署名検証、セッション更新、実コードとメール | 既定Playwright構成の既存`apps/web/tests/e2e/auth/*.spec.ts`内で公開APIを使用する |
| E2E | 利用者の主要な目的を実ブラウザ・認証・DBまで通す | 既存のsignin(旧signupを統合)・delete-account・change-email・signoutとappのspec |

PlaywrightからAPIを呼ぶ結合試験と、画面操作を通すE2Eは、実物で通した境界を区別して報告する。
専用設定・スクリプト・別ジョブ・実行除外を追加せず、既存の体系で実行する。
要求とテストの識別子・対応表は作らず、振る舞いが分かるテスト名にする。

## 共通OTPの単体・コンポーネント

表の行は観点であり、異なる前提や操作は個別のテストにする。
正常系を先に置き、境界・失敗・再試行を続ける。

| 前提・操作 | 期待結果 |
| --- | --- |
| 有効なメールで送信し、届いたコードを確認する | メール入力からコード入力へ進み、確認したメールのOTPセッションを用いて完了処理へ進む。パスワード段階を挟まない。 |
| コード入力からメールへ戻る | メールと送付成功からの再送待機を保ち、コードを消す。メールを変更したら以前の送付先のコードで確認しない。 |
| 送付または再送が成功する | 成功時を起点に60秒の待機を開始し、残り秒数を表示する。失敗で新しい成功起点を作らない。 |
| 待機終了の1ms前・ちょうど・1ms後に再送する | 終了前は拒否し、終了時以後は他条件を満たせば送信できる。戻る操作で待機を解除しない。 |
| 残り秒数が2・1・0のときに1秒の刻みを受ける | 2は1、1は0になり、0は0のまま負にならない(`auth-code.test.ts`の`decrementResendCooldown`)。通常OTP・メール変更・削除が同じ関数を使い、規則の組合せはここで確認して各フローで繰り返さない。 |
| 残り秒数が変わる、0になる、画面を離れる | 1秒後の刻みを予約し、0・離脱・再予約で取り消す。離脱後は残り秒数の更新が起きない(`use-code-entry`の`useResendCooldownTick`)。時刻は共有のClockの偽物で進め、通常OTP・メール変更の画面から同じ部品で確認する。 |
| メール欄・コード欄でEnterを押す | 対応する送信・確認の公開操作へ接続する。メールはemail、コードはone-time-codeの自動入力属性を持つ。 |
| メール未入力・形式不正、またはコード未入力で実行する | 不備を表示してIOを行わない。コードの形式・期限・再使用はAuthへ委ね、未入力以外を独自認可にしない。入力欄は6桁上限を守る。 |
| 実行中、入力不備、オフライン、チェック未完了が重なる | 実行中→入力不備→オフライン→チェックの優先で判定する。オフラインでは送信・保留をせず、入力とチェックトークンを保つ。 |
| チェック未完了で送信または再送し、その後トークンが到着する | 押下時の入力を保持して処理中として待ち、同じ操作を自動再開する。待機中の入力変更を送付先へ混入しない。 |
| 追加チェックを開始する、または追加操作なしで10秒に達する | 追加操作中は待ち続け、追加操作なしでは10秒上限で理由を示して解除する。偽タイマーで上限の直前・ちょうど・直後を確認する。 |
| チェックに失敗し、再度操作する | 共通のエラー欄へ表示して待機を解き、再操作では改めて待てる。追加操作・失敗で展開した欄は完了後もresetまで保ち、resetまたは新段階で畳む。 |
| 送信・再送が成功または失敗する | 消費したCAPTCHAを取り直す。確認はCAPTCHAなしで行い、Authの検証制限を迂回しない。 |
| 送信・確認・再送の未完了中に再押下または戻る | 相互排他を保ち、外部への重複要求を出さず段階を壊さない。完了成功後は遷移まで処理中を保つ。 |
| 誤り・期限切れ・使用済み・制限・CAPTCHA・通信障害を返す | 対応する内側の失敗とフォーム全体の案内を示し、成功にしない。入力を保ち同じ段階で再試行できる。失敗表示と再試行成功は別テストにする。 |
| チェック待ち、またはIO開始後に画面を離れる | 予約を解除し、到着したトークンで新たな要求を始めず、遅い応答で表示・完了遷移をしない。Authで既に成立したセッションを取り消さない。 |

`email-otp-flow.test.ts`と`email-otp.test.ts`に判断の組合せを集める。
`email-otp-form.test.tsx`は操作と手続き・表示の接続を扱い、既存のotp-email-step・otp-code-step・use-check-wait・turnstileの固有規則は各テストで検証する。
内部依存は実物を使い、Auth・Clock・Connectivity・PageReplace・保留Promiseなどの外側だけを制御する。
ClockとConnectivityは既存の共有の偽物を使い、UIはIntlTestProviderと翻訳ヘルパーを使う。

## Authアダプターとセッション

| 前提・操作 | 期待結果 |
| --- | --- |
| 統合入口、削除再確認のコードを送る | 統合入口はshouldCreateUser:true、削除再確認はfalseとcaptchaTokenを渡す。確認はemail・token・type:emailを渡す。登録専用・ログイン専用の入口を持たない。 |
| 削除再確認で未登録の既知の拒否、制限、CAPTCHA、通信失敗をそれぞれ受ける | 既知の未登録拒否だけを共通の送付受理へ写す。自動登録(削除はfalse)やサービスの生の文言の表示をしない。統合入口ではこの拒否を前提にしない。 |
| OTP確認成功、利用者取得、接続不備を受ける | SDK型を内側の結果・利用者IDとメールへ変換し、接続不備はunreachableへ写す。確認成功でも想定外の利用者を削除対象にしない。 |
| SIGNED_IN・起動時復元・SIGNED_OUT・TOKEN_REFRESHEDを受ける | 前二者は利用者ID付きsigned-in、終了はsigned-out、更新だけでは通知しない。 |
| 同じ利用者のOTP再確認、または別利用者への切替を受ける | 同じIDでは再読み込みせず、別IDでは既存の見張りで記録を分離する。サインアウト後の無条件ホーム復帰を起こさない。 |

この層ではSDKの呼出契約を確かめ、実Authとの接続は下記の結合試験で確かめる。

## 発行HookのDB試験

方式と権限は期待値表と実測結果を全件比較し、同じ組合せを個別試験で重複させない。
許可行では入力claimsと出力claimsの完全一致を確認する。
方式の判定元にはHookの実イベントと同じフィールドを用い、実Auth試験でもotp・token_refresh・email_changeの各経路を接続する。

| 今回の発行方式 | 過去のamr | 期待結果 |
| --- | --- | --- |
| otp・token_refresh・email_change | 正常なclaims。token_refreshではpasswordを含む旧セッションも使う | 発行を許可しclaimsを変えない |
| password・recovery・その他の文字列（Hookへ直接渡す入力の判定。実Authの回復コード確認はotpとして渡るため、この行は実Authの結果を示さない） | 任意。有効なOTPを含む場合も試す | 403で拒否 |
| 欠落・null・文字列以外 | 任意 | 403で拒否 |

`supabase_auth_admin`だけが関数を実行でき、必要なschema USAGEを持つ。
PUBLIC・anon・authenticatedは実行できず、SECURITY INVOKERであることを確認する。
方式の欠落を過去のamrで補完して許可しない。
権限は既存の権限行列へ加え、Hookの許可・拒否の結果はauth.sqlで確認する。

## 実Auth・メール・署名検証の結合

| 前提・操作 | 期待結果・観測 |
| --- | --- |
| 新規・登録済みへ標準OTPを送って確認する | コード確認後だけセッションと保護データを得られる。メールは共通本文でコード・15分期限・心当たりがない場合の案内を持つ。 |
| 確認済み・未確認の利用者へ直接回復要求を出す | 応答上送付対象となるメールも共通のコードだけの本文で、認証成立リンク・パスワード操作の案内を含まない。メール本文がコードだけであることを確認する。回復コードの確認は実Authが発行Hookへotpとして渡し、通常のメールOTPと同等のセッション発行を許容する（登録済みメールへ届いたコードの確認で得る認証であり、パスワード認証の復活ではない）。 |
| 正しい旧パスワードで直接grant、直接password signup、OTP後の直接password更新後のgrantを試す | 新規パスワード認証のセッションを発行できず、保護データを読めない。更新API自体の失敗は期待しない。signupで行が作られることだけを認証成立と誤認しない。 |
| 回復要求・回復コード・password更新を試す | 回復後に直接パスワードを更新しても、そのパスワードでのgrantが拒否され保護データを読めない。更新API自体の成否は問わない。回復コードによるOTPセッションの発行は期待値に含め、拒否を期待しない。 |
| 誤り・期限切れ・使用済み・再送前のコードを確認する | 実Authが拒否し、新しい認証済みセッションを得ない。拒否だけでなく保護データの非公開も確認する。 |
| 送信間隔・送信上限・検証上限・CAPTCHA失敗へ達する | Authが拒否し、UIも失敗として扱う。ローカルで無効な制限をモックで成功扱いせず、プレビューの実設定での確認を分けて残す。 |
| 端末Aで送付し端末Bでメールを閲覧する | Bで読むだけではAもBも認証されず、Aでコードを確認した後だけ目的の記録へ進める。メールに認証成立リンクがあれば失敗とする。 |
| 実Authが発行したJWTでPostgRESTの削除RPCを呼ぶ | 新しい通常OTPを許し、古いOTP・passwordだけ・refreshだけを拒否する。JWT改ざん・署名不正はRPCに到達せず拒否される。詳細は削除のテスト設計に従う。 |
| Hookがエラーを返す | 新規発行が失敗し、パスワード発行へ自動で切り戻らない。障害注入は隔離ローカル環境で行い必ず元へ戻す。 |

Mailpitはテストごとの宛先と送信前のメッセージID/取得時点で新着を絞り、再送前のメールを最新と取り違えない。
コードやトークンをログ・添付・失敗メッセージへ出さず、試験名・方式・状態・拒否コードで結果を残す。
期限試験は公開APIで発行したコードを用い、ブラウザ時計の変更をAuth時刻の変更とみなさない。
ローカルで期限だけを短縮する場合は、発動機構の試験と900秒の設定確認を分け、15分の実期限確認を完了したと報告しない。

設定差分ではメール確認必須・6桁・900秒・既存の送信/検証制限と、本番/プレビューの送信間隔60秒を確認する。
confirmation・magic_link・recoveryの参照先が同じemail-otp.htmlであり、旧signup.html・already-signup.html・reset-password.htmlが残らないことを確認する。
テンプレート文字列の検査だけで完了とせず、前表の実配信本文で補完する。

## 切替と旧認証情報の検証

隔離ローカル環境で、自作の利用者と元の記録、切替前passwordセッションとOTPセッションを準備する。
切替前に正しい自作パスワードで認証できることを確認し、Hook切替後は同じ値で拒否されることを確認する。
Hook切替後も両セッションの取得・更新・元の利用者IDと記録へのアクセスを確認する。
DB内だけで切替前後の保存ハッシュの一致を比較し、外へ出すのは一致の真偽だけとする。
署名鍵・Cookie名・セッション期限・rotationを切替理由で変更していないことは設定差分でも確認する。
切替時に旧confirmation/recoveryコードを失効させず、切替直後は最大15分、旧コードが有効なまま残るのを許容する。コードは本人のメールにしか届かず、回復コードをメールOTPと同等とする方針と整合する。
旧コードでの確認が成功しても、得られるのは通常のメールOTPと同等のセッションであり、パスワード認証は復活しないことを確認する。失効やその拒否を期待しない。
旧リンク・未完了PKCE交換は新UIでは使わず、進行中のemail_changeの途中状態と既存セッション・refresh token・利用者ID・記録が切替で変わらないことを比較する。
OTP許可と同時に、新削除RPCと旧引数なしRPCの廃止を確認する。
旧画面・キャッシュからの旧RPC要求は削除を起こさず失敗する。
これらは通常CIのたびに稼働中Authを変更する試験にせず、隔離環境での切替リハーサルとして結果を残す。
既存Hookとの合成、本番/プレビューの期限・CAPTCHA・IPヘッダ・送信間隔60秒は配置前の確認事項とする。
本番の秘密情報、一般利用者のパスワード・ハッシュを取得しない。

## 認証入口の統合と旧アドレス

統合入口の個別の保証は[signin](signin/test-design.md)、旧アドレスの再登録は[change-email](change-email/test-design.md)に置く。
ここでは層をまたぐ割当てだけを定める。

| 観点 | 担当層 | 方針 |
| --- | --- | --- |
| 登録可否(shouldCreateUser) | Vitest単体 | 統合入口はtrue、削除はfalseをアダプター・手続きの契約で確認する。 |
| 新規・既存の区別なし(画面・文言・完了先) | Vitest単体・コンポーネント、E2E1件 | 単体で手続き・画面の分岐がないことを確認し、E2Eは新規・既存で同じ画面・文言が出る1経路に限る。 |
| 認証後の遷移 | Vitest単体(auth-routes・proxy・sign-in)、E2E | 有効な遷移元とホームの全組合せは単体で、新規・既存の両方で、遷移元付き認証から目的の画面へ戻る経路をE2Eで1件ずつ。外部URLの組合せは単体で確認し、E2Eでは繰り返さない。 |
| /signupの廃止 | proxy単体、差分レビュー、navigation E2E | 専用ガード・matcherがなく未定義URLと同じ扱いであること。定数・ページ・処理の不在は差分レビューと型・未使用検査。 |
| 再送待機の共通化 | Vitest単体・コンポーネント | 0の下限と刻みの予約・取消を共通部品で確認し、メール変更の画面から接続を確認する。 |
| 旧アドレスでの新規登録 | 実Auth結合(Playwright) | 既存セッションのない状態で、新旧の利用者IDと記録をローカルDBで照合する。 |
| 未サインイン向けヘッダーの廃止・ロゴ | 差分レビュー・型/未使用検査、Vitest単体、E2E1件、手動確認 | ヘッダーの不在は削除の差分レビューと型・未使用検査で保証し、DOMの不在は期待値にしない。ロゴ部品の高さ指定は単体、認証画面のロゴから紹介「/」への遷移は`signin.spec.ts`の1件。両段階の表示と高さ・余白・配置は手動で確認する。 |

見た目の確認(ビルドを含む`pnpm preview`、port 3000)は、機能テストの実装・実行より前に行い、ユーザーが確認する。
確認前に固定の寸法・配置を期待値にするテストを書かない。

## 廃止機能と既存テストの移行

- password-setup・sign-in-flowの旧規則を共通OTPの試験へ置換し、削除したパスワード入力・設定・変更・再設定の専用試験と補助を削除する。
- `/reset-password`のページ・定数・ガード・matcher・Service Worker・fixtures/inflightの専用経路が残らないことを差分レビューする。アクセスは認証済み/未認証で任意の未定義URLと同じ扱いであることをnavigationの既存specで確認し、廃止機能のspecや互換転送を残さない。
- 設定のpassword項目の定数・分岐・専用互換テストを削除し、任意の未知名を用いた既存の一般的な正規化の試験を維持する。
- `helpers/auth`・`rounds`・`round-fixtures`・`other-device`・`other-browser-device`・`session-revoke`・`reference-data`・`presets`・`auth.setup`の準備を標準OTPとMailpitへ置換する。
- 実SDKと既存SSR Cookieアダプターを使い、ケース・ブラウザ・別端末でセッションを共有しない。認証を検証するケースは画面を通す。
- 失効試験はパスワード変更で作らず、固有利用者の実セッションを終了させる。管理権限を使う既存補助を残す場合もローカルの試験準備に限定し、削除の実行・認可には使わない。
- メール変更の両側確認、サインアウト、オフライン・同期・一覧・記録の利用者分離の既存回帰を維持する。

## 実行・完了条件

VitestはGiven・When・Thenを分け、1テスト1振る舞いにする。
固定クラス・寸法・配色・DOM全体・内部関数の呼出順を期待値にしない。
E2Eは利用者の経路順に段階を確認し、リンクは押してURLと画面を確認する。
未サインイン向けヘッダーを持たず、ヘッダーの遷移リンクのE2Eも置かない。
認証画面のロゴから紹介「/」への遷移は、リンクを持つ画面の機能のE2Eの`signin.spec.ts`に1件だけ置き、`navigation.spec.ts`の同趣旨の件はここへ移して重複させない。
/signupは廃止しており、画面・転送・専用ガードのE2Eは置かず、任意の未定義URLと同じ扱いであることだけを`navigation.spec.ts`で確認する。

1. 共通OTP・入口・削除・アダプター・設定の対象Vitestを実行する。
2. `pnpm validate`で既存の静的検証と単体試験を通し、`pnpm test:db`で権限・RPCの行列と既存DB回帰を通す。
3. 既定構成の`pnpm test:e2e`で結合・主要経路と、準備を変更したラウンド等の回帰を実行する。
4. 手動の`pnpm preview`はport 3000、既定Playwrightは新規ビルドを含むpreviewをport 3100で起動する。両者でビルド出力を競合させず、pnpm devは使わない。

カバレッジは率の目標を増やさず、認可拒否・対象切替・期限・結果不明・離脱の未検証分岐を探すために使う。
任意sleepと無条件retryで失敗を隠さず、メール到着・認証更新・ロック取得など状態の成立を待つ。
後始末は試験ごとに行い、準備途中の失敗でも作成済みの利用者・クライアント・タイマー・購読・ロックを解放する。

未実行・環境不足・従来の失敗を成功に含めず、重要な未検証が残る状態をリリース完了にしない。
