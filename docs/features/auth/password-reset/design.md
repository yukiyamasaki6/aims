# auth/password-reset 設計

## 概要

`/reset-password`でメールアドレス、認証コード(OTP)、新しいパスワードの3段階を進める。
`resetPasswordForEmail`でコードを送り、`verifyOtp`(type: recovery)で確認する。パスワードの変更は、ブラウザから`updateUser`で行う。他の端末のサインインは、認証サービスがパスワードの変更時に終える。他の端末の画面は、アクセストークンの期限後の更新の拒否で、`/signin`へ移る。変更後は`signOut`(範囲`local`)でこの端末のサインインを終え、routerで`/signin`へ移り、自動ではサインインしない。
送信と再送にはTurnstileを使い、`verifyOtp`には使わない。
手順と状態の規則は、サインアップと共有する(集約、手続きの共通の順序、画面の骨組み)。再設定だけが持つのは、登録の有無を判定しないこと、コードの種類、変更後のこの端末のサインインの終了と遷移である。
認証済みで`/reset-password`を開くと、共通の認証ガードが`/rounds`へ送る。

## 画面と状態

| 状態 | 表示 | 次の状態 |
| --- | --- | --- |
| メール入力 | メールアドレス、captcha、送信、サインインへのリンク | 送信成功でコード入力、リンクで`/signin`、検証・送信失敗はエラー表示、送信中は送信ボタンを`aria-disabled`にする。以前のエラーは開始で消す |
| コード入力 | 認証コード、確認、再送、戻る。迷惑メールの確認を案内する | 確認成功でパスワード設定、戻るでメール入力、再送、確認・再送の失敗はエラー表示、処理中は3つのボタンを`aria-disabled`にする。以前のエラーは開始で消す |
| パスワード設定 | 新しいパスワード(表示切替つき)、変更 | 成功で`/signin`(全ての端末のサインインの終了の結果によらない)、検証・変更失敗はエラー表示、処理中は変更ボタンを`aria-disabled`にする。以前のエラーは開始で消す |

- コード入力では、確認・送付(再送)・戻るが互いに排他である(実行中の操作があれば、他の操作を受け付けない)。
- 再送にはクールダウンがあり、中の再送はエラーを表示する。再送ボタンは、待ち中は「再送（N秒）」(`otpResendWait`)と残りを示し、`tickCooldown`が1秒ごとに進める。
- パスワードの入力欄は`PasswordInput`で、表示・非表示を切り替えても入力値を保つ。

## 構成とデータの流れ

構造の方針は`docs/architecture.md`に従う。

- `src/app/(auth)/reset-password/page.tsx`: 入口。認証の実装(接続を作る関数`createClient`を渡す)、遷移の実装、通信の可否の約束(`Connectivity`。送信の直前のオフラインの読み取りに使う)、手続きを生成し、手続きを画面へ渡す。
- `src/features/auth/ui/reset-password-form.tsx`: 再設定の画面の文言とリンク(見出し、サインインへのリンク、パスワード設定の段階の文言)を、UI層の文言の一覧から得る。サインアップと共有の骨組みへ渡す。
- `src/features/auth/ui/password-setup-form.tsx`: 段階の振り分けと、パスワード設定の段階の描画。状態を`useScreenView`で持ち、操作のたびに入力と画面の約束(`ScreenView`)を手続きへ渡す。サインアップと共有する。
- `src/features/auth/ui/otp-email-step.tsx`、`otp-code-step.tsx`: メール入力とコード入力の段階の描画。サインアップと共有する。
- `src/features/auth/application/reset-password.ts`: 手続き。状態を持たず、コードの送付(初回も再送も同じ操作)、確認の順序と、パスワードの設定の後の、この端末のサインインの終了(結果は見ない)と、サインインへの遷移を持つ。
- `src/features/auth/application/password-setup.ts`、`password-setup-authenticator.ts`: サインアップと共有する、手続きの共通の順序(送信の直前にオフラインを1回読むことを含む。操作の開始、コードの送付の依頼、確認、パスワード設定の依頼)と、認証サービスへ頼むことの約束。
- `src/features/auth/domain/password-setup-flow.ts`: 集約。段階、実行中の操作、再送の待ち時間、captchaトークンを持ち、開始の命令(`beginSendCode`ほか)が、操作の可否と入力の検証の順序、確認・再送・戻るの排他を守って`Start`を返す。事実の遷移でトークンの消費を守る。サインアップと共有する。
- `src/features/auth/domain/password.ts`、`auth-code.ts`、`email-address.ts`、`captcha-token.ts`、`auth-failure.ts`、`auth-routes.ts`: パスワードの文字種、認証コードと再送の待ち時間、メールアドレス、セキュリティチェック、失敗の種類、遷移先の規則(domain。経路の文字列は経路表が持つ)。入力の誤りと失敗は種類で返し、文言は持たない。
- `src/features/auth/infrastructure/supabase-auth.ts`: 利用者のセッションで認証サービスに触る唯一の実装(認証の4機能で共通。`docs/features/auth/design.md`)。ブラウザの接続で`resetPasswordForEmail`、`verifyOtp`、`updateUser`、`signOut`(範囲`local`)を使う。応答が無かった場合(接続を作れない、呼び出しが投げた)は、`unreachable`の失敗として返す。
- `src/features/auth/infrastructure/browser-page-load.ts`: サインアウトのセッション喪失の遷移（`window.location.replace`による置き換え、今の場所）の実装。
- `src/features/auth/application/password-setup.ts`の`tickCooldown`: 再送できるまでの秒数を進める1秒の予約(`Clock`)。画面の部品`password-setup-form.tsx`が、残りが変わるたびに予約し直す(依存は描画をまたいで同じ参照の`dispatch`だけで、描画のたびには張り直さない)。
- `src/app/(auth)/layout.tsx`、`src/features/auth/ui/auth-header.tsx`、`src/features/auth/ui/turnstile.tsx`: 認証画面の共通部品と枠。

契約は次のとおりである。

- メールアドレスは形式、パスワードは半角英数字と記号のみ、送信前に検証し、満たさなければ送信しない。コードは未入力だけを送信前に検証し、桁数と正しさは入力欄の`maxLength`(6桁)と認証サービスに任せる。
- パスワードの長さと強さ(8〜72文字で英字と数字を含む)は認証サービスが拒否する。`weak_password`と、パスワードの設定での`validation_failed`は、入力の検証と同じ規則の文面で示す。
- 送信の直前にオフラインを1回読み(購読しない)、入力判定 → オフライン判定 → チェック判定の順に判定する。オフラインでは入力の不備だけを示し、チェック未完了は示さない。入力に不備が無くオフラインなら失敗の種類`offline`を示し、認証サービスへ送らず、トークンも消費しない。
- captchaトークンは、コードの送付(初回も再送も)の成功も失敗も(通信の失敗を含む)消費し、取り直させる。確認とパスワード設定には使わない。
- 再送の間隔は`max_frequency`で、productionとpreviewは60秒、ローカルとCIは1秒である。クールダウンは、送付の成功で始まる(失敗では始まらない)。
- パスワードの設定の成功後は、送信中を解除せず、この端末のサインインを終えてから、routerで`/signin`へ遷移する。この端末のサインインの終了の結果は見ない。他の端末のサインインは、認証サービスがパスワードの変更時に終える。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| 送信の直前にオフライン状態を1回読み、購読しない。オフライン専用の失敗の種類を持つ。確認とパスワード設定は、トークンを使わないが、同じ画面で同じ原因が違う表示にならないよう、同じ判定を適用する | 全失敗でトークンを消費するため、オフラインの再送信がチェック未完了の表示になり原因が分からなくなるのを防ぐ。通信断でトークンを保持する分岐を持たず、判断を1か所にする。「通信エラー」では端末の回線が切れていることが分からない | `navigator.onLine`がtrueのまま通信できない場合も扱いたいとき |
| マジックリンクでなくOTPを使い、メールのテンプレートを差し替える | 同じ画面の中でコードを入力して完結できるため | メール到達の問題が解消されたとき |
| 変更後はサインインを終えて`/signin`へ移り、自動サインインしない | 再設定後に改めて本人確認できるため | 再設定後の自動サインインを要求に加えるとき |
| 集約、手続きの共通の順序、画面の骨組みをサインアップと共有し、再設定だけの動作は再設定の手続きと実装に置く | 認証コードでの本人確認とパスワード設定の規則が変わる理由が同じで、複製を残す理由が無いため。登録の判定の有無、コードの種類、設定後の動作は、共有の部品に分岐として入れない | 再設定とサインアップの規則が分かれるとき |
| 確認・送付・戻るを排他にし、実行中の操作を集約の1つの値で守る | 並行操作で状態が壊れたため、確認中と再送中を独立させる方式をやめた。詳細: #545 | 応答を世代管理する方式にするとき |
| ネイティブの`disabled`、`required`、`minLength`を使わず、クライアント検証と`aria-disabled`を使う | 理由を利用者へ伝え、E2Eでの二重送信を防ぐため | 検証の理由を別の方法で利用者へ伝えるとき |
| パスワードの文字種を`maxLength`でなく送信時に検証する。メールアドレスは形式だけを送信時に検証する。コードは未入力だけを送信前に検証し、桁数と正しさは`maxLength`と認証サービスに任せる | Playwrightの`fill()`が`maxLength`で切り詰めるため。サインインのパスワード欄には適用しない | パスワード規則を変えるとき |
| 認証済みのリダイレクトを`proxy.ts`へ集約し、画面ごとのE2Eは残す | 実装を一箇所にまとめつつ、各画面の挙動を保証するため | ガードの実装を変えるとき |
| captchaは送信と再送に適用し、`verifyOtp`には適用しない | ボットによるメール送信の濫用を防ぐため。テスト用キーは、previewのドメインを事前登録できないため | captchaの方式を変えるとき |
| 水和の完了を`data-hydrated`で示す | E2Eの水和競合を防ぐため。captchaの準備は、E2Eのモックがトークンを渡した回数で待つ(画面に属性を足さない) | E2Eが水和を別の方法で待てるとき |

## 制約と未対応

- 設定の応答待ちに画面を離れたときは、表示も遷移もしない(離脱の原則。`docs/features/auth/design.md`)。パスワードの変更は、要求が認証サービスに届けば行われる。この端末のサインインの終了は、応答の後に行うため、応答前に離れると行われず、再設定のセッションが残る(要求の対象外)。離れた先がラウンドの画面なら、見張りが喪失を検知したときに通常の規則でサインインへ移る(`app/navigation`)。
- この端末のサインインの終了が失敗しても、表示せずに`/signin`へ移る。その端末に再設定のセッションが残りうる(要求の対象外)。
- 確認の成功後、パスワード設定の前に画面を閉じるか再読み込みすると、認証済みのセッションが残り、`/rounds`へリダイレクトされる(要求の対象外)。
- 再設定が行うサインインの終了(この端末だけ。結果は見ずに遷移する)と、サインアウトの手続き(この端末だけ。終えられたかを読み取りで決める)は、完了の意味(再設定は結果によらず移る、サインアウトは終えられたときだけ移る)と遷移(再設定はrouter、サインアウトは置き換え)が違うため、別の手続きにしている。共有するのは認証サービスの実装とサインインのURLの規則だけである。
