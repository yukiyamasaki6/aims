# auth/password-reset 設計

## 概要

`/reset-password`でメールアドレス、認証コード(OTP)、新しいパスワードの3段階を進める。
`resetPasswordForEmail`でコードを送り、`verifyOtp`(type: recovery)で確認する。パスワードの変更と全ての端末のサインインの終了は、要求の入口`changePassword`(Server Action)が、要求のcookieの利用者のセッションで、`updateUser`と`signOut({ scope: "global" })`を1回の要求で行う。
変更後はページ全体を読み込み直して`/signin`へ移り、自動ではサインインしない。
送信と再送にはTurnstileを使い、`verifyOtp`には使わない。
手順と状態の規則は、サインアップと共有する(集約、手続きの共通の順序、画面の骨組み)。再設定だけが持つのは、登録の有無を判定しないこと、コードの種類、変更後のサインインの終了と遷移である。
認証済みで`/reset-password`を開くと、共通の認証ガードが`/rounds`へ送る。

## 画面と状態

| 状態 | 表示 | 次の状態 |
| --- | --- | --- |
| メール入力 | メールアドレス、captcha、送信、サインインへのリンク | 送信成功でコード入力、リンクで`/signin`、検証・送信失敗はエラー表示、送信中は送信ボタンを`aria-disabled`にする。以前のエラーは結果が出るまで残す |
| コード入力 | 認証コード、確認、再送、戻る。迷惑メールの確認を案内する | 確認成功でパスワード設定、戻るでメール入力、再送、再送の成功で以前のエラーを消す、確認・再送の失敗はエラー表示、処理中は3つのボタンを`aria-disabled`にする。以前のエラーは結果が出るまで残す |
| パスワード設定 | 新しいパスワード(表示切替つき)、変更 | 成功で`/signin`(全ての端末のサインインの終了の結果によらない)、検証・変更失敗はエラー表示、処理中は変更ボタンを`aria-disabled`にする。以前のエラーは結果が出るまで残す |

- コード入力では、確認・再送・戻るが互いに排他である。段階の操作は、その段階でだけ受け付ける。
- 再送にはクールダウンがあり、中の再送はエラーを表示する。

## 構成とデータの流れ

構造の方針は`docs/architecture.md`に従う。

- `src/app/(auth)/reset-password/page.tsx`: 画面の入口。認証の実装(接続を作る関数`createClient`を渡す)、ページ全体の読み込みの実装、手続きを生成し、手続きを画面へ渡す。要求の入口の関数を、パスワードの変更の約束として手続きへ渡す。
- `src/app/(auth)/reset-password/actions.ts`: 要求の入口。要求のcookieでサーバーの接続を作り、認証の実装とサーバーの手続き(`createPasswordChange`)を生成して呼ぶ。
- `src/features/auth/ui/reset-password-form.tsx`: 再設定の画面の文言とリンク(見出し、サインインへのリンク、パスワード設定の段階の文言)。サインアップと共有の骨組みへ渡す。
- `src/features/auth/ui/password-setup-form.tsx`: 段階の振り分けと、パスワード設定の段階の描画。状態を`useScreenView`で持ち、操作のたびに入力と画面の約束(`ScreenView`)を手続きへ渡す。サインアップと共有する。
- `src/features/auth/ui/otp-email-step.tsx`、`otp-code-step.tsx`: メール入力とコード入力の段階の描画。サインアップと共有する。
- `src/features/auth/application/reset-password.ts`: 手続き。状態を持たず、コードの送信、再送、確認の順序と、パスワードの変更の要求の後のページ全体の読み込みを持つ。約束は、パスワードの変更の要求(`PasswordChange`。投げることがある)とページ全体の読み込み(`PageLoad`)。
- `src/features/auth/application/password-change.ts`: サーバーの手続き。パスワードの変更と、成功したときの全ての端末のサインインの終了の順序を持ち、画面の手続きの約束`PasswordChange`を満たす。全端末のサインインの終了の約束(`SignOutEverywhere`)を持つ。
- `src/features/auth/application/password-setup.ts`、`password-setup-authenticator.ts`: サインアップと共有する、手続きの共通の順序(操作の開始、コードの送信の依頼、再送、確認、パスワード設定の依頼)と、認証サービスへ頼むことの約束。
- `src/features/auth/domain/password-setup-flow.ts`: 集約。段階、実行中の操作、再送の待ち時間、captchaトークンを持ち、開始の命令(`beginSendCode`ほか)が、操作の可否と入力の検証の順序、確認・再送・戻るの排他を守って`Start`を返す。事実の遷移でトークンの消費を守る。サインアップと共有する。
- `src/features/auth/domain/password.ts`、`auth-code.ts`、`email-address.ts`、`captcha-token.ts`、`auth-failure.ts`、`routes.ts`: パスワードの強さ、認証コードと再送の待ち時間、メールアドレス、セキュリティチェック、失敗の種類、遷移先の規則と文言(値オブジェクト)。
- `src/features/auth/infrastructure/supabase-auth.ts`: 利用者のセッションで認証サービスに触る唯一の実装(認証の4機能で共通。`docs/features/auth/design.md`)。画面はブラウザの接続で`resetPasswordForEmail`、`verifyOtp`を、要求の入口はサーバーの接続で`updateUser`と`signOut`(範囲`global`)を使う。応答が無かった場合(接続を作れない、呼び出しが投げた)は、`unreachable`として返す。
- `src/lib/supabase/server.ts`: サーバーでの接続(要求の利用者のセッション)。
- `src/features/auth/infrastructure/browser-page-load.ts`: `window.location.assign`によるページ全体の読み込み。サインアウトのセッション喪失の遷移（置き換え、今の場所）も同じ実装が満たす。
- `src/hooks/use-countdown.ts`: 再送できるまでの秒数を1秒ごとに進める。
- `src/app/(auth)/layout.tsx`、`src/components/auth-header.tsx`、`src/components/turnstile.tsx`: 認証画面の共通部品と枠。

契約は次のとおりである。

- メールアドレスは254文字以内、コードは6桁、パスワードは半角英数字と記号で8〜72文字で、英字と数字を含む。送信前に検証し、満たさなければ送信しない。
- Supabaseが拒否した`weak_password`は、入力の検証と同じ規則の文面で示す。
- captchaトークンは、認証サービスが応答した送信と再送(成功も拒否も)で消費し、取り直させる。送信と再送が例外で終わった場合は、使っていないので消費せず、同じトークンで再試行できる。確認とパスワード設定には使わない。
- 再送の間隔は`max_frequency`で、productionとpreviewは60秒、ローカルとCIは1秒である。クールダウンは、再送の開始時に始まる。
- パスワードの変更の成功後は、送信中を解除せず、ページ全体を読み込んで`/signin`へ遷移する。全ての端末のサインインの終了はサーバーが同じ要求で行う。サーバーは終了の応答を待ってから応答するが、終了の成否によらず変更の成功を返し、表示中の画面はサインインへ移る。
- パスワードの変更の要求は、自アプリのサーバーを経由する。パスワードをログに残さない。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| マジックリンクでなくOTPを使い、メールのテンプレートを差し替える | 同じ画面の中でコードを入力して完結できるため | メール到達の問題が解消されたとき |
| 変更後はサインインを終えて`/signin`へ移り、自動サインインしない | 再設定後に改めて本人確認できるため | 再設定後の自動サインインを要求に加えるとき |
| パスワードの変更と全ての端末のサインインの終了を、Server Actionの1回の要求にする | ブラウザが順に頼むと、変更の応答の後に画面を閉じたとき、終了が頼まれないため。管理者の鍵は使わず、要求の利用者のセッションで頼む。サーバー用に別の実装を作ると同じ頼みごとの呼び出しが2か所になるため採らない | 認証サービスが、パスワードの変更で全てのセッションを終えるようになったとき |
| 集約、手続きの共通の順序、画面の骨組みをサインアップと共有し、再設定だけの動作は再設定の手続きと実装に置く | 認証コードでの本人確認とパスワード設定の規則が変わる理由が同じで、複製を残す理由が無いため。登録の判定の有無、コードの種類、設定後の動作は、共有の部品に分岐として入れない | 再設定とサインアップの規則が分かれるとき |
| 確認・再送・戻るを排他にし、実行中の操作を集約の1つの値で守る | 並行操作で状態が壊れたため、確認中と再送中を独立させる方式をやめた。詳細: #545 | 応答を世代管理する方式にするとき |
| ページ全体の読み込みを再設定の手続きの約束にし、`Navigation`に足さない | 再設定だけが使う操作を、サインインの汎用の約束に集めないため。前の画面の状態とクライアントのキャッシュを捨てるため、routerの遷移は使わない。セッション喪失の遷移（`replace`、今の場所）は別の約束`PageReplace`にし、実装だけを共有する。約束の置き場は、方針のR02の読み（使い手の手続きの数。`Navigation`は2つの手続きが使い、`PageLoad`と`PageReplace`は使い手が1つ）で決める | `Navigation`の`go`をページ全体の読み込みにするとき |
| ネイティブの`disabled`、`required`、`minLength`を使わず、クライアント検証と`aria-disabled`を使う | 理由を利用者へ伝え、E2Eでの二重送信を防ぐため | 検証の理由を別の方法で利用者へ伝えるとき |
| パスワードの長さを`maxLength`でなく送信時に検証する。メールアドレスとコードは、入力欄の`maxLength`で入力時に制限し、送信時にも検証する | Playwrightの`fill()`が`maxLength`で切り詰めるため。サインインのパスワード欄には適用しない | パスワード規則を変えるとき |
| 認証済みのリダイレクトを`proxy.ts`へ集約し、画面ごとのE2Eは残す | 実装を一箇所にまとめつつ、各画面の挙動を保証するため | ガードの実装を変えるとき |
| captchaは送信と再送に適用し、`verifyOtp`には適用しない | ボットによるメール送信の濫用を防ぐため。テスト用キーは、previewのドメインを事前登録できないため | captchaの方式を変えるとき |
| 水和の完了を`data-hydrated`、captchaの準備を`data-captcha-ready`で示す | E2Eの水和競合を防ぐため | E2Eが水和とcaptchaの準備を別の方法で待てるとき |

## 制約と未対応

- 画面を離れたときは、変更と終了の結果によらず、状態は更新せず、遷移もしない(離脱の原則。例外は無い。`docs/features/auth/design.md`)。パスワードの変更と全ての端末のサインインの終了は、要求がサーバーに届いたときだけ始まり、届いたらサーバーで両方行われる。届かなければどちらも始まらない。画面の操作は要求が届くかを決めず、届く前に閉じても、送信済みの要求が届けば両方行われる。離れた先がラウンドの画面なら、見張りが喪失を検知したときに通常の規則でサインインへ移る(`app/navigation`)。
- 全ての端末のサインインの終了が届かない、または拒否されたときも、表示せずに`/signin`へ移る。他の端末のサインインが残りうる(要求の対象外)。
- 確認の成功後、パスワード設定の前に画面を閉じるか再読み込みすると、認証済みのセッションが残り、`/rounds`へリダイレクトされる(要求の対象外)。
- 再設定が行うサインインの終了(全ての端末。サーバーの要求の中で行い、終了の応答を待つが、成否によらず変更の成功を返す)と、サインアウトの手続き(この端末だけ。終えられたかを読み取りで決める)は、完了の意味と遷移(再設定は手続きが`assign`、サインアウトは手続きが`replace`)が違うため、別の約束にしている。共有するのは認証サービスの実装とサインインのURLの規則だけである。
