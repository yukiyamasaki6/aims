# auth/delete-account テスト設計

## 基準と方針

[要件](requirements.md)・[設計](design.md)と[共通テスト設計](../test-design.md)を基準とする。
最優先は、直近60秒の信頼済みOTP証跡と対象一致なしでデータを変更しないことである。
画面は直近にOTPログインしていても削除のたびに新しいコード確認を求める。DBは通常ログインのOTPも許可し、削除専用コード・単回許可・サインアウト時のJWT即時失効を期待値にしない。
アプリの時間・段階はVitest、認可と原子性はpgTAP、署名付きJWTとSDKの採用は実Auth/PostgREST、削除後の利用者目的はE2Eで検証する。

## 単体・コンポーネント

配置は既存のdelete-account-flow・delete-account・delete-account-form、session、supabase-account-deletionのテストを更新する。

| 前提・操作 | 期待結果 |
| --- | --- |
| 削除画面を開く | 取り消せない旨と削除内容の注意書き、チェック、ボタン1つ（再送待機中は共通の文言「再送(◯秒)」、待機が0のときは「アカウントを削除」）を表示し、別の送信ボタンを置かない。明示的な削除操作までは削除RPCを呼ばない。 |
| コード入力へ進む | ログイン・登録と同じコード入力部品（送信先、コード欄、再送と残り秒数、迷惑メールの案内、本文の「戻る」）と「確認して削除」を表示し、削除の注意書きは表示しない。 |
| 意思確認で「アカウントを削除」を押す | 削除RPCを呼ばず、別のコード送信ボタンの押下なしで続けてコード送信まで行い、成功でコード入力へ進む。押下後は同じボタンが処理中になるだけで別段階を持たない。チェック未完了の押下も受け付けて処理中として待ち、到着で自動再開する。直近にOTPログインした状態でも、追加のコード確認なしで成功後処理へ進まない。ブラウザ時計で省略を決めない。 |
| コードを送信する | 現在のID・メールを取得し、標準OTPを要求する。送付失敗は意思確認に留まり理由を示す。確認前に削除RPCを呼ばない。 |
| 対象に届いたコードで「確認して削除」を押す | コード確認の前に現在ID・メールと対象/送付先を照合し、確認に成功した後に現在の利用者を読み直して利用者・メールが依頼時と一致することを照合する。確認結果の利用者IDは使わない。SDKが新セッションを採用した後に同じ対象IDでRPCを呼ぶ。別のログイン画面や追加の意思確認へ遷移しない。 |
| 送信前・確認前・確認の応答時に利用者またはメールが変わる | 対象不一致として止め、元の対象と異なる利用者のRPCを開始しない。確認前の照合の失敗はコード入力に留まりエラーを表示し、確認成功後の読み直しでの不一致・取得失敗は意思確認へ戻って`failure.other`を表示する。RPC実行時の切替はDBのexpected_user_id照合でも拒否する。 |
| ログイン・登録と同じ共通OTPの送信・再送・確認の挙動（入力不備・オフライン・チェック待ち・排他）が削除でも同じになる | 送付先を入力で受けず現在のメールへ送る点以外の差がない。共通OTPの規則は共通テスト設計で検証し、削除では接続と差分だけを確認する。 |
| 直近のログインから60秒以内に「アカウントを削除」を押し、送信間隔でコード送付を拒否される | 意思確認に留まり、エラーで拒否の理由を表示する。チェック失敗・利用者の取得失敗も同じ。コード入力へ進まず、削除RPCも呼ばない。待機後に押し直して送付できる。 |
| 誤り・期限切れ・使用済み・別利用者コードで確認する | 削除せずコード入力へ留まり、エラーで理由を示す。失敗済みを前提として有効コードで再試行できる。 |
| 再送が成功する | コードを消し、60秒の再送待機を開始する。入力未完了・オフライン・チェック待ち・重複は共通OTPの優先と排他を守る。 |
| 意思確認・コード入力でヘッダーの戻るを押す | `#settings/account`へ戻り削除しない。本文には分類へ戻る操作を置かない。再表示ではコードと途中状態を復元しない。 |
| コード入力で本文の「戻る」を押す | 意思確認へ戻り、チェックのトークンを破棄し、エラーを消す。利用者・メール・再送待機は保持し、コードは破棄する。ログイン・登録の「戻る」と同じ挙動で、処理中は押せない。 |
| 再送待機中に意思確認のボタンを押す | ボタンは「再送(◯秒)」と表示され押せる。押すと再送待機の失敗をボタンの下に表示し、送信しない。待機が0なら「アカウントを削除」と表示する（ログインと同じ）。 |
| 送信・確認・削除の処理中に閉じる・戻る・分類切替・連続操作を試す | 処理中を通知して操作を止め、二重要求を出さない。失敗後は操作を戻す。 |
| コード送信中/入力で待つ | SessionEndを保持せず、実際の認証喪失は既存規則で遷移する。 |
| 「確認して削除」でコード確認と削除のネットワーク処理を開始する | holdEndでサインアウトと排他し、途中のSIGNED_OUTに先回りさせない。確認と削除は同じ保持内で実行する。 |
| ネットワーク処理が90秒直前・ちょうど・直後まで完了しない | 上限前は保持し、上限で結果不明として解除する。古い世代の遅い成功・失敗で表示・端末消去・完了遷移を行わない。 |
| RPCが成功を返す | 90秒計時を止め、対象IDのOpLogStore・参照スナップショット・履歴表示記憶だけを消す。その後hold.completeでサインアウトし、遷移元なしの/signinへ進む。消去の一部失敗でも残りの後処理を進める。 |
| コード確認後のRPCが拒否（認可条件の不足を含む）、確定失敗、通信失敗、結果不明を返す。確認後に利用者・メールの再照合に失敗する | 成功表示・端末消去を行わず、確認成功後の失敗として意思確認へ戻り`failure.other`を赤で表示する。種類による遷移・文言の違いはない。利用者・メール・再送待機を保持し、チェックのトークン・コードを破棄し、SessionEndの保持を解く。オフラインも同じ。保持の90秒上限と削除成功後のサインアウト失敗は従来どおり。再試行できる。再試行で削除済みと判明した場合は認証喪失へ委ねる。 |
| RPC応答待ちに画面を離れる | 遅い表示更新を行わない。保持上限前の成功が確認できれば端末消去・サインアウト・完了遷移は進める。 |
| 完了のサインアウトが応答しない | 既存の10秒上限と完了契約を維持し、削除保持の90秒を重ねて待たない。 |

削除RPCのアダプターは、成功か失敗（確定失敗・結果不明を含む）の二分を返し、otp_confirmation_requiredを含む拒否や例外に専用の失敗の種類を持たないことを確認する。
処理順は「確認したセッションでのRPC」「成功後だけの消去」といった公開副作用の必要な順序だけを固定する。

## DBの認可・権限行列

全行で削除前後の利用者・セッション・記録のスナップショットを比較する。
拒否行は期待するエラーに加え、削除も匿名化も行われないことを確認する。

| 呼出条件 | OTP証跡 | 期待結果 |
| --- | --- | --- |
| authenticated、実在する本人、expected_user_id一致 | 通常ログインを含む直近のotp（DBは画面の新しい確認と区別しない。直接RPC呼出しも許可される残余リスク） | 許可 |
| 同上 | 古いpasswordと新しいotp、otp要素の順序違い | 許可 |
| 同上 | passwordだけ、証跡なし、空配列、非配列、要素不正、method不正 | PT403とotp_confirmation_required |
| 同上 | timestampの欠落・null・文字列・真偽値・数値範囲外、期限超過、未来 | 同上。型変換例外で処理を壊さない |
| 同上 | 古いotpと新しいpassword、iat・refresh・利用者全体の最終ログインだけが新しい | 同上 |
| anon、auth.uidなし、利用者不在、匿名化先 | 新しいotp | 拒否し変更なし |
| authenticated、expected_user_idが別人またはnull | 新しいotp | 通常の拒否。別人を消さず、データを変更しない |

`rls_matrix.sql`等の既存EXECUTE行列でauthenticatedだけを許可し、PUBLIC・anonを拒否する。
SECURITY DEFINER・空search_path・60秒statement_timeoutの属性も維持する。
異常なamrは値そのものの境界検証のために注入し、実Authが通常発行する形であるとは扱わない。

### DB時刻と競合

基準時刻Tに対し、OTP timestampがT−60秒−ε、T−60秒、T−60秒＋ε、T、T＋εの順に、拒否・許可・許可・許可・拒否となることを確認する。
εはDBで比較する精度の正の値とし、数値の小数timestampも扱う。
実時計でtimestampを作って後からRPCを呼ぶ方法では「60秒ちょうど」を保証できないため、59秒/61秒の実時計試験だけで完了にしない。
実装時は隔離DBのrollbackされる試験範囲だけで時刻取得の境界を固定し、同じTで公開RPCを呼ぶ境界試験を用意する。
時刻固定の具体方式は既存DB環境で成立を確認してから採用し、認可式のコピーや本番RPCへのテスト専用引数追加で代用しない。
固定できない場合は厳密な等号境界を未検証として報告し、設計レビューで包含比較を確認しても自動試験完了に数えない。

実際のclock_timestampと複数接続では、次を別に確認する。

- public.usersの対象行を接続Aでロックし、接続Bの削除が待機していることを確認する。BのOTPが60秒を超えてからAを解放すると、Bは拒否され全記録を維持する。
- 同じロック待ちでも取得後に60秒以内なら許可される。トランザクション開始時のnow()を認可時刻として使っていないことを結果で確認する。
- 認可後だけ試験用の待機を入れ、変更中に認証時刻が60秒を超えても一括完了する。待機は60秒statement_timeout以内に収め、期限検査前の待機と区別する。
- 同一対象への競合削除は一方だけが完了し、他方は拒否される。別対象のIDを渡してロックや削除の対象を変更できない。

複数接続は既存Playwrightの結合ケースから隔離ローカルDBを利用するか、既存pgTAPで利用可能な接続機能を使う。
ロック取得を状態で待ち、上限・finallyの解放を設け、共有DBで実行しない。

## 削除・匿名化と原子性の回帰

既存delete_account.sqlのデータ形とスナップショット比較を再利用し、成功の前提の認証方式はotpにする。

- プロフィール・個人プリセット・射つ人と代理の人の参加・auth.usersと認証セッション等が消える。
- 進行中・完了・論理削除済み、代理の人と紐づかない射手が残る場合を含め、他の射つ人がいないラウンドは距離・矢・射手・全履歴まで消える。
- 他の射つ人が残るラウンドでは、対象の射手の行の利用者と役割だけがNULLになり、行のID、番号、射手の数、矢と履歴の射手、点数・revision・履歴本文、他の利用者の行は変わらない。
- 矢を1本も記録していない射つ人の射手も、番号を保って紐づかない射手になる。
- 代理の人の削除は参加の行だけを消し、射手を増やさない。代理の人が記録した矢は指定された射手のまま残る。
- 参加していないラウンドに残った操作者の参照は匿名化先へ移り、射手は増えない。
- 3人の射つ人のうち2人が順に削除すると、2人の矢と履歴は別々の番号の射手として残る。2人だけの場合は、1人目で匿名化し、2人目でラウンドが消える。
- 射手の利用者を別の利用者へ変えた後に元の利用者を削除しても、その番号は変更後の利用者に結び付いたままで、元の利用者が操作者の履歴だけが匿名化先になる。
- 削除の後、対象の利用者IDはどの参加の行にも操作者にも残らず、匿名化先はどの射手の利用者にもならない。
- 匿名化の内部関数は、指定したラウンドの指定した利用者の射手だけを匿名化し、番号の無い参加の行と他のラウンドは変えない。もう一度呼んでも結果は変わらない。
- 削除の本体の内部関数は、利用者が居なければ何も変えずに成功する。
- 残る利用者の一覧と詳細の集計は、削除の前後で同じである。
- 最初の変更後の例外、statement_timeout、deadlockで全体をrollbackし、途中までの匿名化や削除を残さない。
- 削除成功後の再呼出しは拒否する。同じメールで再登録した利用者は別IDとなり旧記録を引き継がない。

2人の同時の削除(ラウンドが消える場合と、2人の射手が残る場合)と、削除とラウンドの操作の競合は、[rolesのテスト設計](../../rounds/roles/test-design.md)の「複数接続のDB結合」で確かめる。

## 復元の検証

既存の`scripts/backup/tests/verify-restore.sh`の準備を、射つ人・番号に結び付く射手・番号を指す矢と履歴の形にする。

- 取得の後に削除する利用者は、自分だけが射つ人のラウンドと、他の射つ人と代理の人、欠番のある紐づかない射手がいるラウンドを持つ。
- 取得の後に同じラウンドの射つ人2人を削除し、残る射つ人を1人置く。削除の記録を実行と逆の順で適用しても、復元後の全記録(射手の行のIDと番号を含む)が削除の後と一致する。
- 削除の記録だけが残り削除が取り消された利用者を含めて復元すると、その利用者の射手は紐づけだけが外れ、全ての射手の番号は取得の時点と同じである。
- 削除の記録なしの復元と、手順の繰り返しの確認は維持する。

## 実Auth・PostgRESTとE2E

実Authの通常OTP直後のJWTで本人IDを指定したRPCが成功することを最初に確認する（DBの契約であり、画面の省略を許す根拠にしない）。
古いOTP JWTとそのrefresh後のJWT、再確認前の同じ利用者の別セッションでは削除が拒否される。
再確認後の新しいセッションだけが新しい認証時刻を持ち、旧JWTに引き継がれないことを、別の使い捨て利用者または成功を最後にする順序で確認する。
送付・受信・閲覧だけでは期間を延長せず、未確認コード・別利用者コードでも削除できない。
署名不正JWTの拒否はPostgRESTを通し、pgTAPのrequest.jwt.claims設定だけで署名検証済みとはしない。

E2Eは既存`auth/delete-account.spec.ts`を中心に次の主要経路へ絞る。

- 直近の通常OTPでログインした直後でも、設定から説明を読み、明示的な削除の後に現在メールへ新しいコードを送り、「確認して削除」で完了する。コード確認なしでは削除されない。/signinは遷移元なしで、保護画面へ戻っても記録を表示しない。
- 古いOTPの利用者も同じ流れで完了する。
- 削除後に同じメールで登録し、新IDに旧記録・未送信操作を表示も送信もしない。別利用者の端末記録を消さない。
- 2人の射つ人のラウンド(DBで用意する)の片方を削除した後、残る射つ人は同じ点数と合計を表示でき、削除した人のマスを直しても射手1の矢として保存され、空のマスへの記録は自分の番号になる。
- 別端末の実セッションが削除後に取得・更新を拒否され、失効検知後にサインインへ進む。期限内旧JWTを直ちに全通信拒否する期待は置かない。

設定のハッシュ直接指定・再読み込み・戻る、未認証からのreturnTo復帰は設定/navigationの既存経路で検証する。
通信失敗・結果不明・90秒上限・離脱の組合せは単体で制御し、すべてを遅いE2Eへ重複させない。
実行条件と完了判定は共通テスト設計に従う。
