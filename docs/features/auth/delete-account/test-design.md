# auth/delete-account テスト設計

## 基準と方針

[要件](requirements.md)・[設計](design.md)と[共通テスト設計](../test-design.md)を基準とする。
最優先は、直近60秒の信頼済みOTP証跡と対象一致なしでデータを変更しないことである。
通常ログインのOTPも許可し、削除専用コード・単回許可・サインアウト時のJWT即時失効を期待値にしない。
アプリの時間・段階はVitest、認可と原子性はpgTAP、署名付きJWTとSDKの採用は実Auth/PostgREST、削除後の利用者目的はE2Eで検証する。

## 単体・コンポーネント

配置は既存のdelete-account-flow・delete-account・delete-account-form、session、supabase-account-deletionのテストを更新する。

| 前提・操作 | 期待結果 |
| --- | --- |
| 削除画面を開く、またはコードを送る | 説明を表示し、明示的な削除操作までは削除RPCを呼ばない。送信先は現在のメールで編集できない。 |
| 意思確認で削除を押す | getUserで対象を確認し、そのIDを付けてRPCを試す。ブラウザ時計で許可・拒否を決めない。直近ログインがあれば追加コードなしで成功後処理へ進む。 |
| 初回RPCがotp_requiredを返す | データを消さずコード要求へ進み、現在のID・メールを取得して標準OTPを要求できる。 |
| 対象に届いたコードで「確認して削除」を押す | 現在ID・メールと対象/送付先を照合し、確認結果のIDも照合する。SDKが新セッションを採用した後に同じ対象IDでRPCを呼ぶ。別のログイン画面や追加の意思確認へ遷移しない。 |
| コード確認後のRPCがOTP不足を返す | 確認済み表示とコードを残さず再要求へ戻る。コード15分の有効期限を削除60秒の認可へ流用しない。 |
| 送信前・確認前・確認の応答時に利用者またはメールが変わる | 対象不一致として止め、元の対象と異なる利用者のRPCを開始しない。RPC実行時の切替はDBのexpected_user_id照合でも拒否する。 |
| 誤り・期限切れ・使用済み・別利用者コードで確認する | 削除せずコード入力へ留まり、理由を示す。失敗済みを前提として有効コードで再試行できる。 |
| 再送が成功する | コードを消し、60秒の再送待機を開始する。入力未完了・オフライン・チェック待ち・重複は共通OTPの優先と排他を守る。 |
| 意思確認・コード要求・コード入力でヘッダーの戻るを押す | `#settings/account`へ戻り削除しない。本文に段階を戻す操作を追加しない。再表示ではコードと途中状態を復元しない。 |
| 送信・確認・削除の処理中に閉じる・戻る・分類切替・連続操作を試す | 処理中を通知して操作を止め、二重要求を出さない。失敗後は操作を戻す。 |
| コード要求/入力で待つ | SessionEndを保持せず、実際の認証喪失は既存規則で遷移する。 |
| 直接削除、または確認と削除のネットワーク処理を開始する | holdEndでサインアウトと排他し、途中のSIGNED_OUTに先回りさせない。確認と削除は同じ保持内で実行する。 |
| ネットワーク処理が90秒直前・ちょうど・直後まで完了しない | 上限前は保持し、上限で結果不明として解除する。古い世代の遅い成功・失敗で表示・端末消去・完了遷移を行わない。 |
| RPCが成功を返す | 90秒計時を止め、対象IDのOpLogStore・参照スナップショット・履歴表示記憶だけを消す。その後hold.completeでサインアウトし、遷移元なしの/signinへ進む。消去の一部失敗でも残りの後処理を進める。 |
| RPCが確定失敗、通信失敗、結果不明を返す | 成功表示・端末消去を行わず、OTP不足以外は意思確認から再試行する。再試行で削除済みと判明した場合は認証喪失へ委ねる。 |
| RPC応答待ちに画面を離れる | 遅い表示更新を行わない。保持上限前の成功が確認できれば端末消去・サインアウト・完了遷移は進める。 |
| 完了のサインアウトが応答しない | 既存の10秒上限と完了契約を維持し、削除保持の90秒を重ねて待たない。 |

アダプターはPT403かつmessage=otp_confirmation_requiredの組合せだけをotp_requiredへ写す。
別messageのPT403、別コードで同message、接続失敗・応答不明を別々に与え、OTP不足へ誤変換しないことを確認する。
処理順は「確認したセッションでのRPC」「成功後だけの消去」といった公開副作用の必要な順序だけを固定する。

## DBの認可・権限行列

全行で削除前後の利用者・セッション・記録のスナップショットを比較する。
拒否行は期待するエラーに加え、削除も匿名化も行われないことを確認する。

| 呼出条件 | OTP証跡 | 期待結果 |
| --- | --- | --- |
| authenticated、実在する本人、expected_user_id一致 | 通常ログインを含む直近のotp | 許可 |
| 同上 | 古いpasswordと新しいotp、otp要素の順序違い | 許可 |
| 同上 | passwordだけ、証跡なし、空配列、非配列、要素不正、method不正 | PT403とotp_confirmation_required |
| 同上 | timestampの欠落・null・文字列・真偽値・数値範囲外、期限超過、未来 | 同上。型変換例外で処理を壊さない |
| 同上 | 古いotpと新しいpassword、iat・refresh・利用者全体の最終ログインだけが新しい | 同上 |
| anon、auth.uidなし、利用者不在、匿名化先 | 新しいotp | 拒否し変更なし |
| authenticated、expected_user_idが別人またはnull | 新しいotp | 通常の拒否。別人を消さずOTP不足と混同しない |
| 旧引数なしRPC呼出し | 新しいotp | 関数不在で失敗 |

`rls_matrix.sql`等の既存EXECUTE行列でauthenticatedだけを許可し、PUBLIC・anonを拒否する。
SECURITY DEFINER・空search_path・60秒statement_timeoutの属性も維持する。
異常なamrは値そのものの境界検証のために注入し、実Authが通常発行する形であるとは扱わない。

### DB時刻と競合

基準時刻Tに対し、OTP timestampがT−60秒−ε、T−60秒、T−60秒＋ε、T、T＋εの順に、拒否・許可・許可・許可・拒否となることを確認する。
εはDBで比較する精度の正の値とし、数値の小数timestampも扱う。
実時計でtimestampを作って後からRPCを呼ぶ方法では「60秒ちょうど」を保証できないため、59秒/61秒の実時計試験だけで完了にしない。
実装時は隔離DBのrollbackされる試験範囲だけで時刻取得の境界を固定し、同じTで公開RPCを呼ぶ境界試験を用意する。
時刻固定の具体方式は既存DB環境で成立を確認してから採用し、認可式のコピーや本番RPCへのテスト専用引数追加で代用しない。
固定できない場合は厳密な等号境界を未検証として報告し、設計レビューで包含比較を確認しても自動試験完了に数えない。

実際のclock_timestampと複数接続では、次を別に確認する。

- public.usersの対象行を接続Aでロックし、接続Bの削除が待機していることを確認する。BのOTPが60秒を超えてからAを解放すると、Bは拒否され全記録を維持する。
- 同じロック待ちでも取得後に60秒以内なら許可される。トランザクション開始時のnow()を認可時刻として使っていないことを結果で確認する。
- 認可後だけ試験用の待機を入れ、変更中に認証時刻が60秒を超えても一括完了する。待機は60秒statement_timeout以内に収め、期限検査前の待機と区別する。
- 同一対象への競合削除は一方だけが完了し、他方は拒否される。別対象のIDを渡してロックや削除の対象を変更できない。

複数接続は既存Playwrightの結合ケースから隔離ローカルDBを利用するか、既存pgTAPで利用可能な接続機能を使う。
ロック取得を状態で待ち、上限・finallyの解放を設け、共有DBで実行しない。

## 削除・匿名化と原子性の回帰

既存delete_account.sqlのデータ形とスナップショット比較を再利用し、成功前提のpasswordをotpへ更新する。

- プロフィール・個人プリセット・編集/閲覧の参加・auth.usersと認証セッション等が消える。
- 進行中・完了・論理削除済み、残る者が閲覧者だけの場合を含め、他の編集者がいないラウンドの距離・矢・全履歴まで消える。
- 他の編集者が残るラウンドでは対象の射手と操作者だけを既存の匿名化先へ移し、他の利用者と点数・射順・revision・履歴本文・表示/集計/同期を保つ。
- 対象が現在参加していないラウンドにも残った射手・操作者の参照を匿名化し、閲覧者だけの場合は参加だけを削除する。
- 最初の変更後の例外、statement_timeout、deadlockで全体をrollbackし、途中までの匿名化や削除を残さない。
- 削除成功後の再呼出しは拒否する。同じメールで再登録した利用者は別IDとなり旧記録を引き継がない。

## 実Auth・PostgRESTとE2E

実Authの通常OTP直後のJWTで本人IDを指定したRPCが成功することを最初に確認する。
古いOTP JWTとそのrefresh後のJWT、再確認前の同じ利用者の別セッションでは削除が拒否される。
再確認後の新しいセッションだけが新しい認証時刻を持ち、旧JWTに引き継がれないことを、別の使い捨て利用者または成功を最後にする順序で確認する。
送付・受信・閲覧だけでは期間を延長せず、未確認コード・別利用者コードでも削除できない。
署名不正JWTの拒否はPostgRESTを通し、pgTAPのrequest.jwt.claims設定だけで署名検証済みとはしない。

E2Eは既存`auth/delete-account.spec.ts`を中心に次の主要経路へ絞る。

- 直近の通常OTPでログインし、設定から説明を読み、明示的な削除を完了する。/signinは遷移元なしで、保護画面へ戻っても記録を表示しない。
- 古いOTPの利用者が削除を試し、現在メールへコードを送り、「確認して削除」で完了する。
- 削除後に同じメールで登録し、新IDに旧記録・未送信操作を表示も送信もしない。別利用者の端末記録を消さない。
- 別端末の実セッションが削除後に取得・更新を拒否され、失効検知後にサインインへ進む。期限内旧JWTを直ちに全通信拒否する期待は置かない。

設定のハッシュ直接指定・再読み込み・戻る、未認証からのreturnTo復帰は設定/navigationの既存経路で検証する。
通信失敗・結果不明・90秒上限・離脱の組合せは単体で制御し、すべてを遅いE2Eへ重複させない。
実行条件と完了判定は共通テスト設計に従う。
