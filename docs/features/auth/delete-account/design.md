# auth/delete-account 設計

## 概要

`#settings/account/delete-account`で削除の意思を確認し、削除のたびに現在のメールへ標準OTPを送って新しいコードを確認してから削除する。
画面は直近のOTPログインがあってもコード確認を省略せず、確認前に削除RPCを呼ばない。
Authがコードを検証し、DBが信頼済みJWTの`amr`で認可する。独自のOTP検証・削除用途の証明・単回許可は持たない。
コードの有効期限は15分、確認後の削除認可は60秒と区別する。

## 画面と状態

| 状態 | 表示・操作 | 次の状態 |
| --- | --- | --- |
| 意思確認 | 削除・匿名化の内容と取り消せない旨の注意書き、チェック、ボタン1つ（再送待機中は共通の文言「再送(◯秒)」、待機が0のときは「アカウントを削除」）。コード送信のためだけの別ボタン・別段階は置かない。再送待機の失敗はボタンの下に表示する | 押下でボタンが処理中になり、削除RPCを呼ばず現在のメールへコードを送る。成功でコード入力。送付拒否・チェック失敗・取得失敗は意思確認に留まり、エラーを表示する |
| コード入力 | 統合サインインと同じコード入力部品（送付先、コード、再送待機と残り秒数、迷惑メールの案内、本文の「戻る」）と、破壊的操作と分かる「確認して削除」。削除の注意書きは表示しない | 「確認して削除」でコード確認・現在ID/メールの再照合・RPC。成功は遷移まで処理中。コード確認そのものの失敗と確認前の照合の失敗はコード入力に留まりエラーを表示する。コード確認成功後の削除の失敗は全て意思確認へ戻る（下記） |

両段階とも`ScreenFrame`のh1「アカウント削除」を維持し、共通コード入力部品は本文の段階見出しを描かない。
コード段階の送付先の説明・本文の戻る・「確認して削除」は維持し、「メールで続ける」は使わない。
処理中は押下したボタンが処理中表示になるだけで、要求段階・処理中の別段階は持たない。段階は意思確認とコード入力の2つだけである。
コード送信と再送・確認は、統合サインインの共通OTP（[signin](../signin/design.md)、[auth共通設計](../design.md)）と同じ挙動・同じ共通の手続きを使う。送付先を入力で受けず、Authから読んだ現在のメールへ送る点だけが異なる。

開いた時点やコード送信だけで削除しない。直近60秒以内にOTPでログインしていても、意思確認の後にコード送信と新しいコードの確認を必ず経る。
画面の流れは、意思確認の「アカウントを削除」（押下でコード送信まで続けて行う）→コード入力→「確認して削除」（コード確認・現在ID/メールの再照合・RPCを続けて行う）である。
チェック未完了の押下は受け付けて処理中として待ち、完了で自動再開する。
削除の注意書きは意思確認の画面にだけ置く。
送信間隔などでコード送付が拒否された場合（直近のログインから60秒以内に削除を押したときを含む）、チェック失敗、取得失敗は、意思確認に留まって理由を表示し、コード入力へ進まない。
コード確認そのものの失敗と、確認前の現在ID・メールの照合の失敗は、コード入力に留まりエラーを表示する。
コード確認に成功した後の削除の失敗は全て、意思確認へ戻り、既存の`failure.other`（「エラーが発生しました。しばらくしてから再度お試しください。」、失敗の種類は持たず固定）を赤で表示する。対象は、削除RPCの拒否（認可の条件を満たさない場合を含む）・確定失敗・通信エラー・結果不明・オフライン、確認後に現在の利用者を読み直したときの不一致・取得失敗である。
この戻りは共通の`emailStepReturned`を通り、利用者・メール・再送待機を保持し、チェックのトークンとコードを破棄し、SessionEndの保持を解く。確認後の失敗の種類は画面では区別せず、専用の遷移・案内を持たない。
保持の90秒上限と、削除成功後のサインアウト失敗の扱いは従来どおりとする。
送付から60秒は再送できず残り秒数を表示する。送信先は入力させずAuthから現在値を読む。
再送後はコードを消す。
ヘッダーの戻るは全段階で設定パネルの分類「アカウント」（`#settings/account`）へ移し、削除を実行しない。
処理中はヘッダーの戻るを無効にする。本文には分類へ戻る操作を置かない。
コード入力の本文の「戻る」は、統合サインインの「戻る」と同じ挙動で意思確認へ戻る。セキュリティチェックのトークンを破棄し、エラーを消し、利用者・メール・再送待機は保持し、コードは破棄する。処理中は無効にする。
意思確認のボタンは再送待機中も押せる。押すと再送待機の失敗をボタンの下に表示する（ログインと同じ）。
ヘッダーの戻る・再読み込み・離脱ではコードと画面内の途中状態を破棄する。
途中状態を破棄しても、既に成立したOTP認証の60秒の証跡をサーバーで失効させることはしない。
オフラインでは要求・再送・確認・削除を送らず、端末へ保留しない。

## 構成とデータの流れ

以下の`src/`は`apps/web/src/`からの相対である。

| ファイル | 責務 |
| --- | --- |
| `src/app/root-client-entry.tsx` | Auth・削除RPC・Clock・Connectivity・SessionEnd・端末消去を手続きへ注入する |
| `src/app/(main)/settings-panel-entry.tsx` | 削除画面へ手続き、分類「アカウント」へ移るヘッダーの戻る、処理中通知を渡す |
| `src/features/auth/domain/delete-account-flow.ts` | 意思確認/コード入力の2段階、統合サインインと共通のOTPの規則（現在のメールへ送る点だけが異なる）、操作の排他、入力・オフライン・チェック・再送待機 |
| `src/features/auth/application/delete-account.ts` | 削除ボタンでの現在の利用者取得とOTP送信（共通OTPの手続きを再利用）、確認時の同一利用者再照合・OTP確認・削除RPC、成功後処理の順序 |
| `src/features/auth/infrastructure/supabase-auth.ts` | 現在利用者のID・メールの取得、標準OTP送信/確認を内側の型へ変換する（確認の結果は利用者IDを返さない） |
| `src/features/auth/infrastructure/supabase-account-deletion.ts` | 対象の利用者IDを付けて削除RPCを呼ぶ。結果は成功か失敗（`{kind:"failed"}`）の二分とし、確定失敗と結果不明は画面上同じ扱いにする |
| `src/features/auth/ui/delete-account-form.tsx` | 意思確認とコード入力の画面、統合サインインと共通のOTP部品、意思の明示、設定パネルへの処理中通知 |
| `src/features/auth/domain/auth-code.ts` | コード入力と60秒の再送待機の共通規則 |
| `src/features/auth/application/session.ts` | 削除のネットワーク実行中の保持、成功後のサインアウトと遷移 |
| `supabase/migrations/`の追加migration | 削除RPCのOTP認可と対象ID契約。既存の削除・匿名化を継承する |

意思確認の削除ボタンではDBへ削除を試行せず、続けてコード送信を行う。送信時にgetUserで対象IDと現在のメールを確定する。ブラウザの時計やJWT解析で認可や省略を決めない。
送信は`signInWithOtp`のshouldCreateUser:falseとcaptchaToken、確認は`verifyOtp`のtype:emailを用いる。
確認は対象ID・送付先が現在値と一致する場合にだけ開始する。確認の結果は利用者IDを持たず、確認に成功した後に現在の利用者を読み直して、利用者・メールが依頼時と一致することを確認する。
確認成功でSDKが新しいセッションを採用してから削除RPCを呼ぶ。旧JWTのamrは更新されない。
コードを確認して削除する操作は最終の意思表示も兼ね、コード確認と削除のネットワーク処理を同じholdEndで保持する。
コード送信中・入力待ちはholdEndを保持せず、「確認して削除」のコード確認の開始で取得し、90秒で結果不明として解く。
成功時は対象IDの端末記録を消去し、hold.completeでサインアウトして遷移元なしの`/signin`へ進む。離脱後も後処理を進める。

### RPC契約

`delete_account(expected_user_id uuid)`は対象の取り違えを防ぐため、要求IDがauth.uidと一致し、利用者が実在し、匿名化の置き先でないことを要求する。
削除対象は常にauth.uidから決め、引数を他人の削除権限として使わない。旧引数なし関数は残さず、旧呼出しで認可を迂回できないようにする。
SECURITY DEFINER、search_pathは空、statement_timeoutは60秒、EXECUTEはauthenticatedだけに与える。
public.usersの行をロックした後、最初のデータ変更の直前にDBのclock_timestampを1回読み、amr内のmethod=otpの数値timestampが「現在時刻−60秒以上、現在時刻以下」であることを検査する。
60秒ちょうどを許容し、パスワードだけ・欠落・不正な形・古い時刻・未来の時刻を拒否する。JWT発行時刻、更新時刻、利用者全体の最終ログイン時刻で代用しない。
認証時刻不足はPT403かつ固定の機械向けmessage `otp_confirmation_required`で返す。アダプターはこのmessageを他の失敗と区別せず、専用の失敗の種類は持たない。
削除・匿名化は既存と同じ1トランザクションで行い、途中の例外・timeout・deadlockは取り消す。成功後の再呼出しは利用者がなく拒否する。
利用者を除くと編集者がいなくなるラウンドと距離・矢・全履歴を削除し、他の編集者が残る記録では対象IDの射手と履歴の操作者を匿名化の置き先へ変更する。
対象IDに一致する射手・履歴の置換は参加中のラウンドだけに限定しない。点数・射順・revision・履歴本文は変えない。
最後にauth.usersを削除し、プロフィール・参加・個人プリセット・認証セッション等を連鎖削除する。匿名化先は既存のサインインできない利用者1行とする。
認可の60秒は変更開始時に検査し、処理中に60秒を超えても完了させる。待機中の期限超過はロック取得後の検査で拒否する。
端末の消去は既存のOpLogStore・参照スナップショット・履歴表示記憶を対象IDで消し、失敗を握りつぶす。成功が確認できない削除では消去しない。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| 画面は削除のたびに新しいコード確認を求める | 取り消せない操作であり、ログイン直後でも本人のメールでの確認を挟むため | 削除の確認方法を変えるとき |
| DBの認可は標準OTPの60秒の証跡のまま | 削除専用の証明・単回許可を持たず、Authの検証制限を維持するため。画面の新しい確認とDBは区別しない | 削除専用の本人確認が必要になるとき |
| コード確認後の削除もDBで判定する | 時計ずれやセッション更新・別タブの変化があっても、DBを認可の唯一の判定者にするため | 認可判定の境界を変えるとき |
| expected_user_idを要求する | 確認中に利用者が切り替わっても、別のアカウントを誤って削除しないため | セッションを要求単位で固定する境界を導入するとき |
| 成功後処理をSessionEndの保持下に置く | 認証喪失による遷移が、削除完了より先に遷移元付きで起きないため | セッション監視を変えるとき |

## 制約と未対応

画面は削除のたびにコード確認を求めるが、DBはその確認を区別しない。直近60秒のOTP由来JWTを持つ者は、通常ログイン直後やサインアウト後の残った有効JWTでも、画面を介さず直接RPCを呼んで、その窓の間に削除を要求できる。削除専用の単回許可や用途束縛は保証しない。
他端末の旧JWTは更新前の時刻を保持する。削除後の共有データへの期限内アクセス等の残余リスクは`docs/security.md`に従う。
