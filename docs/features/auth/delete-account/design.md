# auth/delete-account 設計

## 概要

`#settings/account/delete-account`で削除の意思を確認し、標準メールOTPの直近60秒の認証を使って削除する。
通常ログイン直後のOTPも使い、足りない場合だけ現在のメールへコードを送り直す。
Authがコードを検証し、DBが信頼済みJWTの`amr`で認可する。独自のOTP検証・削除用途の証明・単回許可は持たない。
コードの有効期限は15分、確認後の削除認可は60秒と区別する。

## 画面と状態

| 状態 | 表示・操作 | 次の状態 |
| --- | --- | --- |
| 削除意思の確認 | 削除・匿名化の内容、取り消せない旨、明示的な削除ボタン | 押下で利用者確認と削除RPC。成功は後処理、OTP不足ならコード要求 |
| コード要求 | 現在のメール、チェック、コード送信。パスワードは要求しない | 送付成功でコード入力 |
| コード入力 | コード、自動入力、再送と残り秒数、破壊的操作と分かる「確認して削除」 | 確認成功後に直ちに削除RPC。未確認なら削除しない |
| チェック待ち | 入力を保持し処理中として待つ | 到着で送信再開、失敗・上限で解除 |
| 実行中 | 閉じる・戻る・分類切替・重複送信を止める | 成功は遷移まで維持、失敗は操作可能に戻す |
| OTP不足・期限超過 | 再確認の案内、確認済み表示を持たずコードを消す | コード要求から再開 |
| 通信失敗・結果不明 | 成功表示や端末消去をせず理由を示す | 意思確認から再試行。削除済みなら認証喪失の処理へ進む |

開いた時点やコード送信だけで削除しない。60秒以内でも利用者が削除操作を明示する。
送付から60秒は再送できず残り秒数を表示する。送信先は入力させずAuthから現在値を読む。
コード確認の失敗はコード入力へ留まり、有効なコードを再入力できる。再送後はコードを消す。
ヘッダーの戻るは全段階で設定パネルの分類「アカウント」（`#settings/account`）へ移し、削除を実行しない。
処理中はヘッダーの戻るを無効にする。本文には段階を戻す操作も分類へ戻る操作も置かない。
ヘッダーの戻る・再読み込み・離脱ではコードと画面内の途中状態を破棄する。
途中状態を破棄しても、既に成立したOTP認証の60秒の証跡をサーバーで失効させることはしない。
オフラインでは要求・再送・確認・削除を送らず、端末へ保留しない。

## 構成とデータの流れ

以下の`src/`は`apps/web/src/`からの相対である。

| ファイル | 責務 |
| --- | --- |
| `src/app/root-client-entry.tsx` | Auth・削除RPC・Clock・Connectivity・SessionEnd・端末消去を手続きへ注入する |
| `src/app/(main)/settings-panel-entry.tsx` | 削除画面へ手続き、分類「アカウント」へ移るヘッダーの戻る、処理中通知を渡す |
| `src/features/auth/domain/delete-account-flow.ts` | 意思確認/コード要求/コード入力、操作の排他、入力・オフライン・チェック・再送待機 |
| `src/features/auth/application/delete-account.ts` | 利用者取得、削除試行、必要時のOTP送信/確認、同一利用者確認、成功後処理の順序 |
| `src/features/auth/infrastructure/supabase-auth.ts` | 現在利用者のID・メールの取得、標準OTP送信/確認、確認結果の利用者IDを内側の型へ変換する |
| `src/features/auth/infrastructure/supabase-account-deletion.ts` | 対象の利用者IDを付けて削除RPCを呼び、OTP不足・確定失敗・結果不明を区別する |
| `src/features/auth/ui/delete-account-form.tsx` | 3段階の画面、OTP部品、意思の明示、設定パネルへの処理中通知 |
| `src/features/auth/domain/auth-code.ts` | コード入力と60秒の再送待機の共通規則 |
| `src/features/auth/application/session.ts` | 削除のネットワーク実行中の保持、成功後のサインアウトと遷移 |
| `supabase/migrations/`の追加migration | 削除RPCのOTP認可と対象ID契約。既存の削除・匿名化を継承する |

最初の削除操作ではgetUserで対象IDを確定し、DBへ削除を試行する。ブラウザの時計やJWT解析で認可を確定しない。
OTP不足なら`otp_required`でコード要求段階へ移り、送信時にも現在の利用者とメールを読み直す。
送信は`signInWithOtp`のshouldCreateUser:falseとcaptchaToken、確認は`verifyOtp`のtype:emailを用いる。
確認は対象ID・送付先が現在値と一致する場合にだけ開始し、結果の利用者IDも対象と一致することを確認する。
確認成功でSDKが新しいセッションを採用してから削除RPCを呼ぶ。旧JWTのamrは更新されない。
コードを確認して削除する操作は最終の意思表示も兼ね、コード確認と削除のネットワーク処理を同じholdEndで保持する。
コード要求・入力待ちはholdEndを保持せず、確認直前または直接削除のネットワーク開始で取得し、90秒で結果不明として解く。
成功時は対象IDの端末記録を消去し、hold.completeでサインアウトして遷移元なしの`/signin`へ進む。離脱後も後処理を進める。

### RPC契約

`delete_account(expected_user_id uuid)`は対象の取り違えを防ぐため、要求IDがauth.uidと一致し、利用者が実在し、匿名化の置き先でないことを要求する。
削除対象は常にauth.uidから決め、引数を他人の削除権限として使わない。旧引数なし関数は残さず、旧呼出しで認可を迂回できないようにする。
SECURITY DEFINER、search_pathは空、statement_timeoutは60秒、EXECUTEはauthenticatedだけに与える。
public.usersの行をロックした後、最初のデータ変更の直前にDBのclock_timestampを1回読み、amr内のmethod=otpの数値timestampが「現在時刻−60秒以上、現在時刻以下」であることを検査する。
60秒ちょうどを許容し、パスワードだけ・欠落・不正な形・古い時刻・未来の時刻を拒否する。JWT発行時刻、更新時刻、利用者全体の最終ログイン時刻で代用しない。
認証時刻不足はPT403かつ固定の機械向けmessage `otp_confirmation_required`で返し、アダプターが`otp_required`へ写す。他のPT403と通信不明を混同しない。
削除・匿名化は既存と同じ1トランザクションで行い、途中の例外・timeout・deadlockは取り消す。成功後の再呼出しは利用者がなく拒否する。
利用者を除くと編集者がいなくなるラウンドと距離・矢・全履歴を削除し、他の編集者が残る記録では対象IDの射手と履歴の操作者を匿名化の置き先へ変更する。
対象IDに一致する射手・履歴の置換は参加中のラウンドだけに限定しない。点数・射順・revision・履歴本文は変えない。
最後にauth.usersを削除し、プロフィール・参加・個人プリセット・認証セッション等を連鎖削除する。匿名化先は既存のサインインできない利用者1行とする。
認可の60秒は変更開始時に検査し、処理中に60秒を超えても完了させる。待機中の期限超過はロック取得後の検査で拒否する。
端末の消去は既存のOpLogStore・参照スナップショット・履歴表示記憶を対象IDで消し、失敗を握りつぶす。成功が確認できない削除では消去しない。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| 標準OTPの60秒の証跡を使う | 通常ログインの確認も利用する契約に従い、Authの検証制限を維持するため | 削除専用の本人確認が必要になるとき |
| 初回の削除もDBで判定する | 時計ずれやセッション更新・別タブの変化があっても、DBを認可の唯一の判定者にするため | 認可判定の境界を変えるとき |
| expected_user_idを要求する | 確認中に利用者が切り替わっても、別のアカウントを誤って削除しないため | セッションを要求単位で固定する境界を導入するとき |
| OTP不足を他の拒否と分ける | 再確認へ戻る場合と、削除失敗・結果不明を混同しないため | RPCの失敗契約を変えるとき |
| 成功後処理をSessionEndの保持下に置く | 認証喪失による遷移が、削除完了より先に遷移元付きで起きないため | セッション監視を変えるとき |

## 制約と未対応

直近60秒のOTP由来JWTを持つ者は、通常ログイン直後やサインアウト後の残った有効JWTでも、その窓の間に直接削除を要求できる。削除専用の単回許可や用途束縛は保証しない。
他端末の旧JWTは更新前の時刻を保持する。削除後の共有データへの期限内アクセス等の残余リスクは`docs/security.md`に従う。
