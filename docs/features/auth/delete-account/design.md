# auth/delete-account 設計

## 概要

設定パネルの項目の画面(ハッシュ`#settings/account/delete-account`。`app/settings`)で、サインイン済みの利用者が現在のパスワードを入力して、アカウントと記録を削除する。
再認証は`signInWithPassword`(Turnstile要)で認証サービスに行わせ、DB関数`delete_account()`が、JWTの`amr`に直近60秒のパスワード認証があることを確かめてから、削除と匿名化を1トランザクションで行う。
関数はSECURITY DEFINERで、`service_role`と管理APIは使わない。パスワードの検証と総当たりの制限は認証サービスに委ね、DB関数はパスワードを受け取らない。
匿名化の置き先は、「削除済みの利用者」(`00000000-0000-4000-8000-000000000001`)の1行である。
削除の成功の後に、この端末の記録を消し、サインインを終えて遷移元なしでサインインへ移る。
背景の画面がオフラインで開けるときは、この画面もオフラインで開け(`app/offline-pwa`)、送信は直前にオフラインを判定して拒否する。

## 画面と状態

| 状態 | 表示 | 次の状態 |
| --- | --- | --- |
| 入力 | ヘッダー(名称「アカウント削除」と、分類「アカウント」へ戻る)、本文に、削除される内容と取り消せないことの説明、現在のパスワード欄(`autocomplete="current-password"`、表示切替)、チェック、削除ボタン | 送信で処理中。未入力・チェック未完了・オフラインは理由を示して留まる |
| 処理中 | 削除ボタンが処理中。再度の送信は受け付けない。ヘッダーの戻る(分類「アカウント」へ)も押せず、設定パネルの閉じる操作と分類の切り替えも受け付けない | 成功は遷移まで処理中のまま。失敗と、保持の打ち切り(結果不明)は理由を示して入力へ(チェックをやり直す) |
| 完了 | 画面は持たない。端末の記録を消し、サインインを終えて`/signin`(遷移元なし)へ移る | - |

- 失敗の種類と文言: パスワードの誤り(`current_password_invalid`)、制限(`rate_limited`)、チェック(`captcha_failed`)、通信エラー(`unreachable`)、その他(`other`)。窓を超えて削除関数に拒否されたとき(PT403)は、専用の種類を持たず、その他(`other`)に写す。
- 失敗の後も、現在のパスワードの入力値は保ち(欄を作り直さない。サインイン、パスワード変更と同じ)、チェックだけをやり直す。
- 失敗は全て、使ったチェックのトークンを消費し、チェックをやり直す。成功した再認証の後の失敗も同じである(毎回、再認証からやり直す)。
- 削除前にサインインを失っていたとき(結果不明の後の再試行を含む)は、再認証の前の確認が認証サービスに拒否され、更新を強制した読み取りでサインインの喪失を確定して、サインインへ移る。

## 構成とデータの流れ

チェック未完了の送信は、集約の開始の命令が待ちの状態にし、画面が`useCheckWait`でトークンの到着を受けて同じ操作を再開する(追加チェックの表示中は待ち、失敗と上限は不備として示す)。規則は`docs/features/auth/design.md`の「セキュリティチェックの待ち」に従う。

- `src/app/(main)/settings-panel-entry.tsx`(入口): 設定パネルの表示が`#settings/account/delete-account`のときに描く項目の画面として、手続きを`useDeleteAccount`で受け、`DeleteAccountForm`を描き、設定パネルから受けた戻る操作と処理中の知らせも渡す。
- `src/features/auth/ui/delete-account-form.tsx`、`delete-account-context.tsx`(UI): 画面と、入口が生成した手続きを渡す文脈。画面は、ヘッダー枠(`ScreenFrame`。設定パネルの中で描かれ、メニューボタンは出ない)に、名称(アカウント削除)と、`leading`の分類「アカウント」へ戻るリンク(`SettingsBackLink`。`submitting`の間は押せず、押下は受け取った`onBack`)を置き、本文には見出しも戻るも置かない。`submitting`は処理中の知らせ(`onBusyChange`)で設定パネルへ知らせる。成功の後は遷移まで`submitting`のままなので、設定パネルも閉じない。ブラウザの戻る・進むで画面が外れても、削除の成功の後の消去とサインインの終了は進む(`docs/features/auth/design.md`の離脱の原則)。本文は、枠の本文領域に画面が持つスクロールの入れ物(`h-full overflow-y-auto`)の中に、パスワード変更と同じ中央寄せの`main`で置く。
- `src/features/auth/domain/delete-account-flow.ts`(ドメイン): 集約。開始の命令(`beginDeleteAccount`)は、送信中 → 入力(現在のパスワードの未入力。既存の`validatePasswordPresent`に合わせ、空文字だけを未入力とし、空白だけの入力は入力として扱って認証サービスの照合に任せる) → オフライン → チェックの順に判定し、事実(`captchaChecked`、`failed`)のreducerを持つ。
- `src/features/auth/application/delete-account.ts`(手続き): 次の順で進める。
  1. 開始の命令。
  2. `session.holdEnd()`で、セッションの終了の実行中を保持する(喪失の遷移を保留する)。保持には上限`HOLD_TIMEOUT_MS`(90秒。手順3の再認証と手順4の削除の呼び出しの全体で、手順4の応答を受けた時点で解除する)があり、上限に達すると`expireSignOut`と同じく実行中を解いて世代を進め、結果不明(`unreachable`)として通信エラーを示し、入力へ戻す。保持を取れないとき(サインアウトの実行中)は、送信を始めず、通信エラーを示して入力へ戻す。打ち切りの後に遅れて届いた結果は、世代が違うため何も変えない(端末の記録は消さず、遷移もしない)。
  3. 再認証`authenticator.reauthenticate({ password, captchaToken })`。現在のメールアドレスを`getUser()`で読み、`signInWithPassword`を行う。新しいセッション(amr=password)をSDKが採用する。結果は成功(利用者ID)、失敗、サインインの喪失のどれか。
  4. 削除`account.delete()`(RPC`delete_account`)。
  5. 成功なら、`LocalRecordsEraser.erase(利用者ID)`(失敗は握りつぶす)、`hold.complete()`の順に行う。`complete()`は、`HOLD_TIMEOUT_MS`の対象外で、サインアウトと同じ打ち切り(`SIGN_OUT_TIMEOUT_MS`、10秒)だけを持つ。未認証を確かめられない、または打ち切られたときは、削除と消去は済んでいるため、保持を解き(`release()`)、通信エラーを示して入力へ戻す。再送信は、再認証の前の確認が拒否されて、サインインの喪失の確定でサインインへ移る。サインアウトも、保持が解けているため、設定パネルから行える。
  6. 失敗なら保持を解き(`hold.release()`)、理由を示す。手順3の結果がサインインの喪失のときは、`readSession({ refresh: true })`で喪失を確定させたうえで、保持を解いて通信エラーを示す。確定した喪失は、保持を解いたときの状態確認が、サインインへ移す。
- `src/features/auth/application/session.ts`、`domain/session-end-flow.ts`: `holdEnd()`は、サインアウトと同じ実行中の排他(`beginSignOut`)を取り、`complete()`(この端末のサインインを終え、終えられたら`signInHref(null)`へ移す。サインアウトの終え方と共通)と`release()`(実行中を解き、サインインの状態を確かめて、失っていれば喪失として移す)を返す。実行中は`leave`が遷移を保留する。
- `src/features/auth/infrastructure/supabase-auth.ts`: `reauthenticate`を足す。`invalid_credentials`は`current_password_invalid`に写す。`getUser()`が401・403の拒否のときはサインインの喪失として返す。
- `src/features/auth/infrastructure/supabase-account-deletion.ts`: `DatabaseGateway`の`rpc('delete_account')`を呼ぶ。DBが理由コードを付けて拒否した応答(PT403を含め、全て`other`)だけを「行われなかった」と確実とみなし、応答が無い、コードの無い応答は`unreachable`(結果不明)にする。
- `LocalRecordsEraser`(`erase(userId)`)は入口(`root-client-entry.tsx`)が次の3つで組み、手続きへ渡す。
  - `OpLogStore.erase(userId)`: `aims-sync`の`ops`と`bases`から、その利用者の行を1トランザクションで消す。他の利用者と利用者なし(null)の行は消さない。
  - `eraseReferenceSnapshots(userId)`: `aims:reference:presets:<userId>`と`aims:reference:target-faces:<userId>`を消す。
  - `eraseHistoryViewMemory(userId)`: このタブの`aims:history-view`が、その利用者のものなら消す。
  - 端末の識別情報(`aims:local-user-id`)は、サインアウトの通知(`signed-out`)で消える。Service Workerのキャッシュに利用者の記録は無い(静的資産と枠だけ)ため、消去の対象外である。
  - 消去の後に別のタブが追記した行は、利用者のIDが別のため、表示も送信もされない。
- `supabase/migrations/20261117000006_delete_account.sql`: 次を行う。
  - 「削除済みの利用者」を`auth.users`(`banned_until = 'infinity'`、メールなし)に作る。`handle_new_user`が`public.users`の行を作る。
  - `delete_account()`: SECURITY DEFINER、`search_path = ''`、`statement_timeout = '60s'`、EXECUTEは`authenticated`だけ。
- `delete_account()`の契約:
  - 認可: `auth.uid()`があり「削除済みの利用者」でないこと。`amr`に`method='password'`で`timestamp`が60秒以内の要素があること。満たさなければ`PT403`で、何も変えない。
  - 副作用(1トランザクション。失敗は全て取り消す): `public.users`の行をロックする。利用者を除くと編集者がいなくなるラウンド(利用者が参加し、他の編集者がいないもの。進行中・完了・論理削除済みを区別しない)の矢の変更履歴(対象ラウンドの距離の`distance_id`で絞る)・距離の履歴・ラウンドの履歴を消し、ラウンドを消す(距離・矢・参加は連鎖で消える)。利用者のIDに一致する全行(参加するラウンドに限らない)の、矢の射手、矢の変更履歴の射手と操作者、距離・ラウンドの履歴の操作者を、「削除済みの利用者」に置き換える(参加が外れた後に残る行で、履歴の外部キーによる削除の失敗と、`shots.shooter_id`の連鎖による矢の消失を防ぐため)。置き換えるのは利用者を指す列だけで、点数・射順・`revision`・履歴の中身は変えない(行の`updated_at`は更新トリガーで変わる)。最後に`auth.users`を消す(`public.users`、参加、個人のプリセット、セッション、リフレッシュトークン、identitiesが連鎖で消える)。
  - 冪等性: 成功の後の再呼び出しは、アカウントが無く`PT403`で拒否する。
  - 競合: 同じ利用者の別端末の書き込みとは、利用者の行のロックで直列になり、先の書き込みも匿名化・削除の対象になる。
  - 失敗時: 制限時間(57014)、途中の例外、DB接続の切断は、全て元に戻り、再サインインして再試行すると完了する。デッドロックは取り消された側だけが元に戻り、削除側が取り消されても何も変わらず再試行できる。クライアントの切断ではDB側が止まらず、削除が最後まで進む(結果不明の場合に当たる)。
- 旧アクセストークンの書き込み: 期限内の旧トークンは認証サービス以外へ届くが、ラウンド・矢・履歴・自分のプロフィールの読み取りは空(参加とRLSの`auth.uid() = id`による)、書き込みは参加の確認で`PT403`、利用者の行を参照する書き込み(ラウンドの作成、プリセット)は外部キーで23503となり失敗する。的(`target_faces`)と、`preset_rounds`・`preset_distances`(全体のプリセットと他の利用者の個人プリセット)は、全ての認証済み利用者が読める共有データ(`select_all_authenticated`)で、削除の前と同じく読める。
- 遷移: `app/settings`が項目(経路表の`DELETE_ACCOUNT_HASH`)を並べる。保護と遷移元は背景の画面(`/rounds`の配下)のものが効き、遷移元はハッシュを含む(`auth/signin`)。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| 再認証は`signInWithPassword`で行い、関数は`amr`の鮮度を確かめる | 検証と総当たりの制限・チェックを認証サービスに任せ、関数にパスワードを渡さないため。関数でパスワードを検証すると、認証サービスの制限とチェックを経由せず、誤りを1秒に約25回試せる | 認証サービスが`amr`を変えたとき |
| 窓は60秒 | 再認証の直後の呼び出しに足り、盗まれた古いトークンを弾くため。`amr`のtimestampは、リフレッシュしても変わらない | 通信が遅く、成功した再認証の後の呼び出しが窓を超える頻度が高いとき |
| 匿名化の置き先は「削除済みの利用者」の1行にする | 射手・操作者の列はNOT NULLで外部キーを持ち、行を残すと表示・集計・同期・旧トークンの拒否(外部キー)を変えずに済むため。列をnullにする案は、型と変更履歴の検査を広く変えるため採らない。外部キーを外す案と、`users`に印だけ付ける案は、旧トークンの書き込みを守る外部キーの代わりに、書き込み経路ごとの検査が要り、同じ利用者のIDが履歴に残るため採らない | 匿名化の置き先を表示する要求が出たとき |
| 失敗ごとに、再認証からやり直す | 窓の中の再試行の状態を持たず、再認証済みの状態を画面に持たせないため | 窓を超える頻度が高いとき |
| 削除の完了の遷移を、サインアウトと同じ実行中の排他の下に置く | 削除と同時に起きる喪失の検知が、遷移元つきで先に移すのを防ぐため。サインアウトの完了だけを呼ぶ案は、関数の成功からその呼び出しまでの間の喪失を防げないため採らない | 見張りの設計を変えるとき |
| 大きなアカウントのため、関数に`statement_timeout`を設定する | APIの`authenticated`の既定は8秒で、匿名化を含む削除は、ラウンド1,600・矢345,600本(半数のラウンドに他の編集者がいる)で、属性なしでは約8秒で制限時間に取り消され、60秒の属性を付けると約10秒で完了するため(authenticatedのJWTでPostgREST経由。全てのラウンドが削除対象で匿名化が無い場合は、同じ規模が約0.7秒で完了し、時間の大半は匿名化の更新である) | 削除の所要時間が60秒に近づくとき |
| 端末の消去は失敗を握りつぶし、削除済みの利用者のIDで区切る | 削除は済んでおり、残りは利用者のIDが違うため表示も送信もされないため | 利用者の区切りをやめるとき |

## 制約と未対応

- 他の端末の旧アクセストークンは、期限まで認証サービス以外へ届く。`docs/security.md`の残余リスク(9)。
- 再認証の窓(60秒)の中に盗まれたトークンは、窓の間は削除を呼べる。同(10)。
- 削除済みの利用者は`auth.users`に1行残り、メールもパスワードもなく、サインインできない。
- 削除の所要時間は、記録の量に比例する。
