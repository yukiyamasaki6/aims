# auth Googleでの認証(サインインと設定での追加・解除) テスト設計

## 基準と範囲

基準は、次の要件と確定設計である。

- 要件: `auth/signin`(Googleでサインインする、済まなかったとき、Googleにだけ残るアドレス)、`auth/link-google`、`app/settings`(分類「アカウント」の4行)、`auth/delete-account`、`auth/change-email`、`auth/signout`の各`requirements.md`。
- 設計: `docs/features/auth/design.md`(Hook、Googleでの認証、アカウントの概要の記録)、`auth/signin/design.md`、`auth/link-google/design.md`、`app/settings/design.md`、`docs/security.md`。

対象は、「Googleで続ける」(登録とサインインの統合)、Googleで作ったアカウントのOTPでのサインインと削除とメール変更、設定の「Google認証」の行(追加・解除)、Hookの`oauth`、DBの`ensure_email_identity()`とメールの手段の削除を拒否するトリガーである。
OTP、メールアドレス変更、アカウント削除そのものの既存の規則は変えない。本書は、それらの既存のテストが新しい構成(4行の設定、`/signin`のGoogleの部品)でも通ることだけを照合に使う。
本書はテスト設計であり、テストの実装・実行の結果を示さない。

実際のGoogleでしか確かめられない項目は、自動テストでなく「手動確認」(末尾)に分ける。ローカルとCIは、Googleの提供者をダミーの値で有効にし、手動の結合(`enable_manual_linking`)も有効にしている。確かめられるのは、Googleの画面へ移るまでと、取り消し・失敗の戻りまでである。成功の戻り(`code`、結び付けの完了、`amr`の`oauth`)は再現できない。

## 方針

- 壊れた場合の影響が大きい順に、次を守る。
  1. メールの手段の取り除きによるアカウントの乗っ取りを防ぐこと(DBのトリガー)。
  2. Googleで作ったアカウントが、Googleの解除・アカウント削除・メール変更でも、OTPでサインインできる状態を失わないこと(`ensure_email_identity()`、トリガー、削除)。
  3. HookがGoogleの発行を許し、パスワードなど他の方式を拒否し続けること(DB)。
  4. Googleの戻りを取り違えず、失敗しても再操作できること(単体、E2E)。失敗は決まった1文で示し、取り消しと成功は知らせを出さず、成功でないものを成功と扱わないこと(単体)。
  5. 登録の有無を知らせない方針の例外(Googleにだけ残るアドレス)が、その場合に限られること。
- 分岐・条件・状態遷移は、規則を持つ層の単体で確かめる。E2Eは、利用者がその画面でできることの達成と、実際の認証サービス・DBでしか分からない接続に限る。同じ組合せを上の層で繰り返さない。
- DBの規則(Hook、関数、トリガー)は、行列テストで固定する。認証サービスを通した形(トリガーの拒否が500になること、解除と削除の連鎖)は、E2Eで1件ずつ確かめる。
- Googleの成功の戻りは、単体では偽の認証(約束`GoogleSignInAuthenticator`、`LinkGoogleAuthenticator`)で確かめ、実物とは手動で照合する。偽の認証が表す契約(`identities`の形、戻りのクエリの形、結び付けの時機)は、認証サービスのソースと、偽のGoogleを使ったローカルでの実測に基づく。
- 固定の文言、画面の配置と見た目(「Googleで続ける」とメール入力のフォームの上下の並び、区切りの位置、行の寸法、ロゴの形)は確かめない。文言は`translatorFor`で得る。新しい文言の一覧が設計と一致することは、各画面のテストが表示で確かめる。
- 公開側にテスト専用の部品(`data-hydrated`を除く)を足さない。E2Eは、認証サービスの開始の要求の遮断と、`/callback`の直接の呼び出しで足りる。
- テストデータは実際の形にする。Googleで作ったアカウントは、`auth.users`にメールアドレスを持ち、`auth.identities`に`provider = 'google'`の行だけを持つ(メールの手段なし)。メールで作ったアカウントは`provider = 'email'`の行を持つ。Googleにだけ残るアドレスは、`auth.users.email`とは別のアドレスをGoogleの手段の`identity_data.email`に持つ。トークンの列は空文字にする(NULLだと認証サービスが500になる)。取り消しの戻りは、認証サービスが実際に付ける形(`error=access_denied&error_description=…`、`error_code`なし)にする。

## DBテスト(pgTAP。`supabase/tests`)

### 変更 `auth.sql`(Hook)

Hookの方式の行列(`hook_cases`)に、`"oauth"`を許可(claimsを保つ)として足す。`"id_token"`は拒否(403`authentication_method_not_allowed`)として足す。`password`、`recovery`など既存の拒否の行は変えない。他の既存の確認は維持する。

### 新規 `google_identities.sql`(`ensure_email_identity()`とトリガー`keep_email_identity`)

固定の利用者を準備し、関数は`authenticated`の利用者として呼ぶ(`delete_account.sql`の`call_as`と同じ方法)。結果と、呼び出し前後の`auth.users`・`auth.identities`の全体の同一性を、行列で確かめる。

`ensure_email_identity()`の行列:

| ラベル | 準備 | 期待 |
| --- | --- | --- |
| Googleだけの確認済みの利用者 | google、メールあり、確認済み | メールの手段が1行できる。`provider = 'email'`、`provider_id`は利用者のID、`identity_data`は`sub`(利用者のID)・`email`(利用者のメールアドレス)・`email_verified: true`・`phone_verified: false`、`last_sign_in_at`あり。Googleの手段は変わらず、`app_metadata`も変わらない |
| もう一度呼ぶ(冪等) | 上の続き | 変更なし(メールの手段は1行のまま) |
| すでにメールの手段がある | email、google | 変更なし |
| メールアドレスが空 | google、メールなし | `PT403`で何も変えない |
| 未確認(`email_confirmed_at`がnull) | google | 同上 |
| `is_sso_user` | google | 同上 |
| 削除済み(`deleted_at`) | google | 同上 |
| 「削除済みの利用者」のID | 匿名化先 | 同上 |
| 認証されていない(`auth.uid()`なし) | - | 同上 |
| `anon`ロール | - | EXECUTEの権限が無く`42501` |
| 他人には作れない | AとBがGoogleだけ | Aが呼ぶと、Aの手段だけができ、Bの`auth.identities`は変わらない |

トリガーの行列(`auth.identities`への操作を、認証サービスと同じく直接のSQLで行う):

| ラベル | 準備 | 操作 | 期待 |
| --- | --- | --- | --- |
| 確認済みのアカウントを残したままメールの手段を削除する | email、確認済み | emailの手段の削除 | 拒否(例外)。手段と利用者は変わらない |
| メール+Googleの利用者のメールの手段を削除する | email、google、確認済み | emailの手段の削除 | 拒否 |
| 未確認の利用者のメールの手段を削除する | email、未確認(コードを要求しただけ) | 削除 | 許可(未確認の自動結合で認証サービスが消す形を妨げない) |
| Googleの手段を削除する | email、google、確認済み | googleの手段の削除 | 許可 |
| Googleだけの利用者のGoogleの手段を削除する | google、確認済み | 削除 | 許可(メールの手段は事前の関数が作るため、トリガーの対象外) |
| アカウントを削除する(連鎖) | email、確認済み | `auth.users`の行の削除 | 許可。手段も消える |
| メール変更の完了の更新 | email | 手段の`identity_data`と`provider_id`の更新 | 許可 |
| 関数が作る手段の挿入 | google | `ensure_email_identity()` | 許可 |

加えて、個別に確かめる。

- 拒否された削除の後、`auth.identities`と`auth.users`が削除前と同一である。
- 関数の後にGoogleの手段を削除でき(関数→Googleの解除の順)、その後もメールの手段が残る。
- 2つの関数の属性: `SECURITY DEFINER`で`search_path`が空であること。`pg_proc`の`prosecdef`と`proconfig`を読んで確かめる(`supabase/tests`に既存の書き方は無いため、この書き方を定める)。EXECUTEの権限は、`rls_matrix.sql`の行列が固定するため、ここでは確かめない。
- 同時の呼び出しで2行作らない(利用者の行のロック)ことは、pgTAPで再現できないため確かめない。コードレビューの対象とする。

### 変更 `delete_account.sql`

削除の関数は変えない。Googleだけの利用者(メールの手段なし)が、OTPの認証(`amr`の`otp`が直近60秒)で削除できることと、そのときGoogleの手段を含む`auth.identities`が消えてトリガーが妨げないことを、既存の成功の経路の準備を使って1件足す。その他の拒否・匿名化・原子性は変えない。計画数を更新する。

### 変更 `rls_matrix.sql`、`migrations_final_state.sql`

- 関数のEXECUTEの期待値表に、`ensure_email_identity()`(`anon`偽、`authenticated`真)と、トリガー関数(`anon`・`authenticated`とも偽)の行を足す。期待値の方針のコメントのトリガー関数に新しい関数を含める。
- `migrations_final_state.sql`は、`ensure_email_identity()`・`keep_email_identity()`の関数と、有効なトリガーの存在を確かめる。
- 削除する: `password_email_identity.sql`と、`rls_matrix.sql`のパスワードのトリガー関数の行(パスワードのトリガーは作らないため)。

## E2Eテスト(Playwright。`tests/e2e/auth`、`tests/e2e/app`)

E2Eは、実ブラウザ・実際の認証サービス・DBで、利用者がその画面でできることを確かめる。Googleのドメインへの転送は、認証サービスの開始の要求で止め、`state`を読む。取り消しの戻りは、認証サービスの`/auth/v1/callback?error=access_denied&error_description=…&state=…`を直接開いて、本物の戻りを再現する(既存の`tests/e2e/helpers/google-auth.ts`)。
Googleで作ったアカウント・Googleを結び付けたアカウントは、`pg`(`auth-db.ts`と同じ接続。ローカルのDBだけ)で`auth.users`と`auth.identities`を準備する。サインインは、既存の`signInWithEmailOtp`など、公開のOTPとMailpitを使う。使い捨ての利用者を、テストごとに作る。
検証するのは、画面に出る値、失敗の文が出ないこと、遷移後の画面、アカウントとサインインの状態である。URLの形と`redirect_to`の中身は期待値にしない(戻りのクエリが残らないことだけ確かめる)。

### 準備と前提

- ローカル・CIの許可リストに`http://localhost:3100/**`と`http://127.0.0.1:3100/**`を足す(E2Eのアプリは`localhost:3100`で動くため。決定済み)。手動の結合は`config.toml`で有効にする。いずれも、変更後にローカルの`supabase start`の再起動が要る。
- Googleのドメインへの転送は、`blockGoogle`のように、認証サービスの開始の要求で止める。設定の「追加」は`linkIdentity`の開始の応答を経由するため、遮断の対象にその開始の要求を含める。
- Googleで作った・結び付けた利用者の準備は、`auth-db.ts`に足す(`pg`の接続はローカルのDBだけに限る既存の検査に従う)。
- テスト実装の段階で、`knip`が補助を未使用と判定しないことと、CIのDBのポート(54322)がE2Eの実行から届くことを確認する。
- 「メールアドレスの変更」の1件は、Googleだけの利用者(メールの手段なし)で変更が完了することを確かめる。メールの手段が無いときの変更の完了時の挙動は設計の実測の範囲外のため、結果が想定と違えば、設計担当に戻す。

## 既存のテストへの影響(変更後も通ることを照合に使う)

- 単体: 設定の画面(`settings-account.test.tsx`、`settings-panel.test.tsx`、`settings-panel-entry.test.tsx`)は、行の構成の変更(項目の画面の一覧から4行へ)に合わせて更新する。`signin-form.test.tsx`、`email-otp-form.test.tsx`、`otp-email-step.test.tsx`は、Googleの部品の追加だけで従来の期待が変わらないことを確かめる。`SignInChange`の通知の型に概要を足すため、通知を作る補助(`session-reader-test-helpers.ts`など)を更新する。
- DB: `auth.sql`のHookの行列は、`oauth`と`id_token`の2行だけ増える。`delete_account.sql`と`rls_matrix.sql`は上のとおり。
- E2E: 設定を開いて項目へ移る既存のテスト(メールアドレス変更、アカウント削除、サインアウト)は、4行の「変更」「削除」「サインアウト」の入口を使うよう更新する(振る舞いの検証は変えない)。OTPのサインイン・サインアップ(統合)、削除、メール変更の既存のE2Eは、ローカルの`supabase start`の再起動(Googleの提供者、手動の結合、許可リスト、通知の設定)の後に通ることが、設定の変更の回帰の確認になる。
- 設定のファイル(`config.toml`の`remotes`、通知のテンプレート、workflowの`env`)は自動テストの対象外とし、運営者の確認(下)で確かめる。

## 確かめないもの(理由)

- Googleの成功の戻り(`code`の交換、結び付けの完了、`amr`の実物)、自動結合、メール変更後のサインイン、削除後の再結び付き、別のアカウントで使われているGoogleの追加: 実際のGoogleでしか起きないため手動。
- 認証サービスの通知メール(追加・解除)の本文: 認証サービスが送る。AIMSは有効にして日本語のテンプレート(`google-auth-linked.html`、`google-auth-unlinked.html`)を指すだけで、実際の送信と件名(「Google認証が追加されました」「Google認証が解除されました」)は手動で確かめる。
- 認証サービスが「追加」の戻りで結び付けを終えること、戻り先が`site_url`へ置き換わらないこと(issue #1927): 認証サービスの挙動(保証外)。要件・設計に書かないため、自動テストでも保証しない。手動で再確認する。
- 利用者の行のロックによる同時呼び出しの重複防止: pgTAPで再現できない。
- Googleのボタンの見た目(ロゴの形、ブランドの指針への適合)、行の寸法、区切り線: 固定の見た目で、E2Eでも単体でも期待値にしない。運営者が確認する。
- トリガーの拒否の文言(500の本文の例外の識別子): 画面が呼ばない経路のため、写しの単体で確かめない。
- スタンドアロンのPWAでの完了: 手動の11。

## 手動確認(運営者。プレビュー環境の実際のGoogleアカウント)

実際のGoogleでしか確かめられない次の12項目で、自動テストでは代替できない。

1. 未登録のGoogleで「Googleで続ける」を押すとホームが表示され、同じGoogleで再度認証すると同じ記録に入る。
2. OTPのアカウントと同じアドレスのGoogleで認証すると、アカウントが増えず既存の記録が表示される(自動結合)。設定のGoogle認証の行にアドレスと「解除」が出る。
3. 遷移元(ハッシュ付き)からGoogleでサインインすると、その表示へ戻る。戻り先が本番のドメイン(`site_url`)へ置き換わらない(プレビューの許可リストの一致の確認を含む)。
4. Googleの画面で取り消すと、何も知らせずに`/signin`へ戻る。ブラウザの戻るで戻ったとき、ボタンが処理中のまま残らない。
5. サインインしたセッションのJWTの`amr`が`oauth`である(開発者ツール)。Hookが発行を拒否しない。
6. 設定の「追加」(アカウントと異なるアドレスのGoogle)で認証すると、分類「アカウント」に戻り、行にGoogleのアドレスが出る。以後、そのGoogleでサインインできる。認証サービスの通知メールが日本語で届く。戻り先が`site_url`にならない(issue #1927)。
7. 別のアカウントで使われているGoogleを「追加」すると、追加されず、その旨が表示される。
8. Googleで作ったアカウントでGoogleを「解除」すると、行が「追加」になり、OTPでサインインできる。通知メールが届く。同じGoogleで認証すると再び結び付く。
9. Googleで作ったアカウントのOTPでのサインインと、アカウント削除(OTPの流れ)ができる。削除後、同じGoogleで認証すると新しいアカウントになる。
10. Googleで作ったアカウントのメールアドレス変更の後も、Googleで同じアカウントに入れる。古いGoogleのアドレスで「メールで続ける」を押すと、Googleを使う案内が出る。
11. スマートフォンのホーム画面に追加したアプリ(iOS・Android)で、Googleでのサインインと追加が完了する。
12. コードを要求しただけ(確認していない)のアドレスで、同じアドレスのGoogleで認証すると成功する(トリガーが妨げない)。

運営者が行う設定の確認(自動テストの対象外の設定):

- プレビュー・本番の`supabase config push`(`--dry-run`を含む)で、`[remotes.*.auth.external.google]`の上書き、`additional_redirect_urls`、手動の結合、通知(`identity_linked`・`identity_unlinked`)が効くこと。CLIの`config.toml`のキー名と日本語のテンプレートの反映を含む。プレビュー用はGoogleの設定を含むPRを出す前、本番用は統合の前に、secretsを登録したうえで確かめる。
- 認証サービスのGoogleの提供者が有効な環境でだけ、「Googleで続ける」と「追加」がGoogleの画面へ移ること(無効な環境では認証サービスのエラーの応答になる)。
