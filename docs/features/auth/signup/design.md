# auth/signup 設計

## 概要

`/signup`でメールアドレスの認証コード(OTP)による本人確認を行い、そのセッションでパスワードを設定して登録する。
3つの状態(メール入力、コード入力、パスワード設定)を、`/signup`の中で切り替える。
Supabase Authの`signInWithOtp`、`verifyOtp`、`updateUser({ password })`をこの順にブラウザから呼ぶ。
パスワード設定の完了時に、この端末のセッションを、パスワードで確かめたもの(amr=password)へ置き換え、認証コード由来(amr=otp)の古いセッションをサーバー側でも無効にする(順序は下記)。
認証コード由来のセッションは、現在のパスワードの検査を免除されるため(`docs/features/auth/design.md`)、パスワード変更の検査を登録の直後から効かせる。
登録済みの確認済み利用者には、認証サービスがコードの代わりに案内のメールを送る(テンプレートにコードもリンクも入れない)。画面は登録の有無を出さず、どの場合もコード入力へ進む。
認証済みの`/signup`のリダイレクトは`proxy.ts`が担う。
集約、手続きの共通の順序、画面の骨組みは、パスワード再設定と共有する。

## 画面と状態

| 状態 | 表示と操作 | 次の状態 |
| --- | --- | --- |
| メール入力 | メールアドレス、captcha、送信、サインインへのリンク | 送信成功でコード入力、リンクで`/signin`、検証・送信失敗はエラー表示 |
| コード入力 | 6桁までのコード、確認、再送、戻る。迷惑メールの確認を案内する | 確認成功でパスワード設定、戻るでメール入力、再送、確認・再送の失敗はエラー表示 |
| パスワード設定 | パスワード、captcha、登録 | 成功で`/rounds`、検証・登録・サインインの失敗はエラー表示 |
| 処理中 | 該当ボタンを`aria-disabled`にする。コード入力では確認・送付(再送)・戻るを同時に無効にする。以前のエラーは開始で消す | 完了で元の状態 |

- 戻るとメール入力に戻り、入力済みのメールアドレスを保持する。コードの入力値は破棄する。
- パスワードの入力欄は`PasswordInput`で、表示・非表示を切り替えても入力値を保つ。再送ボタンは、待ち中は「再送（N秒）」(`otpResendWait`)と残りを示し、`tickCooldown`が1秒ごとに進める。
- 確認が成功した時点でセッションは確立済み(amr=otp)である。
  パスワード設定はそのセッションへの`updateUser`で、成功後にセッションを置き換える(下記)。
- パスワード設定の段階にcaptchaを置く。
  コード入力の段階のトークンは持ち越さず、確認の成功で消し、この段階のウィジェットで取り直す。
- 認証済みで`/signup`を開くと`/rounds`へ送る。

## 構成とデータの流れ

構造の方針は`docs/architecture.md`に従う。

- `src/app/(auth)/signup/page.tsx`: 入口。認証の実装(接続を作る関数`createClient`を渡す)、ページ全体の置き換えの実装(`createBrowserPageLoad`)、通信の可否の約束(`Connectivity`。送信の直前のオフラインの読み取りに使う)、手続きを生成し、手続きを画面へ渡す。
- `src/features/auth/ui/signup-form.tsx`: サインアップの画面の文言とリンク(見出し、サインインへのリンク、パスワード設定の段階の文言)を、UI層の文言の一覧から得る。パスワード再設定と共有の骨組みへ渡す。
- `src/features/auth/ui/password-setup-form.tsx`: 段階の振り分けと、パスワード設定の段階の描画。状態を`useScreenView`で持ち、操作のたびに入力と画面の約束(`ScreenView`)を手続きへ渡す。メール入力とコード入力は段階の部品へ渡す。パスワード再設定と共有する。
- `src/features/auth/application/sign-up.ts`: 手続き。
  コードの送信と、パスワード設定の後のセッションの置き換えと、ページ全体の置き換え(`/rounds`)を持つ。
  確認と、操作の開始、コードの送付(初回も再送も同じ操作)の依頼、パスワード設定の依頼は、共通の順序を使う。
  置き換えには、既存の`SignInAuthenticator`の`signIn`と、足す`signOutOthers()`(`supabase-auth.ts`が`signOut({ scope: 'others' })`で実装し、結果は値で返す)を、依存の約束として受け取る。
  サインアップの手続きは、チェックをパスワード設定でも要すること(`requiresCheck`)を持つ。
  共通の順序へ設定として渡し、画面もそこから得る。
  再設定は偽である。
  `PasswordSetup.setPassword`の入力は`{ email, password }`である。
  `email`は置き換えのサインインに使い、再設定でも型は必須で、再設定は使わない(画面は常にメールアドレスを渡す)。
  `createSignUp`の`authenticator`は、`PasswordSetupAuthenticator`、`SignInAuthenticator`、`OtherSessionsSignOut`を1つのオブジェクトで受ける。
  `OtherSessionsSignOut`(`signOutOthers(): Promise<CallResult>`)の型は、`sign-up.ts`が公開する。
- `src/features/auth/application/password-setup.ts`、`password-setup-authenticator.ts`: パスワード再設定と共有する、手続きの共通の順序(送信の直前にオフラインを1回読むことを含む。操作の開始、コードの送付の依頼、確認、パスワード設定の依頼)と、認証サービスへ頼むこと(コードの送信、確認、パスワードの設定)の約束。
- `src/features/auth/domain/password-setup-flow.ts`: 集約。
  段階、実行中の操作、再送の待ち時間、captchaトークンを持ち、開始の命令(`beginSendCode`ほか)が、操作の可否と入力の検証の順序、確認・再送・戻るの排他を守って`Start`を返す。
  事実の遷移(`passwordSetupReducer`)で、トークンの消費を守る。
  パスワード設定の開始(`beginSetPassword`)は、`requiresCheck`が真のときだけ、チェック未完了を不備とし(オフラインでは示さない)、トークンを依頼に含める。
  確認の成功(`codeConfirmed`)でトークンを消す。
  パスワード再設定と共有する。
- `src/features/auth/domain/password.ts`、`auth-code.ts`: パスワードの文字種の規則と、認証コードの桁数(入力欄の上限)、未入力の検査と再送の待ち時間の規則(domain。誤りの種類を返す)。パスワード再設定も使う。
- `src/features/auth/domain/auth-failure.ts`: 認証の失敗の種類(`same_password`はchange-passwordと共用)。
  文言は持たない。
- `src/features/auth/infrastructure/supabase-auth.ts`: 利用者のセッションで認証サービスに触る唯一の実装(認証の5機能で共通。`docs/features/auth/design.md`)。
  コードの目的`sign-up`の`signInWithOtp`、`verifyOtp`、`updateUser`の呼び出しを含む。
  パスワードの設定の応答のうち、422 `same_password`を失敗の種類`same_password`に写す(サインアップ、再設定、パスワード変更で共通。コードの目的は渡さない)。
  呼び出しの結果は`CallResult`(受け付けられた、または失敗)の値で返し、応答が無かった場合(接続を作れない、呼び出しが投げた)は`unreachable`の失敗にする。
- `src/features/auth/ui/password-setup-form.tsx`のパスワード設定の段階は、手続きの`requiresCheck`が真のときだけ、チェックのウィジェットを描き、メールアドレスを手続きへ渡す。
  画面は目的を判定しない。
- `src/features/auth/ui/otp-email-step.tsx`、`otp-code-step.tsx`: メール入力とコード入力の段階の描画。パスワード再設定も使う。
- `src/features/auth/application/password-setup.ts`の`tickCooldown`: 再送できるまでの秒数を進める1秒の予約(`Clock`)。画面の部品`password-setup-form.tsx`が、残りが変わるたびに予約し直す(依存は描画をまたいで同じ参照の`dispatch`だけで、描画のたびには張り直さない)。
- `src/app/(auth)/layout.tsx`、`src/features/auth/ui/auth-header.tsx`、`src/features/auth/ui/turnstile.tsx`: 認証画面の共通部品と枠。
- `supabase/migrations/20261016000000_users.sql`: `auth.users`のINSERTで`public.users`を作るトリガー。

契約は次のとおりである。

- 送信の直前にオフラインを1回読み(購読しない)、入力判定 → オフライン判定 → チェック判定の順に判定する。オフラインでは入力の不備だけを示し、チェック未完了は示さない。入力に不備が無くオフラインなら失敗の種類`offline`を示し、認証サービスへ送らず、トークンも消費しない。
  サインアップのパスワード設定では、`signInWithPassword`が消費し、その失敗は取り直させる。
  `updateUser`はトークンを使わず、その失敗ではトークンを保つ。
  確認の成功で、コード入力の段階のトークンを消し、持ち越さない。
- サインアップのパスワード設定は、入力判定 → オフライン判定 → チェック判定の後、(1)`updateUser({ password })`、(2)`signInWithPassword`(amr=passwordへ置き換わる)、(3)新しいセッションからの`signOut({ scope: 'others' })`の順に行う。
- (3)の完了(失敗を含む)を待ってから`/rounds`へ遷移する。
  待ちの上限は設けない。
  (3)が固まったときは、再読み込みで`/rounds`へ入れる(置き換え済みで、認証済みの`/signup`は`/rounds`へ送る)。
  (3)の失敗は示さず、遷移する。
  古いセッションだけが残る(`docs/security.md`)。
- (1)が`same_password`で拒否されたときは、設定済みとして(2)へ進む。
  サインアップの利用者は設定前にパスワードを持たないため、(2)の失敗後の再試行で同じパスワードが既に設定されている場合だけ起きる。
  認証コード由来のセッションでも、同じパスワードの再設定は422 `same_password`で拒否され、パスワードもセッションも変わらない(実測)。
- (1)の成功後は、画面を離れても(2)と(3)を進め、遷移だけ行わない。
  止めると認証コード由来のセッションが残るため。
- 共有の`applyPassword`は、現行は(1)の失敗の表示と、離脱時の偽の返却を内包し、(2)へ渡す依頼を外へ出さない。
  契約を変え、`Promise<PasswordApplication | null>`を返す。
  `PasswordApplication`は`{ result, mounted, request }`で、設定の結果(受け付けられたか、失敗の種類)、画面が表示中か、開始の依頼(パスワードとcaptchaトークン。(2)のサインインに使う)である。
  `null`は、開始できなかった場合(実行中、入力の不備、オフライン、チェック未完了)で、頼まない。
  失敗の表示は呼び出し側が行う。
  再設定は、従来どおり失敗を表示して止め、離脱時は何もしない。
  サインアップ(`sign-up.ts`)は、`same_password`のときだけ表示せずに(2)へ進む。
- (2)が失敗したときは、理由を示してこの段階に留まる。
  トークンは消費済みのため、集約の`refused`(消費する)に当たり、`failed`(保つ)ではない。
  再試行は(1)から行う。
  認証コード由来のセッションは、(2)が成功するまで残る。
- `public.users`は、登録の経路によらずトリガーが作る。pgTAPでは再現できないため、E2Eで確かめる。
- captchaは、`verifyOtp`と`updateUser`には適用しない。
- コードの有効期限は900秒、再送の間隔は`max_frequency`で、productionとpreviewは60秒、ローカルとCIは1秒である。画面の再送の待ちは、送付の成功で60秒を始める(失敗では始めない)。メール入力へ戻ると0に戻す。

流れは次のとおりである。

1. メール入力で検証し、コードを送る(登録済みの確認済み利用者には、案内のメールが届く)。
2. コード入力で`verifyOtp`を呼び、成功でパスワード設定へ進む。
3. パスワード設定で検証し、(1)〜(3)を行い、`/rounds`へページ全体を置き換える(送信中は解除しない。読み込みは1回)。

## 設計判断

| 判断 | 理由 | 見直す条件 |
| --- | --- | --- |
| 送信の直前にオフライン状態を1回読み、購読しない。オフライン専用の失敗の種類を持つ。確認と、再設定のパスワード設定は、トークンを使わないが、同じ画面で同じ原因が違う表示にならないよう、同じ判定を適用する(サインアップのパスワード設定は、トークンを使い、チェック判定も行う) | 全失敗でトークンを消費するため、オフラインの再送信がチェック未完了の表示になり原因が分からなくなるのを防ぐ。通信断でトークンを保持する分岐を持たず、判断を1か所にする。「通信エラー」では端末の回線が切れていることが分からない | `navigator.onLine`がtrueのまま通信できない場合も扱いたいとき |
| マジックリンクでなくOTPで本人確認する | PKCE、`redirect_to`の許可リスト、ホスト名の不一致の問題が連鎖したため、マジックリンクは採らない。詳細: #90 | SupabaseのマジックリンクのPKCE対応が安定したとき |
| サインアップの完了時に`signInWithPassword`でセッションを置き換え、`signOut({ scope: 'others' })`で古いセッションを無効にする(案A)。そのためにパスワード設定の段階でcaptchaを取り直す | 認証コード由来のセッションは、パスワード設定後も、リフレッシュ後も、amr=otpのまま現在のパスワードの検査を免除される(実測)。置き換えのサインインはamr=passwordで、`others`は古いセッションをサーバー側でも消す(実測)。変更時の自動サインイン(案G)は、変更の1回の呼び出しの前提を崩すため採らない。`signInWithPassword`はcaptchaを要し、コード入力の段階のトークンは確認の前に消費済みで、持ち越しに頼れない | 認証サービスが認証コード由来のセッションの免除をやめたとき、またはパスワード設定の完了時にセッションを置き換える別の手段(例: 設定の応答にセッションが含まれる)が使えるとき |
| 登録済みの確認済み利用者には、認証サービスがコードの代わりに案内メールを送る(テンプレートにコードを入れない)。画面は登録の有無を出さない | 登録の有無を調べる副作用つきの処理(管理者鍵、再設定コードの無効化)を持たないため。コード入りのメールを送ると、既存アカウントのパスワードを上書きできてしまう。登録済みであることは画面に出さず、登録済み用テンプレートのメールで伝える | 登録の有無を画面で伝える要求が出たとき |
| 4つの操作を1つの手続きと1つの集約で持ち、集約、手続きの共通の順序、画面の骨組みはパスワード再設定と共有する。サインアップだけの動作(`/rounds`への置き換え)は`sign-up.ts`に置く | 約束と集約と再送の順序を共有し、同じ理由で変わるため。段階ごとに集約を分けると、1つの出来事が2つの集約を同時に変える。サインアップと再設定は、認証コードでの本人確認とパスワード設定の規則が変わる理由が同じで、複製を残す理由が無い | 段階が互いに独立して変わるようになったとき、または登録と再設定の規則が分かれるとき |
| 確認・送付・戻るを排他にし、実行中の操作を集約の1つの値で守る | 遅れて届いた応答が別の状態へ反映される不整合が起きたため、独立した操作をやめた | 非同期の応答を世代管理する方式にするとき |
| ネイティブの`disabled`を使わず、`aria-disabled`と検証メッセージで表す | 空入力、captcha未完了、クールダウン中の理由を利用者へ伝えるため | 理由を別の方法で利用者へ伝えるとき |
| パスワードは、半角英数字と記号のみ`maxLength`でなく送信時に検証し、長さと強さ(8〜72文字で英字と数字を含む)は認証サービスの拒否を規則の文面で示す。メールアドレスは形式だけを送信前に検証し、長さは制限しない(認証サービスに任せる)。コードは未入力だけを送信前に検証し、桁数と正しさは入力欄の`maxLength`(6桁)と認証サービスに任せる | bcryptが72バイトまでのため。Playwrightの`fill()`が`maxLength`で切り詰めるため | パスワード規則を変えるとき |
| 水和の完了を`data-hydrated`で示し、E2Eはそれを待つ | 水和前の操作によるE2Eの不安定さを避けるため | E2Eが水和を別の方法で待てるとき |

## 制約と未対応

- 確認後はセッションが確立済みのため、パスワード設定の前に再読み込みすると、`/rounds`へリダイレクトされ、パスワードのないアカウントが残りうる。
  認証コード由来のセッションも残る。
- 認証コード由来のセッションが残る場合(置き換えの前の離脱、(2)の失敗後の離脱、(3)の失敗、この変更より前に登録した利用者のもの)と、その受け入れは`docs/security.md`に従う。
  既存のものの掃除は行わない。
- ブラウザでの動作(`signInWithPassword`でのセッションの置き換えと、続く`others`の呼び出しがクライアントの状態に与える影響)は、独立したローカルのスタックでのE2Eで確かめた(確認項目は下記)。
- トークンの有効期間(Cloudflareの仕様は未確認)の中でのパスワード入力は、E2Eでは確かめられない(プレビューのsecretは常に通過するテスト値)。
  本番でのみ確認でき、期限切れでは、チェックが取り直されるまで未完了として示される想定である。
- E2Eの確認項目: 登録の直後のJWTのamrがpasswordであること、現在のパスワードなしの更新が拒否されること、置き換え前のセッションのアクセストークンが拒否されること、サインインの通知(`signed-in`)の重複が端末の識別情報の記録などに影響しないこと、一方の端末で現在のパスワードの誤りを送っても、他方のセッションが生きていること。
- 集約、手続きの共通の順序、画面の骨組みは、パスワード再設定と共有する。これらを変えるときは、サインアップと再設定の両方の振る舞いを確かめる。
