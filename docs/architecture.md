# アーキテクチャ方針

この方針は、アプリの全ての機能に適用する、構造の原則と規則である。
特定の機能への当てはめは、この文書では行わない(第16節)。
層の考え方はオニオンアーキテクチャを参考にした。参考にした記事と、記事と異なる点の理由は第17節に書く。

## 1. 原則

規則は全て、次の原則を、このアプリで具体化したものである。原則は言語とフレームワークによらない。

1. 依存規則: ソースコード上の依存(静的依存)は内側へ向かう。内側の層は外側の層の具体実装を参照しない。内側が外側の機能を使うときは、使う側が約束を持ち、外側の具体実装がそれを満たす。約束は具体的な技術の型を含まない。ドメイン層は、手続き(操作の順序と、外部とのやりとり)を自分で行わず、手続きはアプリケーション層が担う。
2. 組み立て層: 組み立て層を1つの層として置き、既存の入口そのものを組み立て層に分類する。組み立て層の役割は、具体実装と手続きを生成し、使う側へ注入することである。組み立て層は全ての層に静的に依存してよく、どの層も組み立て層に依存しない。そのため組み立て層は、UI層とインフラ層を含む全ての層より外側にある。
3. 層への所属と機能への所属は別である。どのファイルも、1つの層と、1つの機能か共有に属する。
4. 縦は、利用者から見た能力(機能)で切る。機能の間は、機能の入口だけで、一方向に結ぶ。
5. UI層とインフラ層は、互いに静的に依存しない。具体実装を知るのは、組み立て層だけである。さらに構造方針の規則(A06)として、両者は、呼び出しと注入を含め、どの関係も持たない。
6. 整合性は、それを必要とするデータを持つ1つの集約が、変更の入口で守る。
7. 物理の置き場は、使うフレームワークと言語の慣習に従い、用語との対応は対応表(第2節)で表す。

原則が許すことを禁じる規則は、構造方針の規則(第14節)として、理由とともに書く。

## 2. 用語と物理の置き場

規則は、次の表の用語だけで書く。
物理のパスは、この節と、第14節の書き方の前提と、対応表にだけ書く。パスは、アプリのソースのルート(`apps/web/src/`)からの相対である。

| 用語 | 意味 | 帯(第4節) | 既定の物理の置き場 |
| --- | --- | --- | --- |
| 機能 | 利用者から見た一まとまりの能力。中に層を持つ(第9節) | (列) | `features/<機能>/` |
| 共有 | 機能に属さず、複数の機能が使うもの。共有の技術と共有の画面部品からなる | (列) | 下の各行 |
| ドメイン層 | 機能の業務の規則と状態。部品は第6節の集約、エンティティ、値オブジェクト、出来事、ドメインサービス、ドメインの約束 | ドメイン層 | `features/<機能>/domain/` |
| ドメインサービス | どの集約にも属さない業務の規則(状態を持たない) | ドメイン層 | ドメイン層の`*-service.ts` |
| ドメインの約束 | ドメインサービスが判断の途中で問い合わせる、業務の言葉の約束(第7節) | ドメイン層 | ドメイン層の`*-port.ts` |
| アプリケーション層 | 操作の手続きと、手続きの約束 | アプリケーション層 | `features/<機能>/application/` |

| 手続きの約束 | 手続きが外に頼むこと(外部とのやりとり、保存と取り出し、画面の遷移、実行環境の状態の読み出し)の約束(第7節) | アプリケーション層 | 使う手続きのファイル |
| UI層 | 画面の部品。外部のパッケージが与える画面の部品(外部のウィジェットなど)を使うものを含む | UI層 | `features/<機能>/ui/` |
| インフラ層 | 約束の実装、外部への実際のアクセス、外部の形と内側の形の変換 | インフラ層 | `features/<機能>/infrastructure/` |
| 機能の入口 | 機能が他の機能へ公開する唯一のファイル | アプリケーション層 | `features/<機能>/index.ts` |
| 共有の技術 | 業務の言葉を持たない、複数の機能が使う技術の能力。能力ごとに、約束と実装に分ける | (列) | 能力ごとに`lib/<能力>/` |
| 共有の技術の約束 | 共有の技術の約束(型だけ) | アプリケーション層 | `lib/<能力>/contract/` |
| 共有の技術の実装 | 共有の技術の約束の実装と、能力が外部に触る部品。外部の定義から生成した手で書かないファイルを含む | インフラ層 | `lib/<能力>/infrastructure/`、生成されたファイル |
| 共有の画面部品 | 業務の言葉を持たない、複数の機能の画面が使う部品 | UI層 | `components/`、`hooks/`、`lib/`の画面用のファイル |
| 入口 | 画面のパッケージや実行環境が直接読み込むファイル。アプリの起動地点、画面の入口、要求の入口(クライアントから呼ばれる関数のファイルを含む)がある | 組み立て層 | 画面のパッケージが定める場所(`app/`の`layout.tsx`、`page.tsx`、`route.ts`など、`proxy.ts`、`"use server"`のファイル(Server Action)) |
| アプリの起動地点 | アプリで1度だけ読み込まれる入口 | 組み立て層 | `app/layout.tsx` |

| 外部 | アプリの管理の外で動くサービスと、実行環境の状態(第12節)。構造図に描く外部は、管理外のサービスだけである | (外部) | アプリの外 |
| パッケージ | アプリが依存する、管理外のライブラリとフレームワーク。外部ではない。画面のパッケージとその他のパッケージに分け、層ごとに参照してよいものを第12節で決める。構造図に描かない | (描かない) | 適用の設計の対応表に、名前を挙げる |
| 画面のパッケージ | 画面を描く仕組み(描画、状態、遷移、リンク、画像)と、画面の部品を与えるパッケージ。外部のウィジェットを描くものを含む。パッケージの内部の通信は、アプリの部品の関係ではない | (描かない) | 適用の設計の対応表に、名前を挙げる |
| 約束 | 内側の部品が外側に頼むことの、型だけの宣言。ドメインの約束、手続きの約束、共有の技術の約束のどれかに当たる | 当たる約束の帯 | 当たる約束の置き場 |

組み立て層の専用のディレクトリや部品は置かない。入口そのものが組み立て層である。

対応表:
- どのファイルがどの用語に当たるかは、上の表の既定の置き場と、適用の設計が挙げる対応表(ファイルの一覧)で決める。規則の確かめ(第14節)は、この対応表に当たるファイルを対象にする。
- 既定の置き場が、使うフレームワークや言語の慣習と衝突するときは、慣習に従い、対応表に別のパスを挙げる。
- 用語の名前でディレクトリを作らない。
- 方針を適用した領域(第16節)だけを、対応表に挙げる。挙げていないファイル(未適用の領域)には、方針の規則の確かめを当てない。
- テストのファイルと、テストからだけ参照される補助のファイル(既定: `*.test.*`、`*.spec.*`、`*-test-helpers.ts`)は、対応表に当てない。テストのファイルには、レビューで確かめる指針を当てない。テストは、検証のために、どの用語のファイルも参照し、偽の部品や実装を作って注入してよい。

## 3. 関係

部品の間の関係は、次の5つの語で書く。向きは、どれも左の部品から右の部品へである。

| 関係 | 意味 | 向き | 判定 |
| --- | --- | --- | --- |
| 参照 | 型、定数、関数などを取り込む静的依存。型での受け取り(注入先が受け取る型)と、値を取り込むが呼ばない利用を含む | 参照する部品→参照される部品 | 静的依存規則 |
| 実装 | 具体実装が約束を満たす | 具体実装→約束 | 静的依存規則 |
| 呼び出し | 関数やメソッドを呼ぶ。画面の部品を描くことを含む。約束を通して呼ぶとき、相手は約束である | 呼ぶ部品→呼ばれる相手 | 静的依存規則 |
| 生成 | 依存の組み立てを目的として、インスタンスを生成する | 生成を実行する部品→生成対象 | 生成に伴う参照は静的依存規則。生成の置き場は構造方針の規則(A01) |
| 注入 | 生成されたか既存のインスタンスを、使う側が使う振る舞い(コールバックを含む)として外から渡す | 渡される部品(注入元)→受け取る部品(注入先) | 注入そのものは判定しない。注入先が受け取る型は参照として静的依存規則で判定する。最初の受け手への注入の置き場は構造方針の規則(A01) |

- 生成と注入は両端の異なる別の関係で、1つにまとめず、どちらかの有無を他方の条件にしない。注入に、同じ場所での生成を必須としない。
- 注入は、渡す操作を行う部品からの関係ではない。注入の向きは、層の内外と上下で制限しない。例えば、入口で生成した手続きを画面の部品へ渡すことは、手続き→画面の部品の注入である。
- 注入は、依存性逆転を伴う場合に限らない。
- 呼び出しは注入と独立した関係である。注入の有無から呼び出しを導かず、呼び出しの有無から注入を導かない。
- 実行時に実行される関係(約束の背後の具体実装が実行されることなど)は、関係として扱わない。
- 関数型の引数(コールバック)を呼ぶことも呼び出しで、相手は、その関数型を宣言した約束(型)である。約束が呼ぶ部品と同じファイルにあるときは、ファイル間の関係に現れない。注入された具体の関数へは、関係を足さない(実行時に実行される関係)。
- 値として渡すこと(データや状態だけを渡すこと)は、注入ではない。

## 4. 層と帯

各機能の中の層を、外側から順に並べると次のようになる。
外側の層は内側の層に依存してよく、内側の層は外側の層に依存しない。依存してよい先は第12節の表で決める。

| 層 | 置くもの |
| --- | --- |
| 組み立て層 | 入口。具体実装と手続きの生成、使う側への注入、受け取った画面の部品と枠の描画(第5節) |
| インフラ層 | 約束の実装、外部への実際のアクセス、外部の形と内側の形の変換、他の機能の入口を自分の約束で包む実装(第8節) |
| UI層 | 画面の部品(標準のフックで持った状態を描き、手続きを呼ぶ部品と、外部のウィジェットを描く部品を含む)。表示だけの一時的な状態 |
| アプリケーション層 | 手続き、手続きの約束、画面に渡す形がドメインの型と異なるときの見え方の型 |
| ドメイン層 | 集約、エンティティ、値オブジェクト、出来事、ドメインサービス、ドメインの約束(第6節) |

- ドメインは1層である。「ドメインモデル」は、ドメイン層の全体を指す語とし、ドメインサービスと対の分類名にしない。
- UI層とインフラ層は、同じく機能の最も外側の層で、互いに静的に依存せず、関係も持たない(D05、A06)。
- 組み立て層は、UI層とインフラ層を含む全ての層より外側にある。入口は組み立て層に属するため、UI層とインフラ層の独立の例外にはならない。
- 使わない層は置かなくてよい。

構造図の帯:
- 構造図の帯の名前と、上から下への並びは、次の1通りとする: 組み立て層、インフラ層、UI層、アプリケーション層、ドメイン層。
- 用語は、第2節の表の「帯」の列のとおりに、1つの帯に当たる。機能と共有は列であり、外部は帯と列の外にある。パッケージは描かない。
- この並びで、方針が許す層の間の静的依存は、全て同じ帯か下の帯へ向く。
- UI層とインフラ層は、同じく最も外側の層で、帯は便宜上、別に分ける。帯の上下は、依存の許可を意味しない。インフラ層をUI層の上に置くのは、外部へのアクセスを担う層を外部の行に近づける、並びだけの理由による。両者の間には、参照も、呼び出しも、注入も、実装も無い(D05、A06)。UI層が外部とやりとりするときは、アプリケーション層の手続きを通す(L01)。

## 5. 組み立て層

組み立て層は、入口(アプリの起動地点、画面の入口、要求の入口)からなる。

役割:
- 具体実装(インフラ層と共有の技術の実装)と手続きを生成し、使う側へ注入する。注入するものは、生成したものか、画面のパッケージや実行環境から取得した既存のものである。
- 生成したものを入口の寿命の間保ち、注入する既存のものを取得する。そのための画面のパッケージの呼び出しを持ってよい。
- 受け取った画面の部品と枠を描く。そのための画面のパッケージの呼び出しを持ってよい。
- 起動時に決まる設定(実行環境、環境変数)を読み、生成する実装と設定値を選ぶ。設定値を必要とするUI層の部品へは、引数でデータとして渡す(注入ではない。UI層は環境変数を読まない。共有の画面部品は、公開設定だけを読んでよい。X01)。

組み立て層が持たないもの(A05):
- 業務の判断、外部のサービスとのやりとりの処理、UI層の部品の中身(表示の組み立て、入力の扱い)、インフラ層の処理(外部の呼び出し、形の変換、操作のたびに読む実行環境の状態の読み出し)。
- 利用者の操作やデータによる分岐。

依存の組み立ての集約(A01):
- 依存の組み立てを目的とする生成を行ってよいのは、組み立て層だけである。
- 生成または取得したものを最初の受け手へ注入するのは、組み立て層である。UI層の部品は、手続きを組み立て層から受け取り、自分で生成しない。
- 受け取る側は、受け取るものを自分で生成せず、探しにも行かない。受け取る型は、受け取る側が第12節の表で依存してよい先の型とする(型はD03で判定する)。例えば、手続きと具体実装は約束の型で受け取り、UI層の部品は同じ機能のアプリケーション層の手続きの型で受け取る。
- 受け取った振る舞いを、同じ部品の中や、描く子の部品へさらに渡すこと(画面の部品が子の部品へコールバックを渡すなど)は、この規則(組み立て層への集約)の対象に含めない。
- 他の機能が公開する部品を受け取るのは、受け取る側の機能のインフラ層の具体実装だけで、その型は相手の機能の入口が公開する型とする(第10節)。

寿命:
- アプリの起動地点は1つである(A03)。アプリで1度だけ動く部品(裏で動く処理など)は、アプリの起動地点が生成し、始める。
- 画面の入口は、画面を開くたびに、その画面の手続きと具体実装を生成し、注入する。
- 要求の入口は、要求を受けるたびに、その要求の具体実装を生成して呼ぶ。
- 同じ寿命の同じ部品の生成は、組み立て層の1か所だけにする(A04)。
- アプリで1つに保つ部品(複数の機能や画面が共有する接続や記録)は、アプリの起動地点が1度生成して注入するか、生成の関数が呼ばれるたびに同じものを返す実装にする。後者の部品は、画面の入口が生成してよい(A04)。

## 6. ドメイン層

ドメイン層の部品:

| 部品 | 意味 |
| --- | --- |
| 集約 | 同時に一貫していなければならないデータと規則の範囲。変更の入口で不変条件を守る |
| エンティティ | 集約の中で、識別子で区別される部品 |
| 値オブジェクト | 値で等しさが決まり、1つの値で閉じる規則を持つ部品 |
| 出来事 | 集約で起きた、過去形の事実 |
| ドメインサービス | どの集約にも属さない業務の規則。状態を持たない |
| ドメインの約束 | ドメインサービスが判断の途中で問い合わせる、業務の言葉の約束(第7節) |

ドメイン層の中の向き:
- 集約、エンティティ、値オブジェクト、出来事は、ドメインサービスを参照しない(D07)。
- 集約、エンティティ、値オブジェクト、出来事は、約束を参照しない(D08)。外部の値は、手続きが読み、値として渡す。
- ドメインサービスは、集約、エンティティ、値オブジェクト、出来事、ドメインの約束を参照してよい。
- ドメインの約束は、集約、エンティティ、値オブジェクト、出来事の型を参照してよい。
- ドメイン層は、同じ機能のドメイン層だけを参照し、外部、共有の技術、他の層を参照しない(D04)。

集約を置く基準(M01):
1. 「同時に一貫していなければならないデータと規則の範囲」を、1つの集約とする。
2. 集約は、変更の入口(命令)で不変条件を検査し、新しい状態と、起きた出来事、または拒否を返す。
3. 集約の外から、集約の中の部品を直接変えない。集約の中の部品は、集約の根を通してだけ変える。
4. 集約どうしは、識別子で参照する。1つの命令で、2つの集約を同時に変えない。
5. 状態を出来事の列から求めるときは、その求め方を、集約が持つ1通りだけにする。
6. 永続しない状態(画面を開いている間だけの状態など)でも、守るべき規則があれば集約にする。
7. どの集約にも属さない規則は、状態を持たないドメインサービスにする。

集約の書き方(M01):
- 集約は、変更しない型(読み取り専用の型)と、それを受け取って新しい状態を返す関数の組で書く。クラスにしない。
- 命令の関数は、規則を検証し、新しい状態と出来事、または拒否を表す値を返す。引数の状態を書き換えない。
- 集約の外へ出すのは、状態の型、初期の状態の値、命令と問い合わせの関数、それらが受け取る型と返す型、入力の制約の値である。命令は、出来事を受け取って新しい状態を返す1つの関数(`reducer`)にまとめてよい。
- 集約の現在の値は、アプリケーション層の手続きが保持する。画面を開いている間だけの状態は、画面の部品が標準のフック(`useState`など)で保持してよい。そのとき、手続きは、今の値の読み手と、出来事の送り先を受け取る。読み手は、出来事を送った直後の値を、描画を待たずに返す(同じ入力イベントの中で届く2回目の呼び出しが、送信中などの判定で1回目の結果を見るため)。業務の状態の変更は、集約の命令(`reducer`)で行う。

## 7. 約束

約束は、内側の部品が外側に頼むことの型だけの宣言である。約束の引数と戻り値は、約束と同じ層か、それより内側の型だけを使い、外部の型を使わない(D03、D04、X01)。
約束を置く層と、約束に依存してよい部品は、その約束が表す責務で決める(C01)。

| 約束 | 表す責務 | 置く層 | 依存してよい部品 |
| --- | --- | --- | --- |
| ドメインの約束 | ドメイン上の判断に必要な抽象。ドメインサービスが判断の途中で問い合わせる、業務の言葉で表せる事実 | ドメイン層 | ドメインサービス、手続き、インフラ層の実装 |
| 手続きの約束 | アプリケーション上の手続き。外部とのやりとり、集約の保存と取り出し、画面の遷移、実行環境の状態の読み出しなど、操作の順序に置かれる一歩 | アプリケーション層 | 手続き、インフラ層の実装 |
| 共有の技術の約束 | 2つ以上の機能が使う技術の能力 | 共有の技術の約束 | 第12節の表のとおり |

区別の基準:
- 約束が答えるものが、判断の材料になる業務の事実で、状態を変えず、呼ぶ順序と失敗の扱いを含まないなら、ドメインの約束である。
- 外部へ書き込む、外部のサービスへ依頼する、保存し取り出す、画面を移る、実行環境の状態を読むなど、手続きの順序の中の一歩なら、手続きの約束である。
- 手続きの約束を、ドメイン層へ持ち込まない。原則1の「手続きを自分で行わない」は、この意味で読み、ドメイン上の判断に必要な抽象をドメインサービスが利用することを禁じない。

置き場と検査:
- ドメインの約束は、ドメイン層の自分のファイル(`*-port.ts`)に置く。集約、エンティティ、値オブジェクト、出来事からの参照はD08で、他の層からドメインへの向きはD03で、確かめる(確かめ方は第14節)。
- 手続きの約束は、それを使う手続きのファイルに置く。2つ以上の手続きが使うとき、または機能の他の操作が同じ役目を持つことが確かめられるときは、アプリケーション層の自分のファイルに置く(R02)。ドメイン層からの参照はD04で、レビューで確かめる。
- ある約束が、どちらの責務に当たるか(置いた層が正しいか)は、上の基準でレビューで確かめる(C01)。

表示を伴う部品:
- 外部のパッケージが与える画面の部品(外部のウィジェットなど)を描く部品も、画面の部品であり、UI層(共有されるなら共有の画面部品)に置く。結果は、引数のコールバックで受け取り、業務の判断は手続きへ渡す。
- 画面の部品を、インフラ層に置いて組み立て層からUI層へ注入しない。UI層とインフラ層の間に関係ができるためである(A06)。

## 8. 実装

実装の置き場所:
1. その機能だけが使う外部の実装は、その機能のインフラ層に置く。
2. 技術の能力の実装は、共有の技術の実装に置く。
3. 1つの外部に直接触る実装は、原則として1つにする。同じ外部の実装が2つの機能に要るときは、共有の技術へ移す。
4. 永続の保存先は、約束ごとに複数あってよい。保存の接続を開き、その構造の版を管理する部品は、共有の技術に1つだけ置く(X03)。

インフラ層と共有の技術の実装が行ってよいこと(I01):
- 外部を呼ぶこと、外部の形と内側の形の変換、外部の例外を内側の形の結果に変えること、実行環境の状態を読むこと。
- 業務上の扱いの決定(失敗をどう扱うか、利用者に何と伝えるか)は行わない。

## 9. 機能の切り方

機能の切り方(M02):
1. 機能は、利用者が1つの名前で呼べる、一まとまりの能力で切る(例: 商品を探す、注文する、通知を受け取る)。
2. 画面と、その画面のための保存と外部とのやりとりは、同じ機能に置く。
3. 画面と別の寿命で動く能力(画面を閉じても続く処理、アプリで1つだけ動く処理)は、別の機能にする。
4. 技術の関心(保存全般、通信全般)で機能を切らない。それは共有の技術か、各機能のインフラ層に置く。
5. 迷ったら、「変わる理由が同じか」「寿命が同じか」「利用者から見て別の能力か」で決める。

適用した領域の、機能の中は、層のディレクトリと機能の入口だけである(D02)。同じ機能の中の未適用のファイルは、この規則の対象外である(第16節)。

## 10. 機能の間の依存

1. 機能の間の依存は一方向にする。循環させない(D06)。
2. 機能が他の機能へ公開するのは、機能の入口だけである。機能の入口は、アプリケーション層の名前(手続きの生成、公開の型、他の機能が使うための約束)と、ドメイン層の関数と定数だけを再公開し、宣言を持たない(F04)。ドメインの型(分類、状態)は公開しない。公開する関数の引数と戻り値は、ドメインの型を使わず、平らな値にする(F06)。
3. 機能の入口は、他の機能へ公開する名前がある機能だけが、ちょうど1つ持つ(F05)。公開する名前がない機能に、入口を置かない。
4. 他の機能のファイルへの参照は、相手の機能の入口だけである(F01)。他の機能の入口を参照してよいのは、参照する側の機能のインフラ層と、組み立て層だけである(F02)。方針を適用していない領域は、この規則の対象外である(第16節)。組み立て層は、機能の入口に限らず、機能の各層を参照してよい。
   参照の書き方は、適用した領域のファイルについて、参照する側の位置で、次の3つに固定する(参照の確かめを参照の文字列で行うため。未適用の領域は、前の文のとおり対象外である)。
   - 組み立て層から機能のファイルへは、層までのパス(`@/features/<機能>/<層>/<ファイル>`)で書く。入口を経由しない(インフラ層とUI層の名前は、入口に出せない。F04)。
   - 組み立て層以外で、機能の外にあるファイルから機能への参照は、その機能の入口の公開名だけで書く(F01)。
   - 機能の中のファイルどうしは、相対パス(同じ層は`./`、他の層は`../<層>/`)で書き、機能の入口を経由しない(入口は他の機能向けの窓口で、経由すると循環しうる)。
5. 他の機能から何かを受け取る必要があるときは、受け取る側のアプリケーション層に自分の約束を宣言し、受け取る側のインフラ層が、相手の機能の入口でその約束を実装する(相手の形を自分の形に変換する)。

機能の間の伝達(M02):
6. 上流の機能は、下流の機能を知らない。上流から下流への伝達は、上流が公開する記録の読み出しと購読で表す。
7. 下流が上流の記録をもとに自分の状態を持つときは、下流は自分が処理した範囲の情報だけを保存し、上流の記録からそれを除いて、自分の状態を作り直す。同じ事実を上流と下流の2か所に書き込まない。通知は合図にすぎず、正は上流の記録である。
8. 下流の処理の結果が、上流の持つ事実の解釈に必要なとき、その事実の書き込みは、事実の持ち主である上流の機能の入口を通して行う。事実の持ち主は常に1つである。
9. 下流の処理は、同じ記録を2回処理しても結果が変わらない(冪等)ように作る。

## 11. 共有の技術と共有の画面部品

### 共有の技術

置いてよいもの:
- 業務の言葉を持たない技術の能力の約束と実装(例: 時刻、乱数、実行環境の状態、利用者の資格の状態、永続の保存の接続の管理、ログの出力)。
- 2つ以上の機能が使う、または使うことが見込まれるもの。

置いてはいけないもの:
- 業務の型、業務の規則、利用者向けの文言、業務上の分類。
- 画面の部品。
- 特定の機能を知るもの。機能の間の伝達の仲介(機能の間は、第10節の機能の入口で結ぶ)。

位置と依存:
- 共有の技術の約束は、全ての機能に共通のアプリケーション層の約束に当たる。共有の技術の実装は、インフラ層に当たる。
- 機能のアプリケーション層、UI層、インフラ層は、共有の技術の約束に依存してよい。ドメイン層は、共有の技術に依存しない(D04)。
- 共有の技術は、機能と組み立て層を参照しない(P01)。
- 共有の技術の実装を参照してよいのは、組み立て層と、同じ能力の共有の技術の実装だけである(P02)。
- 共有の技術の約束は、共有の技術の約束だけを参照し(P05)、型の宣言だけを持つ(P04)。能力の間の依存は、約束への依存だけとする。

### 共有の画面部品

- 複数の機能の画面が使う、業務の言葉を持たない画面の部品と、そのための画面のパッケージ(外部のウィジェットを描くものを含む)は、共有の画面部品に置く。共有の画面部品は、UI層に当たる。
- 共有の画面部品は、共有の画面部品と、画面のパッケージだけを参照し、機能と共有の技術を参照しない(U01)。
- 機能のUI層と組み立て層は、共有の画面部品を参照してよい。

## 12. 依存の許される向き

| 依存元 | 依存してよい先 |
| --- | --- |
| ドメイン層 | 同じ機能のドメイン層(第6節の中の向きに従う) |
| アプリケーション層 | 同じ機能のドメイン層とアプリケーション層、共有の技術の約束 |
| UI層 | 同じ機能のドメイン層、アプリケーション層、UI層、共有の画面部品、共有の技術の約束、画面のパッケージ |
| インフラ層 | 同じ機能のドメイン層、アプリケーション層、インフラ層、共有の技術の約束、他の機能の入口、パッケージ、外部 |
| 機能の入口 | 同じ機能のアプリケーション層と、再公開するドメイン層の関数と定数 |
| 共有の技術の約束 | 共有の技術の約束だけ |
| 共有の技術の実装 | 共有の技術の約束、同じ能力の共有の技術の実装、パッケージ、外部 |
| 共有の画面部品 | 共有の画面部品、画面のパッケージ |
| 組み立て層 | 全て |

- 上の表にない向きは、全て禁止する(D03)。どの層も組み立て層を参照しない(A02)。
- 参照には、注入先が受け取る型を含む。具体実装の型で受け取れば、注入は成立しても、受け取る型の参照がD03に反する。
- 外部は、管理外のサービスと、実行環境の状態である。実行環境の状態は、URL、端末の情報、保存領域、通信、環境変数(例: `location`、`navigator`、`localStorage`、`indexedDB`、`fetch`、`process`。`window`を通して読むものを含む)である。言語の標準の機能(`URL`、`Map`、`JSON`など)は外部に含めない。画面の描画と操作の機能(`window`、`document`の表示と操作)は、画面のパッケージに含める。パッケージは外部ではなく、構造図に描かない。
- パッケージと実行環境の大域の名前を直接参照してよいのは、インフラ層、共有の技術の実装、組み立て層(どのパッケージも)と、画面のパッケージに限ったUI層と共有の画面部品だけである(X01)。ドメイン層とアプリケーション層は、パッケージを参照しない。
- 依存の循環を禁止する(ファイルの間、層の間、機能の間のいずれも)(D06)。

## 13. 置き場所を決める規則

置き場所(R01):

| 種類 | 置く部品 |
| --- | --- |
| 判断(業務の規則、検査、計算、導出) | 1つの集約のデータで閉じるなら、その集約。複数の集約にまたがるなら、ドメインサービス。1つの値で閉じるなら、値オブジェクト |
| 状態(業務の規則を伴う) | 集約の値。その現在の値の保持は、アプリケーション層の手続き。画面を開いている間だけの状態は、画面の部品が標準のフック(`useState`など)で保持してよい。手続きが読む値は、出来事の直後に最新となる |
| 状態(表示だけの一時的なもの。入力中の文字、開閉など) | UI層 |
| 状態(永続するもの) | 約束を通して、インフラ層の実装が保存する |
| 手続き(操作の順序、保存の順序、外部を呼ぶ時点) | アプリケーション層の手続き。業務の規則は書かない |
| 外部アクセス、実行環境の状態の読み出し | インフラ層、または共有の技術の実装 |
| 変換(外部の形と内側の形) | 外部に触る実装と同じ機能のインフラ層 |
| 変換(他の機能の公開した形と、自分の形) | 受け取る側の機能のインフラ層 |
| 文言(業務上の結果ごとの、利用者向けの文言) | 結果の種類を定めるドメイン層の部品(種類と文言は一緒に変わる) |
| 文言(画面の配置にだけ関わるもの。ボタンの名前など) | UI層 |
| 分類(外部の応答を、業務上の扱いに分けること) | 分類の種類と、種類ごとの扱いは、ドメイン層の部品。外部の応答の形(クラス名、コードなど)を種類に写すのは、インフラ層(変換) |
| 時刻、乱数、外部の状態 | 読むのはインフラ層か共有の技術の実装。手続きが約束から読み、判断へ値として渡す |
| 規則に反する入力 | 集約が拒否の値として返す。例外にしない |
| 外部の失敗 | インフラ層が、内側の形の結果(失敗の種類)に変える。外部の例外を内側へ出さない |
| 複数の機能や画面が使うもの | 業務の言葉を持つなら、それを持つ機能(他の機能へは、その機能の入口から公開する)。業務の言葉を持たない技術の能力なら共有の技術。業務の言葉を持たない画面の部品なら共有の画面部品 |
| 画面に渡す形 | UI層は、同じ機能のドメインの型と、アプリケーション層の公開する型を受け取ってよい。アプリケーション層は、画面に渡す形がドメインの型と異なるときだけ、見え方の型を公開する |
| 外部を呼ぶ時点、保存 | UI層は、これらをアプリケーション層の手続きを通して行う。ドメインの型、初期の状態、問い合わせ、集約の命令(`reducer`)は、UI層が直接使ってよい(L01) |

ファイルの分け方(R02):
- 1つのファイルは、1つの層の、1つの部品(集約、値オブジェクト、ドメインサービス、手続き、画面の部品、具体実装など)を持つ。
- 部品の付属は、その部品のファイルに置く。付属は、部品の命令や関数が受け取る型と返す型、部品の入力の制約の値、部品の中だけで使う値と関数、その部品だけが使う約束である。
- 別の部品が、この部品を通さずに独立に使う規則や値は、自分の部品として自分のファイルに分ける。分けるかは、方針を適用した領域の中の使い方で決め、未適用の領域の使い方では決めない。ただし、約束は、機能の他の操作が同じ役目を持つことが確かめられるなら、その操作が適用済みかどうかによらず、使い方を待たずに自分のファイルに分ける。同じ役目は、約束の型の形と、他の操作の実際の呼び出しで確かめ、適用の設計に根拠を書く。
- 中継だけのファイル(受け取ったものを、そのまま渡すだけの部品)を置かない(R03)。入口は、部品を生成して注入する役割を持つので、これに当たらない。機能の入口は、他の機能へ公開する境界として置き、第10節の3に従う。
- 未適用の領域のファイルを、用語に合わせるためだけに動かさない。方針を適用する領域は、方針と原則から構造を組み直し、既存のファイルの分け方、関数の形、名前を理由に留めない(第16節)。
- テストの置き場所は、この方針では決めない。

## 14. 規則の一覧

規則は、静的依存規則と構造方針の規則のどちらか1つに分類する。分類は、確かめ方とは独立である。

- 静的依存規則は、どのファイルがどのファイル(とパッケージ)を参照してよいかの規則で、原則1と原則5を、このアプリで具体化したものである。原則の「依存規則に反する静的依存」は、「静的依存規則に反する静的依存」と読む。静的依存規則の違反を、静的依存規則の違反と呼ぶ。
- 構造方針の規則は、参照の可否以外の規則で、原則に加えて構造を定める。構造方針の規則に反することを、構造方針の違反と呼ぶ。
- 一方の違反を、他方として扱わない。

方針の規則は、全てレビューで確かめる(確かめ方は、下の表の「確かめ方」と、レビューで確かめる指針)。方針を守らせる手段としての静的検査(リンターの設定の追加)は、この方針の対象外で、全ての機能の移行を終えた後の別作業とする。

### 静的依存規則

| ID | 規則 | 確かめ方 | 判定の材料 |
| --- | --- | --- | --- |
| D03 | 依存は、第12節の表の向きだけである。注入先が受け取る型を含む | レビュー(各ファイルの参照の元と先を、第12節の表と照合する) | 参照の文字列と、参照の元の領域 |
| D04 | ドメイン層は、同じ機能のドメイン層だけを参照する(外部、共有の技術、他の層を参照しない) | レビュー(ドメイン層のファイルが、同じ層以外とパッケージを参照せず、大域の名前を使わない) | 参照の文字列、大域の名前 |
| D05 | UI層とインフラ層は、互いに参照しない | レビュー(UI層とインフラ層の、互いの参照の文字列) | 参照の文字列 |

| D08 | 集約、エンティティ、値オブジェクト、出来事は、約束を参照しない | レビュー(手続きの約束と共有の技術の約束は、D04で検出する) | ドメイン層の参照 |

| F02 | 他の機能の入口を参照するのは、インフラ層と組み立て層だけである | レビュー | 参照の文字列と、参照の元の領域 |

| U01 | 共有の画面部品は、共有の画面部品と画面のパッケージだけを参照する | レビュー | 参照の文字列 |
| A02 | 組み立て層は、どの層からも参照されない | レビュー | 参照の文字列 |

参照の確かめは、参照の文字列で行う。機能への参照の書き方は第10節の4に従い、共有の技術は能力の約束か実装までのパスで書く。

### レビューで確かめる指針

方針の全ての規則(静的依存規則と構造方針の規則)は、次の順で確かめる。

1. 入口: 生成の関係の始点が全て組み立て層にあり(A01)、同じ寿命の同じ部品の生成が1か所にあり(A04)、入口に第5節の役割の外の処理が無い(A05)。
2. 受け取る側: 手続きと具体実装が、受け取るものを自分で生成せず、約束の型で受け取る(A01、D03)。UI層の部品が手続きを組み立て層から受け取る(A01)。 UI層とインフラ層の間に、参照も呼び出しも注入も実装も無い(D05、A06)。
3. 約束: 各約束の責務が、置いた層に合う(C01)。
4. 部品: 各ファイルが用語の1つに当たり(D01)、1つの部品と、その付属だけを持ち(R02)、中継だけのファイルが無い(R03)。業務の判断、文言、分類が第13節の表の置き場にある(R01、M01、I01、L01)。
5. 機能と共有: 機能の中が層のディレクトリと入口だけで(D02)、入口が公開の要る機能だけにあり再公開だけを持ち(F04、F05)、公開する名前にドメインの型が現れない(F06)、外部のパッケージを直接参照する機能が1つ以下で(X02)、共有の技術の約束が型だけである(P04)。層の間と機能の間に循環が無い(D06)。
6. 参照の向き(静的依存規則): 各ファイルの参照が、第12節の表の向きだけで(D03、D05、D07、D08、F01、F02、P01、P02、P05、U01、A02)、パッケージと実行環境の大域の名前の使い方が、X01、X03、D04に合い(UI層が環境変数を読まず、共有の画面部品が公開設定(`NEXT_PUBLIC_*`)だけを読む)、ファイルの間、層の間、機能の間に循環が無く(D06)、1つのパッケージを直接参照する機能が1つ以下である(X02)。

## 15. 関係の判定と構造図

関係の種類、可否、違反の種類は、次の順で求める。

1. 関係の種類を、第3節で決める。
2. 参照、実装、呼び出し、生成に伴う参照、注入先が受け取る型を、静的依存規則(D03からA02の表)で判定する。反するものは、静的依存規則の違反である。
3. 生成の置き場と、最初の受け手への注入の置き場を、A01とA04で判定する。反するものは、構造方針の違反である。
4. 注入そのものは、判定の対象ではない。
5. 両端の部品の帯は、第2節の表の「帯」の列で決める。

構造図:
- 構造図の帯は、第4節の名前と並びで描く。
- 構造図の違反の印は、静的依存規則の違反だけを表す。構造方針の違反は、印にせず、生成の線の始点の帯と、両端の箱で読む。

- 構造図に描く外部は、管理外のサービスだけである。パッケージ(画面のパッケージ、その他のパッケージ)は、箱にも線にも描かない。パッケージへの参照の可否は、X01で確かめる(確かめ方は第14節)。
判定の例:

| 関係 | 種類 | 判定 |
| --- | --- | --- |
| 入口→具体実装、入口→手続き | 生成 | 違反なし(D03で組み立て層は全てに依存してよい。A01を満たす) |
| 具体実装→手続き(具体実装を手続きへ渡す) | 注入 | 判定の対象外。手続きが約束の型で受け取れば、受け取る型も違反なし(D03) |
| 入口で生成した手続き→画面の部品(画面の部品の引数で渡す) | 注入 | 判定の対象外。違反なし(A01を満たす) |
| 手続き→約束 | 参照、呼び出し | 違反なし(D03)。手続き→具体実装の関係は無い(第3節) |
| 具体実装→約束 | 実装 | 違反なし(D03でインフラ層はアプリケーション層とドメイン層に依存してよい) |
| 画面の部品→手続き | 呼び出し | 違反なし(D03)。手続き→画面の部品の注入とは別の関係である |
| 手続きが具体実装を自分で生成する | 生成 | 生成に伴うアプリケーション層→インフラ層の参照が、静的依存規則の違反(D03)。A01にも反する |
| 画面の部品が手続きを自分で生成する | 生成 | 静的依存規則の違反は無い(D03でUI層はアプリケーション層に依存してよい)。構造方針の違反(A01) |
| 手続きが具体実装の型で受け取る | 注入と参照 | 注入は成立する。受け取る型の参照が、静的依存規則の違反(D03) |
| 組み立て層が、インフラ層の部品をUI層の部品へ注入する | 注入 | 静的依存規則の違反は無い(注入は判定の対象外。UI層が受け取る型がインフラ層の型ならD05に反する)。構造方針の違反(A06) |

## 16. 適用

- この方針を特定の機能にどう割り当てるか(機能の分け方、集約、約束、共有の技術の能力、入口の生成と注入の具体)は、適用の設計として、別の文書で行う。
- 方針を適用した領域は、適用の設計が、対応表に挙げた領域である。適用の単位は、機能の全体、または機能の中の利用者の操作(1つの画面とその部品)である。適用する単位は、その単位のファイルと、それが直接または間接に参照するアプリの中のファイルを、方針に合わせて組み直す。同じ機能の中の、適用していないファイルは、未適用の領域に残し、組み直さない。
- 適用する機能の構造は、方針と原則だけから決め、未適用の領域の都合で変えない。
- 未適用の領域のファイルが、適用した部分を参照するときは、他の機能のファイルは、その機能の入口(第10節)だけを参照する。同じ機能の中のファイルは、入口を経由せず、適用した部分のファイルを相対パスで参照してよい(入口は他の機能向けの窓口で、機能の中から経由すると循環しうる)。適用した機能の内部の部品を、他の機能の未適用の領域のために公開しない。ただし、外部の応答を内側の形に写すインフラ層の変換(第13節)を、未適用の領域が必要とするときは、入口に出せない(F04)ので、そのインフラ層のファイルを、層までのパスで参照してよい。入口が公開する名前は、その機能が他の機能へ提供する契約であり、参照する側が適用済みかどうかで決めない。参照する側の機能を適用するときに、参照の元が、インフラ層か組み立て層になるように組み直す(F02)。
- 未適用の領域のファイルは、適用した機能の部品の移動、改名、分割、統合、削除で壊れる参照の付け替えと、新しい部品の形に合わせて振る舞いを保つための変更だけを受ける。

## 17. 参考と、記事と異なる点の理由

参考: 「オニオンアーキテクチャとは何か」(https://qiita.com/cocoa-maemae/items/e3f2eabbe0877c2af8d0)。
依存は外から内へ向かうこと、外側は内側のどの層にも依存できること、約束を内側に置き外側が実装すること、UI層とインフラ層を最も外側の同じ位置に置くこと、ドメインが他の層に依存しないことは、記事に従う。
次の点は記事と異なる、または記事が扱わない範囲で依存を狭める。どれも、構造の分かりやすさと、検証、差し替え、変更の範囲を比べて決めた。

1. ドメインを1層にする(記事はドメインモデルとドメインサービスを別の層にする)。集約、値オブジェクト、ドメインサービスの間の向きはD07とD08で表せるため、層を分けなくても依存の向きは保て、層とディレクトリの数が減る。
2. 約束の置き場を、約束が表す責務で決める(記事は約束をアプリケーション層に置く)。手続きの約束は記事と同じくアプリケーション層に置く。ドメイン上の判断に必要な抽象だけをドメインの約束としてドメイン層に置き、ドメインサービスが使えるようにする。手続きの約束をドメイン層に置かないため、ドメイン層は手続きを持たない。
3. 手続きの約束を、使う手続きのファイルに置く。使う側が約束を持つという原則をそのまま置き場にし、約束だけのファイルを部品の数だけ増やさない。ただし、機能の他の操作が同じ役目を持つことが確かめられる約束は、自分のファイルに分ける(R02)。
4. 組み立てを、最も外側の1つの層とし、入口をそれに分類する(記事は組み立てを扱わない)。生成と注入を入口に集めると、何がどの実装で動くかを1か所で読める。
5. 集約を、状態と振る舞いが一体のオブジェクトではなく、変更しない型と関数の組で書く。状態を出来事の列から1通りに求める作りや、画面の状態管理は、元の値を変えずに新しい値を返す関数とそのまま噛み合う。状態の型とそれを変える関数は集約のファイルに一緒に置くため、データと規則が離れないという一体の利点は保つ。
6. 複数の機能が使う技術の約束を、各機能のアプリケーション層ではなく、共有の技術の約束に置く。各機能に置くと、同じ約束と、それを包むだけの実装が機能の数だけ要る。共有の技術の約束は全ての機能に共通のアプリケーション層として扱うため、依存の向きは記事と変わらない。
7. 約束の実装は、インフラ層と共有の技術の実装だけに置く(記事の例は、UI層にも約束の実装を置く)。画面の部品が外部の状態の持ち主を兼ねると、画面を変える理由と外部を差し替える理由が1つの部品に重なる。外部のウィジェットを描く部品は、表示だけを担うため、UI層に置く。インフラ層に置いて注入すると、UI層とインフラ層が結ばれる。
8. インフラ層は、共有の技術の実装を直接参照せず、共有の技術の約束を通すか、組み立て層から注入される(記事は、最も外側の層の中の参照を制限しない)。共有の実装を差し替えるときと、偽の部品で検証するときにインフラ層を変えずに済む。
9. 機能の入口は、ドメインの型(分類、状態)を公開しない。ドメインの関数と定数は、入口が再公開してよい(F04、F06。記事は機能の分割を扱わない)。他の機能は、公開された名前だけに依存し、ドメインの型には依存しないため、機能の中のドメインを、他の機能に影響を与えずに変えられる。
10. UI層とインフラ層を、最も外側の同じ位置づけに置き、参照と呼び出しだけでなく注入も持たない関係とする(記事は、同じ位置に置くだけで、注入を制限しない)。両者が結ばれると、画面と外部の変更が互いに及ぶためである。
