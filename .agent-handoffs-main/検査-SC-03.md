# 検査-SC-03 パスワードを再設定する

担当: 検査-SC-03。図: `.agent-handoffs/diagrams/検査-SC-03/SC-03.png`(SVG、入力のSC-03.jsonも同じ場所)。
判定の件数: 必要33、不要の疑い19、判断できない9(合計61。SC-01、SC-02と同じ部品の項目は、表の「SC-01 / SC-02」列に番号を記載)。
コードの読み取りと、auth-js 2.112.3の配布物、認証サービス(supabase/auth)の`master`のソース(2026-11-05に取得)の確認だけで行った。
アプリの実行、テストの実行、ローカルSupabaseでの実測、コード変更はしていない。実測が要る点は「未実測」と書く。
認証サービスの`master`のソースは、本番とローカルで動く版とは限らない。版の確認は未実施である。

## 図の範囲

契機は、利用者が/reset-passwordでメールを入力して進むこと。結果は、新しいパスワードが設定され、全端末のサインインが終わり、/signinへ移ること。
列は、画面、再設定の手続き(規則を含む)、サーバーアクション(要求のセッション)、認証サービス(メール・DBを含む)、遷移(ページ全体の読み込み)。
1枚に、メール入力、コード入力(確認・再送・戻る)、パスワード設定(サーバーアクション)の3段階と、パスワード段階の「サインインに戻る」を描いた。
境界の先は描かない: 要求のproxy(認証済みの/reset-passwordの転送、Server Actionを転送しない規則。SC-05)、/signinの表示とサインイン(SC-02)、SIGNED_INによる端末の利用者識別(SC-08。再設定の確認はPASSWORD_RECOVERYで、`other`に写り記録を変えない)。
SC-01との違い: 登録の確認が無い。パスワードの設定は、ブラウザではなくサーバーアクション(要求のcookieのセッション)が行い、続けて全端末のサインインを終える。遷移はrouterではなく、ページ全体の読み込み(`window.location.assign`)。遷移先は`destinationOf`を使わず`SIGN_IN_PATH`固定。

## 不要の疑いの詳細

SC-01、SC-02と同じ項目(2b、3、6、9、10、12、13、14b、14d、15、21、24、27、38、45、46)は、それぞれの報告の詳細と、ユーザー確定の判断(検査-SC-01.md「確定した判断」)に従う。以下は、再設定の場面で新しく示す理由や、確定に必要な情報があるものだけを書く。

### No.3 サイトキー未設定の例外(確定の材料)
- なぜ不要か: Turnstileを使う最後のシナリオで、再設定でも、サインイン・サインアップと別の理由が無い。到達は、デプロイの設定ミスだけ。
- 影響: ミスの時に、描画の例外でなく、チェックが完了しないまま送信が止まる(「セキュリティチェックが完了していません」)。
- 変更案: `turnstile.tsx` 22-26を外す。`page.tsx`の`siteKey: string | undefined`の型は、そのままにするか、`string`にするかを決める。

### No.15 値で返る通信断の消費(再設定側の確認)
- 確認結果: 再設定の`deliver`(送付と再送)は、サインアップと同じ部品。`resetPasswordForEmail`は通信の失敗を戻り値で返すため、保持する側(`unreachable`)は、呼び出しが投げる場合だけ。再設定に、保持を残す別の理由は無い。
- サインイン側との関係: SC-02の項目19、SC-01の項目15と同じ変更(全失敗で消費)で、3画面とも揃う。
- 変更案: SC-02の変更案(d)。`CallResult`を`accepted`と`failed(failure)`の2種にし、`deliver`の`unreachable`の分岐と、`failureOf`(項目26)を外す。

### No.38 遷移が投げたときの通信エラー扱い
- なぜ不要か: `window.location.assign("/signin")`が投げる場面を示す資料が無い。投げても、設定は済んでいるため、「通信エラー」と示すのは実態と合わない。
- 影響: 無し(人工のテストだけが変わる)。
- 変更案: `reset-password.ts` 90-96を`pageLoad.load(SIGN_IN_PATH)`の1行にする。`PageLoad`の例外の宣言(26-28)を直す。`reset-password.test.ts` 489,506、`page.test.tsx` 386、`reset-password-form.test.tsx`の該当を外す。

### No.39 パスワード段階の「サインインに戻る」
- なぜ不要か: 上の表のとおり。この段階では認証済みのため、リンクがサインインの画面を出さず、/roundsへ送る(推定)。ラベルと動作が合わない。サインアップは同じ段階でリンクを出さない。
- 影響: パスワード段階から「戻る」手段が無くなる。ただし、コード確認の後に離れる利用者は、リンクでも、ブラウザの戻る・ロゴ(紹介画面)でも、セッションが残る(SC-01の懸念2。パスワードは変わらない)。

### No.53 `otp.html`の再設定での到達
- なぜ不要か: 再設定は`recovery`だけを使う。magic_linkの到達は、SC-01の項目54のとおり、サインアップの確認と送付の間の競合に限られる。再設定からは到達しない。

## 懸念

1. 登録の確認(SC-01の項目17)が、再設定のコードを無効にする(SC-01の懸念4の確認)。認証サービスの`master`のソースでは、管理者の`generateLink(type: recovery)`が、利用者の`recovery_token`と`recovery_sent_at`を書き換え、同じ種類の一回限りのトークンを消して作り直す(`api/mail.go` 95-170)。サインアップの登録の確認(`isEmailRegistered`)は、captchaもレート制限も無く誰でも呼べる。
   - 影響: 再設定でコードを受け取った利用者のメールアドレスに対して、誰かが(または本人が別のタブでサインアップを開いて)登録の確認を呼ぶと、届いたコードが無効になり、次の再設定の送付も、`max_frequency`(本番60秒)に当たる(`validateSentWithinFrequencyLimit(u.RecoverySentAt)`)。コードを入力する利用者は`code_expired`と示される。
   - 状態: `master`のソースの読み取りだけ。本番の版は未確認、未実測。確かめるなら、ローカルSupabaseで再設定のコードを送り、登録の確認を呼んで、コードが使えるかを見る。
2. 全端末のサインアウトの失敗は、利用者に知らされない(項目34)。ただし、認証サービスが変更時に他の端末を終えるなら、影響は無い(項目31)。
3. パスワード段階の「サインインに戻る」(項目39)と、コード確認後の離脱で、パスワードを変えずにセッションが残る。SC-01の懸念2と同じ構造で、再設定の場合は、「忘れたパスワードを変えずにアプリを使い続けられる」状態になる(コードで本人確認済みのため、危険ではない)。
4. `same_password`(新しいパスワードが今と同じ)は、エラーの種類の対応表に無く、`other`の汎用文言(「エラーが発生しました。しばらくしてから再度お試しください。」)になる。再設定で、思い出したパスワードを再び入れる利用者は到達し得る。認証サービスの`master`は`same_password`を返す(`api/user.go` 196-197)。実害は文言の不親切だけで、変更案は必要なら別に検討する(項目は立てていない)。
5. 登録の有無の列挙(SC-01の懸念1)の、再設定とサインインでの有無: 再設定は、未登録でも同じ画面へ進み、コードで`otp_expired`になるだけで、有無は分からない。サインインは、メール・パスワードの誤りを同じ`invalid_credentials`の文言にまとめる(SC-02の項目17)。両画面に、登録の有無を教える経路は、コードの読み取りの範囲では無い。列挙の経路は、サインアップの登録の確認だけ。ただし、`/recover`が未登録に成功を返すのは、`master`のソースによる(本番の版は未確認、未実測)。
6. 本番のメール送信(SMTP)は、リポジトリから分からない(`config.toml` 238-246はコメントのまま)。Supabaseの既定のメールの送信は、件数と宛先に制限がある。本番で再設定のコードが届くかは、未確認。
