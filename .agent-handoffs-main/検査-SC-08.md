# 検査-SC-08 サインイン状態の変化を購読して、端末の利用者識別を記録する

担当: 検査-SC-08。図: `.agent-handoffs/diagrams/検査-SC-08/SC-08.png`(SVG、入力のSC-08.jsonも同じ場所。4382x10728で縦が8000pxを超えるため、縮小版 `SC-08-縮小.png`(3227x7900)も同じ場所)。
判定の件数: 必要10、不要の疑い11、判断できない0(合計21。項目1〜15がSC-08の流れ、16〜21がSC-08で確定するAUTH-10の共有部品)。
読んだコード: main(344365c)の `apps/web/src`と`apps/web/tests/e2e`(`git show`で読取。作業ツリーは読んでいない)、auth-js 2.112.3の`GoTrueClient.js`(`onAuthStateChange`、`_emitInitialSession`、`__loadSession`、`_recoverAndRefresh`、`_notifyAllSubscribers`、`_removeSession`、BroadcastChannel、`signInWithPassword`)。
コードの読み取りだけで行った。アプリ、テスト、E2E、ローカルSupabaseでの実測、コード変更はしていない。実測が要る点は「未実測」と書く。設計・要件・architecture文書は根拠にしていない。

## 図の範囲

契機は、アプリの起動(ルート入口のマウント)で識別の記録が始まり、認証状態の購読が登録されること。以降、認証状態の通知(INITIAL_SESSION、SIGNED_IN、TOKEN_REFRESHED、SIGNED_OUT、その他)が届くたびに、規則が記録・消去・何もしないを決める。結果は、端末のlocalStorage(`aims:local-user-id`)の利用者IDが書き換わる、消える、または変わらないこと。
購読の始め方と、通知の種類ごとの記録の経路を1枚にした(通知は「次に起きるのは」から戻る矢印)。アンマウントを待つことを終点にした。
列は、入口(root-client-entry)、識別の記録(local-identity)、窓口の変換(supabase-auth.tsの購読と変換)、認証サービスの窓口(auth-jsと端末のセッション)、規則(identityChange)、識別の保存(browser-identity-store、localStorage)。
境界の先は描かない: 通知の発生元の手続き(サインイン=SC-01〜03、更新=SC-07、サインアウト=SC-04、見張りの喪失の経路=SC-06)、同じ通知の他の受け手(記録の利用者の切り替えと常駐取得=SC-52、SC-55)、識別の読み手(同期の開始=SC-54、参照データ=SC-22など)、購読の解除(SC-12)。

## 不要の疑いの詳細

### No.5 signed-inとinitialの区別(軽微)
- なぜ不要か: 受け手の誰も区別しない(識別の記録、起動の同期、記録の利用者の切り替え、見張り)。otherも、利用者がnullである点で「利用者のいないinitial」と全ての受け手で同じ扱いになる(otherの`ignored`は`!userId`と重複する。持ち主はSC-55で確認)。
- 影響: 利用者への影響は無い。
- 変更案: INITIAL_SESSIONとSIGNED_INを同じ種類に写し、種類を4つにする(利用者nullを許す。名前の見直しが要る)。`AuthChange`、`SignInChange`(2か所)、`toAuthChange`、`startsRefresh`、テストの行が変わる。項目14と同時に行う。

### No.9 token-refreshed、otherの種類での除外(軽微)
- 変更案: `identityChange`を「signed-outなら消す、利用者がいれば記録、それ以外は何もしない」にし、`kind`による分岐とテストの行を外す。token-refreshedは毎時間同じ値を書き直すだけになる。項目5と同時なら、規則は3行になる。

### No.12 writeのwindow確認(軽微)
- 変更案: `write`の24行目を外し、`browser-identity-store.test.ts` 94-111の書き込み側を外す。`read`側は、呼び出し元の場面(SC-54、SC-22など)で判断する。

### No.14 型の複製(軽微)
- 変更案: 他の機能へ公開する型を1つ(`index.ts`の`SignInChange`、`SignInChanges`)にし、`AuthChange`と`AuthChanges`、round-syncの複製を、その参照にする。または、複製を残す(層の規則を優先する)。CONFIRM 2。

### No.15 テストの層重複
- 変更案: SC-06:12、SC-07:19と同じ段階にまとめる。

### No.16 メールの254文字上限
- 変更案: `EMAIL_MAX_LENGTH`、`validateEmail`のtooLong、`EmailError`のtooLong、文言(`auth-messages.ts` 31)、`maxLength`属性(`signin-form.tsx`、`otp-email-step.tsx`)、該当のテストを外す。CONFIRM 1。

### No.20 `unauthenticated`の失敗の種類
- 変更案: `AuthFailureKind`から外し、文言`failure.unauthenticated`を外す(`REJECTION_KINDS`の型の`Exclude`からも外れる)。影響は無い。

### No.21 `already_registered`
- 変更案: 登録確認の全廃と同じ段階で、種類、`ALREADY_REGISTERED`、文言を外す。

## 事実の調査

1. 通知の来かた(auth-js): INITIAL_SESSIONは、購読を登録した受け手ごとに1回、初期化の後に届く(`onAuthStateChange`)。読み取りがエラーなら、セッション無しで届く。SIGNED_INは、サインイン、サインアップ後の確認のほか、タブが見えるようになるたびに(有効なセッションがあれば)届く。他のタブのSIGNED_IN、SIGNED_OUT、TOKEN_REFRESHEDはBroadcastChannelで届く。どれも同じ値の書き直しで害は無い。
2. 受け手は、識別の記録、見張り(SC-06、(main)限定)、同期の契機(SC-55)の3つで、並列に呼ばれる。サインアウトでは、`signOut`の中で完了まで待って通知される(SC-04)。
3. 識別の読み手(境界の先): 起動時の同期は、購読の登録の直後に1回読み、INITIAL_SESSIONでの記録より前に読む(SC-54、SC-55で確認)。参照データの読み込みは、都度読む。
4. 未実測: 期限切れ+オフラインの再起動で識別が残り記録が開くこと(項目8)、localStorageの容量超過での挙動(項目11)、環境変数が無い場合の画面の挙動(項目3)、保存先が空でオフライン起動のときの表示(項目8の整合)。
