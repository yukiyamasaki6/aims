# 検査-SC-05 認証が必要な画面・認証専用画面を要求する

担当: 検査-SC-05。図: `.agent-handoffs/diagrams/検査-SC-05/SC-05.png`(SVG、入力のSC-05.jsonも同じ場所。縦が8000pxを超えるため、縮小版 `SC-05-縮小.png`(2465x7900)も同じ場所)。
判定の件数: 必要10、不要の疑い8、判断できない7(合計25)。
読んだコード: main(344365c)の `apps/web/src`(`git show 344365c:` で読取)、`apps/web/tests/e2e`、`supabase/config.toml`、auth-js 2.112.3と`@supabase/ssr` 0.12.4の配布物(`GoTrueClient.js` getUser、`createServerClient.js`)。
コードの読み取りだけで行った。アプリ、テスト、E2Eの実行、ローカルSupabaseでの実測、コード変更はしていない。実測が要る点は「未実測」と書く。設計・要件・architecture文書は判定の根拠にしていない(設計-バッチ1は、共有部品への影響を把握するためだけに読んだ)。

## 図の範囲

契機は、ブラウザが/rounds配下、/signin、/signup、/reset-passwordを要求すること(ページ移動、RSCの取得、Server Action呼び出しのPOSTを含む)。
結果は、未認証なら遷移元つき(一覧だけなら遷移元なし)の/signinへ、認証済みで認証専用画面なら一覧(/signinで有効な遷移元があればそこ)へのリダイレクト応答、または素通し(更新したcookie付き)。
列は、ブラウザ(Service Workerを含む)、要求の入口(proxy.ts)、セッションの更新(session.ts)、経路の規則(auth-routes.ts、round-routes.ts)、認証サービスの窓口(@supabase/ssrとauth-js)、認証サービス(サーバー)。
境界の先は描かない: Service Workerが枠を返す場合(SC-15。proxyを通らない)、リダイレクト先の/signinの表示とサインイン(SC-02)、(main)の見張り(SC-06、SC-07)、matcher外の配信。

## 不要の疑いの詳細

### No.4 規則を関数で受け取る注入(RedirectRule)
- なぜ不要か: 呼び出しも規則も1つ。型を2か所に宣言し、4項目を転送している。
- 影響: 無し。`session.test.ts`が規則のモックで検証している箇所(42-108)が変わる。
- 変更案: `updateSession(request)`を`{ user, response }`を返す形にし、`proxy.ts`が`redirectFor`を呼び、行き先があればリダイレクト、なければ`response`を返す。`RedirectRule`型と`session.ts` 53-61の規則の呼び出しを外す。項目9、13と同じ変更にまとめられる。

### No.5 環境変数の検査
- なぜ不要か: `createServerClient`が同じ条件で投げる。
- 影響: 欠落時の文言が変わるだけ(要求は500のまま)。
- 変更案: `session.ts` 20-25の検査を外し、`process.env.NEXT_PUBLIC_*`を`as string`でなく、そのまま渡す(型は`string | undefined`で、型エラーなら`!`か`?? ""`)。`session.test.ts` 28-40を外す。SC-02の項目5(クライアント側の同種)と方針を合わせる。

### No.9 要求のcookieへの書き込みと応答の作り直し
- なぜ不要か: 要求のcookieを読む後段が、段階14後に無い。
- 影響: 無し(段階14の後)。段階14の前は、`changePassword`が更新後の値を読む。
- 変更案: `setAll`は応答(`supabaseResponse.cookies.set`)にだけ書く。`let supabaseResponse`を`const`にし、`NextResponse.next({request})`の再作成を外す。`session.test.ts` 125-147の「要求とレスポンス双方」を応答だけの検証にする。段階14の後に行う。
