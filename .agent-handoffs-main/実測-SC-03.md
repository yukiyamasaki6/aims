## 実測A(項目31・32・34): パスワード変更だけで他の端末は終わるか

スクリプト: `scratchpad/mA.cjs`(supabase-js 2.112.3、ローカルの既定キーのみ)。出力: `mA3.out`。
各シナリオで新規ユーザーを作成し、(1) パスワードのサインインで端末1・端末2のセッションを作り、(2) アプリと同じく、`resetPasswordForEmail` → Mailpitの6桁コード → `verifyOtp(type: recovery)` で再設定のセッション(自端末)を得て、(3) `updateUser({password})` を行い、(4) 必要なら `signOut` を行った。
各セッションは、アクセストークンでの `GET /auth/v1/user` と、リフレッシュトークンでの `POST /auth/v1/token?grant_type=refresh_token` で調べた。`auth.sessions` の行数も `psql` で数えた。

| シナリオ | 操作 | 端末1・端末2(別セッション) | 自端末(再設定のセッション) | auth.sessions(最初の3行 → 最後) |
| --- | --- | --- | --- | --- |
| z 対照 | 操作なし | GET /user 200、refresh 200(終わらない) | (対象外) | 3 |
| a | `updateUser({password})` だけ | 両方とも GET /user 403 `session_not_found`、refresh 400 `refresh_token_not_found`(終わった) | GET /user 200、refresh 200(残る) | 3 → 1 |
| b | a の後に `signOut({scope: "global"})` | 端末1・2は a と同じ(終わった) | signOut後は GET /user 403、refresh 400(終わった) | 3 → 0 |
| c | a の後に `signOut({scope: "local"})` | 端末1・2は a と同じ(終わった) | signOut後は GET /user 403、refresh 400(終わった) | 3 → 0 |

- 事実: この版(v2.195.0、`secure_password_change = false`)では、再設定のセッションでの `updateUser({password})` だけで、同じ利用者の他のセッションが全て削除され、自端末のセッションだけが残る。`scope` が `global` か `local` かで、最終状態(`auth.sessions` 0行、全セッションの無効化)に差は無かった。
- 事実: a の `updateUser` の直後(signOutの前)に、他の端末は既に終わっている。つまり b・c の signOut は、他の端末には何もしていない(自端末のセッションを消しただけ)。
- 注意: 最初の実行(`mA.out`、`mA2.out`)では、対照の前に「before」の確認でリフレッシュまで行い、リフレッシュトークンが回転して以降の refresh の結果が交絡した。`mA3.out` は「before」を GET /user のみにして直した版で、上の表はこの版の結果である。GET /user の403は最初の実行でも同じだった。
- アプリ内のE2E: 複製の `supabase-auth.ts` の `signOutEverywhere` の scope を `"global"` から `"local"` に替えて、既存の `password-reset.spec.ts` を再実行した(ビルドの出力に `"local"` が入っていることを確認)。5件すべて通過(23.1秒)。このspecは、別のブラウザ文脈でサインインした別端末が、パスワード変更後に `/rounds` を開くと `/signin` へ移されることを確かめている。つまり `local` でも、他の端末の終了のE2Eは通る。
- 未実測: (a) 本番の認証サービスの版・設定での挙動。(b) 項目34の「終了が失敗した場合」(`signOut` を失敗させる状況の再現はしていない)。ただし上記のとおり、他の端末の終了は `updateUser` の時点で完了しているため、`signOut` の失敗が他の端末の終了に影響しない(この版では)ことは、構造上は言える。(c) 通信が `updateUser` の途中で切れた場合(`updateUser` 自体はサーバー側で1回の呼び出しなので、サーバーアクションを通さず、ブラウザから直接 `updateUser` を呼ぶ形で、応答だけが失われる場合は未実測)。

## 実測B(項目39・37)

スクリプト: 複製の `apps/web/tests/e2e/auth/b-measure.spec.ts`、`b2-measure.spec.ts`、`b3-measure.spec.ts`(`scratchpad/work/specs/` にも元がある)。出力: `B-V0.out`、`B2-V0.out`、`B2b-V0.out`、`V2.out`、`V2b.out`。

### 項目39: パスワード段階の「サインインに戻る」(現行コード)

手順: メール入力 → Mailpitのコード → 「確認」でパスワード段階へ → 新しいパスワードを入れずにリンクを押す。
- 事実: リンクは `href="/signin"` の1件(`<a>`、`next/link`)。
- 事実: 押すと URL は `http://localhost:3100/signin` になり、「サインイン」の見出しが出て、30秒近く待っても `/signin` に留まる(`/rounds` へは自動で移らない)。クリック後に `/signin` へのサーバーへの要求は無く、ブラウザ内の遷移(pushState)だった。
- 事実: そのときも `sb-localhost-auth-token` のcookie(再設定のセッション)は残っており、旧パスワードでのサインインはトークンエンドポイントで200(パスワードは変わっていない)。待ち時間を3秒と40秒にした両方で同じ結果。
- 事実: そのまま `page.reload()`(`/signin` のページ全体の読み込み)をすると `/rounds` に移った(proxyが認証済みの `/signin` を `/rounds` へ送る)。
- 事実(プリフェッチ): `/signin?_rsc=...` へのプリフェッチ(`next-router-prefetch: 1`)は、メール入力の画面を開いた直後に6件出て、全て200(`text/x-component`)。パスワード段階に入ってからは、`/signin` へのプリフェッチは出なかった(メール段階の結果がルーターのキャッシュに残り、クリックはそれで描画された)。パスワード段階で押した後の `/rounds` へのプリフェッチ(4件、さらに `/rounds/new` など)は、`/signin` に描画された後に出た。いずれも200で、リダイレクト(307)は観測されなかった。
- 解釈(事実ではない): 押した直後の「/signin が表示される」は、メール段階のプリフェッチ(未認証時)が、パスワード段階の同じ宛先のリンクに再利用された結果と考えられる。キャッシュが無い状況(プリフェッチされていない、有効期限が切れたなど)でのクリックは、サーバーに要求が行き、proxyが `/rounds` へ送る可能性があるが、今回は再現できなかった(メール段階のリンクが常に先に表示されるため)。
- 結論(観測の範囲): リンクを押しても、パスワードは変わらず、再設定のセッションが残り、利用者は `/signin` の画面を見るが、実際には認証済みで、再読み込みや別の遷移で `/rounds` に入れる状態になる。検査-SC-03の項目39の推定(「パスワードを変えずに、コードの確認だけでアプリへ入る」)のうち、「セッションが残る」「再読み込みで `/rounds` に入れる」は実測で確認できた。「押した直後に `/rounds` へ送られる」は確認できなかった(実際は `/signin` が表示される)。

### 項目37: `PageLoad.load`(ページ全体の読み込み)をrouter遷移に替えた場合

複製の `reset-password/page.tsx` で、`pageLoad: { load: (path) => router.push(path) }`(`next/navigation` の `useRouter`)に替えて実行した。
- 事実: 現行(ページ全体の読み込み)では、パスワード変更後、`GET /signin`(通常のページ遷移)が1件出て、URLは `/signin`、見出しは「サインイン」、`sb-*` のcookieは空になる。
- 事実: router.push に替えると、パスワード変更後、`GET /signin?_rsc=...`(RSC、プリフェッチではない)が1件出て、URLは `/signin`、見出しは「サインイン」、cookieは空になる。`/rounds` への誤った遷移は起きなかった。
- 事実: router.push の版で、ページを再読み込みせずに(同じdocument。`window.__mark` が残ることを確認)、そのまま新しいパスワードでサインインすると `/rounds`(「まだラウンドがありません。」)へ入れた。Turnstileは `data-captcha-ready="true"` になった。
- 事実: router.push の版で、既存の `password-reset.spec.ts` は全て通った(7件通過。B系の2件を含む)。
- 解釈(事実ではない): 今回の条件(メール段階で `/signin` がプリフェッチ済みで、パスワード段階にはプリフェッチが無い)では、router遷移でも不具合は出なかった。項目37の懸念(リカバリーのセッションがある間のプリフェッチが `/rounds` へのリダイレクトをキャッシュに残す)は、今回の測定では再現できなかった(そのようなプリフェッチが発生していないため)。
- 未実測: router遷移でクライアントのメモリ上の状態(ブラウザのSupabaseクライアントの内部状態、他のキャッシュ)が残ることの影響(サインイン成功までは確認したが、それ以外の画面の状態の差は見ていない)。項目39のリンクを外した場合の差(リンクの有無を変えた比較は未実施)。

## 実測C(懸念1): 登録の確認が再設定コードを無効にするか

スクリプト: `scratchpad/mC.cjs`。出力: `mC.out`。`isEmailRegistered` の実装(`supabase-registration-check.ts`)と同じ `auth.admin.generateLink({type: "recovery", email})` を、秘密鍵(ローカルの既定の秘密鍵)で呼んだ。

| 手順 | 結果 |
| --- | --- |
| 確認済みユーザーに `resetPasswordForEmail` → Mailpitに1通(件名「AIMS パスワード再設定」、コード 209208) | ok |
| 1.5秒後に `admin.generateLink(recovery)` | ok、`email_confirmed_at` あり(登録済みと判定される形)、別のコード(980145)が返る |
| `verifyOtp({type: recovery, token: メールのコード})` | 403 `otp_expired`「Token has expired or is invalid」(使えない) |
| 対照: `generateLink` を呼ばずに同じ手順 | `verifyOtp` 成功(セッション発行) |
| `generateLink` が返した自身のコードで `verifyOtp` | 成功(その後、メールのコードは `otp_expired`) |
| DBの `auth.users.recovery_token`(先頭12字)と `recovery_sent_at` | 初期は空 → `resetPasswordForEmail` 後 `89e787cb2a23`/01:29:17.259 → `generateLink` 後 `d366748a6b59`/01:29:18.833(上書きされた) |
| 参考: 未確認ユーザーに `signUp` → Mailpitのサインアップコード → `generateLink(recovery)` → `verifyOtp(type: email, サインアップのコード)` | `generateLink` は ok(`email_confirmed_at` は null)。サインアップのコードの `verifyOtp` は成功(サインアップ側の確認コードは影響を受けない) |

- 事実: この版(v2.195.0)では、`generateLink(recovery)` が同じ利用者の保留中の再設定コードを無効にする(`recovery_token` と `recovery_sent_at` を書き換える)。先にメールで届いた再設定コードは使えなくなり、`otp_expired` になる。
- 事実: `generateLink` は、メールを送らずに、その利用者のコードを入れ替えるだけで、新しいコードは(アプリでは)利用者に届かない(返り値の `properties.email_otp` は破棄される)。
- 影響(事実の範囲): 他人が、被害者のメールアドレスでサインアップ画面の「登録の確認」を呼ぶだけで、被害者が再設定のコードを受け取った後に、そのコードを無効にできる。呼び出しにはcaptchaが要らない(`isEmailRegistered` はサーバーアクションで、実装上captchaを確認していない。コード読み取りの結果であり、今回の実測の範囲外)。
- 未実測: 本番の版・設定での挙動。サーバーアクション `isEmailRegistered` の実際の呼び出しにレート制限が無いこと(コード読み取りで言われている点)。

## 判定への影響(推測を含む)

項目31・32・34(事実に基づく判断材料):
- ローカルの v2.195.0 では、`updateUser({password})` だけで他の全端末が終わる。`global` と `local` の差は観測できなかった。既存E2Eは `local` でも通る。
- このため、項目32の(b)「他の端末の終了」を `signOut(global)` が担う必要は、この版では観測されない。(a)「この端末のセッションを終える」は必要(`signOut` を呼ばなければ自端末のセッションが残ることは、実測Aのシナリオaで確認)。
- 項目31のサーバーアクション化の理由(通信が途中で切れても終了が保証される)のうち、他の端末の終了は `updateUser` の完了で済む。残るのは、自端末の終了(cookieの削除)をサーバーが応答に書くかどうかという要件になる。これは本実測の範囲外で、判断(推測)はユーザーが決める。
- 項目34: 他の端末の終了は `updateUser` で済むため、終了(`signOut`)の失敗が他の端末の終了の失敗を隠すという懸念は、この版では当たらない(自端末のセッションだけが残る可能性は残る。失敗の再現は未実測)。
- 本番の版が v2.195.0 以降か、同じ挙動かは未確認。判定の前に、本番の版の確認が要る。

項目37・39:
- 項目39: 「サインインに戻る」を押すと、パスワードを変えずに、再設定のセッションが残ったまま `/signin` が表示される。再読み込みで `/rounds` に入れる。利用者を混乱させる挙動であることは実測で確認できた。リンクを外すと、この挙動は無くなる(リンクがあることによる挙動なので)。外した場合の副作用(戻る手段の消失)は、実測ではなく設計の判断。
- 項目37: router遷移でも、今回の測定では不具合は出ず、新パスワードでのサインインまでできた。プリフェッチとリダイレクトのキャッシュによる懸念は再現しなかった。項目39のリンクが無ければ、この懸念の根拠はさらに弱まる(推測)。ただし、ハードナビゲーションを採る理由(クライアント側の状態を捨てる)は別に残る。実測で差が出たのは、通信の種類(通常のGET対RSCのGET)だけである。

懸念1: この版で再現した。サインアップの登録の確認(`isEmailRegistered`)は、再設定のコードを無効化する副作用を持つ。登録の有無を調べる他の手段に替える(メールを送らない・コードを変えない手段)必要があるかは、ユーザー判断。
