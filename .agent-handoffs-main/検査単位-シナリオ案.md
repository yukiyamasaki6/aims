# 検査単位: シナリオ案(確定版)

検査の単位を、コードのまとまりではなく、利用者や外部の出来事を契機に、結果が反映されるまでの一連の流れ(シナリオ)にした案である。前回の見直し案(195単位)は破棄した。この案は確定版である。検査計画.mdと検査進捗.mdは、この案に合わせてシナリオ単位で作り直した。処理分割.mdは、旧IDの根拠として残す。図は作っていない。

## 1. シナリオの定義

- 1つのシナリオは、利用者または外部の出来事(購読の発火を含む)を契機に、結果(何がどこに反映されるか)が出るまでの、1つの流れである。図は、画面、アプリの処理、認証、端末の記録、送信、DB、同期など、層をまたぐ主体を列にして、契機から結果までを1枚で追えるものにする。
- 正常系だけでなく、失敗、オフライン、取り消しなどの異常系も、そのシナリオの分岐として扱う。ただし、送信の失敗・再試行・破棄・保留、通信復帰の再送のように、どの操作でも同じ経路を通るものは、操作のシナリオごとに繰り返さず、送信のシナリオ(SC-48、SC-49)で扱う。各操作のシナリオは、送信の正常系までを通り、異常系は『SC-48』と参照する。
- 購読は、購読ごとに、『どうやって始め、発火したらどの経路で何が行われるか』のシナリオにする。通信の購読と認証の購読などを、同じシナリオに混ぜない。
- アンマウントを待つことを終点とし、アンマウント時の挙動(購読の解除など)は別のシナリオにする(SC-12、SC-28)。
- 複数のシナリオが使う部品、規則、DB関数は『共有される処理』として、第4節にまとめた。判定は、各シナリオの検査の中で、その場面で必要かを見て行う。
- ファイルと行範囲は、各シナリオが通る関数の範囲を、処理分割.mdの範囲(旧処理)を目安にして割り当てた。同じ範囲が複数のシナリオに現れるのは、共有されているためである。

## 7. 確定した判断

ユーザーの判断で、次の3点を確定した。シナリオ62件、バッチ18は、現時点で問題ないとの判断である(後で覆す可能性はある)。

1. 操作のシナリオは、送信の正常系までを通る。送信の失敗・再試行・破棄・保留と、通信復帰の再送は、共通のシナリオ(SC-48、SC-49)で扱う。
2. 共有される処理は、各シナリオで場面ごとの要否を記録し、使う最後のシナリオで判定を確定する(第4節の最後の列)。
3. 大きいシナリオ(SC-20、SC-23、SC-59)の図は、基本的に、大きくても分けない。検査の開始時にコードを見て、どうしても読めないと判断した場合に限り、分け方を提案する。
