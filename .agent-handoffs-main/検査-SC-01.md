# 検査-SC-01 サインアップする

担当: 検査-SC-01。図: `.agent-handoffs/diagrams/検査-SC-01/SC-01.png`(SVG、入力のSC-01.jsonも同じ場所)。
判定の件数: 必要36、不要の疑い20、判断できない5(合計61。うちSC-02と同じ部品の項目は表の「SC-02」列に参照を記載)。
コードの読み取りと、auth-js 2.112.3の配布物の確認だけで行った。テスト実行とコード変更はしていない。

## 図の範囲

契機は、利用者が/signupでメールを入力して進むこと。結果は、アカウントと端末のセッションができ、一覧(/rounds)へ移ること。
列は、画面、サインアップの手続き(規則を含む)、登録の確認(サーバー)、認証サービス(メール・DBを含む)、遷移。
1枚に、メール入力、コード入力(確認・再送・戻る)、パスワード設定の3段階を描いた。
境界の先は描かない: 認証済みで/signupを開いたときの転送と/signupの要求(SC-05)、SIGNED_INによる端末の利用者識別の記録(SC-08)、サインインへのリンク先(SC-02)。

## 懸念

1. 登録の確認のServer Action(`isEmailRegistered`)は、利用者の確認(captcha、レート制限)が無く、誰でも呼べる。メールの登録有無を、captchaを通らずに調べられる(captchaは、確認の後のコード送付で初めて使う)。画面も「既に登録されています」と示す。設計文書は、列挙のリスクを受け入れたとしている。ユーザーの判断が要る(確認の前にcaptchaを検証するか、受け入れるか)。
2. コードを確認した時点で、端末にサインインのセッションができ、パスワード設定の前に離れると、パスワードの無いアカウントが残る。/signupを開くと認証済みとして/roundsへ転送される(SC-05の`redirectFor`)ため、設定の画面に戻れない。後でセッションが切れると、パスワードでサインインできず、パスワード再設定が必要になる。
3. users行は、コード送付の時点(未確認)でできる。コードを入力せずに離れた行は、残る(削除する処理は無い)。登録の確認は未確認を未登録として扱うので、再登録は妨げない。
4. 未確認: `generateLink`(recovery)が、利用者のrecoveryトークンを書き換え、保留中のパスワード再設定のコードを無効にする可能性がある(GoTrueの実装は確認していない)。確かめるなら、ローカルSupabaseで、再設定のコード送付の後に、サインアップの登録の確認を呼び、コードが使えるかを見る。
