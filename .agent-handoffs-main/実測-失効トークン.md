製品コード・設定・テストは変更していない。実測は、main(344365c)の `git clone --local` 複製 `/tmp/claude-0/-home-user/8d234c46-e442-5d63-b5e4-2eb590f18707/scratchpad/sc05/aims` でだけ行った(元の作業ツリーとbranchには触れていない)。
スクリプトと出力は `.../scratchpad/sc05/m/d1.cjs`、`d1-V0-*.out`(現行 `getUser`)、`d1-V1-*.out`(`getClaims` に替えた版)。`lib.cjs` は実測-SC-05のものを再利用した。

## 測定1: 失効後のアクセストークンでの直接アクセス

トークンの `session_id` に対応する `auth.sessions` の行が無い状態(失効)で、同じトークンを `apikey: <publishable>`、`Authorization: Bearer <AT>` で送った。3通りの失効で結果は同一だった(`d1-V0-*.out`)。
保護対象はマイグレーションで確認した。全テーブルでRLS有効。読み取りは `authenticated` への SELECT ポリシー(`rounds` などは `is_round_member`、`users` は `auth.uid() = id`)。書き込みは、テーブルへの直接の権限は無く、`SECURITY DEFINER` のRPC(`create_round`、`update_round`、`disable_round` など)を `authenticated` に EXECUTE 付与している。アプリも書き込みをこのRPCで行う(`round-op-transport.ts`)。

| 要求(失効後、期限内のAT) | 結果 |
| --- | --- |
| GoTrue `GET /auth/v1/user` | 403 `session_not_found`「Session from session_id claim in JWT does not exist」 |
| GoTrue `PUT /auth/v1/user`(メタデータ更新) | 403 `session_not_found` |
| REST `GET /rest/v1/rounds` | 200、自分のラウンドの行が返る |
| REST `GET /rest/v1/round_events`、`users`、`target_faces` | 200、行が返る |
| REST `POST /rest/v1/rpc/create_round`(新規作成) | 200 `applied: true`。DBに行が増えた |
| REST `POST /rest/v1/rpc/update_round`(既存の名前変更) | 200 `applied: true`、`revision: 2`。DBの名前が変わった |
| REST `POST /rest/v1/rpc/disable_round` | 200。DBでイベントが増えた |

- 事実: 失効したセッションのトークンでも、期限内ならPostgREST経由のRLSで保護された読み取りと、RPC経由の書き込みが成功した。GoTrueの `/user` だけが403になる。
- 事実: 失効前(対照)も同じ要求が成功している。失効の前後でRESTの結果は変わらなかった。
- 事実(PostgREST は GoTrue を呼ばず、JWTの署名・期限・`role` で判定する、という構造): PostgREST は `session_id` の存在を確認していない。これは結果からの推定で、PostgREST の実装は読んでいない。
- (b) RealtimeとStorage: 製品の `config.toml` で `[realtime] enabled = false`、`[storage] enabled = false`。アプリのコード(テスト以外)にも `channel(`、`storage` の使用は無い。ローカルでは両サービスが起動せず、`/storage/v1/bucket` は名前解決失敗だった。したがって測定対象外で、有効化された場合の挙動は未実測。
- 未実測: 期限(3600秒)を実際に過ぎたトークンでのRESTの拒否(待っていない。`expires_at` の書き換えではトークン自体の `exp` は変わらないため)。失効後のリフレッシュは実測-SC-03で `refresh_token_not_found` の400(つまり、アクセストークンの期限が切れた後は新しいトークンを得られない)と確認済みで、今回は再測していない。

## 測定2: 失効したトークンのまま保護ページを要求したときの応答

cookie `sb-localhost-auth-token` に、失効したセッションの(期限内の)トークンを入れて、本番ビルドの `next start`(ポート3105)へ `redirect: manual` で要求した。

| 失効の方法 | ページ | 現行(`getUser`) | `getClaims` 版 |
| --- | --- | --- | --- |
| signout-local | `/rounds` | 307 → `/signin` | 200(18812 bytes) |
| signout-local | `/rounds/new` | 307 → `/signin?returnTo=%2Frounds%2Fnew` | 200(20664 bytes) |
| signout-global | `/rounds`、`/rounds/new` | 同上 | 200(同上) |
| pwchange-other-device | `/rounds`、`/rounds/new` | 同上 | 200(同上) |

- 失効前(対照)は、どちらの版も `/rounds`、`/rounds/new` が200だった。
- 事実: `getClaims` 版では、失効したトークンのまま保護ページが200で返る。応答時間はおおむね 5〜15ms で、現行版の 35〜46ms(リダイレクトの場合)や失効前の 50〜100ms より短い(ローカル、1回ずつの値で統計はとっていない)。
- 事実: 200の応答のHTMLに、利用者ID、ラウンド名は含まれていなかった(`contains-round-name=false`、`contains-user-id=false`。HTML全体の文字列検索)。ページの枠(ログイン後のシェル)で、データは含まない。
- 事実: `getClaims` 版では、同じ cookie で `/signin` が `/rounds` へ307で送られる(実測-SC-05の `c3-V1.out`。今回は再測していない)。失効したセッションの利用者が `/signin` を開くと `/rounds` へ戻される形になる。
- 事実: 現行版でもcookieの `expires_at` が過去(トークンの更新が要る)の場合は、どちらの版も、失効したセッションの更新が失敗して `/signin` へ送られる(実測-SC-05の `c3-V0.out`、`c3-V1.out`)。

## 結論

事実(今回の測定の範囲、ローカル v2.195.0・ES256):
- 現行の `getUser` は、失効を要求の時点で検知し、保護ページを `/signin` へ送る。`getClaims` に替えると、期限内のトークンなら失効後も200でページの枠が返る。
- 失効後のトークンでも、期限(jwt_expiry、既定3600秒)まで、RESTのRLS付き読み取りと、RPC経由の書き込みは成功する。proxyが `getUser` で守っているのはページの枠(HTML)の取得だけで、データへのアクセスは守っていない。
- 返ってきた200のHTMLにはデータは含まれない。

(i)か(ii)か:
- (i)ページのHTMLの枠の取得だけ、が事実として言える。(ii)データへのアクセスは守っていない(proxyを通らない直接のREST要求は、失効後も期限まで成功する)。
- 「データが失効後も期限まで読めるなら、`getUser` が防ぐ害は枠の表示に限られる」と言えるか。言える範囲は次のとおり。
  - proxyの `getUser` を外しても、データの露出は増えない。失効したトークンの持ち主がデータを読めるのは、proxyの有無と無関係に期限までである(事実)。
  - ただし、これは「`getUser` が無くても害が増えない」ことで、「失効後のデータアクセスが安全」ということではない。失効しても期限まで読み書きできること自体が残る。書き込みも同様に成功した(事実)。
  - 枠の表示が害になるかは、設計の判断。表示される枠はデータを含まない(事実)ので、害は小さい(推測)。クライアント側のコード(ブラウザ側の見張り)が枠の表示後にセッションを確認して移すかは、今回は未実測(実測-SC-05・検査-SC-06/07の範囲)。

推測・未確認(事実と区別):
- 本番のGoTrueの版・署名鍵の種類・`jwt_expiry` は未確認。`getClaims` 版の200は、ローカルが非対称鍵(ES256)で端末内検証になるため。本番が対称鍵(HS系)なら、`getClaims` は `getUser(token)` に落ちるので(コードの読み取り)、失効を検知して現行と同じく `/signin` へ送る、と推測できる(未実測)。つまり、`getClaims` に替えても失効の即時検知が失われるかは、本番の署名鍵しだい。
- 期限切れ後のRESTの拒否は未実測(PostgRESTがJWTの `exp` を検査することは一般的な挙動としての推定)。
- 失効後に期限まで書き込める点は、認可の設計(RPC内で `auth.uid()` だけを見て、セッションの存在を見ない)に由来する。セッションの存在まで確認するには、RPC側で `auth.jwt() ->> 'session_id'` と `auth.sessions` を照合するなどの変更が要るが、実装も測定もしていない(案にとどまる)。
