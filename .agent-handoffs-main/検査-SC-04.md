# 検査-SC-04 サインアウトする

担当: 検査-SC-04。図: `.agent-handoffs/diagrams/検査-SC-04/SC-04.png`(SVG、入力のSC-04.jsonも同じ場所)。

読んだコード: main(344365c)の `/root/worktrees/aims-batch1-simplify/apps/web/src`、auth-js 2.112.3の配布物(`GoTrueClient.js` 3398-3440、4308-4407)、既存のE2E(`tests/e2e/auth/signout.spec.ts`)とテストの題名。
コードの読み取りだけで行った。アプリ、テスト、E2Eの実行、ローカルSupabaseでの実測、コード変更はしていない。実測が要る点は「未実測」と書く。本番の認証サービスの版と設定は未確認。

## 図の範囲

契機は、利用者がレフトパネル下端の「サインアウト」を押すこと。結果は、この端末のセッションが消え、遷移元なしで/signinへページ全体を置き換えて移ること(または失敗の表示、取り消し、画面が離れた場合の破棄)。
列は、画面(ボタンと確認ダイアログ)、サインアウトの手続き(規則を含む)、認証サービスの窓口(auth-jsと端末のセッション)、認証サービス(サーバー)、遷移(ページ全体の読み込み)。
境界の先は描かない: SIGNED_OUTの通知先(見張り=SC-06、端末の利用者識別の消去=SC-08、記録の利用者の切り替え=SC-55。記録のメモリは捨てられ、保存済みの操作は端末に残る)、/signinの表示(SC-02)、オフライン時の/offline応答(SC-15)。
通信復帰の購読(connectivity)は、サインアウトの流れでは使わない(下の訂正)。

## 不要の疑いの詳細

### No.9 開始結果の3種(確定案。SC-01:12、SC-02:12、SC-03:12の受け手)
- 確定案: 不要の疑い。4操作(サインイン、サインアップ、再設定、サインアウト)の受け手は、`use-screen-view.ts` 31と`session.ts` 81の2か所で、どちらも`started`か否かだけを見る。busyとinvalidを区別する本番コードは無い。状態が変わったかは`state`で分かる。
- 影響: `begin`の戻りで`request`があるかないか(2種)に畳める。`Start<State, Request>`を`{ state, request: Request | null }`にする案。`flow.ts` 22-33、`sign-in-flow.ts` 35-38、`password-setup-flow.ts` 55-60、`session-end-flow.ts` 28-33、受け手2か所と、テストの`kind`の断言(grep上で約48か所)が変わる。利用者への影響は無い。
- 変更案: 上記。SC-08のAUTH-10の確定と合わせて実施。

### No.12 結果3種と`failureOf`(SC-01:15、SC-02:19、SC-03:15,26の確定案)
- 確定案: SC-02の変更案(d)(`CallResult`を`accepted`と`failed(failure)`の2種にする)で、サインアウトにも不都合が無い。サインアウトの受け手(`session.ts` 82)は`failureOf`で畳んで使い、通信断かどうかで分ける箇所が無い(トークンも無い)。ユーザー確定の「通信断かどうかによる分岐の廃止」と同じ向き。
- 残す必要があるもの: `unreachable`の失敗の種類と文言は残る(オフラインかつ期限切れで実際に出る。項目14、17)。「投げた場合」(項目13)は`failed(unreachable)`に畳める。

## 懸念

1. オフラインのサインアウトは、サインアウト済みになった後、/signinへ移る(Service Workerが/offlineを返す)。見張りはオフラインでの/signinへの移動を行き止まりとして保留する(`session.ts` 112)のに対し、サインアウトは移る。意図の食い違いの可能性があるが、E2E 61-91は/offlineの表示を期待結果としている。この食い違いを意図としてよいかは、ユーザーの確認が要る(CONFIRM 1)。
2. オフラインでサインアウトすると、サーバー側のセッションは無効化されない(通信が失敗し、保存先だけが消える)。端末のセッションは消えるが、更新トークンはサーバー側で有効なまま残る。認証サービスの有効期限(`config.toml`の設定)まで。共有端末の用途での影響は未確認。
3. 環境変数の欠落のテスト(`layout.test.tsx` 197-262)は、ブラウザの実行中に`NEXT_PUBLIC_*`が失われる状況を作っているが、Next.jsはこれらをビルド時に埋め込むため、実行中に失われる経路は無いと考えられる(Next.jsの仕様による見立て。未実測)。SC-02の項目5(接続を送信時に取得する。保留)の判断材料になる: サインアウトの場面でも、環境変数の欠落で動くのは、ビルドに変数が無い場合だけで、その場合は事前描画が先に失敗する。
4. SIGNED_OUTの通知先の購読者(SC-06、SC-08、SC-55)は、通知を`await`で待たれる(`GoTrueClient.js` 4331-4337)。購読者が遅いと、`signOut`の完了が遅れる。通知先のコストは各シナリオで確認する。
