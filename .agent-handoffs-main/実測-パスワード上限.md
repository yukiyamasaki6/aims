# 実測-パスワード上限

`apps/web/src/features/auth/domain/password.ts` の「72文字以内・半角英数記号のみ」が、クライアントの検査として必要かを判断する材料を、ローカルSupabaseで実測した。
製品コード・設定は変更していない(git statusは空)。

- supabase CLI 2.115.0、supabase-js 2.112.3(`apps/web` の依存)。ローカルの既定キーのみ使用。
- 認証の設定(`supabase/config.toml`): `minimum_password_length = 8`、`password_requirements = "letters_digits"`、`secure_password_change = false`、captcha有効(テスト用キー)。

- スクリプト: `/tmp/claude-0/-home-user/8d234c46-e442-5d63-b5e4-2eb590f18707/scratchpad/pw/m.cjs`、`m2.cjs`。出力: 同じ場所の `out1.txt`、および `m2.cjs` の標準出力(本書に転記)。

## password.ts の現状(読み取り)

- 最大長は `password.length <= 72`(JavaScriptのUTF-16コード単位数)で数えている。バイト数ではない。
- 許す文字は `/^[!-~]*$/`(0x21〜0x7E、半角英数記号のみ)。空白・制御文字・非ASCIIは全て拒否される。
- そのため、この規則を通る入力は全てASCIIの1文字1バイトで、「文字数 = バイト数」が成り立つ。コメントの「許す文字は半角英数記号だけなので、文字数をバイト数として扱える」はこの前提に基づく。
- 最小長8、英字と数字を各1文字以上、の規則も同じ関数にある。

## 実測1: 設定の可否

設定方法は3つ。
- 設定A: 新規ユーザー(admin作成、`Base-pass-1`)でサインインしたセッションからの `updateUser({password})`。
- 設定B: `auth.admin.createUser({password})`。
- 設定C: `signUp({password})`。
ここでの「字数」はコードポイント数、「B」はUTF-8バイト数。英字・数字を含めたもので測った(d3は例外で、拒否の確認用)。

- 事実: この版の認証サービスは、72を超えるパスワードを設定時に拒否する。拒否の単位はバイト数である(26字74Bは拒否、25字71Bと26字72Bは成功。27字73Bは拒否)。エラーメッセージは "characters" と書くが、数えているのはUTF-8バイト。
- 事実: 認証サービス側の拒否のコードは `validation_failed`(HTTP 400)。弱いパスワードの拒否(`weak_password`、422)とは別のコード。password.ts の `PASSWORD_RULE_MESSAGE` は「認証サービスが弱いパスワードとして拒否したとき」に示すと書かれているので、`validation_failed` の拒否がアプリ側でどう扱われるかは別途コードを見る必要がある(本実測の範囲外)。
- 事実: admin APIの `createUser` は、72超で `500` かつコード・メッセージなし(`Internal Server Error`)を返す。サーバーの内部エラーとして見える。ただし本アプリで利用者向けの設定に使うのは updateUser か signUp と想定される(未確認)ため、この経路は参考。
- 事実: 非ASCII(日本語、絵文字、全角)・空白・タブ・改行・NUL・DEL・制御文字を含むパスワードは、72B以内なら設定できる。弱いパスワードの規則(letters_digits)は半角の英字と数字を要求し、全角英数のみは拒否される(d3)。
- 事実: 最小長8は字数で判定されているように見える(d3は10字30Bで長さでは拒否されず、強さの規則で拒否)。これ以上の最小長の境界は測っていない(未実測)。

## 実測2: サインインの可否(bcryptの72バイト切り捨て)

サインインは `signInWithPassword`。

### 設定に成功した全入力

設定したパスワードの全文で、全てサインインできた(a、d1、d2、d4、e1、f1〜f7、境界測定の各成功例)。設定前のパスワード(`Base-pass-1`)と、全文に `Z` を足した入力は、全て `400 invalid_credentials` で失敗した。つまり、非ASCII・空白・NUL・DEL・制御文字を含んでも、設定とサインインは一貫して動いた。

追加で、前後に空白を含む ` Passw0rd12 ` は、全文ではサインインでき、trimした `Passw0rd12` では `400 invalid_credentials` だった(認証サービスは空白を削らない)。NUL入りは、全文のみ成功し、NULより前(`Pass`)、NULを除いた `Password123`、`Pass\u0000` はいずれも失敗した(NULで切られていない)。

### 72Bちょうどのパスワード(a、設定済み)に対し、長い入力でサインイン

| サインインの入力 | バイト数 | 結果 |
| --- | --- | --- |
| 設定した72B全文 | 72 | 成功 |
| 全文+`Z` | 73 | 成功 |
| 全文+`y`×128 | 200 | 成功 |
| 全文+`y`×928 | 1000 | 成功 |
| 先頭71B+別の1文字(72B) | 72 | 失敗 `invalid_credentials` |
| 先頭72B中の1文字を変え、後ろに`y`×128 | 200 | 失敗 `invalid_credentials` |
| 誤った1000Bの入力 | 1000 | 失敗 `invalid_credentials` |

- 事実: サインインには長さの上限検査がなく、72Bを超える入力でも、先頭72Bが一致すれば成功する。つまりサインインではbcryptの72バイト切り捨てが起きている(73B、200B、1000Bの入力が、72Bのパスワードで通る)。72B以内の違いは切り捨てられず、判別される。

### 依頼のb・eの(i)〜(iii)

b(73B以上)とe(72B超の日本語など)は、この版では設定が拒否された。そのため、「設定した全文でサインイン」「先頭72Bだけでサインイン」「先頭72B+別の文字でサインイン」は、設定できたパスワードが無く、そのまま測れなかった(未実測)。代わりに上の表で、「72Bのパスワードに対する73B以上の入力」の切り捨てを確認した。
admin APIでも73B以上は作成できなかったため、72B超のパスワードがDBに入っている状態の再現は、この環境ではできなかった。

## 考察

### 事実(上記の実測から)

1. 認証サービスは、設定の経路(updateUser、signUp)で、72バイトを超えるパスワードを `validation_failed` で拒否する。文字種の制限は、強さの規則(半角の英字と数字を1文字ずつ要求)以外にない。
2. 72バイト以内なら、空白・制御文字・NUL・非ASCII・絵文字を含んでも設定でき、サインインもできる。
3. サインインは長さを検査せず、先頭72バイトが一致すれば通る(bcryptの切り捨て)。
4. 拒否の単位はバイト数で、字数ではない。

### password.ts の検査が防いでいるもの(事実と推測)

- 防いでいる(事実に基づく): 認証サービスが拒否する「72バイト超」。password.ts は文字種を半角英数記号に限るので、字数 ≤ 72 なら必ずバイト数 ≤ 72になり、日本語30字(90B)のような「字数は72以下だがバイトは超える」入力は、文字種の制限で先に拒否される。つまり、72を字数で数えていても、半角英数記号に限るため、バイトでも正しい。
- 過剰ではない/重複している点: 認証サービスが72B超を拒否するため、「72文字以内」の検査は、認証サービスにもう一段ある同じ規則の先回りである。クライアントでこれを検査する意味は、(推測)認証サービスの拒否(`validation_failed`、既定の英語メッセージ)を待たずに、日本語の文言で即座に伝える利用者体験にある。安全上の必要性は、設定の経路では認証サービス側が担保している。
- 防ぐものが残る危険: サインイン時の切り捨て(73B以上の入力でも通る)。これは設定ができない状況では、72Bのパスワードを使う利用者が、末尾に余計な文字を打ってもサインインできるという範囲に限られ、攻撃上の弱点は増えない(先頭72Bが必要)。password.ts は新しいパスワードの検査(`validateNewPassword`)で、サインインでは課さない、とコメントされている。
- 過剰に弾いている入力(事実): 非ASCII(日本語、絵文字、全角英数)、空白、タブ、改行、制御文字を含むパスワードは、認証サービスは72B以内なら設定でき、サインインもできる。password.ts の `/^[!-~]*$/` はこれらを全て拒否する。例えば `Pass word123`(空白入り)、`パスワードの設定12ab`(28B)、`Pass😀word123` は、認証サービスは受け付けるが、password.ts は拒否する。
- 半角英数記号に限る規則の根拠は、72を字数で数えることを可能にする、という点が、コードのコメントにある。もしこの制限を外すなら、72を字数ではなくバイト数(`new TextEncoder().encode(password).length`)で数える必要がある。字数で数えたままだと、26字74Bのような入力がクライアントを通り、認証サービスの `validation_failed` で拒否される。
- 推測を含む副次的な理由: 空白や制御文字を弾くことで、貼り付け時の混入(前後の空白、改行)で意図せず設定してしまう事故を防ぐ(認証サービスは空白を削らないため、前後の空白入りで設定すると、trimした入力ではサインインできない)。これは実測のf2と整合するが、事故が実際に起きる頻度は測れない。

### 判断への含意(推測)

- 「72以内」だけをクライアントから外すと、認証サービスの拒否に任せることになり、メッセージが英語のまま `validation_failed` として返る。アプリ側がそれを `PASSWORD_RULE_MESSAGE` に変換しているかは未確認。
- 「半角英数記号のみ」の制限は、安全上は必須ではない(認証サービスは広く受け付ける)。ただし外すと、72の数え方をバイトに変える必要があり、全角英数のみは `weak_password`、空白・制御文字の扱いなど、別の方針の判断が要る。

## 未実測

- 本番の認証サービスの版・設定での挙動。
- 72B超のパスワードが既にDBに入っている状態(過去の版では設定できた可能性)でのサインイン。この環境では設定できないため再現できなかった。
- アプリのサーバーアクション・フォームを通した場合の、`validation_failed` の画面上の表示(認証サービスへの直接呼び出しのみで測った)。
- 最小長8の境界、強さの規則(letters_digits)の他の境界。
- 非ASCIIの正規化(NFC/NFD)の違いによるサインインの可否。
- 先頭72Bが多バイト文字の途中で切れる場合のサインイン(72B超が設定できないため、再現できなかった)。
