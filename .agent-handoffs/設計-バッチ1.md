## 1. 方針

- 新しい仕組みを足さず、削除・既存の共有・既定値で済ませる。足すのは2つだけ(案内メールのテンプレート1つ、サインインのメール欄のEnterで次の欄へ移す数行)。
- 1項目(または不可分な数項目)を1段階とし、各段階は単独で `pnpm lint`(biome・`lint:text`・`lint:messages`)、`typecheck`、`knip`、`test`、必要なE2Eが通り、1コミットで戻せる。**未使用になる文言キー・export・テストはその段階で消す**(`lint:messages`/`knip` が落ちるため)。
- 順序: 依存の無い小さな削除を先、共通部品を先、画面側を後、構造を変える段階は依存する段階の後。
- 「変更前の状態に戻せる」: 各段階は `git revert` で戻る。外部設定(段階01のテンプレート)は戻しても app は壊れない向きにする。

## 2. 確かめ直した現状(実コード)

- パスワード変更は Server Action(`app/(auth)/reset-password/actions.ts` → `password-change.ts`、`lib/supabase/infrastructure/server.ts` の `createServerClient`)。ページ遷移は `createBrowserPageLoad().load`。`createBrowserPageLoad` は `app/(main)/layout.tsx` が `replace`/`here` に使うため**ファイルは残る**(`load` と `PageLoad` 型の import だけ消える)。
- 登録確認は Server Action(`signup/actions.ts` → `supabase-registration-check.ts` → `createAdminClient`)。**`"use server"` はこの2つだけ**。両方消えると `server.ts` は全体が不要。
- `CallResult` は3種。`failureOf` は `session.ts`(サインアウト=SC-04)・`verifyCode`・`applyPassword` も使うため**関数は残す**(2種化後は `accepted` なら null、`failed` なら failure)。
- `begin` の `step` 引数と `flow.step !== step`(項目13)、`resendCooldown` の `operation === "resend"` 分岐(項目25)は `password-setup-flow.ts` の `begin` 内。`emailStepReturned` は待ちを**保つ**テストがある。
- `ScreenView` の「直前の適用の結果に適用」契約は `docs/architecture.md` 第6節と `screen-view.ts` にも書かれている(11b で改める文書)。共有テスト補助 `screen-view-test-helpers.ts` は最新値に適用する偽物で、2回呼びの検証は手続きのテスト側だけが前提にする。
- magic_link のテンプレートは `supabase/config.toml` で `otp.html`(コードを表示)。CD は `supabase/templates/**` と `config.toml` の変更で `supabase config push`(本番)を実行する。
- GoTrue v2.195.0 のソース(raw.githubusercontent、2026-11-05)で確認: `signInWithOtp`(`Otp` → `MagicLink`)は、**確認済みの既存利用者には `sendMagicLink` を呼び、`recovery_token`/`recovery_sent_at` を書き換え、`magic_link` テンプレートを使う**(`mail.go` 479-520)。未確認・未登録は signup と同じ confirmation テンプレート。頻度制限(`max_frequency`)は再設定と共有の `RecoverySentAt`。

## 3. 具体策を決める項目

### 3.1 懸念1: 登録確認が再設定コードを無効にする / 登録有無の列挙

選択肢:

| 案 | 内容 | 影響 |
| --- | --- | --- |
| A(ユーザー確定) | 登録確認を全廃。`signInWithOtp` を常に呼ぶ。`magic_link` テンプレートを「既に登録済みです。サインイン/再設定へ」の案内(コード・リンク無し)に差し替える。登録済みでもコード入力画面へ進み、メールの内容で分かる | Server Action・管理者鍵・`generateLink`・`createAdminClient` が消える。captcha と頻度制限が付く(今は無し)。**画面に「既に登録されています」が出なくなる**(要件変更)。登録済みの利用者がサインアップするとコード入力画面で止まるため、文言で案内する。再設定コードの無効化は、**誰でも `resetPasswordForEmail` で同じことができる**既存の性質と同程度になり、新たな攻撃面は増えない。メールは既存のコードメールと同じ経路で送られ、新しい送信基盤は不要 |
| B | 管理者APIの別手段(`listUsers` 等、副作用なし)で判定し、通知メールは別基盤で送る | SMTP/メール基盤が無く(本番のSMTPはリポジトリから不明)、導入費用が大きい。列挙は残る。採らない |
| C | 現状の画面表示のまま、判定だけ副作用の無い手段に替える | 列挙が残る。管理者鍵とServer Actionが残る。ユーザーの着想(通知メール)と合わない |

案Aの決定事項:
- サインアップの `sendCode` は登録確認を持たず、再設定と同じ `deliver` のみ(段階15)。
- 案内テンプレートは `supabase/templates/already-registered.html`(件名「AIMS 登録済みのメールアドレスです」)。本文は `{{ .SiteURL }}/signin` と `/reset-password` への案内、心当たりが無ければ破棄の旨。`{{ .Token }}` と `{{ .ConfirmationURL }}` を**入れない**(入れるとコードで既存アカウントに入れてパスワードを上書きできる元の危険が戻る)。
- 検査-SC-01:54 / SC-03:53(magic_link の節を外す)は、**案Aでは「外す」でなく「案内テンプレートへ書き換える」に変わる**。確定のユーザー判断(「到達の有無を確認してから確定」)に沿う: 到達する(確認済みの既存利用者のサインアップ)ことをソースで確認した。
- 段階01(テンプレート)を**先に単独でマージし、デプロイされてから**段階15を出す。旧アプリは登録済みを先に止めるので magic_link に到達せず、先行しても安全。逆順だと、段階15だけが先に出た間に、登録済みの利用者へコード入りのメールが届く。

### 3.2 懸念2: パスワード未設定のアカウントを設定画面に固定する(案C 現状維持。パスワード変更の設計時に決める)

事実: コード確認でブラウザにセッションができ、`/signup` は認証済みなので `proxy.ts` が `/rounds` へ送る。クライアントから「パスワード未設定」は分からない(JWT/ユーザーに該当項目なし)。

案(以下は将来の判断材料。SC-05 の検査結果を加えると、SC-05 は案A「目印+proxy+(main)の見張り+出口」が3層にまたがり、案B「/signup・/reset-password の認証済み転送を外す」は固定にならず、案C「現状」を挙げている。今回はコードを変えない):
1. 目印を `user_metadata` に持つ: `signInWithOtp({ options: { data: { password_pending: true } } })` で新規作成時だけ立て、`updateUser({ password, data: { password_pending: false } })` で下ろす。既存利用者は目印が無く、対象外(バックフィル不要)。
2. `proxy.ts`(`updateSession` が既に `getUser()` を持つ)から `redirectFor` へ目印を渡し、目印があれば保護の範囲と未認証専用の画面を `/signup` へ送り、`/signup` は認証済みかつ目印ありなら初期の段階をパスワード設定にする。
3. 別案(流れの入れ替え): パスワード入力→`signUp`→コード、とするとパスワード無しのアカウントが生まれないが、段階の順序を変える要件変更で、既存利用者への `signUp` の応答の挙動の実測が要る。採らない。

今回の変更(段階20〜23)は `redirectFor` と `updateSession` を整理するが、`user_metadata` の目印を渡す拡張は入れない。後で案Aを採るときは、段階23で `updateSession` が返す `user` を `redirectFor` へ渡すだけで足りる形になる。
